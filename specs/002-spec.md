# 002-spec — Awesome Mall 상품 카탈로그·소계·할인 계산

## 요구 원문
> "Awesome Mall의 고정 상품 10개 장바구니에서 수량을 조절하면 소계·합계를 실시간으로 보여주고, 할인율을 입력하면 최종 할인가를 계산한다"

---

## 가정 (Q&A)

`(확정)` = 브레인스토밍/인터뷰 확정, `(확인 요청)` = 기본값 제시, 사람 승인 필요

- **A01. 고정 카탈로그 (확정)**: 상품 10개는 하드코딩 고정값. 등록·수정·삭제·검색 없음. 전체 목록 조회만 제공.
- **A02. 상품 모델 재사용 (확정)**: 001-spec의 `Product(productId, name, price)`를 그대로 사용.
- **A03. 카탈로그 검증 — addItem 계약 확장 (확인 요청)**: `ProductCatalog`는 Cart의 선택적 협력 객체로 주입된다. **주입 시** 카탈로그에 없는 productId는 거부. **미주입 시** 001 A2 동작("주어진 것으로 받음") 유지 → 001 기존 테스트 영향 없음.
- **A04. 소계 정의 (확정)**: 소계 = 항목의 `단가 × 수량`. 항목마다 계산.
- **A05. 합계 정의 (확정, 001 A8 재사용)**: 합계 = 모든 항목 소계의 총합. `CartView.totalPrice`는 **할인 전** 합계로 의미를 유지한다 (001 S05·S06 테스트 단언 보존).
- **A06. "실시간" 의미 (확인 요청)**: 순수 도메인. "수량 변경 직후 조회하면 갱신된 소계·합계가 반환된다"로 해석.
- **A07. 할인율 단위 (확정)**: 0~100 사이 **정수 %**. 소수 할인율 미지원.
- **A08. 할인 범위 구별 (확정)**: 001이 범위 밖으로 선언한 "할인/프로모션"은 쿠폰·코드 기반 시스템을 의미한다. 002의 할인은 **stateless rate 인자 방식** (호출 시점 전달, 상태 아님)으로 성격이 다르다.
- **A09. 할인 적용 대상 (확정)**: 항목별이 아니라 **합계(totalPrice) 전체**에 한 번 적용.
- **A10. 할인금액 반올림 (확인 요청)**: `할인금액 = floor(합계 × 할인율 / 100)`. 최종가 = 합계 − 할인금액. **원 단위 미만 버림(floor)**. 다른 반올림 정책 원하면 수정 요청.
- **A11. 범위 밖 할인율 (확정)**: 음수·100 초과는 거부(예외). 0%·100% 유효.
- **A12. 빈 장바구니 할인 (확인 요청)**: 합계 0에 유효 할인율 적용 시 할인 0·최종가 0 반환 (예외 아님).
- **A13. 할인율은 상태 아님 (확인 요청)**: 계산 시점 인자. 장바구니가 상태로 저장하지 않음 (함수형 계산).
- **A14. CartView 확장**: 기존 `items`, `totalPrice`에 항목별 `subtotal`, 할인 결과용 `finalPrice`(=최종가)를 추가. `totalPrice`의 기존 의미 유지.
- **A15. 영속화 없음 (확정)**: 인메모리. 카탈로그도 메모리 상 고정 목록.

## 시나리오

### S01. 고정 카탈로그 전체 조회 (A01)
- Given: 시스템이 초기화된 상태
- When: 상품 카탈로그를 조회한다
- Then: 정확히 10개 상품이 반환되며 각 상품은 `productId`, `name`, `price`를 가진다

### S02. 카탈로그 안정성 (A01)
- Given: 시스템이 초기화된 상태
- When: 카탈로그를 두 번 조회한다
- Then: 두 결과의 `productId` 목록과 각 `price`가 동일하다

### S03. 카탈로그에 없는 상품 담기 거부 (A03)
- Given: ProductCatalog가 주입된 장바구니, 비어 있음
- When: 카탈로그 10개에 없는 `productId` 상품을 담으려 한다
- Then: 담기가 거부되고 오류가 발생하며, 장바구니는 비어 있는 상태로 유지된다

### S04. 단일 항목 소계 계산 (A04)
- Given: 단가 1000인 P1이 수량 3으로 담긴 장바구니
- When: 목록(뷰)을 조회한다
- Then: P1 항목의 소계(`subtotal`)가 3000으로 표시된다

### S05. 수량 변경 후 소계 갱신 (A04, A06) — 할인 선행 조건
- Given: 단가 1000인 P1이 수량 3(소계 3000)으로 담긴 장바구니
- When: P1 수량을 5로 변경한 뒤 목록을 다시 조회한다
- Then: P1 소계가 5000으로 갱신되어 표시된다

### S06. 다항목 소계와 합계 일관성 (A04, A05, A06) — 할인 선행 조건
- Given: P1(단가 1000, 수량 2), P2(단가 500, 수량 3)이 담긴 장바구니
- When: 목록을 조회한다
- Then: P1 소계 2000, P2 소계 1500이 표시되고, `totalPrice`(합계)는 두 소계의 합 3500이다

### S07. 수량 변경이 합계에 반영 (A05, A06) — 할인 선행 조건
- Given: P1(1000×2), P2(500×3)로 합계 3500인 장바구니
- When: P2 수량을 1로 변경한 뒤 합계를 조회한다
- Then: `totalPrice`가 2500(2000 + 500)으로 갱신된다

### S08. 유효한 할인율 적용 — 정수로 떨어지는 경우 (A09)
- Given: `totalPrice` 3000인 장바구니
- When: 할인율 10%를 적용한다
- Then: 할인금액 300, `finalPrice` 2700이 반환된다

### S09. 할인금액 원 단위 미만 버림 (A10)
- Given: `totalPrice` 1005인 장바구니
- When: 할인율 33%를 적용한다
- Then: 331.65 → floor → 할인금액 331, `finalPrice` 674가 반환된다

### S10. 할인율 0% 경계 (A11)
- Given: `totalPrice` 3000인 장바구니
- When: 할인율 0%를 적용한다
- Then: 할인금액 0, `finalPrice` 3000이 반환된다

### S11. 할인율 100% 경계 (A11)
- Given: `totalPrice` 3000인 장바구니
- When: 할인율 100%를 적용한다
- Then: 할인금액 3000, `finalPrice` 0이 반환된다

### S12. 음수 할인율 거부 (A11)
- Given: `totalPrice` 3000인 장바구니
- When: 할인율 -1%를 적용한다
- Then: 적용이 거부되고 `InvalidDiscountRateException`이 발생하며, 결과값은 반환되지 않는다

### S13. 100 초과 할인율 거부 (A11)
- Given: `totalPrice` 3000인 장바구니
- When: 할인율 101%를 적용한다
- Then: 적용이 거부되고 `InvalidDiscountRateException`이 발생하며, 결과값은 반환되지 않는다

### S14. 빈 장바구니에 할인 적용 (A12)
- Given: 비어 있는 장바구니 (`totalPrice` 0)
- When: 유효한 할인율 20%를 적용한다
- Then: 할인금액 0, `finalPrice` 0이 반환된다 (예외 아님)

### S15. 수량 변경 후 할인 재계산 (A06, A09, A13)
- Given: `totalPrice` 3000인 장바구니
- When: 수량을 늘려 `totalPrice`가 4000이 된 뒤 다시 할인율 10%를 적용한다
- Then: 할인금액 400, `finalPrice` 3600으로 재계산된다

## 충돌 분석

### 충돌 1 — 001 A2 vs 002 A03: addItem 계약 (해소됨)
- **원 충돌**: 001 A2는 "주어진 것으로 받음"(카탈로그 조회 없음), 002 A03은 카탈로그 검증을 요구.
- **해소**: A03에서 ProductCatalog를 선택적 의존성으로 명시. 미주입 시 001 A2 동작 유지 → 001 기존 테스트 영향 없음.

### 충돌 2 — 001 범위 밖 "할인" vs 002 할인 기능 (해소됨)
- **원 충돌**: 001이 "쿠폰/할인/프로모션"을 범위 밖으로 선언.
- **해소**: A08에서 구별 명시. 001이 배제한 할인은 코드 기반 프로모션 시스템. 002 할인은 stateless rate 인자이므로 성격이 다름.

### 중복 — S04-S07 vs 001 S05 (의도적)
- S04-S07은 합계 계산 자체의 재검증이 아닌 **할인 계산의 선행 조건 수립**. 001 S05를 전제로 하며 소계(subtotal) 노출이 추가되는 점이 차별화 근거.

### 영향 범위 요약
- **001 테스트**: A03 선택적 의존성 설계 시 영향 없음.
- **CartView 확장 필요**: `CartItem.subtotal`, `CartView.finalPrice` 신규 추가 (기존 필드 유지).
- **신규 타입**: `ProductCatalog`, `InvalidDiscountRateException`, 할인 계산 메서드 (`applyDiscount(rate)` 또는 유사).

## 게이트 — 사람 승인 대기

확인이 필요한 가정:
- **A03**: 카탈로그 선택적 주입 방식 동의 여부
- **A06**: "실시간 = 조회 시 갱신" 해석 동의 여부
- **A10**: 할인금액 **버림(floor)** 정책 동의 여부 (반올림/올림 원하면 수정)
- **A12**: 빈 장바구니 할인 시 예외 대신 0 반환 동의 여부
- **A13**: 할인율 상태 미보존(함수형) 동의 여부
