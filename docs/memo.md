생각
- 레거시 php 리팩터링
    - 만들면 좋기야 한데, 당장 쓸 일이 있는가? 4주동안 이걸 얼마나 사용하려고 할까? 적어도 회사에서는 이걸 사용하기가 애매한 상황이다. 왜냐하면, 신규 프로젝트들 때문에 레거시 php 들여다볼 시간이 많지 않다. 그래서 회사에서 사용해보고 효능감을 느끼기에 덜 유리하다.
    - 만약 만든다면, 두 가지 버전이 필요할 수 있다. 첫 번째는 php 에서 바로 spring, next 로 가는 것이다. 두 번째는 php 에서 백엔드가 될 수 있는 부분만 php 로 가는 것이다.
    두 가지 버전이 모두 필요한 이유는, 내가 작성할 수 있는 next에 대한 코드는 오직 관리자 페이지에 한하기 때문이다. 고객 표면에 열린 php 페이지는 내가 작성할 수 없으므로, 만약 마이그레이션을 한다면, 오직 백엔드에 해당하는 부분만 가능하다.
    - 실험이 가능한가? 실험 대상은 명확하고, 만약 만들어진다면 언젠가 사용할 때 굉장히 편해질 것 같기야 하다.
    - 실험대상이 되는 고객센터는 솔직히 내 마음대로 해도 될 것 같기도 하다.
    - 잘 만들어진다면, AI 에이전트 여기에 붙여볼 수도 있지 않을까 싶기도 하고. 어찌되었든 간에 올해 내에 해야하는 일이기도 하다.

- 조금 더 범용적인 걸 만든다면.
    - 티켓 -> 구현에 이르는 걸 만들 수 있을 것이다. 인터뷰를 해서 정책 같은 걸 보다 세분화할 수도 있을 것 같고, 적절한 패턴 같은 것도 덧입혀 볼 수 있을 것 같다.
        - 그러나 이건 사이드프로젝트에 한하지 않을까 싶기도 하다.
        - 회사에서는 이게 어떻게 필요하지? 회사에서는 프로젝트가 다양해서 애매하달까. 특정 프로젝트에 해당하는 프로세스를 만들 수는 있을 것 같기는 하다. 그런데, 범용적으로 만들기는 애매한 것 같기도 하다. 때로는 php 를 건들여야 하고, 때로는 next를 건들여야 하고, 때로는 구 Java, 때로는 Kotlin, Spring을 쓴다. 기술스택 통일성이 없어서 애매하지는 않은가 싶기도 하다.

    - 버그가 있고, 접근하기 어렵게 작성된 PHP코드를 우선 고치는 과정이 필요한 걸까?
    - AI가 잘 돌아갈 수 있는 환경인지 아닌지, 확인이 필요하다. 이거는 만들면서 경험적으로 이루어지는 것인가.
    - 지금 옮기려고 하는 php 에 대해 잘 알고 있어야 잘 옮길 수 있는 걸까.
- 처음부터 커다란 걸 만들려고 하니까 잘 안 되는 느낌이랄까. 무언가를 하긴 했는데, 이게 잘 된 건지 아닌지 모르겠는 느낌이 있다.
- 과연 좋은 도구를 선택한 것이 맞는지 의구심이 든다.
