# 컨텍스트 주입 최적화 — 정량 비교 (도전 2)

> DAY2 도전 2. 컨텍스트 체계의 최적화(**계층형 로딩** · **세션당 1회 dedup**)를 **실제 주입 바이트**로 정량 측정한다.
> 방법: `inject-domain.sh`에 편집 이벤트(JSON)를 먹여 반환된 `additionalContext`의 크기를 잰다. (하드 지표=바이트, 토큰은 대략치.)

## ① 계층형(tiered) vs 전체 주입 — 큰 도메인 문서
큰 도메인 문서(약 120줄, 12.6KB)를 편집할 때 주입되는 양:

| 방식 | 주입 크기 |
|---|---|
| 전체 주입(목차 + 문서 전체) | **12,621 bytes** (~3.5k토큰 대략) |
| 계층형(목차 + 머리 16줄 + "전체는 Read" 포인터) | **1,840 bytes** (~500토큰) |
| **절약** | **10,781 bytes · 85%** |

문서가 클수록 절약 폭↑. 작은 문서는 임계(60줄) 미만이라 계층형에서도 **전체 주입**한다(예: `auth.md` 2.6KB → 요약 없이 전체).

## ② 세션당 1회 dedup — 같은 도메인 반복 편집
같은 도메인 코드를 한 세션에 **5회 편집**하는 경우 누적 주입량:

| 방식 | 누적 주입 |
|---|---|
| dedup 없음(매 편집 주입) | **9,200 bytes** (1,840 × 5) |
| dedup 있음(세션당 1회) | **1,840 bytes** |
| **절약** | **7,360 bytes · 80%** |

(2번째 편집부터 주입 0 bytes — mark 파일로 세션·도메인당 1회 보장.)

## 방법 (재현)
- `inject-domain.sh`에 `{tool_input.file_path, session_id}` JSON을 stdin으로 주고, `jq`로 `additionalContext`를 뽑아 `wc -c`.
- 큰 문서는 임시 프로젝트(격리)로 생성. `session_id`를 바꿔 dedup mark를 제어.
- 토큰 수치는 바이트 기반 대략치 — 정확한 하드 지표는 바이트/문자.

## 결론
두 최적화가 합쳐지면 **"큰 도메인 × 반복 편집"** 상황에서 순진한 *전체-매번-주입* 대비 컨텍스트를 **한 자릿수분의 일**로 줄인다(계층형 85% + dedup 80%). 도메인·문서가 늘수록 이득이 커진다 — **계층형 목차/상세 분리**와 **dedup**이 "쓸수록 무거워지는" 컨텍스트 폭증을 막는 것이 수치로 확인된다.
