# 정산 계산 배치 성능 개선 런북 (perf-loop)

> **무엇:** 내가 만든 **정산 페이지**의 정산 계산 배치(`SETTLE_CALC`)를 `/perf-loop`(게이트 달린 랄프 루프)로 빠르게 만드는 방법. **왜:** 이 문서만 보고 바로 이어 돌릴 수 있게 한 자기완결 핸드오프.
> 목표: 계산 배치를 **5분 → 2분 30초(150초) 이하**로.
> 방법: 측정 게이트 + 정확성 게이트 + 점수 루브릭(≥90 통과). 실제 라운드 기록은 [[settlement-calc-rounds]](`settlement-calc-rounds.md`).
>
> 환경 상세(호스트·포트·자격증명 등)는 각자 값으로 채우도록 `<...>` 플레이스홀더로 뒀다.

작성 2026-07-16. 대상: `<정산 배치 서버 저장소>`, 브랜치 `<perf 브랜치>`.

---

## 0. 목표와 판정

- **속도 목표**: 운영 LAN에서 전체 계산 **≤ 150초(2:30)**.
- **정확성**: 생성 이용권의 **수·시각(use_year_month)·serial_no 가 종전과 완전히 동일**해야 한다. 정산 데이터다 — 바뀌면 버그.
- **채택 조건**: 아래 §6 점수 루브릭 **총점 ≥ 90 AND 정확성 게이트 통과**.

운영 서버 배치 정지/재가동 (SSH):
```bash
ssh -i <SSH 키> -p <port> <user>@<운영 인스턴스 host>
#   정지:  배치 프로세스 kill
#   재가동: <배치 실행 스크립트>
```

### 🛑 운영 DB 안전 규칙 (절대 준수)
운영 DB를 직접 다룬다. 아래는 협상 불가.
- **소스 DB(read 데이터소스)는 절대 쓰지 않는다.** 계산은 소스를 **읽기만** 한다
  (`read.repository` 는 전부 SELECT, write 호출 0건 — 검증됨). 여기에 INSERT/UPDATE/DELETE 가 생기면 즉시 중단.
- **정산 DB(main)만 쓴다.** 그것도 **배치의 정상 동작(이용권 차분·run 로그)**뿐, 측정자가 임의로 데이터를 수정하지 않는다. 쓰는 건 **재실행하면 같은 상태로 수렴하는(자가 복구) 것**만.
- 성능 개선은 **동작(코드)만 바꾸고 데이터는 안 바꾼다**가 전제다. 결과(이용권 수·시각·serial)가 달라지면 그건 버그.

## 2. batch 로컬 구동 (이렇게 안 하면 프로세스가 죽거나 dev로 뜸)

```bash
cd <정산 배치 서버 로컬 경로>
JAVA_HOME=<지정 JDK 경로> ./gradlew bootRun --console=plain "--args=--spring.profiles.active=prod" > /tmp/batch-run.log 2>&1
```

- ⚠️ **프로파일은 반드시 `--args=--spring.profiles.active=prod` 로 넘길 것.** `SPRING_PROFILES_ACTIVE` 환경변수는 bootRun 포크 JVM에 안 먹어서 `dev` 로 떠버림 → localhost DB(닫힘) → 기동 실패.
- ⚠️ **bootRun을 백그라운드 태스크의 "직접 명령"으로** 돌릴 것. `nohup ... &` 로 감싸면 런처 셸이 끝날 때 프로세스가 회수돼 죽는다.
- 기동 성공 신호: 로그에 `Started ...Application` + `HikariPool-1 Start completed` + `HikariPool-2 Start completed`.

## 3. 측정 트리거 — DB 자격증명·API 없이 자율 실행

임시 컴포넌트 `PerfBenchTrigger.java` 가 두 파일을 1초마다 감시한다.

### 3-a. 마이크로 벤치 (루프 반복용 — **이걸 써라**)
프로젝트 ID를 한 줄에 하나씩 넣으면, 그 프로젝트만 직접 계산하고 프로젝트당 시간을 로그로 찍는다.
batch_job 테이블을 안 거치므로 **stuck 없음, 몇 십 초면 끝남.**
```bash
printf "<P1..P12 프로젝트ID 12줄>" > /tmp/perf-settle-bench
```
**고정 벤치 세트(12개)** — before/after 비교하려면 항상 같은 세트를 써라.

결과 읽기:
```bash
grep -E "\[BENCH\]|\[BENCH_SPLIT\]" /tmp/batch-run.log
#   [BENCH] projectId=P1 elapsed=2136ms
#   [BENCH_SPLIT] projectId=P1 settleCalc=2040ms unitBuild=408ms
#   [BENCH] === done projects=12 totalElapsed=30086ms ===
```

### 3-b. 전체 실행 (최종 검증용 — VPN 위에선 느림)
```bash
touch /tmp/perf-settle-trigger   # 전체 계산 큐잉 → 스케줄러가 실행
```
- VPN 위에서 **30~60분+**. 중간에 죽이면 작업이 `P`(진행중)로 멈춰 이후 큐잉을 막는다.
- 멈춘 작업 정리(사람이 DB에서): `UPDATE batch_job SET status='F', fail_reason='perf aborted' WHERE id=<id>;`
- 전체 계측 로그: `grep "\[SETTLE_CALC\]" /tmp/batch-run.log` → `total`, `projectType=N`, `rebuildOrderIndexes`, `slow projectType..` 라인.

## 4. ⚠️ VPN 왜곡 — 반드시 이해할 것

로컬에서 돌지만 DB는 운영(VPN 너머)이라 **쿼리 한 번마다 ~250ms 왕복 지연**을 낸다.
- 같은 프로젝트: 운영 서버(DB와 같은 LAN) **~30ms** vs 로컬(VPN) **1.5~4초** = **50~100배**.
- 그래서 **로컬 절대 시간은 운영 5분과 무관**하다. 대신 **왕복 수를 줄이는 최적화(N+1 제거 등)는 신호가 크게 증폭**돼 보인다 → 로컬 벤치는 그런 최적화의 상대 측정에 유효.
- **최종 "≤2:30" 판정은 반드시 운영 LAN**(운영 서버에서 전체 실행)에서 확인. 로컬은 상대 개선만 증명.

## 5. R0 베이스라인 + 진단 (2026-07-16 측정)

**벤치 12개, 프로젝트당 789~5820ms, 중앙값 ~2255ms, 합 ~30초 (VPN 값).**
분해:
| | 프로젝트당 평균 | 정체 원인 |
|---|---|---|
| settleCalc (조회+차분) | ~1,750ms | **고정 DB 왕복 ~6-7개** (프로젝트/상품ID/티켓/소스/finish/재조회) |
| unitBuild (정산단위) | ~840ms | 왕복 ~3-4개 |

**진단**: 티켓 0건 프로젝트도 **프로젝트당 고정 왕복 ~10개**가 나간다. 개별 프로젝트가 무거운 게 아니라 **프로젝트마다 반복되는 쿼리 × 프로젝트 수**가 5분의 정체. `rebuildOrderIndexes`(전 유효티켓 로드+재저장)는 **아직 미측정 — 별도 유력 용의자.**

**R1 후보 (다음 라운드)**:
1. 프로젝트별 반복 쿼리를 **프로젝트 전체에 걸쳐 배치화** (모든 대상 프로젝트의 티켓/상품ID/소스를 한 번에 로드) — 가장 큰 레버, 구조 변경 큼
2. 프로젝트당 고정 왕복 수 줄이기 (예: 0건 프로젝트의 불필요 재조회 스킵)
3. `rebuildOrderIndexes` 측정 후 개선 (전 티켓 메모리 로드 회피)

## 6. 점수 루브릭 — 총점 100, **≥90 만 통과** (정확성은 하드 게이트)

각 라운드의 변경을 항목별로 채점해 합산한다. **정확성 게이트 실패 시 총점 무관하게 불합격.**

| 항목 | 배점 | 채점 기준 |
|---|---:|---|
| **정확성 보존** (하드 게이트) | **30** | `/verify full` 통과 **AND** 이용권 수·use_year_month·serial_no 가 종전과 바이트 동일. **실패 시 전체 불합격.** |
| **속도 목표 달성** | **30** | 운영 LAN 전체 계산 시간: **≤150초 → 30점**. 150~300초 사이는 선형 부분점(예: 210초→18점). 개선 없음/악화 → 0점. |
| **측정 신뢰성** | **15** | 같은 조건 3회 측정 중앙값, 개선폭 > 노이즈(분산), before/after 숫자 명시. 추측·1회 측정 → 감점. |
| **블라스트 반경 / 되돌리기** | **10** | 변경 범위 좁고 격리됨, revert 쉬움. 공유 base·핫코어 광범위 수정일수록 감점. |
| **스케일 지속성** | **10** | 벤치뿐 아니라 **운영 규모**에서도 유효(알고리즘 O 개선 > 상수배). 장난감 입력에서만 빨라지면 감점. |
| **유지보수성** | **5** | 속도당 추가되는 복잡도·가독성 손실이 낮을수록 만점. |

- **통과 = 총점 ≥ 90 그리고 정확성 게이트 통과.**
- 통과 못 한 변경은 **되돌린다**(랄프 루프가 쓰레기를 안 쌓게).
- 채택된 변경은 측정 수치(before→after)를 커밋 메시지에 남긴다.

## 7. 루프 한 라운드 절차

```
1) 후보 하나 고름 (§5 R1 후보 + 루브릭으로 판단)
2) 코드 수정 (한 번에 하나만 — 분리 측정 위해)
3) 컴파일 + 배치 재기동 (§2)
4) 벤치 3회 (§3-a) → 프로젝트당 중앙값 before/after 비교
5) 정확성: /verify full  + 이용권 수/시각/시리얼 동일 확인
6) §6 루브릭 채점 → ≥90 이고 정확성 통과면 채택, 아니면 revert
7) 로그 남기고(§8) 다음 라운드. 정체/목표달성/후보고갈이면 종료
8) [최종] 운영 LAN 전체 실행으로 ≤2:30 확인
```

## 8. 라운드 기록은 별도 문서에 (매 이터레이션마다 append)

**실제 라운드 기록(R0, R1, …)은 이 런북이 아니라 [[settlement-calc-rounds]](`settlement-calc-rounds.md`) 에 남긴다.**
이 런북은 *루프를 돌리는 방법*(환경·트리거·루브릭·절차)만 담고, *라운드마다 무엇을 바꿨나*는 라운드 로그로 분리한다.

**매 라운드가 끝나면(채택이든 폐기든) 반드시 라운드 로그에 스냅샷을 append 한다.** 폐기 라운드도 반드시(왜 안 됐는지가 자산). **최대 100라운드.** 스냅샷 형식은 [`/perf-loop` SKILL](../../.claude/skills/perf-loop/SKILL.md) §R-e 참조.
라운드 로그 상단에는 **누적 요약 + 루프 총 경과(착수~현재, 총 소요, 완료 라운드 수)**를 유지한다.

## 9. ⚠️ 정리 (측정 끝나면 반드시)

임시 측정 코드는 **커밋 안 된 로컬 상태** (perf 브랜치). **운영 배포 금지, 측정 종료 시 제거:**
- `PerfBenchTrigger.java` (신규 — 삭제)
- `BatchJobService.enqueueIfRunnable(...)` 오버로드 (되돌리기)
- `BatchJobExecutor` 의 `[SETTLE_CALC]` / `[BENCH_SPLIT]` 계측 (되돌리거나, 정식 계측으로 유지할지 결정)

종료 체크리스트:
- [ ] 로컬 배치 중지 (`pkill -f "GradleWrapperMain.*bootRun"`)
- [ ] 트리거 파일 삭제 (`rm -f /tmp/perf-settle-*`)
- [ ] 멈춘 batch_job(status 'P') 있으면 정리
- [ ] **운영 서버 배치 재가동** (§1)
- [ ] 임시 perf 코드 제거 후 커밋

## 10. 참고 — 이미 적용된 최적화 (배포됨/커밋됨)

계산·정산은 이미 여러 라운드 최적화가 커밋돼 있다(별도 이력). 이번 perf-loop는 **그 위에서** 계산을 2:30까지 더 줄이는 작업이다.
