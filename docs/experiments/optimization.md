# 컨텍스트 체계 최적화 + 정량 비교

컨텍스트 체계의 핵심 비용은 토큰이다(OS.md B-3: "파일마다 로딩 시점이 다르고 토큰
비용이 거기서 갈린다"). 그 비용을 재고, 설계 선택이 실제로 얼마를 아끼는지 숫자로
확인했다.

## 측정 단위

문자 수(`wc -m`). 토큰은 세션·모델마다 달라 스크립트로 정확값을 못 내지만, 문자
수는 결정적·재현 가능하고 전략 간 상대 비교(%)엔 충분하다. 한국어+마크다운은 대략
문자 2~3개당 토큰 1개꼴이라, 토큰은 문자 수를 그 비율로 나눈 근사로 읽는다.
재현: `bash tools/measure-context.sh`.

## 비교 1 — 점진적 공개 (무엇을 항상 켜 두나)

컨텍스트를 전부 always-on으로 인라인하는 순진한 방식 대비, 지금은 4개만 `@import`로
켜고 레지스트리·도식은 이름으로만 참조(필요할 때 로딩)한다.

| 전략 | 항상 켠 비용 |
|---|---|
| 순진 — 전부 인라인 always-on | 5095자 |
| 현재 — 4개 import + 나머지 lazy | 2146자 |
| 절감 | 2949자 (57%) |

항상 켠 자리(가장 비싼 슬롯)를 57% 줄였다. 레지스트리(1084자)·도식(1723자)은 매 세션
비용 0이고, 필요할 때만 읽힌다.

## 비교 2 — 단일 출처 이름 참조

`writing-style`은 5개 컴포넌트(design-doc·investigate·analyze·code-writer·
code-reviewer)가 쓴다. 복붙 대신 이름으로 참조한다.

| 방식 | 유지 대상 |
|---|---|
| 복붙 | 사본 5벌 × 253자 = 1265자, 5곳 동기화 필요 |
| 현재 이름 참조 | 원본 1벌. 사본 0, 드리프트 위험 0 |

한 사실을 한 곳에만 두는 규칙이 중복 1265자와 5중 동기화 부담을 없앤다.

## 적용한 최적화 — 매트릭스 중복 제거

측정 중 자기 위반을 발견했다. 주입 매트릭스가 `INDEX.md`와 `context-map.md` 두 곳에
같이 있었다("한 사실은 한 곳에만" 위반). `context-map`은 다이어그램(고유 가치)만
남기고 매트릭스는 `INDEX`를 가리키게 고쳤다.

| | before | after |
|---|---|---|
| context-map.md | 1865자 | 1723자 (-142자) |

문자 절감(142자)은 작다 — 둘 다 lazy라 매 세션 비용엔 안 잡힌다. 진짜 이득은
드리프트 위험 소거다: 주입 규칙이 바뀌면 이제 `INDEX` 한 곳만 고치면 된다.

## 검증

- 배선 테스트 `tools/verify-injection.sh` — 최적화 후에도 통과(exit 0). 주입은 안 깨졌다.
- A/B 실험 결과(README.md)와 합치면, 항상 켠 4개 중 행동을 실제로 바꾼 건
  work-principles였다. 그래도 나머지도 always-on을 유지한다: writing-style은 비한국어
  출력·일관성에, user는 상호작용 전반에, project 스켈레톤은 "도메인 가정 금지" 신호에
  값을 한다. 넷 다 제 자리를 번다.

## 결론

- 현재 설계(import + 이름 참조)는 순진한 인라인 대비 항상 켠 비용을 57% 아끼고,
  단일 출처로 중복 1265자·5중 동기화를 없앤다.
- 최적화 여지는 크지 않았다 — B-3를 지키며 지은 덕에 이미 얇다. 남은 중복 한 건을
  제거해 단일 출처를 완성했다.
- 더 줄이려다 always-on에서 뭔가 빼면 A/B가 보인 행동 이득(묻고 하기)을 잃는다.
  얇게는 하되 효과를 깎지 않는 선이 지금이다.
