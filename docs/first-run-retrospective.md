# 첫 실행 회고 — 슬라이스 1개를 끝까지 돌린 결과

2026-09-01. 8단계 흐름을 처음으로 Phase 0 부터 Phase 8 까지 완주했다. 대상은 읽기 전용
슬라이스 하나였다.

이 문서는 설계 문서(`legacy-migration-os.md`)의 입력이다. 여기서 확인된 것과 드러난 결함이
그 문서의 다음 개정에 반영된다. 회사 코드의 구체(파일명·심볼·테이블·호스트·기능 결함 내용)는
적지 않는다 — 실패의 **부류**만 적어도 이 회고의 목적은 달성된다.

## 규모

| | |
|---|---|
| 원장 규칙 | 85행 (도메인 60 / 화면 25 / 경계 0) |
| e2e | 75 spec |
| 서브에이전트 | 15개 / 19회 호출(재개 포함) |
| API 요청 | 약 1,330회 (오케스트레이터 200 · 서브에이전트 1,130) |
| 처리 토큰 | 약 3억 2천만 — 캐시 읽기 96% · 캐시 쓰기 3% · **출력 0.6%** |
| API 정가 환산 | 약 **$200** (캐싱 없었다면 약 $1,160) |
| 루프 회차 | L0 4회 · L1 1회 · L2 4회 · L3 3회 |
| 휴먼 게이트 | 2회 통과 + 감사 후 결정 3회 |

읽기 전용 슬라이스 하나에 약 $200 이 들었다(구독으로 돌렸으므로 실제 지출은 아니고 API 정가
환산이다). 처리 토큰의 **96%가 캐시 재독**이고 출력은 0.6%다 — 이 비율이 11번의 결론을 바꾼다.

측정 방법을 밝혀 둔다. 세션 트랜스크립트는 **한 번의 API 요청을 콘텐츠 블록마다 한 줄씩** 기록하고
`usage` 를 각 줄에 반복한다. 입력측(캐시 읽기·쓰기)은 줄마다 동일하므로 요청 단위로 한 번만 세야
하고, `output_tokens` 는 줄마다 다르며 `stop_reason` 이 있는 마지막 줄만 진짜 값이다(앞 줄은 1, 5
같은 자리표시자). 이 규칙을 모르고 세면 출력이 4~5배 부풀거나 1/5로 줄어든다.

**작업 중 화면에 보이는 `subagent_tokens` 값은 쓰지 않았다.** 에이전트별로 실측치와 대조해 봤으나
출력·요청수·캐시읽기·캐시쓰기 어느 것과도 비례하지 않았다(비율 0.19~0.42로 흩어진다). 그 값이
무엇을 세는지 확인하지 못했으므로 근거로 삼지 않는다.

## 1. 확인된 것 — 두 오라클이 실제로 작동했다

**이 OS 의 존재 이유가 이번에 증명됐다.**

e2e 75개가 토글 양쪽에서 **전부 초록**이었다. 거기서 멈추면 슬라이스는 "완료"였다. 그 상태에서
완전성 감사가 코드를 다시 읽어 **실제 동등성 파괴 두 건**을 찾았다. 오케스트레이터가 독립적으로
재측정해 확인했다. 둘 다 특정 문자가 든 입력에서 옛 경로와 새 경로가 다른 결과를 내는 것이었다.

e2e 가 그것을 못 본 이유는 e2e 의 결함이 아니다. **그 입력이 원장에 없었기 때문이다.** 아래 3번이
그 이야기다.

두 번째 오라클이 없으면 이 슬라이스는 완료로 기록되고 배포됐다. 이건 가설이 아니라 일어난 일이다.

## 2. 확인된 것 — 렌즈 설계와 잔류합의

**레드팀 렌즈는 의도대로 작동했다.** 4라운드가 각각 8·8·6·7건을 찾았고 **성격이 겹치지 않았다.**
각 라운드가 앞 라운드가 구조상 볼 수 없던 것을 찾았다. 수렴 실패가 아니라 렌즈가 일한 것이다.

**잔류합의를 사람만 발급하게 한 것도 옳았다.** 도메인 60행 중 32행이 옛 코드에 남았고 전부 이유와
승인자·일자가 붙었다. 이 장치가 없으면 감사는 영구 FAIL 이거나 무의미했다. 감사가 그 32행을
"이유가 코드와 맞는지"로 검증했고, 그 과정에서 두 행의 이유가 실제와 어긋난다는 것을 잡았다.

**게이트 위치도 옳았다.** 게이트 1에서 사람이 내린 계약 관련 결정이 나중에 감사 지적으로
되돌아왔다 — 결정이 아래로 흐르고 감사가 그것을 검증한 것, 즉 고리가 닫혔다.

---

## 3. 결함 — 위험이 원장에 도달하는 경로가 없다

**가장 비싼 실패.** 설계 담당이 설계서에 "이 지점은 옛 경로와 달라질 수 있다, 반드시 기준선과
대조해야 한다"고 **정확히 예측해 적었다.** 스왑 담당이 스왑 기록에 미검증으로 다시 올렸다.

그런데 e2e 작성자의 입력은 **원장뿐이다.** 설계서도 스왑 기록도 읽지 않는다. 그래서 그 의심이
spec 이 될 경로가 없었고, 동등성 루프가 그 위에서 초록으로 닫혔다.

문서 셋이 위험을 알고 있었고 **아무 오라클도 그것을 볼 수 없었다.**

일반화: **원장을 경유하지 않는 문서 간 인계는 전부 누출이다.** 원장이 조인 키라는 말의 진짜
의미가 이것이고, 설계 자신의 의심도 예외가 아니다.

**반영**: 설계자 에이전트가 표류를 의심한 지점을 원장 행 후보로 내도록, Phase 3 게이트가 그것을
확인하도록 고쳤다. **미반영**: 스왑 기록 쪽 같은 경로. 위험을 명명할 수 있는 문서가 셋인데
고친 것은 하나다.

## 4. 결함 — 오케스트레이터의 병합을 검사하는 것이 없다

감사 지적을 **세 번 덜 적용했다.** 한 번은 지적문이 "다섯 행 (+한 행 더)"라고 썼는데 개수만 읽고
목록을 읽지 않아 한 행을 빠뜨렸다. 나머지 둘은 원장의 두 칸 중 한 칸만 고쳤다.

셋 다 **다음 감사 라운드가 잡았다.** 즉 오케스트레이터를 잡아주는 것은 감사 하나뿐이고, 감사는
Phase 6 뒤에야 돈다. 라운드 하나가 통째로 이 실수 때문에 돌았다.

**이 파이프라인에서 실수가 가장 자주 나는 지점이 오케스트레이터가 원장을 병합하는 곳인데,
거기에는 아무 검사도 없다.** 휴먼 게이트는 설계와 레거시 편집에만 있다.

## 5. 결함 — L0 루프의 종료 조건이 달성 불가능하다

종료 조건은 "레드팀이 2회 연속 빈손"인데 **네 라운드 동안 한 번도 발생하지 않았다.** 상한 3을
치고 사람에게 올렸고, 승인받은 4라운드가 가장 값진 발견들을 냈다.

문제는 이 조건이 **답할 수 없는 질문**을 묻는다는 것이다. "다 찾았는가"는 알 수 없다. 실제로
도달한 한계는 **"정의된 렌즈를 다 썼는가"** 였고, 그건 답할 수 있다.

지금 설계는 이 두 가지를 혼동한다.

## 6. 결함 — 아무 자동 검사도 없는 규칙이 보이지 않는다

브라우저로 관찰할 수 없는 규칙은 `불가` 로 적고, 그 의무는 백엔드 단위 테스트로 넘긴다.
이번에 11행이 `불가` 였고 5행이 보상 테스트를 받았다.

**나머지 6행은 옛 코드에 남은 규칙이라 백엔드 테스트를 만들 수가 없다.** e2e 도 단위 테스트도
그 6행을 검사하지 않는다. 감사의 소스 독해가 유일한 확인인데 그것은 일회성 행위이고 회귀
가드가 아니다.

**원장 포맷에 그 사실을 표시하는 칸조차 없다.** 지금 그 6행은 세지지도 않은 채 무방비다.

## 7. 결함 — 감사가 테스트가 아니다

감사는 매번 새 에이전트가 소스를 읽는 행위다. 자기교정은 실제로 작동했다 — 2라운드가 1라운드의
판단 하나를 "그것은 1라운드 자신의 오류였다"고 정정했다.

그러나 **회귀 가드가 없다.** 누가 다음 달에 교체 지점을 고치면 새 감사를 돌려야만 안다. CI 에
걸 수 있는 값싼 버전이 필요하다 — 예: 원본 메서드 본문의 해시 불변 확인, 범위 밖 파일에
스위치 호출이 없는지 확인. 감사의 판단을 대체하지는 못하지만 **명백한 파괴는 자동으로 막는다.**

## 8. 결함 — 문서 간 정합을 검사하는 것이 없다

설계서의 규칙 배치표와 원장의 이관 열은 **같은 사실의 두 사본**이고 서로 다른 에이전트가
관리한다. 이번에 실제로 어긋났고 감사가 잡았다. 스크립트 하나로 잡히는 종류다.

## 9. 결함 — 에이전트 병렬화가 런타임 상태를 무시한다

두 담당을 병렬로 보냈다. 판단 근거는 **"서로 다른 저장소를 건드리니 독립적이다"** 였다. 틀렸다.
둘 다 검증하려고 **같은 토글을 뒤집었고**, 한쪽이 다른 쪽의 작업 중 상태에서 스위트 전체를 돌려
21개가 실패했다. spec 결함도 이관 결함도 아닌 실패였다.

**파일이 다른 것과 독립적인 것은 다르다.** 에이전트들은 토글·컨테이너·데이터베이스·백엔드
프로세스를 공유한다.

**반영**: Phase 6 에 "토글은 공유 가변 상태이므로 그것을 뒤집는 작업을 둘 이상 동시에 돌리지
말 것"과 "빨간 실행과 초록 실행을 동등하게 의심하고 토글을 애플리케이션에서 읽을 것"을 넣었다.

## 10. 결함 — 환경을 소유하는 단계가 없다

이번 세션에서 오케스트레이터가 실제로 한 일 중 상당 부분이 환경이었다. 서버 프로세스가 설정
오류로 기동 거부한 것 복구, 컨테이너 재생성, 리버스 프록시가 업스트림 주소를 캐시하는 문제 진단,
백엔드 재기동, 마지막에 내부망 밖이라 데이터베이스에 닿지 않는 상황 진단.

**8단계 어디에도 이 일의 자리가 없다.** `local-stack` 스킬이 있지만 "환경이 도중에 바뀌었다"를
다루지 않는다. Phase 0 에서 한 번 확인하고 끝이다.

## 11. 결함 — 비용이 컨텍스트 재독에 있고, 깊이를 지정할 수 없다

비용 구성이 예상과 달랐다.

| 항목 | 금액 | 비중 |
|---|---|---|
| 캐시 읽기 | 약 $109 | **54%** |
| 캐시 쓰기 | 약 $53 | 26% |
| 출력 | 약 $39 | 20% |
| 순 입력 | ~$0 | 0% |

**비용을 결정하는 것은 에이전트가 얼마나 쓰느냐가 아니라 "컨텍스트 크기 × 턴 수"다.** 출력은
금액으로 20%, 토큰으로 0.6%에 불과하다. 그러니 "에이전트가 말을 짧게 하게" 하는 최적화는 거의
의미가 없고, 줄여야 하는 것은 **턴 수와 턴당 컨텍스트**다.

가장 큰 지출처가 **오케스트레이터 자신**이었다(요청 200회, 약 $67, 전체의 1/3). 서브에이전트 어느
하나보다 크다. 세션 내내 컨텍스트가 커진 채 매 턴 전체가 다시 읽히기 때문이다. 서브에이전트는 각자
자기 컨텍스트만 들고 시작하므로 오히려 싸다 — **위임이 비용 측면에서도 옳았다**는 뜻이고, 반대로
오케스트레이터가 직접 파일을 많이 읽을수록 그 비용이 세션 끝까지 매 턴 반복된다.

깊이 문제는 그대로 남는다. `slice-scout` 이 위험도로 슬라이스를 고르는데 그 위험도가 파이프라인의
깊이를 바꾸지 않는다 — 레드팀 라운드 수, 보상 테스트 요구, 감사 라운드 수가 전부 고정이다. 다음
슬라이스가 **"얕게"** 를 말할 수 있어야 한다.

## 12. 결함 — 중단은 즉시 멈추지 않는다

에이전트 호출을 두 번 중단했다(한 번은 실수, 한 번은 의도적). 둘 다 **각각 100회를 넘는 API 요청을
이미 처리한 뒤에** 죽었다. 버려진 작업이 약 $11, 전체의 5.6%다.

즉 **중단 버튼은 되돌리기가 아니다.** 이미 쓴 것은 그대로 청구되고, 재개가 아니라 재실행이면 그만큼
두 번 낸다. 값비싼 에이전트를 띄우기 전에 프롬프트를 한 번 더 확인하는 것이 실제로 돈을 아낀다.

## 오케스트레이터가 가장 약한 부품이었다

에이전트들이 오케스트레이터의 지시보다 일관되게 나았다. 기록해 둘 값어치가 있는 사례들:

- **사실 오류 정정 3회.** 잘못된 상수를 쓰라고 지시했고(담당이 다른 방법을 골라 살았다),
  어댑터의 값 변환 원인을 잘못 진단했고(원인이 다르면 고치는 법도 다르다), 원장에 적은 실패
  기전이 판별 실험으로 반증됐다.
- **지시 거부 2회, 둘 다 옳았다.** 도달하지 않는 입력에 방어 코드를 넣지 않은 것,
  재현할 레거시 동작이 없는 곳에 규칙을 만들어 넣지 않은 것. 둘 다 "없는 규칙을 만들지 않는다"는
  원장의 원칙을 오케스트레이터보다 정확히 지켰다.
- **자기 초안의 버그를 스스로 잡은 사례.** e2e 담당이 기대 집합은 전체인데 실제 응답은 기본
  페이지로 잘리는 실수를 했고, 한 케이스가 **우연히 통과**하고 다른 케이스가 시끄럽게 실패해서
  잡혔다. "assertion 을 약화시키지 마라"는 규율이 작성자 자신에게 작동한 것이다.

에이전트 정의가 잘 됐다는 좋은 신호이고, **오케스트레이터 역할에 검사가 없다는 나쁜 신호다.**

## 없앨 것은 없다

8단계·루프 4개·게이트 2개가 많아 보이지만 **모든 단계가 무언가를 잡았다.** 한 단계도
낭비가 아니었다. 이해 단계가 규칙을 찾았고, 기준선이 동등성의 기준을 세웠고, 설계 게이트가
계약 결정을 사람에게 물었고, 구현이 관문을 넣었고, 스왑 게이트가 운영 코드 편집을 멈춰
세웠고, 동등성이 두 결함을 잡았고, 감사가 e2e 가 못 본 두 건을 잡았고, 문서화가 기획 결정
목록을 만들어냈다.

문제는 개수가 아니라 두 가지다: **깊이를 조절할 수 없다**는 것, 그리고 **오케스트레이터를
검사하는 것이 없다**는 것.
