# 4주 OS 주제 후보

> 나만의 클로드 코드 OS 만들기 — 주제 결정용 작업 문서. 확정될 때까지 계속 갱신한다.
> 최초 작성 2026-08-25

## 판단 기준

온보딩 문서의 OS 예시 4개(티켓 처리 / 스펙·테스트 주도 / 시각 회귀 / 논문 재현)에서 뽑은 축.

- **채점기** — AI가 자기 결과물을 스스로 채점하고 고칠 수 있는 객관적 기준.
  예시 4개 전부에 박혀 있다(3회 상한 / PASS·FAIL 독립 리뷰 / 적대적 이미지 비교 / 채점 후 자가수정).
  이게 없으면 루프가 수렴하지 않고 그냥 프롬프트 모음이 된다. **주제보다 채점기를 먼저 고른다.**
- **입력 확보** — 4주 내내 루프에 밀어 넣을 재료가 끊기지 않는가.
- **사람 개입** — `의사결정 → 승인 → 기준 제공 → 시작 버튼` 순으로 오른쪽이 진보한 형태.
- **차별성** — 2기 수강생이 만든 예시 4개와 겹치는가.

## 후보 목록

### 1. 운영 티켓 처리 *(아이디어: 나)*

티켓을 입력으로 요구사항 분석 → 구현 → 테스트·리뷰 자동수정 → PR.

- **채점기** — 기존 테스트 스위트. 이미 있음.
- **입력 확보** — 티켓은 계속 들어옴.
- **사람 개입** — 많음(단계마다 의사결정).
- **차별성** — 낮음. 온보딩 예시 1과 사실상 동일.
- **메모** — 가장 빨리 효능감이 나오는 안전한 선택. 대신 조별 리뷰에서 새로 나눌 게 적다.

### 2. 스펙/테스트 주도 *(아이디어: 나)*

요구사항 → 정책 분해 → 독립 리뷰 → 실패 테스트 먼저 → TDD 구현 → 실패 원장.

- **채점기** — 테스트. 가장 튼튼함.
- **입력 확보** — 새 기능이 있을 때만.
- **사람 개입** — 중간(요구사항 + 정책 승인).
- **차별성** — 낮음. 온보딩 예시 2와 동일.
- **메모** — `spec → code-analysis → writing-plans → TDD → review` 스킬 체인이 이미 있어 절반쯤 해본 상태.

### 3. 기획(피그마·노션) 검토 후 루프 개발 *(아이디어: 나)*

기획 산출물을 입력으로 받아 구현 루프를 돈다.

- **채점기** — **없음.** 별도 설계 필요. "기획대로 됐는지"를 자동 판정할 방법이 관건.
- **입력 확보** — 기획 문서가 나올 때만. 4주 동안 몇 번 안 될 수 있음.
- **사람 개입** — 중간.
- **차별성** — 높음. 예시 4개에 없는 유일한 주제.
- **메모** — MCP 연동에 시간을 다 쓸 위험. 시작은 Notion 페이지를 복사한 마크다운으로 충분하다.
  채점기는 2번에서 빌려올 수 있음(수용 기준 추출 → 테스트로 커버 → 커버리지로 판정).

### 4. PR 리뷰 에이전트 *(아이디어: 나)*

PR diff를 입력으로 다중 리뷰어가 병렬 검토 후 인라인 코멘트.

- **채점기** — 어렵지만 **만들 수 있음.** 세 가지 장치:
  - 적대적 검증 — 지적을 별도 에이전트가 반박, 반박 실패한 것만 생존
  - 골든 셋 — 나중에 버그가 터진 과거 PR을 정답지로 사용
  - 정밀도 원장 — 지적 중 실제로 고쳐진 비율을 주차별 추적
- **입력 확보** — PR은 계속 생김.
- **사람 개입** — 적음(AI가 판정자). 스펙트럼상 시각 회귀와 같은 칸.
- **차별성** — 중간. 시각 회귀의 도메인을 화면에서 코드로 옮긴 형태.
- **메모** — `agent-team-review` 스킬이 출발점. 실패 모드는 "틀려서"가 아니라 **"시끄러워서"**.
  3번을 확장으로 흡수 가능: 기획 문서를 컨텍스트로 주입하면 "코드가 맞나" → "원래 의도대로 됐나"로 질문이 올라감.

### 5. 장애 재현 OS *(아이디어: Claude)*

알럿·에러 로그 → 원인 가설 → 재현 테스트 작성 → 수정 → PR.

- **채점기** — **재현 테스트.** 가설이 틀리면 재현이 실패하므로 원인 적중 여부가 자동 판정된다.
  수정 후 통과 여부로 한 번 더 채점. 두 번 걸러짐.
- **입력 확보** — 불확실. 4주 동안 장애가 몇 번 날지 모름. 과거 인시던트 백테스트로 보완.
- **사람 개입** — 적음(알럿 투입 + 원인 승인).
- **차별성** — 높음.
- **메모** — `debug` 스킬이 출발점.

### 6. 레거시 객체지향 리팩터링 OS *(아이디어: Claude)*

비대한 Service → 책임 분석 → 협력 재설계 → 단계적 리팩터링.

- **채점기** — **두 겹.** 안전성은 기존 테스트 전체 통과(행위 보존), 개선은 지표(클래스 크기·순환복잡도·의존성 수).
  "리팩터링했는데 나빠졌다"를 숫자로 잡아낼 수 있다.
- **입력 확보** — 무한. 레거시는 마르지 않음.
- **사람 개입** — 적음(대상 지정 + 설계 승인).
- **차별성** — 높음.
- **메모** — `object-design` 스킬(책임 주도 설계)과 직결. 온보딩의 "설계자의 눈"과 가장 잘 맞물림.

### 7. 지식 증류 OS (메타 OS) *(아이디어: Claude)*

머지된 PR·리뷰 코멘트·회고 → 반복 패턴 추출 → 규칙 후보 → 검증 후 CLAUDE.md/스킬로 승격.

- **채점기** — 추출한 규칙을 과거 PR에 소급 적용했을 때 실제 리뷰 코멘트를 재현하는가.
- **입력 확보** — 충분(과거 PR 이력).
- **사람 개입** — 적음(규칙 승격 승인만).
- **차별성** — 매우 높음. OS가 스스로 두꺼워지는 구조.
- **메모** — 온보딩의 질문 "우리가 가진 지식을 AI에게 어떻게 전달하지?"에 정면으로 답함.
  **리스크: 추상적이라 효능감이 늦다.** "일단 동작하는 걸 만들라"는 권장과 상성이 나쁨.

### 8. 뮤테이션 테스팅 OS *(아이디어: Claude)*

AI가 의도적으로 결함을 주입 → 기존 테스트가 잡는지 확인 → 못 잡으면 테스트 보강.

- **채점기** — **뮤테이션 스코어.** 숫자 하나로 나오는 가장 객관적인 채점기. 주차별 개선을 그래프로 제시 가능.
- **입력 확보** — 무한.
- **사람 개입** — 적음(대상 지정만).
- **차별성** — 높음. "적대적 비교" 정신을 가장 극단까지 밀어붙인 형태.
- **메모** — 도구 세팅 필요(PIT 등). 주제가 좁아 4주를 채울 확장 여지를 따져봐야 함.

## 현재 추천

**4번(PR 리뷰) 또는 6번(레거시 OO 리팩터링).** 둘 다 입력이 마르지 않고, 사람 개입이 적은 칸에 있고,
채점기를 만들 수 있다. 4번은 기존 `agent-team-review` 자산이 있어 출발이 빠르고,
6번은 채점기가 이미 존재해서(테스트 + 지표) 설계 부담이 가장 적다.

3번은 단독으로는 채점기가 없어 4번의 확장으로 흡수하는 것을 권장.
7번은 가장 흥미롭지만 효능감이 늦어 4주 과제로는 위험.
