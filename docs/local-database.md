# 통제된 로컬 데이터베이스

- 상태: **조건부 가능 — 2026-09-14 실험으로 확인.** 스키마를 원격과 동일하게 재현했고, 레거시 PHP 를 한 줄도 고치지 않은 채 로컬 DB 에 붙였다
- 푸는 문제: `environment-readiness.md` 3장 B. 검증은 검사 대상 말고는 전부 통제돼야 하는데 지금 **입력(행)이 통제 밖**이다
- 여는 것: 쓰기 페이지의 동등성. 이중 실행과 가짜값 주입이 둘 다 부작용 때문에 막히는 자리에서, 데이터 자체를 정답지로 삼는 길
- 실험 기록 원본은 `.claude/.state/localdb-probe/` 에 있다(추적하지 않는다). 이 문서는 그중 **환경에 의존하지 않는 부분만** 옮긴 것이고, 실제 호스트명·스키마명·계정명은 `workspace.json` 에만 산다

---

## 1. 이 조치가 여는 것

읽기 페이지에서는 이중 실행이 동등성을 답한다. 쓰기 페이지에서는 답하지 못한다. 후보 경로에 부작용이 있으면 이중 실행이 데이터를 두 번 바꾸기 때문이다. 가짜값 주입도 같은 이유로 막힌다 — 그 검사는 레거시 본문을 **여전히 실행하고** 반환값만 버리는 것이라, 쓰기에서는 그게 곧 중복 쓰기다.

검사 여섯 개를 갈라 보면 이렇게 나뉜다.

| 검사 | 쓰기 페이지에서 |
|---|---|
| 구조 린트 · 본문 해시 · 호출자 전수 · 필드 대조 | **작동한다.** 정적 검사라 실행과 무관하다 |
| 실행된 줄 (Xdebug) | **작동한다.** `migrated` 에서 레거시를 아예 실행하지 않고 세므로 부작용이 없다 |
| 기준 캡처 | 반쪽만 작동한다. 같은 입력을 두 번 넣으면 이미 상태가 달라져 있다 |
| 이중 실행 | **불가.** 데이터가 두 번 바뀐다 |
| 가짜값 주입 | **불가.** 레거시 본문을 실행하므로 쓰기가 두 번 일어난다 |

**완전성 쪽은 대부분 살아남고 동등성 쪽이 죽는다.** 그래서 남는 길이 화면이 아니라 **데이터를 정답지로 삼는 것**이고, 그것은 입력을 복원할 수 있을 때만 성립한다. 이 문서가 그 전제 조건을 다룬다.

**트랜잭션 롤백은 쓸 수 없다.** PHP 워커가 자기 커넥션을 쓰므로 테스트 프로세스의 트랜잭션 밖이다. 복원은 트랜잭션이 아니라 스냅샷 되돌리기여야 하고, 읽기 페이지는 패스당 1회, 쓰기 페이지는 spec 파일 단위다.

## 2. 스키마를 손으로 만들면 안 된다 — 이것이 이 문서의 핵심

가장 값싸 보이는 길은 "쿼리에 나오는 테이블만 최소 스키마로 직접 만든다"이다. **그 길은 막혀 있고, 막힌 이유가 실측으로 확인됐다.**

콜레이션이 **DB·테이블·컬럼 세 층 모두에서 섞여 있다.**

| 층 | `<schema-a>` | `<schema-b>` |
|---|---|---|
| DB 기본 | `utf8` / `utf8_general_ci` | `euckr` / `euckr_korean_ci` |
| 테이블 | utf8_general_ci **140**, euckr_korean_ci **5** | euckr_korean_ci **204**, utf8_general_ci **75** |
| 컬럼 | utf8 **240**, euckr **27**, **utf8mb4 1** | euckr **899**, utf8 **166** |
| 엔진 | InnoDB 143, MyISAM 2 | InnoDB 216, MyISAM 63 |

두 스키마가 각각 다른 문자셋을 기본으로 두면서 **서로의 문자셋 테이블을 수십 개씩 품고 있다.** 컬럼 하나는 혼자 utf8mb4 다. 엔진도 섞여 있어서 MyISAM 과 InnoDB 가 한 스키마 안에 공존한다.

로컬을 한 가지 문자셋으로 통일해 만들면 **정렬 순서와 비교 결과가 조용히 달라진다.** 설계 문서가 "불안정을 부정확으로 바꾸는 것이 더 나쁘다 — 불안정은 시끄럽지만 부정확은 조용하다"고 적은 바로 그 자리다.

> **스키마는 덤프한 DDL 을 그대로 적용한다. 행은 직접 만든다.**

두 문장이 서로 반대 방향인 것이 중요하다. 스키마는 **정확성**이 요구되고, 행은 **통제**가 요구된다. 원격의 행을 복사하면 통제한다는 목적 자체가 사라지고, 이 서비스의 행에는 개인정보가 들어 있을 수 있다.

## 3. 스키마를 얻는 법 — 세 순위

### 1순위 — `mysqldump --no-data` 는 통한다

"덤프 권한이 없다"는 예상은 **빗나갔다.** 정확히는 **"기본 옵션이 안 맞는다"** 였다.

```
mysqldump -h <host> -P <port> --protocol=TCP -u <account> \
  --no-data --skip-lock-tables --skip-triggers --skip-add-locks \
  --databases <schema>
```

`--skip-lock-tables` 와 `--skip-triggers` 가 필수다. 그 계정의 권한이 `SELECT, INSERT, UPDATE, DELETE, EXECUTE` 뿐이고 `LOCK TABLES`·`TRIGGER`·`SHOW VIEW`·`RELOAD` 가 없기 때문이다. 기본 `mysqldump` 는 `--no-data` 여도 테이블 잠금을 걸고 트리거를 뜨려 하므로 옵션 없이는 실패하고, **그 실패가 "권한 없음"으로 오독된다.**

두 스키마 합쳐 400여 테이블, 450 KB, 8초 안쪽이다.

### 2순위 — `SHOW CREATE TABLE`

`SELECT` 권한만으로 동작한다. 확인했다. 덤프가 막히는 환경에서는 테이블별로 돌려 모으면 같은 결과를 얻는다.

### 3순위 — `information_schema` 재구성

`COLUMNS`(타입·널·기본값·콜레이션) · `STATISTICS`(인덱스) · `TABLE_CONSTRAINTS` 와 `KEY_COLUMN_USAGE`(제약) · `TABLES`(엔진·콜레이션)를 읽어 조립한다. 앞의 둘이 통했으므로 시도하지 않았다.

### 적재할 때의 함정

10.5 클라이언트가 만든 덤프의 첫 줄은 sandbox 지시자다. **그것을 5.5 클라이언트에 그대로 먹이면 1행에서 죽는다**(재현함). 적재 스크립트가 그 줄을 지워야 한다.

```
sed '1{/^\/\*M!999999/d;}' <dump>.sql | docker exec -i <db container> mysql -uroot
```

### 한국어 주석은 보존된다

이 트리에서 업무 의도는 한국어 주석에 있으므로 중요한 축이다. 덤프 파일 바이트가 정상 UTF-8 이고, 적재 후 utf8 커넥션으로 되읽어 정확히 얻었다. **5.5 클라이언트가 euckr 커넥션으로 물음표를 보여주는 것은 저장 손상이 아니라 표시 문제다.** 이것을 손상으로 오독하지 말 것.

## 4. arm64 에서 MariaDB 5.5 를 띄우는 법

### 이미지 제약 — 패치 버전은 못 고정한다

| 사실 | 내용 |
|---|---|
| arm64 빌드 | **없다.** `platform: linux/amd64` 로 에뮬레이션해야 한다 |
| 패치 태그 | `5.5.46`·`5.5.47` 은 **schema1 매니페스트**라 지금 Docker(containerd 2.1+)가 거부한다 |
| 실제로 받을 수 있는 최신 5.5 | **5.5.64** |

설계 문서가 고정하라고 정한 것은 **메이저·마이너**이므로 요건상 충족이다. 패치까지 맞추려면 배포처의 5.5.46 타르볼을 amd64 베이스에 얹어 이미지를 직접 만들어야 하고, 그것이 필요한지는 아직 사람이 정하지 않았다(9장).

### 막은 것 둘 — 둘 다 풀렸다

| 증상 | 원인 | 조치 |
|---|---|---|
| 공식 엔트리포인트가 즉시 죽는다 | `gosu` 의 Go 런타임이 QEMU 에서 동작하지 않는다 | 컨테이너를 `user: mysql` 로 띄워 그 분기를 건너뛴다 |
| mysqld 가 커넥션 처리 중 죽는다 | 기본 `thread_stack` 288K 가 에뮬레이션에서 부족하다 | `--thread-stack=1048576` |

공식 엔트리포인트의 임시 서버 절차도 QEMU 에서 죽으므로, `mysql_install_db` 뒤에 바로 `exec mysqld` 하는 얇은 스크립트로 대체했다. **둘 다 관측된 크래시이지 예방 조치가 아니다.**

### 숫자 — 에뮬레이션인데도 원격보다 빠르다

| 항목 | 값 |
|---|---|
| 콜드 기동 (datadir 초기화 포함) | **2.76 s** |
| 웜 재기동 | 0.85 s |
| DDL 424테이블 적재 | 1.7 s |
| 메모리 | 174 MiB |
| **쿼리 왕복** | **0.02–0.12 ms** (원격 개발 DB 는 2.1 ms) |
| CPU 바운드 작업 | 1103 ms (원격 372 ms) |

**왕복이 20~100배 빠르고 CPU 바운드만 3배 느리다.** 페이지 응답은 왕복 수에 지배되므로 총합은 로컬이 이긴다. 런타임은 Docker Desktop 이 아니라 colima 였고 `rosetta: false`, 곧 **QEMU 사용자 모드**였다. Rosetta 비교는 하지 않기로 했다(9장).

## 5. 레거시를 한 줄도 고치지 않고 붙이는 법

레거시 DSN 클래스는 호스트명을 문자열로 박아 두었다. 그래서 **DB 컨테이너에 그 이름을 네트워크 별칭으로 주면** 컨테이너 안의 PHP 가 이름을 그대로 풀어 로컬 DB 에 닿는다.

```yaml
services:
  <db service>:
    image: mariadb:5.5
    platform: linux/amd64
    user: mysql                       # gosu 분기 회피
    entrypoint: ["bash", "<entry script>"]
    command: [--character-set-server=<charset>, --collation-server=<collation>,
              --sql-mode=<mode>, --default-storage-engine=<engine>,
              --thread-stack=1048576, --skip-name-resolve]
    environment: { TZ: "<timezone>" }
    networks:
      <compose network>:
        aliases: ["<the hostname the legacy DSN hardcodes>"]   # ← 이 한 줄
```

레거시 코드 수정 0줄, `extra_hosts` 불필요, 되돌리기는 오버레이 제거뿐이다.

**오버레이를 별도 파일로 두는 것이 규칙이다.** 체크인된 `docker-compose.yml` 은 회사 저장소의 파일이므로 건드리지 않는다. `-f 원본 -f 오버레이` 로 겹쳐 쓰면 원본에 아무 변경도 남지 않는다. 오버레이와 엔트리 스크립트는 이 OS 의 추적하지 않는 상태 디렉터리 아래에 둔다.

### 기존 스택을 재생성하지 않는다

`up -d --no-deps <db service>` 로 DB 서비스만 올린다. 실험에서 PHP·웹 컨테이너의 ID 와 기동 시각이 전후 동일함을 확인했다. **5일째 돌고 있던 컨테이너를 그대로 두고** 그 안에서 레거시 코드를 실행했다.

## 6. 무엇을 확인했는가

### 스키마 충실도 — 차이 없음

엔진·테이블 콜레이션·컬럼 콜레이션·데이터 타입 분포·인덱스 수·DB 기본 콜레이션을 46행으로 뽑는 같은 질의를 원격과 로컬에 각각 돌려 `diff` 했다. **완전 동일.**

### 접속 경로 — 지름길을 쓰지 않았다

PDO 팩토리에서 DSN 클래스로 이어지는 **페이지 DAO 가 쓰는 것과 완전히 같은 경로**로 붙였다. 별도 PDO 를 만들어 확인하면 그 확인은 아무것도 증명하지 않는다.

### 의미론 — 손으로 심은 행으로

| 확인한 것 | 결과 |
|---|---|
| PHP 가 보는 연결 문자셋 | 서버 기본값이 그대로 온다(팩토리가 charset 을 주지 않는다) |
| utf8 테이블 저장 바이트 | UTF-8 로 정확히 저장됨 |
| euckr 테이블 저장 바이트 | euckr 로 정확히 저장됨 |
| `utf8_general_ci` 대소문자 | 대소문자를 무시하고 두 행이 매치 |
| `NO_BACKSLASH_ESCAPES` 꺼짐 | 백슬래시가 든 행을 이스케이프한 `LIKE` 로 매치 |

**마지막 줄이 이 조치의 존재 이유다.** 첫 실행 회고의 백슬래시 건은 "그 문자가 든 행이 개발 DB 에 없으면 그 규칙은 검사할 수 없다"였다. 여기서는 그 행을 직접 심어 규칙을 실제로 관찰했다. `불가` 로 기록될 뻔한 행이 관찰 가능으로 돌아온 첫 사례다.

## 7. 행 데이터 정책

**원격의 행은 한 건도 복사하지 않는다.** 대신 센다. 실험은 두 스키마의 테이블을 행 수 구간별로 분포만 기록했다.

검증용 행은 **손으로 심는다.** 설계 문서가 말하는 진짜 수확이 이것이고, 시드는 두 층이다.

| 층 | 내용 | 수명 |
|---|---|---|
| 구조 시드 | 스키마 + 마스터·코드 테이블 | 한 번 만들어 오래 간다 |
| 시나리오 필요 입력 | 백슬래시 · `%` · `_` · 4바이트 문자 · NULL 정렬값 · 초장문 | 페이지마다 는다 |

두 번째 층이 `불가` 행을 관찰 가능으로 되돌린다. 어느 행에 어떤 데이터가 필요한지는 규칙 목록의 `필요 입력` 절이 적고, 시드 스크립트가 그것을 읽는다.

**마스터·코드 테이블은 예외를 두되 사람이 고른다.** 코드값이나 분류처럼 값이 없으면 페이지가 아예 뜨지 않는 테이블이 있다. 실험은 이름과 행 수로 후보 35개(약 4,500행)를 추렸으나, 개인정보 포함 여부를 열 이름만으로 단정할 수 없어 **옮기지 않고 목록만 남겼다.**

## 8. `workspace.json` 에 추가할 키

`legacy` 아래 `database` 블록 하나다. 추적되는 `workspace.example.json` 에는 같은 블록을 두되 호스트 별칭·스키마·컨테이너·자격증명을 전부 플레이스홀더로 둔다.

```jsonc
"legacy": {
  "database": {
    "mode": "local",                  // local | remote — 어느 쪽으로 도는지 한 곳에서만 읽는다
    "service": "<compose service>",
    "container": "<db container>",
    "image": "mariadb:5.5",
    "platform": "linux/amd64",
    "composeOverlay": "<abs path to the overlay yml>",
    "entrypointScript": "<abs path to the entry script>",
    "hostAlias": "<the hostname the legacy DSN hardcodes>",
    "hostPort": <port>,
    "credentials": {
      "usernameEnv": "<env var the legacy DSN reads>",
      "passwordEnv": "<env var the legacy DSN reads>",
      "_comment": "로컬 전용 값을 쓴다. 회사 계정을 로컬 DB 에 만들지 않는다"
    },
    "schemas": ["<schema-a>", "<schema-b>"],
    "fixed": {
      "_comment": "설계 문서가 고정하라고 정한 넷. 기동 직후 되읽어 어긋나면 멈춘다",
      "versionPrefix": "5.5",
      "sqlMode": "<mode>",
      "characterSetServer": "<charset>",
      "collationServer": "<collation>",
      "timeZone": "<tz>"
    },
    "serverArgs": ["--thread-stack=1048576", "--skip-name-resolve"],
    "ddlDir": "<abs path to the dumped DDL>",
    "seedDir": "<abs path to hand-written seed SQL>",
    "dumpArgs": ["--no-data", "--skip-lock-tables", "--skip-triggers", "--skip-add-locks"],
    "resetPolicy": { "read": "per-pass", "write": "per-spec-file" }
  }
}
```

**`mode` 를 명시적 키로 두는 이유가 설계상 중요하다.** 로컬 DB 가 떠 있지 않을 때 도구가 원격으로 조용히 넘어가면, 이 조치가 풀려던 문제가 그대로 되살아난다. 두 패스가 같은 입력을 보지 못하는 상태로 돌아가는데 아무도 그 사실을 모른다. 팀 경계 문서의 **"키가 없으면 멈춰서 어느 키가 없는지 말한다"** 와 같은 성질이고, 조용히 좁은 답을 내는 것을 막는 장치다.

기동 직후 `fixed` 의 다섯 값을 **되읽어 대조하는 것**도 같은 이유다. 설정 파일에 값을 쓰는 것과 그 값이 서버에 도달하는 것은 다른 일이다.

## 10. 이 실험이 드러낸 조용한 실패 하나

로컬 DB 와 직접 관계는 없으나 같은 회차에서 나왔고, 이 저장소가 반복해 고쳐 온 실패 모양이다.

**이 셸의 `grep` 은 CP949 파일을 통째로 건너뛰고 exit 1 을 낸다.** ugrep 의 `-I` 래퍼이기 때문이다. 레거시 DSN 을 열거했을 때 `grep` 은 4건을 냈고 `/usr/bin/grep` 은 16건을 냈다. **75%가 조용히 빠졌다.**

조용한 실패 목록의 1번 항목은 "검색이 인코딩에서 눈이 멀었다"인데, 그 항목이 말하는 것은 **검색 대상 파일의 인코딩**이다. 셸의 `grep` 자체가 다른 프로그램으로 바꿔치기되어 있는 경우는 다루지 않는다. 전용 도구를 쓰라는 규칙이 이미 있으므로 새 규칙이 필요한 것은 아니고, **그 규칙을 어겼을 때의 대가가 이번에 측정된 것이다.**

## 11. 재현

실험의 스크립트·DDL·오버레이·충실도 비교 파일은 `.claude/.state/localdb-probe/` 에 있다. 추적하지 않으므로 회사 값이 그대로 들어 있고, 이 문서는 그중 환경에 의존하지 않는 부분만 옮긴 것이다.

정리 상태도 그 보고서가 적고 있다. 실험이 띄운 컨테이너·볼륨·네트워크는 전부 제거했고, 체크인된 compose 파일은 한 글자도 고치지 않았으며, 원격에는 읽기만 했다. 이미지 `mariadb:5.5` 는 다음 회차가 내려받기를 반복하지 않도록 남겨 두었다.
