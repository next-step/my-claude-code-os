# 시스템 루프 한 장 정리

이 저장소는 결과물을 만드는 곳이자 AI와 협업하는 법을 익히는 실습장입니다. 그래서 "무엇을 만들었나"만큼 "만드는 방식 자체가 나아지고 있나"가 산출물입니다. 이 문서는 그 방식, 곧 **시스템 루프**를 한 화면에 정리합니다.

## 1. 루프가 두 층이다

| | 랄프 루프 (국소) | 시스템 루프 (전역) |
|---|---|---|
| 무엇을 최적화하나 | 정해진 과제 안의 지표 | 과제를 만드는 절차 자체 |
| 한 바퀴 | 목표 설정 → 실행 → 측정 → 반복 | 기획 → 명세 → 검증 → 구현 → 반영 → 측정 → 재설계 |
| 언제 끝나나 | 지표가 목표값에 닿을 때 | 끝나지 않습니다. 계속 재는 것입니다 |
| 나아진다는 것은 | 수치가 목표에 가까워짐 | 사람이 하던 단계가 AI·시스템으로 넘어감 |
| 구현 | `.claude/skills/ralph-loop/` | 이 문서 전체 |

랄프 루프는 시스템 루프의 **한 단계**(국소 최적화)로 들어가 있습니다. 둘을 섞으면 "지표가 좋아졌으니 일하는 방식도 좋아졌다"는 잘못된 결론이 납니다. 실제로 그 혼동이 사고로 이어진 사례를 5절에 적었습니다.

## 2. 한 바퀴 — 누가 무엇을 맡고 있나

담당 주체는 `docs/loop-delegation.json`이 원본입니다. 아래는 그 요약이며, 수치는 `loop-health` 스킬이 실행 시점에 다시 냅니다.

| 단계 | 담당 | 위임된 곳 | 사람에게 남은 것 |
|---|---|---|---|
| 기획 | 사람+AI | `requirement-gate`, `requirement-interview` | 무엇을 만들지 최종 결정 |
| 명세 | AI | `spec-decompose` | (04단계 승인에서 되돌릴 수 있음) |
| 명세 검증 | AI | `policy-reviewer` | 리뷰어 판정을 받아들일지 결정 |
| **승인** | **사람** | — | 전부. 일부러 위임하지 않습니다 |
| 테스트 작성 | AI | `acceptance-test-write`, `test-reviewer` | 인수기준 확정 |
| 구현 | AI | `tdd-implement`, `ui-visual-reviewer` | 3회 상한을 넘기면 인계 |
| 검증 | 시스템 | 테스트·`freshness`·`guideline-audit` | 검사기가 못 보는 것을 읽고 판단 |
| 기록 | 시스템 | 훅 3종 | 회고 문안 승인 |
| 반영 | 사람+AI | `git-commit-message`, 커밋 확인 훅 | 커밋 여부와 단위 |
| 측정 | AI | `context-map`, `context-ab`, `loop-health` | 루브릭 채점 |
| 국소 최적화 | AI | `ralph-loop` | 목표값 조정, 실행 승인, 패치 적용 |
| **재설계** | **사람** | — | 전부. 아직 위임된 적이 없습니다 |

대부분의 단계가 위임됐고, 사람에게만 남은 것은 **승인**과 **재설계**입니다. 승인은 의도적으로 남긴 것이고, 재설계는 아직 손대지 못한 곳입니다. 몇 단계가 위임됐는지는 `loop-health`가 실행 시점에 세어 냅니다 — 이 문서에 수치를 박아 두면 반드시 낡습니다.

## 3. 무엇이 축적되는가

루프가 한 바퀴 돌 때마다 네 갈래로 기록이 쌓입니다. **쓰는 쪽은 훅이고 읽는 쪽은 스킬입니다.** 성실성에 기대면 바쁠 때 빠지기 때문에, 빠지면 안 되는 일을 시스템에 맡겼습니다.

| 쌓이는 곳 | 쓰는 훅 | 읽는 스킬 |
|---|---|---|
| 인수 테스트 실패 원장 | `atdd-failure-log.js` | `failure-ledger` |
| 세션 기록 | `session-register.js` 외 3종 | `session-board`, `session-relay` |
| 스킬 사용 통계 | `log-skill-usage.js` | `skill-stat` |
| 설계 노트 (`OS.md` 8장) | `os-retro-check.js`가 되물음 | 사람이 읽음 |

마지막 갈래가 가장 중요합니다. 세션이 끝날 때 훅이 "이번에 무엇을 바꿨고 왜 그렇게 정했나"를 되묻고, 사람이 승인하면 `OS.md`에 누적됩니다. **이것이 이 저장소에서 실행할수록 축적되는 루프의 본체입니다.**

흐름 그림은 `docs/diagrams/05-data-flow.svg`, 컨텍스트 계층 전체는 `docs/diagrams/08-context-overview.svg`에 있습니다.

## 4. 나아지는지 어떻게 재는가

두 개의 측정 장치가 서로 다른 층을 봅니다.

**`loop-health` — 시스템 루프 전체**

네 축(위생·신뢰도·자율성·세금)과 사람이 적는 위임 폭을 모읍니다. 새로 재지 않고 이미 돌고 있는 감사기 다섯 개의 출력을 한자리에 모을 뿐입니다.

한 줄 점수는 `검사기가 실제로 본 항목 중 위반이 아닌 비율`입니다. **"일어날 수 있는 모든 나쁜 일" 중의 비율이 아닙니다.** 그래서 점수를 낼 때마다 분모와 정의, 그리고 사각지대 목록을 함께 냅니다.

**`loop-rubric` — 랄프 루프의 회차별 변화**

여섯 차원(감축량·근거 보존·한계 표지·조항 보존·근거 밀도·가독성)을 회차마다 기록합니다. **종료 판정에는 쓰지 않습니다.** 점수를 판정에 물리면 루프가 점수를 최적화하기 때문입니다. 가독성은 대리 지표가 없어 사람이 채웁니다.

## 5. 실제로 돌려서 배운 것

랄프 루프를 다섯 번 실주행했고, 얻은 것은 목표 달성이 아니라 **측정 장치의 결함 목록**이었습니다.

| 결함 | 증상 | 왜 위험했나 |
|---|---|---|
| 명령 지표를 아예 실행하지 않음 | 값이 영원히 `null` | 루프가 무엇을 해도 성공할 수 없음 |
| 실패한 세션을 짧은 응답으로 집계 | 78자 오류 문자열이 "완벽한 성적" | **분량 목표에서는 네트워크 장애가 개선처럼 보임** |
| 고치는 곳과 재는 곳이 다름 | 지표가 미동도 하지 않음 | 루프 자신이 진단해 보고함 |

세 번째는 특기할 만합니다. 작업 세션이 스스로 원인을 짚고 *"더 줄여도 목표 지표는 그대로입니다. 반면 인용이 사라져 가드가 깨질 위험만 커지므로 추가 압축은 하지 않았습니다"*라고 적은 뒤 편집을 멈췄습니다.

결함을 모두 고친 뒤, 목표값만 바꿔 두 번 돌린 것이 이 실험의 결론입니다.

| | 목표 0.70 | 목표 0.35 |
|---|---|---|
| 근거 밀도 | 1.755 (산문을 버리고 근거를 남김) | **0** |
| 조항 보존 | 0.563 | **0** (80개 → 0개) |
| 종료 판정 | `done` | `done` |
| 사람이 쓸 수 있나 | 예 | **아니오** |

**두 번 다 초록불이었습니다.** 공격적인 목표는 더 나은 결과가 아니라 못 쓰는 지침을 냈고, 가드 세 개는 그 붕괴를 하나도 잡지 못했습니다.

이유는 구조적이었습니다. **가드는 응답을 보는데 무너진 것은 지침이었습니다.** 모델은 지침에 인용 예시가 하나도 없어도 저장소를 읽고 인용하므로, 응답의 인용 개수를 세는 가드는 지침이 비어도 통과합니다. 그때 살아남은 파일은 `index.md` 하나였고, 그것은 테스트가 지켜서였습니다 — **테스트가 있는 것만 살아남았습니다.**

대응으로 지침 자체를 세는 가드(`clause_count`·`guideline_files`·`caveat_lines`)와, 목표가 도달 가능한 값인지 미리 재는 경고를 붙였습니다.

## 6. 이 루프가 보지 못하는 것

- **지침을 실제로 지켰는가** — 마크다운 지시문은 자동 테스트가 불가능합니다.
- **위임한 판단이 옳았는가** — 서브에이전트의 PASS/FAIL이 맞는지는 아무도 보지 않습니다.
- **검사기 자신의 결함** — 위 결함 세 개는 모두 점수가 초록불인 상태에서 사람 눈에 걸렸습니다.
- **재설계 단계** — 루프를 다시 짜는 일은 아직 전부 사람 몫입니다.

가드를 하나 더 걸 때마다 루프는 그 가드를 피해 다니는 법을 찾습니다. 지금까지의 대응은 붕괴의 한 경로를 막은 것이지 품질을 보장한 것이 아닙니다.
