# 인터뷰: `interview` 스킬 설계

> 무언가를 만들기 전에 애매한 결정 지점을 사용자에게 끝까지 질문해, 구현 시점에 의문이 남지 않게 하는 스킬.
> 이 문서 자체가 그 스킬로 만들 첫 인터뷰 기록이다(셀프 부트스트랩).

## 배경

사용자 요청: "선택지가 갈리는 애매한 것을 계속 질문해서, 인터뷰 내용을 토대로 만들면 더 이상 의문이 안 생길 정도로 물어봤으면 좋겠다. 고민은 인터뷰 후 문서를 어떻게 관리할지."

## Q1. 발동 방식

- **결정**: 사용자가 명시 호출할 때만 (`/interview 주제`, "인터뷰하자").
- **기각**: ① 새 스킬 제작 시 자동 발동 ② 모든 애매한 작업에 자동 발동.
- **이유**: "언제 발동할지"의 기준이 또 하나의 애매함이 된다. 명시 호출이 예측 가능.

## Q2. 질문 방식

- **결정**: AskUserQuestion 선택지형. 라운드당 최대 4개, 각 선택지에 트레이드오프 설명.
- **기각**: ① 자유 대화형 — 답변 부담이 크고 인터뷰가 늘어짐 ② 혼합형.
- **이유**: 선택지가 답하기 쉽고, 선택지 밖 생각은 '기타(Other)' 입력으로 커버된다.

## Q3. 종료 기준

- **결정**: AI가 "더 물을 게 없다"고 판단하면 결정 전체를 요약해 제시 → 사용자가 확인하면 종료. 빠뜨린 게 있으면 요약 단계에서 잡힌다.
- **기각**: ① 사용자 종료 선언 — AI가 끝까지 압박(질문)하라는 취지와 어긋남 ② 고정 체크리스트 — 주제별 특수 질문을 놓침.
- **이유**: "의문이 안 남을 정도"의 판정 주체는 질문하는 쪽(AI)이 자연스럽고, 요약 확인이 안전망.

## Q4. 문서 관리 (핵심 고민)

- **결정**: `docs/interviews/YYYY-MM-DD-주제.md`에 중앙 append-only 누적. 같은 날 같은 주제 재실행은 `-2`, `-3` 접미사.
- **기각**: ① 산출물 옆 SPEC.md — 산출물이 없는 인터뷰(설계 논의)를 담을 곳이 없음 ② 문서 없이 결정만 반영 — "왜 그렇게 물었고 뭘 기각했는지" 유실 ③ 둘 다 — 문서 2벌 관리 비용.
- **이유**: `data/analyses` 등 기존 OS의 append-only 기록 패턴과 일관. 결정의 역사가 남는다.

> 이 결정은 이후 [Q18](#q18-후속-인터뷰의-기록-위치)에서 "후속 인터뷰는 파일 분리 대신 같은 파일에 이어 쓴다"로 갱신됐다.

## Q5. 기록 내용

- **결정**: 질문별 **결정 + 기각 대안 + 이유** 정제본 (이 문서의 형식). OS-log(1~2문장)의 상세 버전.
- **기각**: ① 전체 Q&A 원문 박제 — 길어서 안 읽힘 ② 최종 결정 요약만 — 기각 이유가 유실돼 같은 고민을 반복.
- **이유**: 나중에 "왜 이렇게 안 했지?" 복기가 이 기록의 존재 이유.

## Q6. 산출물과 멀어져 묻힐 위험

- **결정**: 인터뷰 기반으로 산출물을 만들 때 산출물에 `설계 근거: docs/interviews/....md` ref 한 줄을 남긴다.
- **기각**: ① OS-log에서만 링크 — 산출물만 봐서는 근거 문서 존재를 모름 ② 연결 안 함.
- **이유**: 추천 기록이 분석 기록을 ref로 역참조하는 기존 패턴(save_run → save_analysis)과 동일한 해법.

## Q7. 구현 연결

- **결정**: 인터뷰 스킬은 **기록만 남기고 종료**. 구현은 사용자가 별도로 지시.
- **기각**: ① 요약 확인 = 구현 승인으로 보고 바로 구현 ② 마지막에 선택지로 물음.
- **이유**: 관심사 분리. 인터뷰만 해두고 구현은 다음 세션에 해도 되는 구조가 유연하다.

## Q8. 저장 방식

- **결정**: SKILL.md에 기록 템플릿을 정의하고 AI가 직접 Write.
- **기각**: `save_interview.py` 스크립트 — 기존 기록 스크립트 패턴과의 일관성은 있으나 과함.
- **이유**: 산문 기록이라 결정론적 스크립트의 장점(숫자 정밀성·스키마 강제)이 약하다.

## 후속 (2026-07-02) — 기록 '이유'의 출처 표기

첫 기록(위 Q1~Q8)의 '이유'가 사용자 본인의 판단처럼 읽히지만, 실제로는 AI가 선택지 설명에 쓴 트레이드오프를 옮긴 것이었다. 사용자가 이 불일치를 지적해 후속 인터뷰로 처리 방식을 정했다.

## Q9. 기록의 '이유' 란 출처 처리

- **결정**: 이유는 지금처럼 AI가 정리하되 출처를 명시한다 — `이유(AI 정리·확인됨)`. 사용자가 '기타'·메모로 직접 말한 이유가 있으면 `이유(사용자 원문)`으로 원문 인용해 구분 표기.
- **기각**: ① 선택 직후 "왜 골랐나" 되묻기 — 기록 신뢰도는 최고지만 질문 수가 배로 늘어 인터뷰가 무거워짐 ② 그대로 둠 — 미래의 복기자가 추정된 이유를 본인 판단으로 착각할 위험.
- **이유(AI 정리·확인됨)**: 인터뷰 속도를 유지하면서 착각 위험만 제거한다. 요약 확인 단계가 이유의 승인 관문 역할을 하므로, 출처만 정직하게 밝히면 된다.
- **이유(사용자 원문)**: "이유는 내가 작성한게 아니고 그냥 너가 생각한 이유인거야? 근데 작성하는게 되게 사용자가 이런 이유로 이걸 골랐다 라는 느낌이 나는데 괜찮을려나"

> 위 Q1~Q8 '이유'도 같은 성격(AI가 제시하고 요약 단계에서 확인받은 근거)임을 이 기록으로 명시한다. 원본은 박제 원칙에 따라 소급 수정하지 않는다.

## 후속 (2026-07-02) — 스킬 개선: 누락 방지·중단 안전망·진행 UX

## Q10. 개선 범위

- **결정**: ① 질문 품질·누락 방지 ② 중단·재개 안전망 ③ 인터뷰 진행 UX, 세 영역.
- **기각**: 기록의 검색·활용(인덱스, 상호 참조 등) — 이번 범위에서 제외.
- **이유(AI 정리·확인됨)**: 실제 겪었거나 걱정되는 문제를 우선. 기록 활용은 기록이 더 쌓인 뒤의 문제.

## Q11. 실패 모드 진단

- **결정**: 걱정되는 실패 모드는 **누락**(물었어야 할 결정을 안 물음)과 **선택지 품질**. 과잉(사소한 질문)은 문제가 아니므로 1단계의 "코드·문서로 답할 수 있는 건 묻지 않기" 규칙은 현행 유지.
- **기각**: 과잉 질문 방지 장치 추가.
- **이유(AI 정리·확인됨)**: 누락은 스킬의 목적(구현자가 지어낼 게 없는 상태)을 직접 위협하는 반면, 과잉은 아직 체감된 바 없음.

## Q12. 누락 방지 장치

- **결정**: **범용 결정 체크리스트를 SKILL.md에 내장**(범위·발동/트리거·입출력과 기록 위치·실패/엣지 처리·기존 패턴과의 일관성·수명주기/갱신 규칙 등). 결정 지도 작성 시와 종료 판정 전, 두 번 대조한다. 주제에 안 맞는 항목은 건너뛴다.
- **기각**: ① 종료 전 셀프 감사 지침만 — AI 재량에 맡겨져 재현성이 낮음 ② 지도의 사용자 검토로 충분 — 사용자도 모르는 영역(unknown unknowns)은 둘 다 놓침.
- **이유(AI 정리·확인됨)**: 재현성 있는 누락 방지. 첫 인터뷰 Q3에서 기각한 '고정 체크리스트'는 종료 기준으로서였고, 이것은 보조 점검표라 양립한다.

## Q13. 선택지 품질 규칙

- **결정**: ① **들러리 선택지 금지** — 실제 고려 가치 없는 구색용 대안을 넣지 않는다. 진짜 대안이 2개면 2개만. ② **질문에 영향 범위 명시** — 각 질문에 "이 결정이 무엇을 좌우하는지" 한 줄을 반드시 담는다.
- **기각**: ① 장점·대가 쌍 강제 — 현행 트레이드오프 지침으로 충분 ② 추천 근거 명시 강제.
- **이유(AI 정리·확인됨)**: 선택지 품질 문제의 핵심은 "진짜 대안인가"와 "결정의 무게를 알고 답하는가". 설명 형식의 추가 강제는 길이만 늘림.

## Q14. 결정 지도 (진행 UX)

- **결정**: 인터뷰 시작 시 앞으로 물을 **결정 지점 목록(지도)을 제시하고 "빠진 지점 있나요?"를 첫 라운드로 확인**받는다. 중간에 새 결정 지점이 생기면 "지도에 추가됨"을 알린다.
- **기각**: ① 지도 제시만 하고 바로 시작 — 사용자가 빠진 지점을 지적할 자연스러운 통로가 없음 ② 라운드마다 진행 표시 ③ 라운드당 질문 수 조정 ④ 요약 단계 개선 — 지도 하나로 전체 그림·진행 파악이 해결됨.
- **이유(AI 정리·확인됨)**: 전체 그림과 분량을 미리 알 수 있고, 누락을 초반에 사용자가 잡는 기회가 되어 Q12(누락 방지)와 직결.

## Q15. 중단 안전망

- **결정**: **라운드가 끝날 때마다 정식 기록 파일에 즉시 저장**하고 frontmatter를 `outcome: 진행중`으로 둔다. 완료 시 확정으로 갱신.
- **기각**: ① 드래프트 파일 분리 — 생성·삭제 규칙이 하나 더 필요 ② 수동 '보류 마감'만 — 예기치 못한 세션 끊김엔 여전히 유실 ③ 현행 유지(종료 시에만 저장).
- **이유(AI 정리·확인됨)**: 세션이 언제 끊겨도 답변 무손실. 라운드 결과 추가는 문자 그대로 append이고, outcome 갱신은 기존 "status 갱신 = 평가 덧붙임" 논리와 같은 성격이라 박제 원칙과 충돌하지 않음.

## Q16. 재개 방식

- **결정**: 같은 주제로 재호출 시 진행중 파일을 **감지하면 지금까지의 결정을 요약해 보여주고 "이어서 / 새로 시작"을 확인**한다. 새로 시작이면 기존 파일은 `outcome: 보류`로 마감하고 `-2` 파일로 진행.
- **기각**: ① 자동 이어가기 — 생각이 바뀌어 처음부터 하고 싶을 때 번거로움 ② 명시 요청에만 재개 — 진행중 파일의 존재를 잊으면 영영 방치됨.
- **이유(AI 정리·확인됨)**: 안전(의사 확인)과 발견(존재 상기)을 질문 1회 비용으로 모두 얻는다.

> 이 결정은 이후 [Q18](#q18-후속-인터뷰의-기록-위치)에서 "확정된 주제의 후속 인터뷰도 기본은 이어쓰기, 파일 분리는 처음부터 다시 시작하는 경우로 한정"으로 갱신됐다.

## Q17. 파생 세부 (AI 판단, 요약 확인으로 승인)

- **결정**: ① 진행중 저장본의 이유는 `이유(AI 정리)`로 적고, 최종 요약 확인을 통과한 시점에 `확인됨`으로 승급 — "요약 확인 = 이유의 승인 관문"(Q9)에서 따라 나오는 귀결. ② 체크리스트 항목의 구체 문안은 구현 때 작성.
- **기각**: 진행중 저장본에도 '확인됨' 표기 — 승인 관문을 지나지 않은 이유에 도장을 찍는 셈이라 Q9 취지에 어긋남.
- **이유(AI 정리·확인됨)**: 기존 결정(Q9)의 논리적 귀결이라 별도 질문 없이 요약 단계에서 확인받음.

## 후속 (2026-07-05) — 후속 인터뷰 기록 위치 재검토

## Q18. 후속 인터뷰의 기록 위치

- **결정**: 같은 주제의 후속 인터뷰는 기존 파일 맨 끝에 새 Q로 append한다(과거 Q 섹션은 수정하지 않음). 완전히 처음부터 다시 시작하고 싶은 경우에만 `-2`, `-3` 접미사로 새 파일을 만든다.
- **기각**: 지금까지처럼 후속 인터뷰마다 `-2`, `-3` 파일로 분리 — Q 번호는 시리즈로 이어지는데 파일이 쪼개져 현재 상태 파악에 여러 파일을 추적해야 하는 비용이 큼.
