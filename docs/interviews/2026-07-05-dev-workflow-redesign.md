# 인터뷰: 개발 워크플로우 재설계 (인터뷰→플랜→구현→검증→회고)

## 배경
기존엔 대화 중 결정을 `docs/OS-log.md`에 즉흥적으로 기록했다. `interview` 스킬 도입 후 "OS-log가 여전히 필요한가"를 논의하다가, 사용자가 앞으로의 개발 워크플로우 자체를 인터뷰→플랜→구현→검증→회고 5단계로 재정의하고 싶다고 밝혀 이를 정리하는 인터뷰를 시작했다.

## Q1. 인터뷰 범위
- **결정**: 이번 인터뷰에서 5단계 각각의 트리거·산출물·어떤 도구/스킬로 만들지까지 정한다. 각 스킬 내부의 세부 로직(질문 형식, 프롬프트 등)은 필요 시 별도 인터뷰로 미룬다.
- **기각**: 5단계의 개념적 역할만 정하고 트리거·도구 선택은 다음 인터뷰로 미루는 안 — 그러면 OS-log 운명 같은 연쇄 결정이 지금 안 풀린다.
- **이유(AI 정리·확인됨)**: 트리거·도구까지 정해야 OS-log 존속 여부 등 뒤따르는 결정이 지금 풀린다.

## Q2. 5단계 강제 여부
- **결정**: 오탈자 수정·간단한 버그 수정 등 사소한 변경은 인터뷰→플랜을 건너뛰고 바로 구현→검증으로 간다. 5단계를 모든 작업에 항상 강제하지 않는다.
- **기각**: 모든 작업에 5단계를 항상 강제 — 일관성은 있지만 사소한 수정에도 오버헤드가 커서 실제로는 안 지켜질 위험이 있다.
- **이유(AI 정리·확인됨)**: 기존 CLAUDE.md 규칙("설계 논의 중엔 구현 착수 금지")도 "결정지점이 있을 때"를 전제로 하는 것과 일치한다.

## Q3. 기존 패턴 충돌 — retrospect 이름
- **결정**: 신규 프로세스 회고 스킬이 `retrospect` 이름을 그대로 갖는다. 기존 투자 추천 회고 스킬은 `portfolio-retrospect`로 개명한다.
- **기각**: 기존 이름 유지 + 신규가 다른 이름(`workflow-retro` 등) — 신규가 5단계의 정식 구성요소이므로 일반명이 더 어울린다고 판단해 기각.
- **이유(AI 정리·확인됨)**: 신규 회고가 워크플로우의 정식 5번째 단계이므로 일반명(`retrospect`)을 갖는 게 자연스럽고, 기존 스킬은 대상(포트폴리오)을 이름에 명시하는 편이 더 명확하다.

## Q4. OS-log 운명
- **결정**: `docs/OS-log.md`를 완전 폐지한다. 앞으로 의미있는 결정은 `/interview` → `docs/interviews/` 기록 + OS.md 본문(이유 포함) 갱신으로 남기고, 사소한 수정은 별도 기록을 남기지 않는다.
- **기각**: 축소 유지(인터뷰를 거치지 않은 즉흥적 결정만 계속 OS-log에 기록) — 사소한 것까지 남길 필요가 없다고 판단해 기각.
- **이유(사용자 원문)**: "어차피 중요한 결정 같은건 지금처럼 너가 인터뷰로 진행하자 할거고 사소한 수정 (오탈자나, 간단한 버그 같은거) 은 따로 기록해두지 않아도 추후 고치는데 어렵지 않을거 같은데"
- **이유(AI 정리·확인됨)**: 실제로 기존 OS.md에도 이미 중요한 설계 이유(예: 현재가 앵커 결함 수정의 "왜 둘로 나누나")가 본문에 직접 박혀 있어, OS-log는 그걸 반복하는 중복 계층이었다.

## Q5. 기존 OS-log.md 파일 처리
- **결정**: 파일을 삭제하지 않고 그대로 보관한다(박제, 더 이상 새 항목을 추가하지 않음). OS.md의 "진행 로그" 섹션은 이 파일을 "과거 이력(종료됨)"으로만 연결한다.
- **기각**: 삭제 — git 이력엔 남지만 OS.md에서 바로 링크해 볼 수 없어져 기각.
- **이유(AI 정리·확인됨)**: 과거 결정 히스토리를 한 파일에서 훑어볼 수 있는 가치가 삭제 대비 크다.

## Q6. CLAUDE.md 개정 시점
- **결정**: CLAUDE.md의 규칙 3(OS.md 먼저 읽기)과 "OS.md 작성 규칙" 섹션(진행 로그 규칙 포함)의 실제 문구 수정은 이 인터뷰에서 하지 않고, 이후 구현 단계에서 처리한다.
- **기각**: 지금 이 인터뷰에서 최종 문구까지 확정 — 인터뷰는 "무엇을 정했는지"까지만 책임지고 문서 편집 자체는 구현이라는 역할 분리 원칙과 안 맞아 기각.
- **이유(AI 정리·확인됨)**: 인터뷰 스킬 자체의 설계 원칙("질문·기록만 하고 구현하지 않는다")과 일치시켰다.

## Q7. 플랜 단계 도구·이름
- **결정**: 새 스킬 `plan`을 만든다. 인터뷰 결과를 받아 OS.md를 실제로 갱신하는 전용 스킬.
- **기각**: 기존 Claude Code 기본 Plan 모드(EnterPlanMode/ExitPlanMode) 재사용 — 계획 승인까지는 되지만, OS.md 고유의 작성 규칙(이유 함께 적기, 열린 질문 섹션, 체크리스트 형식 등)을 매번 사람이 직접 챙겨야 해서 기각.
- **이유(AI 정리·확인됨)**: `interview` 스킬이 자신의 기록 규칙(박제·출처 표기 등)을 스킬 자체에 내장해 매번 안 잊게 하는 것과 같은 논리를, OS.md 갱신에도 적용.

## Q8. 신규 retrospect(프로세스 회고) 트리거
- **결정**: 수동 호출. 기존 투자 회고(이제 `portfolio-retrospect`)와 동일한 패턴 — 사용자가 명시적으로 부를 때만 실행.
- **기각**: 검증 통과 후 자동으로 "회고할까요?" 제안 — 작은 작업마다 물어보면 피로감이 쌓일 수 있어 기각.
- **이유(AI 정리·확인됨)**: 자동 제안은 사소한 작업까지 매번 끼어들어 오히려 5단계를 무겁게 만든다.

## Q9. 신규 retrospect 산출물 위치
- **결정**: `docs/` 아래 append-only 로그(예: `docs/workflow-retros/YYYY-MM-DD.md`)에 남긴다.
- **기각**: 회고에서 나온 개선안을 CLAUDE.md에 즉시 반영 — 기록·과정·근거가 안 남아 기각.
- **이유(AI 정리·확인됨)**: 기존 투자 회고의 `data/retros/` append-only 패턴과 같은 결을 유지하되, 투자 데이터가 아니므로 `docs/` 하위에 둔다.

## Q10. 워크플로우 문서화 위치
- **결정**: 5단계 사이클(인터뷰→플랜→구현→검증→회고) 자체를 CLAUDE.md에 명시한다.
- **기각**: 별도 문서(`docs/workflow.md`) 신설 — CLAUDE.md가 길어지는 걸 막을 순 있지만 참조 파일이 늘어나 기각.
- **이유(AI 정리·확인됨)**: CLAUDE.md가 이미 "작업 전 지침" 역할을 하므로 워크플로우 사이클을 추가하는 게 자연스럽다.

## Q11. OS.md와 계획 문서의 분리
- **결정**: OS.md는 지금처럼 프로젝트의 큰 틀(주제·원칙·로드맵·스킬별 설계와 이유)만 담당하는 서사형 문서로 남긴다. 순서가 있는 "할 일 목록"은 새 파일 `docs/TODO.md`로 분리하고, 각 항목의 상세 계획은 `docs/plans/`(예: `docs/plans/<topic>.md`) 개별 파일로 만들어 TODO.md에서 링크한다.
- **기각**: 체크리스트를 OS.md 안에 그대로 두는 안(직전 라운드에서 AI가 처음 제안) — OS.md가 서사와 잦은 체크박스 갱신을 함께 떠안아, OS-log를 분리했던 것과 같은 비대화 문제가 재발할 우려로 기각.
- **이유(사용자 원문)**: "OS.md 는 지금처럼 큰 틀을 잡아주는 문서 역할로 남겨두고 새로 TODO.md 같은 해야할 일 문서를 만들어서... 체크리스트 역할을 하도록"
- **이유(AI 정리·확인됨)**: OS.md의 서사(원칙·이유)는 안정적으로 유지되고, 자주 바뀌는 "다음에 뭘 할지" 큐만 TODO.md가 전담해 두 관심사가 각자 최적 형태(서사 vs 목록)를 가질 수 있다. OS.md 기존의 굵은 단계별 표(로드맵·4주 계획)는 유지하고, TODO.md는 그보다 더 잘게 쪼갠 "다음 구현 항목" 큐로 역할을 분리한다(겹치지 않음).

## Q12. plan 스킬의 산출물 갱신 범위 (Q7 보강)
- **결정**: `plan` 스킬은 인터뷰 결과를 받아 (a) `docs/TODO.md`에 순서가 있는 항목을 추가/재배치하고 (b) 항목별 상세를 `docs/plans/`에 새 파일로 작성한다. OS.md는 구조적인 큰 틀 변경(원칙·로드맵 자체가 바뀔 때)에만 갱신한다.
- **기각**: Q7에서 정한 "plan이 OS.md를 직접 갱신"을 그대로 유지 — 그러면 OS.md에 계획 상세까지 계속 쌓여 이번 후속 논의의 발단이 된 비대화 문제가 재발.
- **이유(AI 정리·확인됨)**: Q11의 문서 역할 분리를 그대로 따른 결과.
