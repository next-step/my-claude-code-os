# 인터뷰: nextstep-start 스킬

## 배경
넥스트스텝 온라인 코드리뷰 요청 1단계 문서(next-step/nextstep-docs의 codereview/review-step1.md)를 스킬로 만들 수 있는지 검토한 결과, 8단계 중 commit·push·PR은 기존 스킬(commit, nextstep-pr)이, 이후 단계 브랜치는 nextstep-advance가 이미 커버함을 확인했다. 미커버 구간인 "미션 최초 시작(fork → clone → 최초 작업 브랜치 생성)"을 신규 스킬 nextstep-start로 만들기로 방향을 정하고, 범위·방식을 확정하기 위해 인터뷰했다. 스킬 위치는 CLAUDE.md 규칙에 따라 `.claude/skills/nextstep-start/`로 확정(질문 생략).

## 결정 지도
- [x] 범위 — fork→clone→브랜치만 vs 앞뒤 수작업 구간 안내 포함 → Q1
- [x] Fork 실행 방식 — gh CLI 직접 실행 vs 브라우저 안내 → Q2
- [x] 입력 방식 — 미션 저장소를 어떻게 알아내나 → Q3
- [x] Clone 위치 — 고정 규칙 vs 매번 확인 → Q4
- [x] upstream remote — 클론 직후 추가 vs nextstep-advance에 위임 → Q5
- [x] 최초 브랜치 이름 — 기본값 vs 매번 확인 → Q6
- [x] 엣지 케이스 — 이미 fork/clone 됨, gh 미설치·미인증 → Q7, Q8

## Q1. 범위 — 수작업 구간 안내 포함 여부
- **결정**: 안내 포함. fork→clone→브랜치 실행에 더해, 앞(넥스트스텝 사이트 미션 시작 버튼)·뒤(IDE Import) 수작업 구간을 한 줄 안내로 포함한다.
- **기각**: 실행 구간만 다루기 — 스킬이 짧고 순수해지지만, 미션 시작 버튼을 안 눌러 리뷰어 배정이 안 되는 실수를 못 막아줌.
- **이유(AI 정리·확인됨)**: 처음 하는 사람이 전체 흐름을 놓치지 않게 하는 가치가 문서 분량 증가보다 크다.

## Q2. Fork 실행 방식
- **결정**: `gh repo fork`로 스킬이 직접 실행한다.
- **기각**: 브라우저 Fork 안내 — gh 의존성은 없지만 브라우저↔터미널 왕복이 생김.
- **이유(AI 정리·확인됨)**: 클릭 왕복 없이 한 번에 끝난다. fork는 본인 계정에만 생기는 되돌리기 쉬운 동작이라 nextstep-pr의 "PR은 사용자 몫" 원칙과 충돌하지 않는다.

## Q3. 입력 방식 — 미션 저장소 식별
- **결정**: 호출 시 URL·저장소명이 있으면 바로 쓰고, 없으면 사용자에게 질문한다.
- **기각**: URL 필수 입력 — 동작은 단순하지만 URL 없이 부르면 매번 되묻는 턴이 생김.
- **이유(AI 정리·확인됨)**: 유연성이 분기 하나 추가되는 비용보다 크다.

## Q4. Clone 위치 (요약 확인 단계에서 수정됨)
- **결정**: 스킬을 호출한 **현재 디렉토리 바로 아래**에 클론한다(`{현재 위치}/{미션 저장소}`). 위치를 따로 제안하거나 묻지 않는다.
- **기각**: `~/Workspace/nextstep/` 고정 기본값 제안 + 확인 (최초 결정이었으나 요약 확인에서 사용자가 수정) / 매번 질문.
- **이유(사용자 원문)**: "Clone 위치는 해당 스킬을 사용한 디렉토리에 바로 하는걸로 하자. 예를 들면 ~/Workspace/nextstep 에서 해당 스킬 사용하면 ~/Workspace/nextstep/미션 저장소, ~/Workspace 에서 사용하면 ~/Workspace/미션 저장소"
- **이유(AI 정리·확인됨)**: 사용자가 스킬을 어디서 부르느냐로 위치를 표현하므로 별도 확인 단계 없이 의도가 반영되고, 고정 경로 가정도 사라진다.

## Q5. upstream remote 세팅 책임
- **결정**: 스킬이 확인·보장까지 책임진다. 클론 마지막에 `git remote -v`로 origin(본인 fork)/upstream(원본)이 둘 다 있는지 확인하고 없으면 추가한다. (`gh repo fork --clone`은 둘을 자동으로 잡아주지만, 폴백 경로로 진행했을 때를 대비한 확인.)
- **기각**: gh 기본 동작에 맡김 — 스킬은 짧아지지만 브라우저 폴백 경로에서 upstream이 빠질 수 있음.
- **이유(AI 정리·확인됨)**: 어느 경로로 왔든 nextstep-advance가 바로 쓸 수 있는 상태로 마무리된다. advance는 "이미 있으면 건너뛴다"라 충돌 없음.

## Q6. 최초 작업 브랜치 이름
- **결정**: 관례적 기본값 `step1`을 제안하고 확인만 받는다(다르면 '기타'로 수정).
- **기각**: 매번 질문 — 미션별 관례 차이에 안전하지만 한 단계 늘어남.
- **이유(AI 정리·확인됨)**: 대부분 미션이 step1부터 시작하므로 빠른 기본값이 낫다.

## Q7. gh CLI 미설치·미인증 시
- **결정**: 브라우저 폴백. Fork 버튼 URL을 안내하고, 사용자가 fork한 뒤 `git clone`부터 스킬이 이어서 진행한다.
- **기각**: 설치·인증 안내 후 중단 — 경로가 하나라 단순하지만 당장 진행하고 싶은 사용자를 막음.
- **이유(AI 정리·확인됨)**: 어떤 환경에서도 막히지 않는 것이 경로 둘의 복잡성보다 중요하다.

## Q8. 이미 fork/clone 돼 있을 때 (재실행 안전성)
- **결정**: 재사용하고 이어서 진행. fork가 있으면 그대로 쓰고, clone 디렉토리가 있으면 새로 받지 않고 그 안에서 다음 단계(브랜치 생성)로 넘어간다.
- **기각**: 중단하고 사용자 판단 — 덮어쓰기는 확실히 없지만 재실행마다 수동으로 이어가야 함.
- **이유(AI 정리·확인됨)**: 중간에 끊겨도 재실행이 안전한(멱등한) 스킬이 된다. 덮어쓰기 동작이 없어 위험도 없다.
