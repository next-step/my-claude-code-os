# 인터뷰: TODO.md 완료 항목 정리 주기

## 배경
`plan` 스킬이 `docs/TODO.md`에 항목을 추가하고 완료 시 체크(`[x]`)하지만, 완료된 항목을 지우거나
정리하는 로직이 없어 큐가 계속 불어난다. 사용자가 "완료된 항목을 계속 유지해두는 게 불필요하니
일정 주기로 정리하면 좋겠다"고 제안해 정리 방식·트리거·보존 형태를 정하기 위해 인터뷰를 시작한다.

## 결정 지도

- [x] 완료 항목 보존 형태 (완전 삭제 / 별도 아카이브 파일로 이동 / 그대로 유지) → Q3

## Q1. 정리 대상 범위
- **결정**: `docs/TODO.md`의 완료(`[x]`) 체크박스 항목만 정리 대상으로 한다. `docs/plans/<topic>.md` 상세 계획 파일은 삭제하지 않는다.
- **기각**: TODO.md + plans/ 파일 모두 정리 — 둘 다 깔끔해지지만, 나중에 "이 기능을 왜 이렇게 만들었나" 복기할 근거가 사라짐.
- **이유(AI 정리·확인됨)**: plans 파일은 구현 상세·설계 근거가 담긴 참고 기록이라 남겨두는 편이 나중에 가치가 있고, TODO.md만 지워도 "지금 뭘 할지" 큐는 충분히 깔끔해진다.

## Q2. 트리거 방식
- **결정**: 별도 자동화 인프라 없이, `plan` 스킬이 호출될 때마다 자동으로 완료 항목을 정리한다.
- **기각**: cron/loop로 완전 자동 주기 실행 — 진짜 "주기적"이지만 스케줄링 설정·유지보수 부담이 생김. 수동 호출 전용(별도 명령) — 사용자가 잊고 안 부르면 정리 자체가 누락됨.
- **이유(AI 정리·확인됨)**: `plan`이 이미 TODO.md를 다루는 유일한 스킬이라, 그 호출 시점에 자연스럽게 정리 주기가 생겨 별도 인프라가 필요 없다.

## Q3. 완료 항목 보존 형태
- **결정**: 완료 항목은 완전히 삭제한다. 이력이 필요하면 git history로 조회한다.
- **기각**: `docs/TODO-done.md` 같은 별도 아카이브 파일로 이동 — OS-log가 겪었던 "무한정 쌓이는 로그" 비대화 문제가 그대로 재발할 위험.
- **이유(AI 정리·확인됨)**: TODO.md는 애초에 "지금 뭘 할지" 큐이지 이력 문서가 아니므로, 완료분을 파일 내에 보존할 이유가 없다. OS-log 폐지 선례와 같은 논리.

## Q4. docs/plans/<topic>.md 파일 처리
- **결정**: TODO 항목을 지우기 직전에, 연결된 `docs/plans/<topic>.md`의 frontmatter `status:`를 `완료`로 갱신한다(파일 자체는 유지).
- **기각**: status 갱신 없이 그대로 둠 — status 필드가 사실상 관리되지 않는 죽은 필드로 방치될 가능성.
- **이유(AI 정리·확인됨)**: 파일은 남기기로 했으니(Q1), 최소한 상태 필드는 최신으로 유지해야 나중에 "이거 끝난 건가?"를 파일만 보고 알 수 있다.

## Q5. 엣지 케이스 — 삭제 시점
- **결정**: `plan` 스킬이 호출될 때마다 완료([x]) 항목을 즉시 전부 삭제한다. 유예 기간을 두지 않는다.
- **기각**: 일정 기간(예: 생성 후 1주) 유예 후 삭제 — 유예를 관리하려면 완료 날짜를 체크박스와 별도로 기록해야 해서 구현이 복잡해짐.
- **이유(AI 정리·확인됨)**: 유효기간 개념 없이 단순하게 처리하는 편이, `plan`을 자주 부를수록 자연스럽게 자주 정리되는 흐름과도 맞는다.

## Q6. 엣지 케이스 — plan 스킬 절차 내 삽입 위치
- **결정**: `plan` 스킬의 1단계(입력 파악) 직전에 완료 항목 정리를 수행한다.
- **기각**: 5단계(마무리) 직후에 수행 — 새로 추가된 항목과 정리 대상이 뒤섞여 보여 헷갈릴 수 있음.
- **이유(AI 정리·확인됨)**: 가장 먼저 정리해서 깨끗한 큐 상태를 먼저 파악한 뒤 새 항목을 추가하는 순서가, 사람이 청소 후 새 일을 올리는 흐름과 자연스럽게 맞는다.

- **이유(AI 정리·확인됨)**: 이어지는 Q10에서 드러나듯, 사용자가 원한 "정확함"은 단순 타이밍이 아니라 "실제로 검토한 뒤 정리"였다. `plan`은 새 작업을 큐에 얹는 시점일 뿐 완료 여부와 무관하고, 완료 판단이 실제로 일어나는 `retrospect` 시점으로 옮기는 게 그 취지에 맞는다.

## Q9. 정리 지연 허용 여부

- **기각**: `plan` 호출 시 "정리 안 된 완료 항목 N개, retrospect 권장" 알림만 추가 — 실질적 정리 없이 로직만 두 스킬에 걸쳐 늘어남.
- **이유(AI 정리·확인됨)**: 체크박스로 진행중/완료가 이미 구분되어 실행 큐 파악에는 지장이 없고, 알림 로직을 더하는 건 이번 결정의 단순함을 해친다.

- **기각**: `plan`의 기존 로직처럼 `[x]` 항목을 무조건 기계적으로 전부 정리(트리거 시점만 옮김).
