# 인터뷰: 넥스트스텝 미션 조건 충족 확인·피드백 스킬 설계

## 배경
사용자가 넥스트스텝 미션 조건을 넘겨주면, 실제 구현이 그 조건을 충족했는지 확인하고 피드백해주는
새 스킬을 만들고 싶어 함. `nextstep-pr`·`nextstep-advance`와 같은 계열의 개발 워크플로 보조 스킬.

## Q1. 확인 범위
- **결정**: 넘겨준 미션 조건만 확인 대상으로 삼는다. 넥스트스텝 공통 코드 컨벤션(else 예약어 금지, 들여쓰기 depth 1, 메서드당 10줄, 3항 연산자 지양 등)은 이번 범위에 넣지 않는다.
- **기각**: 미션 조건 + 공통 컨벤션을 항상 함께 확인 — 실전에 더 가깝지만 컨벤션 목록을 스킬에 하드코딩/유지보수해야 하고 미션과 무관한 지적이 섞일 수 있어 기각.
- **이유(AI 정리·확인됨)**: 스킬을 단순하게 유지하고 조건 텍스트와 1:1로 대조하는 것이 목적에 더 부합. 컨벤션 체크는 필요해지면 별도 옵션으로 추가 가능.

## Q2. 조건 입력 형태
- **결정**: 대화에 텍스트/이미지로 붙여넣는 방식으로 조건을 받는다.
- **기각**: 파일 경로 지정 — 재사용엔 편하지만 매번 파일을 만들어야 하는 손이 더 간다.
- **이유(AI 정리·확인됨)**: 별도 파일 관리 없이 즉시 시작 가능해 미션마다 1회성으로 쓰기에 적합.

## Q3. 확인 대상 코드 범위
- **결정**: 현재 브랜치의 diff(base 대비 변경분)를 확인 대상으로 삼는다.
- **기각**: 작업 디렉토리 전체 코드 — 이전 단계에서 이미 지적된 부분까지 다시 걸릴 수 있고 범위가 넓어 느리다.
- **이유(AI 정리·확인됨)**: `nextstep-pr`과 동일하게 base 브랜치(본인 아이디) 대비 diff를 기준으로 삼으면 이번 단계 작업에 집중된 피드백을 준다.

## Q4. 확인 방식
- **결정**: 정적으로 코드를 읽고 조건 문구와 대조하는 방식만 사용한다. 테스트/빌드 실행은 하지 않는다.
- **기각**: 테스트/빌드 실행 포함 — 더 확실하지만 프로젝트마다 빌드 도구가 달라 실행 환경 의존성이 생기고 매번 빌드 명령을 파악해야 한다.
- **이유(AI 정리·확인됨)**: 넥스트스텝 미션은 Java/Kotlin 등 프로젝트마다 빌드 체계가 다르므로, 스킬을 프로젝트 비의존적으로 유지하려면 정적 대조가 안전하다.

## Q5. 출력 형태
- **결정**: 조건별 충족/미충족 체크리스트 + 근거(해당 코드 위치·이유)로 보여준다.
- **기각**: 자유 서술형 피드백 — 읽기는 자연스럽지만 어떤 조건이 빠졌는지 한눈에 안 들어옴.
- **이유(AI 정리·확인됨)**: 미션 조건은 원래 항목형이라, 항목별 대조가 가장 직접적으로 대응된다.

## Q6. 기록 여부
- **결정**: 파일로 남기지 않고 대화에서만 보여준다.
- **기각**: docs/ 하위에 append-only로 남김 — 일회성 정보라 누적 관리 부담이 더 크다.
- **이유(AI 정리·확인됨)**: 미션 조건 충족 여부는 PR이 병합되면 의미가 사라지는 일회성 정보라 영구 기록할 필요가 적다.

## Q7. 기존 워크플로와의 관계
- **결정**: `nextstep-pr`과 분리된 완전 독립 스킬로 만든다. 자동 연결하지 않는다.
- **기각**: `nextstep-pr`의 사전 단계로 연결 — 자동으로 걸리게 하면 편하지만 두 스킬이 결합되어 복잡해지고, 조건 텍스트가 없을 때 nextstep-pr 흐름이 애매해진다.
- **이유(AI 정리·확인됨)**: 각 스킬을 단순하게 유지하고, 사용자가 원할 때 명시적으로 부르는 편이 유연하다.

## Q8. 모호한 조건·판단 불가 처리
- **결정**: 조건 문구가 모호하거나 코드만으로 충족 여부를 판단할 수 없으면 '판단 보류'로 표시하고 왜 판단이 어려운지 이유를 설명한다.
- **기각**: 애매하면 보수적으로 '미충족' 처리 — 단순하지만 실제로는 맞게 구현됐는데 과하게 미충족으로 나올 수 있어 신뢰도가 떨어짐.
- **이유(AI 정리·확인됨)**: 충족/미충족으로 억지로 이분하면 오답이 섞이므로, 판단이 안 서는 경우를 별도 상태로 정직하게 드러내는 것이 낫다.

## Q9. diff 없음·미커밋 변경 처리
- **결정**: base 대비 diff가 없거나 커밋 안 된 변경만 있어도, working tree의 커밋 안 된 변경까지 포함해 확인한다.
- **기각**: 커밋된 변경만 확인하고 없으면 먼저 커밋 안내 — `nextstep-pr`과 일관되지만, 이 스킬은 리뷰 성격이라 커밋 전에도 자주 쓰고 싶은 용도.
- **이유(AI 정리·확인됨)**: 미션 조건 확인은 PR 직전이 아니라 작업 중간에도 수시로 돌리고 싶은 용도이므로, 커밋 여부와 무관하게 현재 코드 상태를 본다.

## Q10. 스킬 이름
- **결정**: `nextstep-check`
- **기각**: `nextstep-verify`(프로젝트의 범용 `verify` 스킬과 이름 혼동 우려), `nextstep-review`(범용 `code-review`/`review`와 개념적으로 겹침).
- **이유(AI 정리·확인됨)**: "넘겨준 조건을 체크한다"는 동작이 명확히 드러나고, 기존 범용 스킬과 이름이 부딪히지 않는다.
