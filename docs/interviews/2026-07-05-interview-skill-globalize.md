# 인터뷰: interview 스킬을 ~/.claude로 전역화

## 배경
현재 `interview` 스킬은 이 프로젝트(`my-claude-code-os`) 안에만 있다. 사용자가 다른 프로젝트에서도 같은 인터뷰 절차를 쓰고 싶어 `~/.claude`로 옮겨 전역 스킬로 만들 생각을 밝혔다. 다만 CLAUDE.md 규칙 1("클로드 OS 관련 모든 파일은 반드시 프로젝트 안에 만들 것")과 정면 충돌하고, SKILL.md 내 상대경로 참조·프로젝트 전용 표현(docs/OS.md·docs/OS-log.md)도 걸린다.

## 결정 지도
- [x] CLAUDE.md 규칙 1과의 충돌 해결 방식 → Q1
- [x] 이동 방식 (완전 이동 vs 복사, 진실원천) → Q2
- [x] 프로젝트 전용 로직(OS.md 읽기) 일반화 방식 → Q3
- [x] 프로젝트 전용 로직(OS-log.md 기록) 일반화 방식 → Q4 (요약 확인 중 재검토 → Q8로 정정)
- [x] 설계 근거 문서(docs/interviews/2026-07-02-interview-skill.md) 처리 → Q5
- [x] 인터뷰 기록(docs/interviews/) 위치 → Q6
- [x] docs/ 구조 없는 프로젝트에서 호출될 때 동작 → Q7

## Q1. CLAUDE.md 규칙 1과의 충돌 해결
- **결정**: 규칙 1은 그대로 유지한다. 프로젝트 안의 사본은 그대로 두고, `~/.claude`에도 복사본을 둔다(양쪽 존재).
- **기각**: (a) 규칙 문구를 "OS 콘텐츠 파일" vs "범용 메타 스킬"로 구분해 개정 — 완전 이동 가능해짐. (b) 규칙은 그대로 두되 "interview는 예외" 한 줄만 추가 — 역시 완전 이동 전제.
- **이유(AI 정리·확인됨)**: 규칙 문구를 건드리지 않아 규칙의 안정성을 지키면서도, 두 곳에 실물을 둬 규칙 위반이 발생하지 않게 하는 절충안.

## Q2. 동기화 방식과 원본
- **결정**: 심볼릭 링크는 제외(원격 클론 시 깨짐). 두 사본 다 실물 파일로 유지하되, **프로젝트 사본을 원본**으로 삼아 수정하고, 확정되면 `~/.claude`로 수동 복사해 갱신한다.
- **기각**: (a) 심볼릭 링크로 자동 동기화 — 과제 제출물이라 원격 클론 시 `~/.claude` 경로가 없어 깨짐. (b) `~/.claude` 사본을 원본으로 삼기 — 평소 개선은 빠르지만 제출 직전 동기화를 깜빡하면 과제 제출물이 구버전일 위험.
- **이유(사용자 원문)**: "지금 복사하려는 이유가 어찌되었든 인터뷰 스킬도 과제하다 만든거여서 깃헙에 제출해야 되니까 복사하려는건데" — 프로젝트 사본이 채점/제출 대상이므로 그쪽을 원본으로 삼는 것이 자연스럽다는 사용자 설명.
- **이유(AI 정리·확인됨)**: 채점 대상인 프로젝트 사본을 원본으로 두면 참조 대상이 항상 최신·정확하게 유지된다.

## Q3. OS.md 참조 일반화
- **결정**: SKILL.md 1단계의 "docs/OS.md 먼저 읽기"를 "프로젝트의 살아있는 설계 문서(있다면) 먼저 읽기"로 일반화한다.
- **기각**: 이 프로젝트 표현을 그대로 두고 다른 프로젝트에서는 Claude가 알아서 판단하게 맡기는 안 — 매번 즉흥 판단에 의존해 일관성이 없어짐.
- **이유(AI 정리·확인됨)**: `docs/OS.md`를 읽는 진짜 목적은 "이미 답이 있는 걸 또 묻지 않는 것"이고, 그 역할을 하는 문서가 프로젝트마다 다를 수 있으므로 파일명이 아닌 역할로 표현해야 진짜 전역 재사용이 된다.

## Q4. OS-log.md 참조 일반화
- **결정**: 6단계 "docs/OS-log.md 맨 끝에 항목 추가"를 "프로젝트의 진행 로그 파일(있다면) 맨 끝에 항목 추가"로 일반화한다. 진행 로그가 없는 프로젝트에서는 이 단계를 생략한다.
- **기각**: 이 단계 자체를 삭제해 인터뷰 스킬의 책임을 `docs/interviews/` 기록까지로 한정 — 이 프로젝트에서 쓰던 "OS-log 자동 연결" 기능을 잃게 됨.
- **이유(AI 정리·확인됨)**: Q3(OS.md 일반화)와 동일한 패턴(파일명 대신 역할로 표현)을 적용해 규칙의 일관성을 유지.

## Q5. 설계 근거 링크 처리 (~/.claude 사본)
- **결정**: `~/.claude` 사본에서는 `docs/interviews/...` 상대경로 링크를 "my-claude-code-os 프로젝트(원본 저장소)의 docs/interviews/ 참고"같은, 클릭은 안 되지만 어디 있는지 알 수 있는 설명 텍스트로 바꾼다. 프로젝트 사본(원본)은 지금과 같은 상대경로 링크를 그대로 유지.
- **기각**: `~/.claude`에도 `docs/interviews/` 폴더를 함께 복제 — 링크는 살지만 원본이 프로젝트인데 문서 사본까지 동기화 대상이 되어 원본 개념이 흐려짐.
- **이유(AI 정리·확인됨)**: 설계 이력의 단일 진실원천은 프로젝트 저장소 하나로 유지하고, `~/.claude` 사본은 "어디 가면 이력을 볼 수 있는지"만 안내하는 역할로 축소.

## Q6. 인터뷰 기록(docs/interviews/) 위치
- **결정**: 전역화 이후에도 인터뷰 기록은 각 프로젝트 자신의 `docs/interviews/`에 남긴다(SKILL.md의 상대경로 `docs/interviews/...`는 지금 그대로 둔다).
- **기각**: `~/.claude/interview-records/프로젝트명/`처럼 전역 한곳에 모으기 — 조회는 편하지만 프로젝트 저장소와 기록이 분리돼 git 버전관리·프로젝트 삭제/이동 시 기록이 고아가 될 위험.
- **이유(AI 정리·확인됨)**: 인터뷰 기록은 해당 프로젝트의 의사결정 맥락이므로 그 프로젝트 안에 있어야 git 이력과 함께 움직이고, 다른 프로젝트만 봐도 전부 보인다.

## Q7. docs/ 관례 없는 프로젝트 처리
- **결정**: 다른 문서 관례가 있는지 사용자에게 묻지 않고 `docs/interviews/`를 새로 만들어 바로 진행한다.
- **기각**: 매번 사용자에게 먼저 확인 — 그 프로젝트의 문서 관례를 존중하지만, 인터뷰 스킬 첫 호출마다 본론 전에 부대 절차가 끼어들어 번거로움.
- **이유(AI 정리·확인됨)**: 이 스킬의 기록 관습(`docs/interviews/`)은 이미 고정 규약으로 못박혔으므로, 매번 물을 대상이 아니라 그냥 적용하면 되는 정해진 규칙으로 취급.

## Q8. OS-log 갱신 책임 재검토 (Q4 정정)
- **결정**: 요약 확인 단계에서 사용자가 Q4를 재검토 요청. 6단계("진행 로그 파일에 항목 추가")를 **삭제**한다. 인터뷰 스킬은 설계 문서(OS.md 같은 것)를 **읽기**만 하고, 쓰기는 `docs/interviews/` 기록 하나로 한정한다. 진행 로그 갱신은 인터뷰 스킬의 책임이 아니며, 필요하면 사용자가 별도로 하거나 구현 커밋 시점에 함께 처리한다. (Q4는 과거 판단으로 보존하고 이 Q8이 이를 대체한다.)
- **기각**: Q4에서 확정했던 "진행 로그 파일(있다면) 맨 끝에 항목 추가"로 일반화 — 인터뷰 스킬에 '기록'과 '로그 갱신' 두 가지 쓰기 책임을 지우게 되고, 프로젝트마다 다른 로그 관례에 얽매이게 됨.
- **이유(사용자 원문)**: "인터뷰 스킬에서 OS-log.md 파일을 수정하는게 맞는걸까? 실제 OS.md 같은 설계 문서만 확인하고 그 문서 바탕으로 인터뷰 진행한뒤 인터뷰 진행한 내용만 docs/ 폴더에 저장하면 되는거 아냐?"
- **이유(AI 정리·확인됨)**: 인터뷰 스킬 본연의 책임 분리 원칙("인터뷰는 기록까지, 구현은 별도")과 같은 논리를 로그 갱신에도 적용 — 로그가 궁금하면 `docs/interviews/`를 참고하면 되므로 중복 책임을 인터뷰 스킬에 지울 이유가 없다.
