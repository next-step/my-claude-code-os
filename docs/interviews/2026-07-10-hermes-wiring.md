## Q1. 헤르메스가 클로드 코드를 호출하는 경로
- **결정**: **`hermes cron ... --script --no-agent` 로 셸 스크립트를 스케줄 실행하고, 그 스크립트가
  `claude -p '/스킬명'` 을 직접 호출**한다. 헤르메스 LLM 에이전트는 루프에 개입하지 않는다.
- **기각**: 헤르메스 LLM 에이전트 + `--skill claude-code` 경유 호출 — 실패 시 재시도·요약·통지가
  공짜로 따라오지만, 매매 루프 밖에 결과를 해석하는 LLM 층이 하나 더 생긴다.
- **이유(AI 정리·확인됨)**: 헤르메스는 '스케줄러'이지 '판단자'가 아니어야 한다. 판단은 위원회(B)와
  시뮬(E) 안에 있고, 그 바깥에 비결정론적 LLM 층을 더하면 매일 토큰 비용·실패 지점이 늘고
  무인 루프의 재현성이 떨어진다. `--no-agent`는 배선을 로그로 재현 가능한 결정론 층으로 남긴다.

## Q2. 아침 체인(A→B→D)의 체이닝 단위
- **결정**: **단계별 독립 `claude -p` 세션.** 브리핑이 끝나면 새 프로세스로 위원회를 띄운다.
  앞 단계가 실패(비정상 종료)하면 체인을 중단한다.
- **기각**: 한 클로드 세션에서 A→B→D 연쇄 — '끝나면 다음'이 자연히 보장되지만, 7인 위원회
  토론까지 같은 컨텍스트에 쌓이고 중간에 죽으면 아침 전체를 다시 돌려야 한다.
- **이유(AI 정리·확인됨)**: 산출물 토폴로지가 이미 단계 간 인계를 **파일**(브리핑 append 로그 → 위원회가
  Read)로 설계해 뒀으므로 컨텍스트를 이어 붙일 이유가 없다. 세션을 나누면 실패가 격리되고
  재시도 단위가 단계와 일치한다. 대가인 세션별 컨텍스트 재로딩은 하루 몇 회라 감수한다.

## Q3. 시뮬 엔진(E)의 실행 형태
- **결정**: **`fill_engine.py poll`을 헤르메스가 `--no-agent` 스크립트로 09:00에 띄우고(LLM 없음),
  스크립트가 emit한 `fill`·`emergency` 이벤트 한 줄마다 `claude -p`를 새로 호출**해 반영시킨다.
  6.5시간 클로드 세션을 살려 두지 않는다.
- **기각**: 09:00에 클로드 세션 하나를 15:30까지 유지(현재 SKILL.md의 실행 모델) — 스킬을 그대로
  둘 수 있으나, `claude -p`가 '백그라운드 프로세스 이벤트로 세션이 재호출되는' 대화형 하니스
  동작을 지탱하는지 미지수고 6.5시간 세션의 컨텍스트·안정성 리스크를 진다.
- **이유(AI 정리·확인됨)**: 폴링은 순수 파이썬이라 토큰을 쓰지 않는다는 기존 설계의 핵심 이점은 이 안에서도
  그대로 유지되고(조용한 장 = 클로드 호출 0), 이벤트당 짧은 세션이라 실패가 이벤트 단위로 격리된다.
- **파생 작업**: `sim-engine/SKILL.md` 2단계(실행 모델)를 '헤르메스가 poll을 소유, 스킬은 이벤트
  반영만 담당'으로 고쳐야 한다.

## Q4. 이벤트 동시 발생 시 직렬화
- **결정**: **무조건 직렬 처리.** 디스패처가 `claude -p`를 동기로 기다렸다가 다음 이벤트를 꺼낸다.
  poll은 별도 프로세스로 계속 돌며 파이프에 쌓는다.
- **기각**: 긴급 이벤트가 대기 중인 체결 큐를 선점 — 가드레일('긴급의 본질은 속도')과 더 맞지만,
  디스패처가 우선순위 큐를 가진 상태 기계가 되고 밀린 fill 처리 규칙이 또 필요해진다.
- **이유(AI 정리·확인됨)**: `data/portfolio.md`는 상태 문서라 동시 쓰기가 곧 손상이다. 직렬화는 경합을
  원천 차단하고 구현이 가장 단순하다. 긴급 지연은 수십 초~1분 수준이라 모의 루프에서 감수 가능하고,
  실제로 문제가 되면 회고(F)가 표본을 보고 선점 큐를 되살린다(뼈대 우선).

## Q5. 공휴일·임시 휴장일 처리
- **결정**: **개장 여부를 스크립트가 판정해 조기 종료.** 아침 체인 진입 전에 휴장일이면 클로드를
  호출하지 않고 끝낸다.
- **기각**: 그냥 돌린다(YAGNI) — 방어막을 미리 치지 않는 원칙엔 맞지만, 휴장일 회의록·계획서가
  박제돼 주간 회고(F)의 표본을 오염시킨다.
- **이유(AI 정리·확인됨)**: 이건 '안 겪은 문제에 대한 방어막'이 아니라 **기록 무결성** 문제다. 거래가 없던
  날의 위원회 회의록이 append 로그에 남으면 F가 '왜 그 판단을 했나'를 되짚을 때 잡음이 된다.
  헛된 토큰 절약은 부수 이득.
- **파생 결정 지점**: 휴장일을 무엇으로 판정하나(지도에 추가).

## Q6. 무인 `claude -p` 실행 권한
- **결정**: **`--dangerously-skip-permissions`.** 모든 권한 프롬프트를 건너뛴다.
- **기각**: `--allowedTools` 화이트리스트 — 최소권한 원칙에 맞지만, 스킬 5종이 사실상 전체 툴셋
  (Read/Write/Edit/Bash/WebSearch/Agent)을 쓰므로 방어 효과가 거의 없고, 스킬이 툴을 하나 더 쓰기
  시작하는 순간 리스트가 썩어 무인 루프가 조용히 멈춘다.
- **이유(AI 정리·확인됨)**: 권한 프롬프트는 무인 루프의 정지 조건이다. 이 루프는 전부 모의(페이퍼)라
  실주문·자금 이동이 없고 영향 범위가 로컬 저장소에 갇혀 있어(trading-principles 루프 층 1),
  화이트리스트가 막을 실질 위험이 없다. 실계좌 연동 층이 생기면 이 결정을 다시 본다.

## Q7. 헤르메스에 넘기는 인계 산출물의 형태
- **결정**: **실행 가능한 셸 스크립트까지 저장소에서 만들고 동작을 확인한다.** 헤르메스 에이전트에겐
  "이 스크립트를 이 스케줄로 cron 등록해달라"만 부탁한다.
- **기각**: 배선 명세서만 남기고 스크립트 작성·배치·등록을 헤르메스에 위임 — 헤르메스 규약(경로·로그·
  디렉터리)에 맞춰 쓰게 할 수 있으나, 루프의 핵심 배선 로직이 저장소·git·리뷰 밖으로 나간다.
- **이유(AI 정리·확인됨)**: CLAUDE.md 규칙 1(클로드 OS 관련 모든 파일은 프로젝트 안)과 정합하고, 배선이
  버전관리·검증 대상이 된다. 헤르메스에는 '무엇을 언제 실행하나'라는 **스케줄 등록만** 남겨
  헤르메스를 순수 스케줄러로 유지한다(Q1과 같은 방향).
- **이유(사용자 원문)**: "배선 등록은 내가 해당 인터뷰 자료 보고 결정된걸 바탕으로 연결해달라고
  헤르메스 에이전트에게 부탁할거야"

## Q8. poll ↔ 클로드 상태 동기화 (watchlist 재적재)
> 발견 경위: `fill_engine.py`의 `poll_loop`은 watchlist를 **기동 시 한 번만** 읽고 메모리에서만
> 관리한다. 긴급위가 시장가로 청산하거나 신규 주문을 내도 poll은 그 사실을 모른다.

- **결정**: **poll이 watchlist 파일의 mtime을 매 사이클 확인해 리로드**한다. 클로드가 이벤트를
  반영한 뒤 `watchlist.json`을 다시 쓰면 poll이 `orders`·`positions`를 갈아끼운다.
  `session_anchor`(급락 판정의 세션 첫 관측가)는 프로세스가 살아 있으므로 보존된다.
- **기각**: 이벤트마다 poll 프로세스를 죽이고 재기동 — `fill_engine.py`를 안 고쳐도 되지만
  `session_anchor`가 리셋돼 급락 판정 기준가가 '재기동 시점 가격'으로 밀린다. 오전에 이미 크게
  떨어진 종목의 추가 급락을 못 잡는다(급락 감지의 의미가 훼손).
- **이유(AI 정리·확인됨)**: 앵커 보존이 급락 감지의 정확성 자체이고, 리로드는 mtime 비교 한 줄이라
  재기동보다 오히려 단순하다. 상태 동기화의 진실원천을 `watchlist.json` 파일 하나로 두면
  '계획서·포트폴리오 → watchlist → poll'의 단방향 흐름이 유지된다.
- **파생 작업**: `fill_engine.py`에 리로드 로직 추가, `poll` 서브커맨드가 watchlist 경로를
  계속 참조하도록 수정.

## Q9. 긴급 이벤트 반복 emit 억제
> 발견 경위: `emergency`는 one-shot이 아니다. 손절가에 닿은 종목은 breach가 풀릴 때까지
> **매 분 emit**되고, 직렬 디스패처는 그때마다 `claude -p`를 부른다.

- **결정**: **위원회가 갱신한 watchlist가 1차 해소책, 종목별 최소 쿨다운이 안전망.**
  긴급위가 청산하면 그 종목이 `positions`에서 빠져 자연 해소되고, 홀드하면 위원회가 **새 손절가를
  정해** watchlist에 반영해 재소집 조건을 스스로 다시 그린다. 어떤 갱신도 없었던 경우를 대비해
  종목별 쿨다운(초기값 30분 — 튜닝 상수)을 둔다.
- **기각**: 종목+사유별 '세션 1회'만 emit — 구현은 가장 단순하나, 손절가 도달 후 '홀드'를 결정한
  종목이 그 뒤 더 깊게 무너져도 긴급위가 다시 안 열린다. '긴급의 본질은 속도'라는 취지와 정면충돌.
- **이유(AI 정리·확인됨)**: 재소집 임계를 스크립트 상수가 아니라 **위원회가 정한 손절가**로 삼는 것은
  "전술 값(손절 폭)은 위원회가 매 계획에서 결정한다"는 가드레일과 그대로 정합한다. 쿨다운은
  판단이 아니라 '무한 호출 방지'라는 기계적 안전망이라 상수로 둬도 층이 섞이지 않는다.
- **파생 작업**: `fill_engine.py`에 종목별 emergency 쿨다운 상태 추가(`fetch_fail`의
  `FETCH_FAIL_REMIND_MIN` 합치기와 같은 패턴).

## Q10. 휴장일 판정 소스
- **결정**: **파이썬 라이브러리로 거래소 달력을 조회**한다.
- **기각**: 저장소에 KRX 휴장일 표 하드코딩 — 의존성이 0이지만 임시공휴일마다 사람이 손으로
  갱신해야 하고, 잊으면 Q5가 막으려던 '빈 날 기록'이 그대로 남는다. / 공공데이터 특일정보 API —
  가장 정확하나 API 키 보관과 네트워크 실패 규칙이라는 새 실패 지점이 무인 루프에 생긴다.

## Q19. '위원회가 안 열렸다'의 판정 근거

## Q20. 시뮬 기동 시각과 아침 체인의 경합
- **결정**: **아침 체인이 위원회를 끝내면 스크립트가 시뮬을 직접 이어서 띄우고, 09:00 cron은

## Q21. 중복 실행 방지

## 확정된 배선의 전체 그림

세 개의 셸 스크립트(`scripts/hermes/`)가 헤르메스 cron job 셋에 각각 대응한다.

| 스크립트 | 스케줄 | 하는 일 |
|----------|--------|---------|
| `morning-chain.sh` | `0 8 * * 1-5` | 휴장일 게이트(Q5·Q12·Q18) → flock(Q21) → `claude -p '/morning-briefing'` → `claude -p '/investment-committee'`(각 1회 재시도, Q13) → `sim-chain.sh` 직접 호출(Q20) → 요약을 `#일간`으로 |
| `sim-chain.sh` | `0 9 * * 1-5` (백스톱) | flock(Q21) → `claude -p '/sim-engine watchlist 조립'`(Q16, 회의록 유무로 진입 주문 포함 판정 — Q19) → `fill_engine.py poll` 기동 → emit되는 이벤트마다 `claude -p '/sim-engine ...'`를 **동기 호출**(Q3·Q4) → 마감 후 체결 요약을 `#일간`으로 |
| `weekly-chain.sh` | `0 9 * * 6` | flock → `claude -p '/weekly-retrospect'` → 리포트를 `#주간`으로(Q11·Q17) |

모든 `claude -p`는 `--dangerously-skip-permissions`로 실행한다(Q6). 실행 로그는 `~/.hermes/logs/`,
`data/` 하위 기록물(회의록·체결·브리핑)과 성격이 다르다(Q22).

## 이 인터뷰가 만든 구현 숙제 (배선 밖의 파생 작업)

1. `fill_engine.py` — watchlist mtime 리로드(Q8), 종목별 emergency 쿨다운(Q9) 추가.
2. `sim-engine/SKILL.md` — 실행 모델(2단계)을 '헤르메스가 poll 소유, 스킬은 이벤트 반영만'으로 수정(Q3).
3. `exchange_calendars` 의존성 추가(Q12).
