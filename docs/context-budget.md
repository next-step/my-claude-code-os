# 컨텍스트 예산 — 측정 이력

세션을 열 때마다 무조건 나가는 비용(**상시 로드**)을 실제로 재고, 줄인 기록을 남긴다.

이 문서는 **"지금 이 순간의 수치"가 아니라 "그때 무엇을 재서 무엇을 바꿨는가"의 로그**다
(`docs-diagrams.md`의 "문서에 지금 이 순간의 수치를 박아 넣지 않는다"). 현재값은 항상 아래 명령으로 다시 잰다.

```bash
node -e "const{buildContextMap,summarizeBudget}=require('./.claude/lib/context-map.js');console.log(JSON.stringify(summarizeBudget(buildContextMap({projectDir:process.cwd()})),null,1))"
```

## 무엇을 상시 비용으로 세는가

| 분류 | 포함 | 이유 |
|---|---|---|
| **상시 로드** | `CLAUDE.md`의 `@import` 체인 **전문** + 스킬·서브에이전트의 `description` | 세션 시작 시 전부 들어온다. 쓰든 안 쓰든 낸다 |
| 온디맨드 | 스킬 `SKILL.md` 본문, 서브에이전트 본문 | 실제로 호출될 때만 로드된다 |
| 비용 0 | 훅 | 이벤트에 스크립트가 실행될 뿐 컨텍스트를 차지하지 않는다 |
| **미측정** | MCP 서버의 툴 이름 목록·server instructions | 세션마다 로드되지만 **크기를 디스크에서 알 수 없다**. 개수만 세고 합계에 섞지 않는다 |

집계 기준은 `.claude/lib/context-map.js`의 `summarizeBudget()` 한 곳에 고정했다 — 호출부마다 덧셈을 다시 하면 같은 저장소를 두고 사람마다 다른 수치를 말하게 된다.

## 2026-09-07 — 개인 지침 계층을 심고, 그 비용을 줄였다

### 배경

지침 1개(`requirement-gate.md`)에서 8개로 늘리면서 상시 로드가 **9,644자 → 15,263자(+58%)** 로 커졌다. 지침은 세션마다 전부 들어오므로 늘어난 글자가 그대로 매 세션의 세금이 된다. 늘린 직후에 줄이는 작업을 붙인 이유다.

### 적용한 최적화 (4가지)

| 방법 | 무엇을 했나 | 절감 |
|---|---|---|
| **A. 구조** | `index.md`를 순수 레지스트리로. "추가하는 법·경로 규칙·커밋 정책" 산문을 `README.md`(로드 안 됨)로 넘기고 `@` 목록만 남김 | **-990자** |
| **B. 중복 제거** | 지침 간 겹치는 문장 3곳 정리 (`commit-habits`↔`sensitive-info`, `sensitive-info`↔`hook-discipline`, `explanation-style`↔`code-vs-instruction`) | **-75자** |
| **C. 표현 압축** | `os-builder`의 `description` 축약 (트리거 문구는 유지) | **-81자** |
| **D. 근거 줄 압축** | 각 지침 끝의 `근거:` 줄을 제거하지 않고 형태만 축약 | **-177자** |
| | **합계** | **-1,323자 (-8.7%)** |

결과: **15,263자 → 13,940자** (import 7,341 / 스킬 desc 5,232 / 에이전트 desc 1,367). 온디맨드는 58,033자, 훅 8개는 비용 0.

### 측정해 보고 적용하지 않은 것 (3가지)

절감량이 커도 다른 것을 망가뜨리면 최적화가 아니다. 잰 값과 버린 이유를 같이 남긴다.

| 후보 | 잠재 절감 | 왜 안 했나 |
|---|---|---|
| **D′. `근거:` 줄을 `README.md`로 이동** | 677자 | 규칙과 근거가 떨어지면 "왜 이 규칙이 있지"를 두 파일을 오가며 찾게 된다. 제거 대신 **압축(D)** 으로 대체해 지역성을 지켰다 |
| **E. 스킬 `description` 상위 6개 30% 압축** | 891자 | `description`은 **어떤 스킬을 부를지 정하는 유일한 근거**다. 여기서 아끼면 스킬이 안 불린다 — 컨텍스트를 아끼려다 기능을 끄는 셈 |
| **F. `requirement-gate.md` 30% 압축** | 546자 | 이 게이트는 바로 이번 세션에 값을 했다(서브에이전트 3개가 전부 독립 심판이라는 발견). 방금 효과를 확인한 절차를 글자 수 때문에 깎지 않는다 |

### 배운 것

- **효과는 구조에서 나왔다.** A 하나가 전체 절감의 **75%**다. 문장을 다듬은 B·C·D를 다 합쳐도 A의 3분의 1이다. 줄일 곳을 찾을 때는 문장이 아니라 **"이게 왜 상시 로드에 있지"** 를 먼저 묻는 편이 낫다.
- **중복 제거는 기대보다 작았다(-75자).** 지침들이 이미 서로 다른 축을 다루고 있었다는 뜻이라, 이건 나쁜 소식이 아니다.
- **가장 큰 항목이 가장 손대면 안 되는 항목이었다.** 스킬 `description` 5,232자는 상시 비용의 38%지만 기능의 진입점이다. 비용 크기와 절감 우선순위는 같지 않다.

## 2026-09-07 ② — 가장 큰 항목이 계기판에 아예 없었다 (MCP)

### 무엇을 발견했나

`grep -i mcp .claude/lib/` 가 **0건**이었다. 이 문서는 "세션 시작 시 무조건 나가는 비용"을 잰다고
선언하는데, `summarizeBudget()`은 MCP를 한 글자도 세지 않고 있었다.

### 잰 값 (전부 2026-09-07, Claude Code 2.1.263)

| 항목 | 값 | 어떻게 쟀나 |
|---|---|---|
| 연결된 MCP | `notion` (HTTP), 툴 **42개** | `~/.claude.json` 의 `projects[…].mcpServers` |
| **지금 실제로 실리는 양** | 툴 **이름만** 1,521자 | 시스템 프롬프트의 deferred tool 목록을 세어 봄 |
| 툴 스키마 2개 표본 | `notion-create-pages` + `notion-search` = 약 **13,000자** | `ToolSearch`로 실제 로드해 봄 (create-pages는 description이 잘리기까지 했다) |
| 42개 전부 실렸다면 | 약 **27만 자** | 위 2개 표본에서 외삽 — **추정치이며 실측이 아니다** |
| 비교: 당시 상시 로드 총량 | 13,940자 | 이 문서 위 항목 |

→ 지연 로딩이 없었다면 MCP 서버 **하나**가 지침 8개 + 스킬 13개를 다 합친 상시 컨텍스트의
**약 20배**였을 것이다. "MCP는 컨텍스트 효율이 나쁘다"는 말은 여기서 나왔고, 사실이었다.

### 그런데 이미 대부분 해소돼 있었다

Claude Code 2.1.263은 MCP 툴을 **이름만 싣고 스키마는 지연 로딩**한다(`ToolSearch`).
42개 툴이 27만 자가 아니라 1,521자로 들어와 있다 — 약 **1/180**이다.

지연 로딩이 막아 주지 **못하는** 비용은 3가지다.

| 남는 비용 | 통제 가능한가 |
|---|---|
| 툴 이름 목록 | 서버를 빼는 것 말고 방법이 없다 |
| server instructions (Notion은 문단 하나를 싣는다) | 서버가 정한다. 사용자가 못 줄인다 |
| **툴 응답 크기** | **서버가 정한다 — 직접 만들면 통제할 수 있다** |

세 번째가 직접 만드는 실질적 이유다. `.claude/lib/notion-min.js`의 `maxChars`가 바로 그 손잡이다.

### 무엇을 바꿨나

`listMcpServers()`를 `context-map.js`에 추가하고 `summarizeBudget()`에 `unmeasured` 칸을 만들었다.

**`alwaysLoaded.total`은 일부러 건드리지 않았다.** 추정치를 합계에 섞으면
이 문서에 쌓인 이력과 비교가 깨지고, 잰 값과 어림값이 한 숫자로 뭉개진다.
`AC-M6` 테스트가 이 경계를 잠근다 — MCP가 있든 없든 `alwaysLoaded`가 같아야 통과한다.

### 배운 것

- **재지 않는 것은 관리되지 않는다.** 이 문서는 8개 지침을 1,323자 줄인 기록을 자랑스럽게 남겼는데,
  같은 화면 밖에 그 20배짜리 항목이 있었다. 절감 작업보다 **계기판의 사각지대를 찾는 일**이 먼저다.
- **"측정 불가"를 0으로 적지 않는다.** 모르는 값을 0으로 채우면 사각지대가 영구히 사각지대로 남는다.
  칸을 만들고 "여기는 못 쟀다"고 적어야 다음 사람이 잴 생각을 한다.
- **비용의 형태가 버전에 따라 바뀐다.** "MCP는 비싸다"는 명제는 2026-09-07 기준으로 이미 낡았다.
  숫자를 문서에 박지 않고 다시 재는 명령을 함께 남기는 이 문서의 방침이 여기서 값을 했다.

## 2026-09-07 ③ — A/B 하네스를 심고, 그 비용을 먼저 냈다

### 배경

이 문서와 `docs/context-ab-test.md`는 서로 다른 결함을 하나씩 갖고 있었다.
이 문서는 **재기는 하는데 효과를 증명하지 않았고**, 저쪽은 **증명은 했는데 재현이 불가능했다**
(팔 사본과 실행 스크립트가 `/tmp`에 있어 커밋되지 않았다). `context-ab` 스킬은 두 번째를 메운다.

### 비용

| 항목 | 자수 |
|---|---|
| 지침 `context-experiment.md` 1개 추가 | **+645** |
| 스킬 `context-ab`의 description | **+404** |
| **합계** | **+1,049 (14,210 → 15,259자, +7.4%)** |

측정: `git archive HEAD`로 뽑은 사본과 작업 트리를 각각 `summarizeBudget()`으로 재서 뺐다.
작업 트리만 두 번 재면 이미 추가한 스킬 description이 "이전 값"에 섞여 들어간다 — 실제로 한 번 그렇게 재서 틀렸다.

### 트레이드오프

**재는 도구가 재는 대상을 키운다.** 이번 추가분은 앞선 최적화 절감분(-1,323자)의 79%를 도로 쓴 것이다.
그래도 심은 이유는 두 가지다.

- 절감을 이야기하려면 절감이 **무엇을 잃게 하는지** 잴 수 있어야 한다. 지금까지는 지침을 지울 때 잃는 것을 못 쟀다.
- 지침 1개(645자)는 한 번 내고 마는 값이 아니라 **매 세션 내는 값**이다. 그래서 다른 지침보다 짧게 썼다 —
  `requirement-gate`(1,821)의 3분의 1, 지침 9개 중 6번째로 짧다.

### 한계

- `context-ab`의 SKILL.md 본문(6,937바이트)은 온디맨드라 상시 비용에 안 잡히지만, 스킬이 **호출되면** 그때 다 낸다.
- 이 하네스가 실제로 값을 하는지는 아직 모른다. **한 번도 전체 실행을 돌리지 않았다.**
  dry-run과 1회 실측만 확인했다(아래 `docs/context-ab-test.md`의 실험 1~3은 이 하네스가 아니라 손으로 돌린 것이다).
