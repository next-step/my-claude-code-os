## 스킬별 개선 제안

### /plan — 제안 2건
**[제안 P1] 1차 스캔에서 vendored/의존성 디렉토리 제외**
- **무엇을**: `plan/SKILL.md` 1단계 스캔에 "의존성 디렉토리 제외" 한 줄 추가.
- **왜(마찰)**: Plan 5줄이 `find . -name "*.py"` → 0건을 "재활용 코드 전무·전부 신규" 근거로 박았으나 지금은 2326건(전부 `.venv`)이라 단언이 정반대로 오도. 1단계(52~66줄)에 `.venv` 같은 벤더 트리를 거르라는 지시가 없는 게 근원.
- **어떻게(한 줄)**: 1단계 2번 항목 밑에 —
  > "1차 스캔·환경 확인 시 vendored/의존성 디렉토리(.venv·node_modules·site-packages 등)는 제외한다. '재활용 코드 N건' 같은 수치는 제외 후로만 세고, Plan에 고정 단언으로 박지 않는다(나중에 뒤집힌다)."

**[제안 P2] "손댈 파일"과 "구현 단계"는 단일 파일명 체계 강제**
- **무엇을**: 3단계 Plan 서브에이전트 출력 형식(155~164줄)에 두 절의 파일명 정합 요구 한 줄 추가.
- **왜(마찰)**: 손댈 파일 트리는 레이어 구조(`controllers/`·`services/`·`repositories/`)인데 구현 단계 텍스트(128·129·131줄)는 평면명(`security.py`·`schemas.py`·`routers/auth.py`)이라 **두 정본 공존** → /impl이 "트리가 정본"을 별도 주입해야 divergence를 막음. 단일 생성 때도 막을 장치가 없는 잠재 갭.
- **어떻게(한 줄)**: 출력 형식 블록 끝(164줄 근처)에 —
  > "단, '손댈 파일' 트리와 '구현 단계'는 반드시 동일한 파일명·경로 체계를 써라(트리가 정본). 한쪽만 고쳐 두 체계가 섞이지 않게 하라."

### /impl — 제안 1건
**[제안 I1] 디스패치 전 Plan 내부/현실 모순 점검 → 해소 지침 명시(또는 /plan 반송)**
- **무엇을**: `impl/SKILL.md` [준비] 단계에 Plan 모순 점검 한 문장 추가.
- **왜(마찰)**: 소비한 Plan에 내부 모순(전부 신규 vs 기존 리팩터링 / 트리·평면 파일명 상충)이 있었으나 /impl이 감지 못 함 → 사람 오케스트레이터가 "트리가 정본"을 수동 주입. [준비]는 승인만 확인(42~43줄), 1-b는 Plan을 그대로 실어 넘기라고만 함(64~71줄) — 모순을 거르라는 문구 없음. 격리된 구현 에이전트는 모순 Plan을 받으면 임의로 한쪽을 골라 어긋난 구조를 만든다.
- **역할 경계**: /impl 고유 책임 안. 근거 — (a) 스스로 "디스패처"로 규정(격리 에이전트가 안 헷갈릴 프롬프트를 만드는 게 이 스킬 일), (b) 이미 "설계문제→/plan 에스컬레이션" 출구(103~104줄)가 있어 "못 풀 모순은 /plan으로"가 기존 분기와 정합, (c) 모순 해소는 *검증(사후)*이 아니라 *디스패치 구성(사전)* — 뒤로 미루면 잘못 구현 후 재구현 낭비.
- **어떻게(한 줄)**: [준비] 42~43줄 뒤에 —
  > "읽으며 Plan의 **내부 모순·현실 불일치**(예: 신규/재활용 상충, 파일 구조 상충)를 점검한다. 있으면 **정본을 정해 디스패치 프롬프트에 해소 지침으로 명시**하고, 스스로 못 정할 모순이면 구현 대신 **/plan으로 돌려보낸다**(설계문제 분기와 동일)."
