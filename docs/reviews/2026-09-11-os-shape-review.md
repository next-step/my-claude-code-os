# 마이그레이션 OS 모양 재검토: 루프 길이 · 크기 · 축적 장치

> 작성: 2026-09-11 · 브랜치 `day3` · 대상: `legacy-slice` 오케스트레이터와 그 위성 스킬·에이전트·도구·문서 전체
> 방법: 서브에이전트 여덟(내부 독해 넷 · 외부 조사 셋 · 직전 조사 재추출 하나, 전부 Opus 또는 Sonnet)의 보고를 오케스트레이터가 대조하고, 설계 근거가 되는 주장은 오케스트레이터가 파일과 원문을 직접 확인했다. 확인한 주장에는 파일:줄 또는 URL 을 붙였다.
> 이 문서는 제안이다. 구현된 것은 없다. 설계 정본(`docs/legacy-migration-os.md`)에 반영할지는 사용자가 정한다.

## 0. 결론

**사용자의 지적은 맞다. 다만 이유가 절반만 맞다.** 회차가 너무 길다는 것은 실측으로 확인된 사실이고, 그 원인은 슬라이스가 컸기 때문이 아니라 **한 회차의 비용이 슬라이스 크기와 무관하게 Phase 일정으로 고정되어 있기 때문**이다. 한 페이지·한 규칙 슬라이스도 여섯 페이지 슬라이스와 같은 수의 에이전트 파견(normal 11회)과 같은 분량의 지시문(약 2,000줄)을 낸다. 그러므로 "슬라이스를 작게 자르면 고정 비용을 두 번 낸다"는 직전 세션의 반론은 지금의 모양 안에서만 참이고, 고칠 것은 슬라이스 크기가 아니라 그 고정 비용의 위치다.

**OS 는 근거보다 먼저 자랐다.** v1 은 실행 전에 하루에 설계·구현되었고(08-30, 스킬 6·에이전트 8·훅 2·루프 4·게이트 2), 한 번 돌린 뒤 회고는 "없앨 것은 없다"고 결론지었으며, v2 는 그 한 번의 감사 FAIL 을 근거로 하룻밤에 약 7,800줄을 새로 써서 09-09 01:13~01:51 에 커밋되고 **01:56 에 실행이 시작되었다.** 설계 정본 스스로 "닫은 것 중 어느 것도 v2 를 돌려서 닫은 것이 아니다"라고 적고 있다. 두 번의 실행에서 나온 교훈 31개 중 다음 실행이 실제로 읽는 자리에 도달한 것은 11개다.

**"컨텍스트가 쌓여서 정교해진다"는 가설은 절반만 지지된다.** 외부 근거가 지지하는 것은 더 좁은 명제다: **루프가 매번 다시 읽는 버전 관리된 산출물(규칙집·원장·판정된 예외 목록·픽스처)이 쌓이고, 그 산출물은 반복된 실패에만 개정되며, 만료 조건을 가진다.** 프롬프트가 쌓이는 것은 지지되지 않는다. 자가 생성 피드백으로 하네스를 진화시키면 진화하지 않은 기준선보다 나빠진다는 측정이 있고(Evo-Harness 4.6절), 산문 지시는 한 달이면 썩는다는 보고가 있다(Temporal).

**제안은 축소다.** 작업 단위를 이음새 함수 하나(페이지 하나)로 줄이고, 설계·도메인 문서를 영역 단위 살아있는 문서로 올리고, 오케스트레이터가 손으로 도는 동등성 루프를 스크립트와 `state.json` 으로 바꾸고, 사이에 결함이 숨었던 두 에이전트를 합치고, 원장을 기계가 읽는 얇은 표로 바꾸고, 역할별 저널과 승인 게이트 하나를 학습 장치로 더한다. 새로 더하는 장치는 관찰된 실패 하나에 하나씩이고, 장치가 대체하는 산문은 같은 변경에서 지운다.

## 2. 진단

### 2-1. OS 는 근거보다 먼저 자랐다

| 시점 | 스킬 | 에이전트 | 훅 | 스크립트 | 컨텍스트 | 문서 |
|---|---|---|---|---|---|---|
| 첫 실행 병합(09-02, `6f41cc3`) | 1,471 | 838 | 405 | 0 | 0 | 900 |
| 두 번째 실행 직후(09-09, `5f51130`) | 2,658 | 1,009 | 1,686 | 6,667 | 324 | 2,166 |

줄 수 기준으로 약 3,600줄이 약 14,500줄이 되었다. 그중 3,528줄은 회사 체크아웃에서 옮겨온 기존 도구(`e2eb0d9`)이고, 약 7,800줄은 09-09 하루에 새로 쓴 것이다(이음새 도구 4,129 · 컨텍스트 주입 1,996 · 스킬과 에이전트 개정 약 1,700). 이것을 정당화한 근거는 첫 실행의 감사 FAIL 하나다.

문서 독해가 만든 성장 원장은 추가 항목 49개를 근거의 종류로 나눴다: 실행에서 관찰된 실패에 대한 응답 21, 설계 검토나 환경 준비에서 관찰된 것 4, 관찰된 적 없는 가설 7, 원칙이나 선호 15, 근거 미기재 2. 첫 실행 전에 만든 것은 거의 전부 가설·원칙·미기재였다. 첫 실행 회고는 "없앨 것은 없다"(`docs/first-run-retrospective.md:216`)라고 결론지었고, 그 다음 개정이 루프 하나·기계 게이트 둘·도구 넷·컨텍스트 파일 일곱을 더했다.

v2 의 유일한 정당화 수단으로 설계 정본이 지목한 비교 실험(`docs/legacy-migration-os.md:571`, 여섯 축: 요청 수·토큰·비용·회차·`불가` 행·사람 개입 지점)은 같은 슬라이스로 v2 를 돌렸다는 점에서 실행되었으나, 여섯 축 중 셋(회차·부분 토큰·사람 대기 0)만 기록되고 요청 수·비용·`불가` 행 수는 어디에도 없다. 두 번째 실행 뒤 발견된 결함 여섯 중 둘만 고쳐졌고, 고쳤다고 기록된 `무방비` 정의 축소는 추적 파일 어디에도 없다(`표면 유지` 는 회고에만 한 번 나온다).

### 2-2. 회차 길이는 Phase 일정이 정한다

스킬 독해의 계산이다. depth `normal` 에서 에이전트 파견은 최소 11회, `shallow` 에서 10회이고, 이 수는 슬라이스 크기와 무관하다. `depth: shallow` 가 빼는 것은 레드팀 라운드·migrated 골든 비교·Playwright 셋뿐이고 고정 비용에는 손대지 않는다. 한 페이지·한 규칙 슬라이스의 정직한 최소 경로는 18단계·7파견인데, 지금 텍스트에는 그 축소를 선언할 방법이 없다.

`legacy-slice/SKILL.md` 323줄 중 약 57%(약 183줄)가 크기 불변 서술이고, 위성 스킬 열 개를 합친 2,013줄의 읽기 경로 중 약 90% 가 페이지 수나 규칙 수로 분기하지 않는다. 한 페이지 슬라이스가 여섯 페이지 슬라이스의 뼈대 비용을 전부 낸다.

두 번째 실행의 실측(`docs/retrospectives/2026-09-09-second-slice-v2.md`)이 이를 뒷받침한다: 벽시계 12.2시간, 사용량 한도 정지 5.1시간, 실제 계산 7.1시간 중 서브에이전트 5.0시간(14건 순차), 오케스트레이터 2.1시간. 사람 게이트를 둘 다 위임해 사람 대기가 0 이었는데도 그랬다. 초반 루프 셋(L0 1/3 · 커버리지 1/2 · L1 2/5)은 즉시 닫혔고, 동등성 루프만 10/5 로 상한의 두 배를 돌았으며 그중 절반은 환경 둘과 오케스트레이터 자신의 제외 목록 실수 셋이었다.

### 2-3. 서브에이전트 배치가 격리/축적 표의 가장 나쁜 칸에 있다

서브에이전트 공식 문서는 "여러 Phase 가 상당한 컨텍스트를 공유하면, 예컨대 계획·구현·테스트라면, 메인 대화에서 하라"고 적는다. 우리 Phase 2~4 가 정확히 그 예다. Anthropic 의 2026-01 글은 다중 에이전트의 정당화를 셋(컨텍스트 보호 · 병렬화 · 전문화)으로 한정하고 비용을 3~10배로 잡는다. 우리는 같은 슬라이스 위에서 14개의 일회성 에이전트를 순차로 돌렸다: 병렬화 이득은 없고 인계 비용은 전부 냈다. LangChain 의 2026-01 측정이 이 표를 가장 명확히 적었다: 격리는 일회성 작업에서 이기고, 축적은 같은 컨텍스트를 반복해 쓸 때 이긴다. 우리 파이프라인은 같은 컨텍스트를 14번 다시 모으는 쪽이다.

에이전트 층 독해의 계수: 정의 11개 664줄 중 절차 49% · 금지 15% · 출력 형식 28% · 첫 실행의 역사 8%(문자 기준 11%, 네 에이전트에서는 15~18%). 다섯 에이전트가 훅이 이미 주입하는 `legacy-tree.md` 의 규칙을 본문에 다시 적고 있다. 훅을 만든 이유는 "읽으라는 지시는 읽었다는 보장이 아니다"였는데, 장치를 만든 뒤 그것이 대체한 산문을 지우지 않았다. 감사자는 주입 예산 24,576 B 의 86.5%(21,259 B)에 있고, 넘치면 알파벳 순으로 마지막인 `team-boundary.md`, 곧 공개 저장소 경계가 먼저 잘리며 흔적은 stderr 한 줄이다.

### 2-4. 쌓이는 것이 없다: 학습이 곧 산문 증식이다

에이전트 11개 중 어느 것도 "이전 실행의 교훈"을 입력으로 받지 않는다. 다음 슬라이스를 위해 쓰라고 정한 유일한 기록(`meta.json` 의 루프 회차, `SKILL.md:283`)은 읽는 곳이 없다. 원격 측정 파일 여섯은 보고서 셋을 만들지만 어느 것도 스킬·에이전트·게이트·설정을 바꾸지 않는다. 두 실행의 교훈 31개 중 다음 실행이 읽는 자리(에이전트·스킬·컨텍스트·스크립트·셀프테스트)에 도달한 것은 11개, 부분 도달 2개, 저장소 밖 3개, 회고나 인수인계 산문에만 있는 것 15개다.

지금의 학습 장치는 사람이 산문을 고치는 것이고, 고칠 때마다 "첫 실행에서 …" 절이 늘어난다(`SKILL.md:29, 103, 166, 180, 182, 226, 295`). Claude Code 공식 문서는 CLAUDE.md 200줄·SKILL.md 500줄을 상한으로 두고 "규칙을 계속 어기면 파일이 너무 길어 규칙이 묻힌 것"이라고 적는다. 두 번째 실행에서 어겨진 규칙 셋(L2 상한 · 제외 목록 시점 · 레거시 직접 읽기 금지)은 전부 장치 없는 산문 규칙이었고, 장치가 있는 규칙은 하나도 어겨지지 않았다.

같은 저장소의 `goal-loop` 는 이 문제를 이미 반대로 풀었다: "개선은 프롬프트가 아니라 저널에서 온다"(`goal-loop/SKILL.md:98`). 그 장치가 마이그레이션 OS 에는 없다.

### 2-5. 완전성은 검사가 없는 층으로 계속 도망간다

v1 의 실패는 규칙이 이음새 위에 있어서 아무도 보지 않은 것이고, v2 의 실패는 규칙이 백엔드에 있는데 어댑터가 그 필드를 요청하지 않아 아무도 읽지 않은 것이다(회고 4장). 완전성 검사 셋(구조 린트 · 본문 해시 · 호출자 전수)은 전부 정적이고 각각 한 층만 본다. 층이 하나 생기면 검사가 하나 필요하고, 그 검사는 다음 실패 뒤에야 만들어진다.

외부 근거는 층에 무관한 답을 두 가지 준다. 하나는 동적 관찰이다: `migrated` 모드에서 래퍼 안의 레거시 반환값에 독을 넣어도 화면이 그대로면 화면의 값은 백엔드에서 왔다(직전 조사의 절차 B). 레거시 컨테이너에 그 PHP 버전에 맞는 Xdebug 2.x 를 붙이면 `migrated` 모드에서 레거시 본문의 실행 줄이 0 인지도 잰다. 다른 하나는 값이 아니라 기전을 읽는 감사다: Google 의 검증 사다리는 "AST 가 원본과 같으면 무효"와 "이 변경이 필요했는가를 모델에 되묻는" 단계를 두고, SWE Refactor Bench 는 동작을 보존하며 마이그레이션을 건너뛴 30/520 을 기전 감사로만 잡았다.

### 2-6. 비용을 쓴 곳과 결함을 잡은 곳이 다르다

회고 3-3절이 기록한 것: 이중 실행이 셋, migrated 골든이 둘(이중 실행이 "예상 밖 불일치 0" 인 상태에서), 감사가 하나를 잡았고, 기계 게이트 셋은 한 번도 거짓 통과가 없었다. 원장(115 KB)·이음새 계획(61 KB)·설계(77 KB)를 만든 판단 중심의 초반 단계가 잡았다고 기록된 결함은 없다. 레드팀은 68행을 78행으로, 설계의 부재 점검표는 다시 7행을 더했지만 그 17행이 뒤에서 무엇을 잡았는지는 기록이 없다. 그리고 감사가 잡은 그 하나는 스키마 필드 목록과 어댑터 요청 필드 목록의 차집합, 곧 스크립트 한 줄이었다.

(1) 끝낸 사례는 전부 **작고 균일하며 기계로 열거되는 단위**를 썼다. 단위가 컸던 둘이 완전성이 가장 나빴다: VB6 사례는 단위가 커질수록 동등성이 92%→81%→47% 로 떨어졌고 비용은 초선형으로 올랐으며(입력 토큰이 99.6%, 레거시를 반복해 다시 읽음), 실패 유형은 "인접 모듈 누락"과 "다단계 흐름의 중간 단계 생략"이었다. 이것은 여섯 페이지 슬라이스가 Phase 7 에서 FAIL 한 모양과 같다.

(2) 비싼 산출물은 **캠페인당 한 번** 만들고 단위마다 나눠 낸다. Anthropic 키트의 원칙 문장: "코드를 고치지 말고 코드를 만든 과정을 고쳐라. 개별 실패는 수정 에이전트가 소진하고, 반복된 실패는 규칙을 기소하며, 규칙이 개정된다." 개정된 규칙이 건드린 파일만 다시 생성한다. 직전 세션의 고정 비용 반론이 성립하는 조건은 설계·게이트·환경 준비를 슬라이스마다 다시 내는 것이고, 그것이 고칠 대상이다.

(3) 쌓이는 것은 **프롬프트가 아니라 파일과 코드**다. Google 은 프롬프트를 12개월 고정하고도 좋아졌다. Anthropic 은 개별 실패가 프롬프트를 가르치는 것을 명시적으로 금지한다. Airbnb 만 프롬프트가 쌓였는데 4만~10만 토큰까지 자란 뒤 97% 에서 튜닝을 멈추고 손으로 마감했다.

(4) 축적된 산문은 **썩는다.** Temporal 은 지시 파일이 약 한 달 뒤 이미 삭제된 파일을 고치라고 지시하고 있었다고 보고했고, 그것을 정직하게 유지할 절차가 없었다고 인정했다. 만료 조건 없는 축적 장치는 어디에도 없다.

(5) 완전성 오라클은 산업 사례에 거의 없고, 있는 셋(Google 의 AST 동일·필요성 되묻기, VB6 의 규칙 목록 대조, 벤치마크의 기전 감사)이 가짜 마이그레이션을 발견한 셋이다. 고정 테스트를 다 통과한 제출물의 68.2% 가 한 시간짜리 적대적 검증 에이전트에 깨졌다(SWE Refactor Bench).

(6) **AI 로 PHP 를 다른 언어로 옮긴 공개 사례는 없다.** 있는 것은 버전 업그레이드(MyHeritage PHP 7→8, 원문 접근 불가로 미검증)와 이름이 가짜인 마케팅 글이다. 우리 모양에는 외부 선례가 없다.

### 3-3. 우리 가설에 불리한 증거

정직하게 적는다.

- Anthropic 의 가장 최근 하네스(2026-03)는 모델이 좋아지자 **생성 단위를 늘리고 평가를 끝으로 몰았다.** 다만 그 사례는 새 앱을 만들고 진행이 단조적이다(기능이 쌓임). 우리 파이프라인은 감사 FAIL 이 설계까지 되감는 비단조 진행이고, 그것이 단위를 작게 두어 판정을 최종으로 만들어야 하는 이유다.
- Google 의 12개월 기록에서 숙련이 쌓이자 단위는 **커졌다.** 작은 단위는 출발점이었고 목적지가 아니었다. 이것은 사용자의 "필요에 따라 키운다"와 같은 방향이다.
- FreshBrew 는 난이도 대 성공률이 역 U 자임을 보였다: 너무 작은 단위도 나쁘다. 페이지 하나에 규칙 10~15개는 그 중간이다.
- 7시간짜리 실행 한 번이 FAIL 한 것은 모양의 증거가 아니다(n=1). 축소의 근거는 그 실패가 아니라 고정 비용의 위치와 축적 장치의 부재다.
- 직전 세션의 고정 비용 반론(두 3페이지 슬라이스는 6페이지 슬라이스의 120~130%)은 지금 모양 안에서 맞다. 답은 슬라이스를 크게 두는 것이 아니라 고정 비용을 영역 단위와 스크립트로 옮기는 것이다.
- 우리의 완전성 질문(값이 같은데 논리가 옮겨갔는가)은 조사한 문헌 어디에도 그대로는 없다. 구조 린트·해시·호출자 전수는 선례가 아니라 우리 발명이다.

## 4. 네 질문에 대한 답

### 4-1. 페이지 단위 마이그레이션은 맞는가

**교체 단위로서 페이지별 이음새 함수는 맞고, 작업 단위도 그것으로 내려야 한다.** 지금의 슬라이스 단위 규칙 "대상 DAO 를 부르는 페이지 전부"(`SKILL.md:103`, `slice-scout/SKILL.md:26`, `legacy-migration-os.md:351`)의 근거는 둘이다: 진입점 밖 호출자가 있다는 것, 그리고 PC 와 모바일이 같은 메서드를 정반대 페이징 계약으로 써서 "백엔드가 정상 해석하면 모바일이 조용히 깨진다"는 것. 두 번째는 교체 지점이 DAO 하나였던 v1 에서만 성립한다. v2 는 페이지마다 자기 이음새 안에서 교체하므로(`SKILL.md:31`), PC 페이지만 옮겨도 모바일은 레거시 본문으로 계속 돈다. 남는 근거는 "API 를 설계할 때 호출자 전부를 알아야 한다"이고, 그것은 scout 단계의 `phpseam callers` 한 번으로 충족된다. 정확성은 더 이상 여섯 페이지를 한 슬라이스에 묶기를 요구하지 않는다.

외부 근거도 같은 방향이다. 끝낸 사례는 전부 파일 단위였고, 단위가 커질수록 완전성이 무너졌다. Anthropic 키트는 재설계 마이그레이션의 단위를 모듈로 두는데, 우리 이음새 함수는 반환 형태를 원본과 같게 고정하므로("반환 형태는 원본과 정확히 같아야", `SKILL.md:199`) 재설계 마이그레이션을 경계에서 구조 보존 마이그레이션처럼 만드는 장치다. 그래서 단위를 이음새 함수 하나로 둘 수 있다.

호출자를 묶어야 할 진짜 이유는 백엔드 API 설계의 경제성이다. 그것은 설계를 영역 단위 살아있는 문서로 올리면 해결된다. 단위가 작아진 뒤 같은 영역에서 감사 FAIL 없이 N 페이지가 지나가면 두 페이지 단위로 키우는 규칙을 두면 된다(Google 의 숙련 곡선).

### 4-2. 문서 작성 방식은 맞는가

**절반은 아니다.** 슬라이스마다 문서 여섯, 373 KB 가 나오고, 그중 `03-dualrun.md` 는 읽는 곳이 없으며 `05-domain-doc.md` 는 상태 파일 번호를 올리기 위한 한 줄 포인터다. 에이전트는 읽은 양의 2.3~5.2배를 쓰고, 그 산출물이 다음 에이전트의 입력이 되어 장황함이 사슬을 따라 누적된다. 원장은 규칙 하나에 약 1,300자다. 그리고 회고와 인수인계가 지적한 교차 검사(설계 배치표 ↔ 원장 `이관`, 감사 `다음 조치` ↔ 원장, `ignore.json` ↔ 승인 행)는 Markdown 산문을 파싱해야 하므로 만들어지지 않았다.

제안: **기계가 먼저 읽는 형식으로 바꾸고, 사람 산문은 두 곳에만 남긴다.** 원장은 JSONL(행마다 id · 규칙 한 문장 · 분류 · 출처 파일:줄 · 줄 범위 · 관찰 · 이관 · 승인)로, 에이전트는 자기 역할의 상태 필드만 고칠 수 있다(Anthropic 2025-11: 모델은 JSON 을 Markdown 보다 덜 덮어쓴다). 설계는 영역 단위 살아있는 문서에 배치표를 표로, 슬라이스에는 델타만. 감사는 판정과 행 id 목록. 사람이 읽는 산문은 영역 도메인 문서(이미 영역 단위로 제자리 개정된다, `SKILL.md:278`)와 각 산출물의 `요약` 20줄만이다. 회고는 사람이 쓰는 문서 대신 슬라이스 종료 스크립트가 `state.json` 에 남기는 기록(상한 대 실제 회차 · 오라클별 결함 · 토큰 · 벽시계 · 착지하지 않은 교훈)으로 대체하고, 사람은 그 위에 판단만 덧붙인다.

설계 정본은 그대로 정본이다. 다만 3일치 기록이 비어 있다(09-09 실행의 변경 이력 행이 없고, `goal-loop` 가 어디에도 없다). 저장소 자신의 규칙("스킬을 고치기 전에 문서를 먼저 고친다")이 어겨지는 이유는 회차가 길어 문서를 고칠 시점이 오지 않기 때문이고, 그것이 회차를 짧게 만들어야 하는 또 하나의 이유다.

### 4-3. 서브에이전트 활용 방식은 맞는가

**분리가 판정의 독립성을 사는 곳만 맞다.** 지켜야 할 분리는 둘이다: 원장을 쓴 쪽과 반박하는 쪽(분석가/레드팀), 만든 쪽과 감사하는 쪽(구현자·스왑 담당/감사자). 감사자가 `Edit`·`Write` 를 못 갖는 것은 이 저장소에서 설정으로 강제된 유일한 분리다.

그 밖의 분리는 Phase 가 나뉘어 있어서 생긴 것이다. (1) 구현자와 스왑 담당: 두 번째 실행을 FAIL 시킨 결함이 정확히 이 둘 사이에 있었고 한 회차에 두 번 나왔다. 스키마 필드는 구현자의 산출물, 어댑터 요청 필드는 스왑 담당의 산출물인데 둘을 함께 보는 독자가 없었다. 합치고, 그래도 기계 검사(`phpseam fields`)를 둔다. (2) 코퍼스 담당: `필요 픽스처` 표를 `corpus.json` 으로 옮기는 패턴 작업이고 판단은 `관찰` 값 하나다. 분석가에 접고 `불가` 를 `htmlsnap corpus validate` 전에 쓰지 못하게 기계로 막거나, Xdebug 커버리지로 `관찰` 자체를 측정값으로 바꾼다. (3) 서기: 59줄짜리 sonnet 에이전트로, JSONL 원장에서 템플릿으로 생성하고 사람이 읽을 부분만 에이전트가 다듬는다. (4) 스왑 담당은 자기 파일이 "일부러 멍청하게" 만들라고 하는 일을 opus 로 17.8 KB 의 주입 컨텍스트를 받아 한다.

레드팀은 기본 0 라운드로 두고, 뒤 단계가 원장에 없는 규칙을 발견했을 때만 그 증거를 들고 한 라운드를 돈다(근거 기반 depth). 추출 담당의 계획 모드는 v2 에서 가장 어려운 판단이므로 남기고, 추출 모드의 캡처→편집→린트→캡처→비교 루프는 스크립트가 돌린다.

프롬프트 위생: 역사 서술(문자의 11%)은 설계 정본의 변경 이력으로 옮기고, 주입 컨텍스트를 본문에 다시 적은 다섯 에이전트에서 그 복사본을 지우고, 감사자의 주입 예산을 줄이거나 주입 순서를 우선순위(경계 파일 먼저)로 바꾼다. 서브에이전트 정의 합계는 15,000 토큰 경고선 아래로 유지한다.

### 4-4. 루프 길이와 OS 크기

**루프는 짧아야 한다는 가설은 맞다. "컨텍스트가 쌓여서 정교해진다"는 표현은 고쳐야 한다.** 쌓여야 하는 것은 대화의 컨텍스트가 아니라 루프가 매번 다시 읽는 버전 관리된 산출물이고, 그것은 반복된 실패에만 개정되며, 만료 조건을 가진다. 근거는 3-1 의 (3)(4) 와 3-2 의 Evo-Harness·ACE·Temporal 이다.

고정 비용 반론은 다음 세 변경으로 해소된다. (1) 설계와 G2 를 영역 단위로: 첫 페이지가 영역의 자원 모양·에러 매핑·인가를 정하고 다음 페이지는 델타만 낸다. (2) Phase 0 과 Phase 6 을 스크립트로: 환경 검증 셋(백엔드가 이 슬라이스의 스키마를 가졌는가 · 상류에 닿는가 · 토글 되읽기가 자리표시자가 아닌가)은 요청 한 번씩이고, 토글 전환·캡처·집계·비교는 기계 절차다. (3) Phase 8 을 N 슬라이스마다: 도메인 문서는 이미 영역 단위다. 이 셋을 하면 페이지당 고정 비용은 에이전트 기동(정의 + 주입, 에이전트당 약 20~35 KB)만 남고, 그것은 14회 파견에서 7회 이하로 준다.

OS 크기는 "필요에 따라 키운다"를 규칙으로 만든다: 장치 하나는 관찰된 실패 하나에 대응하고, 설계 정본에 먼저 적히며, 그 장치가 대체하는 산문은 같은 변경에서 지운다. 지시 파일에는 상한을 둔다(오케스트레이터 스킬 150줄 · 에이전트 60줄 · 컨텍스트 파일 40줄을 제안한다).

## 6. 회차를 거듭할수록 정교해지기 위한 장치

여덟이다. 앞의 넷은 새 장치이고 뒤의 넷은 규칙이다. 전부 관찰된 실패 하나에 대응한다.

**(1) 역할별 저널, 근거 있는 항목만.** 각 에이전트는 끝날 때 자기 역할의 저널에 `{lesson, trigger, evidence, scope}` 항목을 덧붙인다. `evidence` 는 명령·출력·diff·불일치 로그의 경로여야 하고, 없으면 항목이 아니다(Evo-Harness 4.6절: 자가 생성 피드백은 기준선보다 나쁘다). 다음 슬라이스의 같은 역할이 최근 N 항목을 읽는다. 오케스트레이터는 저널을 읽지 않는다(`goal-loop` 의 일방향 흐름). 대응하는 실패: 교훈 31개 중 15개가 산문에만 있다.

**(2) 승인 게이트를 가진 진화자.** 슬라이스가 끝나면 저널의 근거 있는 항목에서 `.claude/context/*.md` 에 대한 델타(`Add / Merge / Revise / Skip`)를 제안하고, 사람이 diff 로 승인한다. 에이전트가 스스로 적용하지 않는다(Anthropic 키트: "개정은 당신 앞에 줄 서고, 스스로 적용되지 않는다"; misevolution: 감독은 루프 밖에). 통째로 다시 쓰지 않고 델타만 댄다(ACE). 장치가 대체하는 산문은 같은 델타에서 지운다. 만료: 항목이 인용한 파일·심볼이 사라지면 항목은 만료 후보로 표시된다(Temporal 의 한 달 부패). 대응하는 실패: 학습이 산문 증식으로만 일어난다.

**(3) 결함은 다음 단위 전에 픽스처나 셀프테스트가 된다.** 오라클이 잡은 결함은 `dualrun-report --as-fixtures` 출력이 실제로 구현 단계의 입력으로 넘어가고(지금은 넘기는 단계가 없다), OS 도구의 결함은 같은 세션에서 `selftest_*` 사례가 된다. 슬라이스는 미해결 OS 결함을 안고 다음 단위로 가지 않는다. 대응하는 실패: 회고 "여섯 중 둘만 고쳤다", "회차를 끝까지 미는 것이 학습을 미룬다". Anthropic 2026-01: 평가 세트는 실제 실패 20~50건에서 시작한다. 두 실행이 이미 교훈 31개와 도구 결함 7개를 냈다. 그것이 첫 평가 세트다.

**(4) 슬라이스 종료 기록이 다음 슬라이스의 설정을 정한다.** `state.json` 에 상한 대 실제 회차 · 오라클별 결함 · 토큰 · 벽시계 · 착지하지 않은 교훈이 스크립트로 남고, 다음 슬라이스의 depth 와 상한은 그 파일을 읽는 규칙이 정한다. 대응하는 실패: `meta.json` 의 회차 기록은 읽는 곳이 없고 "사람이 기억으로 답하면 비용이 항상 낮게 기억된다"(`SKILL.md:283`).

**(5) 오라클은 신뢰하기 전에 깨뜨려 본다.** 독 주입 검사와 `phpseam fields` 는 실패한 슬라이스의 Phase 6 산출물(결함 둘이 알려진 상태)에 먼저 돌려 빨간불이 켜지는지 확인한다(Anthropic 키트: 심판은 고의로 깨뜨린 코드로 먼저 검증; `goal-loop`: 반증 가능한 게이지). 대응하는 실패: 두 오라클이 초록인데 완주하지 못했다.

**(6) 지시 파일 상한과 미사용 조사.** 오케스트레이터 스킬 150줄 · 에이전트 60줄 · 컨텍스트 파일 40줄 · 서브에이전트 정의 합계 15,000 토큰 이하. 실행마다 부르지 않은 스킬·도구를 집계한다(`/skill-doctor` 의 원칙: 비용이 높고 한 번도 불리지 않은 것부터 끈다). 대응하는 실패: 어겨진 규칙 셋이 전부 장치 없는 산문이었다.

**(7) 회사 트리 없이 도는 셀프테스트, 실제로 갈라진 짝을 검사하는 셀프테스트.** 지금 `selftest.py` 는 `legacy.root` 없이 시작하지 못하고, 교차 검사 다섯은 OS 자신의 사본끼리 비교하며 실제로 갈라진 짝(`이관` 어휘 · L2 종료 조건 · 진단표 넷)은 목록에 없다. 대응하는 실패: 회고의 결함 일곱 중 셀프테스트가 잡을 수 있었던 것이 없다.

**(8) 단위 성장 규칙.** 같은 영역에서 감사 FAIL 없이 N 페이지가 지나가면 두 페이지 단위를 허용한다. 대응하는 것은 실패가 아니라 Google 의 숙련 곡선이다: 작은 단위는 출발점이다.

## 7. 제안하는 v3 모양: 축소

### 7-1. 단위와 산출물

작업 단위는 이음새 함수 하나, 곧 페이지 하나다. `slice-scout` 는 대상 DAO 의 호출자 전부를 여전히 열거하되, 그것은 슬라이스 목록이 아니라 영역의 API 설계 입력이다.

| 범위 | 산출물 | 형식 | 쓰는 쪽 |
|---|---|---|---|
| 영역 | 설계(자원 모양 · 에러 매핑 · 인가 · 배치표) | Markdown, 제자리 개정 | 설계자, 델타로 |
| 영역 | 도메인 문서 | Markdown, 템플릿 재생성 + 사람 산문 | 서기(N 슬라이스마다) |
| 영역 | 역할별 저널 | JSONL | 각 에이전트 append |
| 슬라이스 | 원장 | JSONL, 역할별 상태 필드만 편집 | 분석가 · 구현자 · 감사자 |
| 슬라이스 | `corpus.json` · `pins.json` · `ignore.json`(항목마다 원장 행 id) | JSON | 추출 담당 · 스크립트 |
| 슬라이스 | `state.json`(회차 · 상한 · 판정 · 토큰 · 벽시계 · 토글 상태) | JSON | 오케스트레이터와 스크립트만 |
| 슬라이스 | 요약 20줄 | Markdown | 각 에이전트 |

### 7-2. 한 페이지의 루프

| 단계 | 누가 | 무엇 | 게이트 |
|---|---|---|---|
| 0 준비 | 스크립트 | 스택 기동 · 백엔드가 이 슬라이스의 스키마를 가졌는가(요청 1) · 상류에 닿는가(요청 1) · 토글 되읽기 · **레거시 대 레거시 잡음 바닥 측정 → `ignore.json` 씨앗** | 실패 시 멈춤 |
| 1 추출 | 추출 담당(계획) → 사람 → 스크립트가 도는 추출 루프 | 줄 분류 · 시그니처 · 막는 구간 · 코퍼스 초안; 캡처→편집→린트→캡처→비교→핀 | **G1**(작음) · 골든 identical · 린트 0 · 핀 |
| 2 원장 | 분석가 | JSONL 10~15행 · 커버리지 = 줄 범위. 레드팀 기본 0 | 미커버 0 |
| 3 설계 델타 | 설계자 | 영역 설계를 읽고 이 행들의 배치와 교정만 | **G2**(작음): 사람이 행과 배치를 읽는다 |
| 4 구현+배선 | 합친 에이전트 하나 | Kotlin 구현 · 어댑터 · 실험 스위치 | 빌드 · `phpseam check/lint/callers` · **`phpseam fields`** |
| 5 `slicecheck` | 스크립트, 오케스트레이터는 숫자만 읽음 | dual 캡처 → 집계 → migrated 캡처 → 기준선 비교 → **독 주입 비교** → (있으면) 레거시 본문 실행 0 → 토글 legacy | `state.json` 회차/상한, 상한 도달 시 사용자 |
| 6 감사 | 감사자 | 5 가 초록일 때만; 판정 어휘 닫힘; 재진입은 `boundary-audit` 모드 A 로 싼 재감사 | PASS / 판정 |
| 7 마감 | 스크립트 + 진화자 | `state.json` 종료 기록 · 저널 · 컨텍스트 델타 제안 → 사람 diff 승인 | 미해결 OS 결함 0 |

사람 게이트는 여전히 둘이지만 둘 다 한 페이지 분량이라 실제로 읽힌다. 에이전트 파견은 계획 1 · 분석 1 · 설계 1 · 구현 1 · 감사 1 · (N 슬라이스마다 서기 1), 곧 5~6회다.

### 7-3. 성장 규칙

(1) 장치 하나는 관찰된 실패 하나에 대응한다. (2) 설계 정본에 먼저 적힌다. (3) 장치가 대체하는 산문은 같은 변경에서 지운다. (4) 지시 파일 상한을 넘기면 무엇을 지울지 먼저 정한다. (5) 스킬을 고칠 때는 교훈 31개와 도구 결함 7개로 만든 평가 세트를 먼저 돌린다.

## 8. 순서

1. **살아있는 노출부터.** `guard-company-content.py` 가 `git commit -am` 과 `git push` 를 통과시키는 것, `redaction.json` 이 없으면 조용히 꺼지는 것, 주입 훅이 넘칠 때 `team-boundary.md` 를 먼저 버리는 것. 셋 다 한 파일 수정이다.
2. **설계 정본 먼저.** 09-09 실행의 변경 이력 행, `goal-loop` 항목, 그리고 이 문서의 v3 절을 정본에 옮긴다. 저장소 자신의 규칙이다.
3. **축소 구현.** `slicecheck` + `state.json` + 상태 줄 · 구현자와 스왑 담당 병합 · JSONL 원장과 검증기 · 영역 설계 · 저널과 진화자 · `phpseam fields` · 잡음 바닥 · Phase 0 검증 셋 · 읽는 곳 없는 산출물 제거 · 중복 산문 삭제 · `표면 유지` 를 실제 값으로.
4. **실패한 슬라이스의 한 페이지로 시험.** Phase 1~6 산출물이 있고 결함 둘이 정답지다. 새 검사가 빨간불을 켜는지 먼저 본다(6장 (5)). 여섯 축을 전부 기록한다. 그것이 아직 안 된 비교 실험이다.
5. **같은 영역의 두 번째 페이지.** 영역 설계가 실제로 비용을 나누는지, 저널이 무엇을 바꿨는지 잰다.

## 9. 사용자가 정해야 할 것

1. 첫 시험을 실패한 슬라이스의 기존 산출물에서 시작할지(정답지가 있다), 새 페이지로 할지.
2. Xdebug 를 지금 컨테이너에 붙일지, `slicecheck` 가 먼저 돌아간 뒤 붙일지. 컨테이너 변경이 필요하다.
3. 원장 형식을 JSONL 로 바꿀지. 기존 슬라이스의 Markdown 원장은 변환이 필요하다.
4. 레드팀을 기본 0 으로 둘지. 두 실행에서 레드팀이 더한 행이 뒤에서 무엇을 잡았는지 기록이 없다는 것이 근거이고, 반대 근거는 v1 회고의 "네 라운드가 겹치지 않는 규칙 8·8·6·7 을 찾았다"이다.
5. 이 문서를 어디에 둘지. 지금은 `docs/reviews/` 에 추적되지 않은 채 있다.
