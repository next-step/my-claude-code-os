# Day2 필수 2 — 컨텍스트 주입 A/B 동작 비교

> 목적: `.claude/context/` 컨텍스트가 스킬·에이전트 동작을 **실제로 바꾸는지** 검증한다.
> 방법: 같은 입력을 `classifier` 서브에이전트에 두 번 준다. A = 컨텍스트 읽고 판단(정상),
> B = `.claude/context/` 와 `maintenance/capacity.md` 를 읽지 말고 요청문 + 일반 지식만으로 판단.
> 대상 스킬: `classifier` — `team-capability.md`(@import 항상 로드) + `classification-policy.md`
> + `sizing.md`(Lazy Read) + `capacity.md` 를 한꺼번에 소비하고, 출력이 구조화돼 차이가 보인다.
> 측정일: 2026-09-07

## 라운드 1 — "게시판을 iOS/Android 네이티브 앱으로 다시 만들어 스토어 출시"

| 항목 | A (컨텍스트 ON) | B (컨텍스트 OFF) |
| --- | --- | --- |
| 판단 | outsource | outsource |
| 규모 | L | L |
| **신뢰도** | **높음** | **낮음** |
| 근거 성격 | `team-capability.md` "범위 밖 — 기본 외주" 목록에 **모바일 네이티브·디자인이 명시적으로 해당** (결정론적) | "별도 역량이 필요할 가능성이 크다", "보통 전문 벤더가 담당" (확률적 추측) |
| **적용한 기준(인용)** | **8개** — `§0`, `§1②`, `team-capability 범위밖`, `sizing.md`, `§1④`, `§2`, `§3`, `capacity.md` | **없음** — 본인이 "정식 절차로는 감사 불가"라고 명시 |
| 확인이 필요한 점 | 구체적·실행가능 — 백엔드 API 작업만 떼어내 internal 처리 가능한지, `§3` 차월 이관 후보, 스토어 개발자 계정 주체 | 자기 한계 나열 — "classification-policy 트리 적용 못 함", "team-capability 미확인 → **판단이 뒤집힐 수 있음**", "sizing 루브릭 없이 추정" |
| 도구 호출 | 5회 (context 파일 실제 Read) | 0회 |

**해석**: 최종 판단(label)은 같다 — 모바일 네이티브가 워낙 명백한 범위 밖이라 일반 지식만으로도 outsource로 떨어진다.
그러나 A는 규칙을 가리키며 **확신**하고, B는 **운 좋게 맞은 추측**이다. B 스스로 "팀에 네이티브 개발자가 있으면 판단이 뒤집힐 수 있다"고 인정한다.

## 라운드 2 — "사내 SSO(OAuth 2.0, Keycloak) 로그인 연동, POST /posts 인증 게이트"

| 항목 | A2 (컨텍스트 ON) | B2 (컨텍스트 OFF) |
| --- | --- | --- |
| 판단 | internal | internal |
| **규모** | **L** | **M** |
| 신뢰도 | 중간 | 중간 |
| **판단 경로** | `classification-policy.md §0 선판정` — "보안 예외 처리, 권한·계정 정책 → internal(사내 IT팀 직접 수행)". `§1 ①`에서 **즉시 종료** | "표준 OIDC 리소스 서버 패턴, 라이브러리 지원, 변경 표면 작음" → **다른 이유로** internal |
| 적용한 기준(인용) | 6개 — `§0`, `§1①`, `§2`, `§3`, `sizing.md`, `team-capability.md` | 없음 |
| 규모 근거 | `sizing.md` "두 등급 사이면 큰 쪽 + 신뢰도 하향" → L | 근거 없이 M ("변경 표면이 작다") |
| 놓친 것 | — | `§0`의 "보안은 사내에서 처리" 라우팅 규칙 자체를 모름. "Keycloak 관리 주체가 외주사일 수도 있다"고 열어둠 |

**해석**: 여기도 최종 판단은 우연히 같지만, **판단에 이른 경로가 완전히 다르다.**
A2는 "우리 회사는 보안·계정 정책을 무조건 사내에서 한다"는 **회사 고유 규칙**(`§0`)으로 1초 만에 결론냈다.
B2는 그 규칙의 존재조차 모르고 "OIDC는 일반적으로 쉬우니까"라는 일반론으로 우회했다.
회사 정책이 일반 상식과 어긋나는 지점에서는 B가 반드시 틀린다 — 이번엔 label이 겹쳤을 뿐이다.
규모도 갈렸다: A2는 루브릭 적용으로 L, B2는 감으로 M.

## 라운드 3 — "관리자 대시보드를 React SPA로 새로 만들어달라"

| 항목 | A3 (컨텍스트 ON) | B3 (컨텍스트 OFF) |
| --- | --- | --- |
| **판단** | **outsource** | **internal** |
| 규모 | L | L |
| 신뢰도 | 중간 | 낮음 |
| 판단 근거 | `team-capability.md` 부분대응 표 "안 하는 것 → **SPA(React/Vue) 신규 구축, 복잡한 상태관리**" 에 정면 해당. `§1③` 범위 밖 → outsource 쪽으로 강하게 + `§1④` (범위 밖 + L) → outsource | "React SPA는 범용 기술이고 외부 벤더를 강제할 도메인 특수성·독점 기술·계약 제약이 없다. 우리 저장소 코드라 관리 주체가 명백히 우리다" → internal |
| 적용한 기준(인용) | 11개 (`§0`~`§4`, `team-capability` 부분대응·주력, `sizing.md`, `capacity.md`) | 없음 |
| 스코프 제안 | 프론트 SPA = 외주 / 백엔드 통계 엔드포인트(Flask·pytest, 주력) = internal 분리 | (동일하게 트랙 분리 제안) |

**해석**: **드디어 최종 판단(label)이 갈렸다** — A3 = outsource, B3 = internal.
차이의 원인은 오직 하나, `team-capability.md` 에 적힌 "우리는 SPA 신규 구축을 하지 않는다"는 **회사 고유 사실**이다.
이건 일반 소프트웨어 지식으로는 알 수 없다 — React 대시보드는 상식적으로 "평범한 프론트 작업 = 내부 처리"다.
B3 도 "React가 팀 주력 스택인지 확인되지 않았다 — 아니라면 프론트는 outsource" 라고 **불확실성은 감지**했지만,
근거 문서가 없으니 "우리 코드 + 범용 기술 = internal" 이라는 기본값으로 떨어졌다.

> 참고: A3·B3 **둘 다** "엔드포인트 2~3개" 는 과소평가(`created_at`·작성자·인증 체계 부재로 선행 작업이 큼)라고 잡아냈다.
> B가 무능한 게 아니다 — **회사 규칙이 일반 상식과 갈리는 지점에서만** 어긋난다.

| 3 | 판단 경로 | 회사 고유 규칙(`§0` 등)으로 결론 | 일반론으로 우회 — 정책이 상식과 다른 지점에서 어긋남 |
| 4 | 규모 루브릭 | `sizing.md` "애매하면 큰 쪽으로" 일관 적용 | 매번 감으로 M/L 오락가락 |

> **교훈**:
> 1. 쉬운 입력(라운드 1·2)에서는 label 이 우연히 겹친다. 이때도 컨텍스트는
>    "같은 답을 **근거 있고·감사 가능하고·재현되게**" 만든다 — 신뢰도, 인용, 규모 루브릭.
> 2. **회사 규칙이 일반 상식과 갈리는 입력(라운드 3)에서는 label 자체가 뒤집힌다.**

>    이게 없으면 classifier 는 "우리 코드 + 범용 기술 = internal" 로 오분류한다.
> 3. 컨텍스트 주입은 "AI를 더 똑똑하게" 가 아니라 "**우리 조직의 판단 기준을 AI에 이식**" 하는 것이다.

## 부수 발견 — 필수 1 배선 검증

- A·A2·A3 모두 도구 호출 5~8회로 `classification-policy.md`·`team-capability.md`·`sizing.md`·`capacity.md` 를
  **실제로 Read** 했다 → `classifier.md` 의 "판단 전 반드시 Read 할 것" 지시(Lazy 주입)가 작동함이 확인됨.
  (B·B2·B3 는 "Read 하지 마라" 지시를 지켜 context 파일을 안 읽음 — 주입 차단도 정상 동작.)
- 이번에 새로 추가·배선한 **`sizing.md`** 가 A·A2·A3 세 번 모두 `적용한 기준` 에 인용됨 → 필수 1의 배선이 실제로 소비됨을 입증.
- `team-capability.md`(@import 항상 로드) 도 세 라운드 전부에서 인용됨. 특히 라운드 3의 판단을
  뒤집은 결정적 근거가 이 파일의 "부분대응 → 안 하는 것" 표였다.
- **갭 발견 → 채움**: A2·A3 가 "`sandbox/board` 의 관리주체·담당 벤더가 문서로 확인 불가 → 추측으로 대체"
  를 지적. `.claude/knowledge/systems/board.md` 부재가 원인이었음.
  → **이후 `board.md` 생성** (내부 관리·벤더 없음·스택·REQ-001 이력). 이제 `classifier` §1② 가
  추측이 아니라 조회가 되고, `context/README.md` 의존 표 + 배선 검사(`check-context-wiring.sh`)에 포함됨.
  (A/B 는 재실행하지 않음 — 발견 자체는 유효하고, 채운 뒤 배선만 확인.)

## 재현 방법 (classifier A/B)

`classifier` 서브에이전트에 아래 프롬프트로 각각 요청:

- **A**: "너의 정의(`.claude/agents/classifier.md`)대로 context 파일을 Read 하고 판단하라"
- **B**: "`.claude/context/` 와 `maintenance/capacity.md` 를 절대 Read 하지 마라. 요청문 + 일반 지식만으로 판단하고 `적용한 기준` 은 비워라"

입력(요청 원문 + 접수 정리)은 라운드별로 동일하게 고정.

# 스킬 레벨 정량 비교 — `/spec` ± `dod-patterns.md` (skill-creator)

> 과제 문구의 "`/skill-creator` 로 비교" 를 이행. `skill-creator@claude-plugins-official` 플러그인 설치 후
> 그 워크플로(병렬 실행 → assertion 채점 → 벤치마크 → 블라인드 comparator)로 진행.
> 위 classifier A/B 는 "컨텍스트가 왜 중요한가" 서사, 이 절은 "스킬 하나에서 컨텍스트 파일 유무의 정량 효과".

## 설정

| | 버전 A (컨텍스트 O) | 버전 B (컨텍스트 X) |
| --- | --- | --- |
| 스킬 | 현행 `.claude/skills/spec/SKILL.md` | A 복제본에서 **딱 한 줄 제거**: "완료 기준 작성 전 `dod-patterns.md` 의 패턴·안티패턴을 따른다" |
| 공통 | 둘 다 `spec/SKILL.md` 의 "완료 기준을 '잘 동작함' 같이 모호하게 쓰지 않는다 — 측정 가능해야" 인라인 규칙은 **유지** |
| 테스트 입력 | 게시판 요청 3개 고정 (제목 부분검색 `?q=` / body 5000자 상한 / `GET /posts/count`) |
| 측정 | `/spec` 이 쓰는 **완료 기준의 검증 가능성** (입력·명령·정확한 기대값이 있어 `/verify` 가 바로 실행 가능한가) |
| 실행 | eval 3개 × A·B = 서브에이전트 6개 병렬. 각자 SKILL.md 따라 "4. 스펙" 작성 |

## 정량 결과

### ① assertion 채점 (객관 규칙 7개: 번호매김 / 모호표현 없음 / 실행명령 포함 / 정확한 상태코드·JSON / 회귀 확인 / 범위 밖 존재 / eval별 엣지)

| | 통과율 | 평균 토큰 | 평균 시간 |
| --- | --- | --- | --- |
| A 컨텍스트 O | **21/21 (100%)** | 44,013 | 108s |
| B 컨텍스트 X | 20/21 (95%) | 39,744 | 89s |
| **델타 (A − B)** | **+4.8%p** | **+4,269** | **+18s** |

→ assertion 은 거의 다 통과(비변별적). B의 인라인 규칙만으로도 기본기는 나옴. 컨텍스트 비용은 실행당 **토큰 +4.3k · 시간 +18s** (파일 Read 오버헤드).

### ② 블라인드 comparator (심판 3명, 각 eval의 A·B를 X/Y 로 섞어 제시 — 어느 게 무엇인지 모름)

| eval | 심판 판정 | 검증가능성 점수 (승 vs 패) | 완료 기준 개수 (승 vs 패) |
| --- | --- | --- | --- |
| body 5000자 상한 | **A 승** | 9 vs 8 | 13 vs 10 |
| `GET /posts/count` | **A 승** | 9 vs 7 | 10 vs 8 |
| 제목 부분검색 `?q=` | **A 승** | 9 vs 6 | 11 vs 10 |

→ **3/3 모두 컨텍스트 O 승.** 점수 격차 +1 ~ +3.

## 심판이 A를 고른 이유 (반복된 패턴)

- **기대값을 정확히 못박음** — 응답 바디 전체/고정 id(`[1,2,3]`)/JSON(`{"count": 0}`)/pytest exit code. B는 "개수 기반"("앞 2건", "전체")이라 검증자가 스스로 추론해야 함.
- **실행 가능한 명령을 항목에 붙임** — `grep -c "q=" README.md → 1 이상`, `git diff` 로 기존 테스트 무수정 확인, `12 passed → 16 passed`. B는 "문서에 설명이 있다", "기존 테스트 통과" 수준.
- **엣지 케이스를 완료 기준으로 승격** — 빈 저장소 + `?q=`, 한글 5000자 경계, off-by-one 전용 항목. B는 구현 접근 산문에만 언급하고 검증 항목엔 없음.

이 3가지가 정확히 `dod-patterns.md` "패턴 카탈로그" + "안티패턴" 이 시키는 것.

## 결론

- **컨텍스트 파일이 완료 기준의 검증 가능성을 일관되게 끌어올린다** — 블라인드 3/3, 격차 +1~+3점.
- 다만 "천지차이"는 아니다. `/spec` 이 이미 "모호하게 쓰지 마" 인라인 규칙을 갖고 있어 B도 통과율 95%. → **`dod-patterns.md` 의 값은 "0을 1로" 가 아니라 "7을 9로"**. classifier A/B(정책 파일 없으면 감사 불가·label flip)와는 효과의 성격이 다르다.
