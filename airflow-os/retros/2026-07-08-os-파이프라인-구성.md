## 무엇을
OS.md 7단계 청사진을 실제 스킬/서브에이전트로 구현하고 여러 차례 다듬었다.
- 신규: `airflow-pipeline`(오케스트레이터), 워커 3종 `dag-builder`/`dag-tester`/`dag-reviewer`, `retro`(회고)
- 이동: `interview`를 전역 → 내부로
- 통합: 기존 `local-airflow-admin`(로컬 Airflow 3.2.2 venv 인프라)을 파이프라인 ③테스트와 연결
- 커밋: 23a3cb1 ~ 96d645a

## 왜 (결정과 트레이드오프)
- **스킬 vs 서브에이전트 경계**: 사람이 개입하는 지점(①설계=interview, ⑤승인, ⑦회고)은 스킬(메인 컨텍스트), 자체적으로 도는 loop(②구현·③테스트·④리뷰)는 서브에이전트(격리 워커). 근거 — 사람 개입은 요청·승인 2회뿐이고, 리뷰는 구현과 다른 눈이 필요해 격리가 유리.
- **전역 스킬 안 쓰기**: harness에 전역 로딩 통짜 차단이 없어서, 워커의 `tools`에서 `Skill`을 빼 다른 스킬 호출을 원천 차단 + 오케스트레이터에 "로컬만" 규칙 명시. (config로 개별 off도 가능하나 전역 30개를 다 끄는 건 비현실적이라 배제.)
- **interview 역할 A로 확정**: interview는 설계도 합의까지만, 개발은 호출자(단독=메인, 파이프라인=builder)가 이어받음. "설계 게이트"와 "구현"을 분리해 파이프라인과 충돌 제거.
- **진단-먼저 모드 추가**: 신규는 질문(interview)이 먼저지만, 수정·리팩터는 코드가 이미 있으니 진단(dag-reviewer)이 먼저. reviewer를 ①진단·④검증 앞뒤로 재사용.
- **운영 경로 = 심링크 SSOT**: 운영 코드를 복사하면 stale, 절대경로를 여러 파일에 하드코딩하면 이동 시 산탄. `prod-airflow` 심링크 + `.gitignore`로, 절대경로는 `setup.sh`의 `PROD_AIRFLOW_REPO` **한 줄**에만 남김.

## 발견 / 배운 점
- **문서가 실제 흐름을 못 따라간 사례**: 리팩터링 실전에서 이미 "코드 먼저 읽고 안티패턴 뽑은 뒤 범위만 질문"(=진단 먼저)으로 흘렀는데 스킬 문서엔 interview(질문)만 앞단이라 적혀 있었다. 실행이 설계보다 앞서 있었고, 그걸 뒤늦게 문서로 굳혔다.
- **도구 자신의 낡은 API**: `verify.sh`가 검증 대상이 아니라 자기 자신이 deprecated `airflow.models.dagbag`를 import 중이었다(→ `airflow.dag_processing.dagbag`). 검증 도구도 검증 대상이다.
- **Airflow 3.2.2 이관**: `PythonOperator`는 `airflow.providers.standard.operators.python`에서 import(구 `airflow.operators.python`은 deprecated, provider는 코어에 이미 존재).
- **심링크를 처음엔 과소평가**: "심링크는 절대경로 박혀 머신 종속"이라 비추했으나, `.gitignore`와 조합하면 머신별로 각자 걸어 그 단점이 사라진다. 사용자 제안이 더 나았다.

## 다음에 재사용할 것
- 새 워커(서브에이전트)는 `tools`에서 `Skill` 제외로 격리. 새 스킬은 로컬 `.claude`만 참조.
- 운영 절대경로가 필요하면 `setup.sh`의 `PROD_AIRFLOW_REPO` 한 곳만 보고/고친다. 나머지는 `prod-airflow/` 상대경로. 새 환경은 `setup.sh`가 심링크를 생성.
- 수정·리팩터 요청은 `airflow-pipeline`이 `dag-reviewer` **진단**부터 태운다(질문이 아니라 코드 읽기가 먼저).
- 리팩터링은 "동작 보존 vs 안티패턴 제거"가 충돌하는 지점을 ①에서 먼저 합의(동작이 바뀌는 항목은 순수 리팩터가 아니다).
- Airflow 3.x import 경로 주의: `PythonOperator`(providers.standard), `DagBag`(dag_processing).
