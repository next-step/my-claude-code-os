# airflow-os

## 코드 위치
- 실제 운영 DAG는 `prod-airflow/dags/` (심링크 → ops repo). 로컬 `dags/`엔 샘플뿐.
- Glob/Grep은 심링크를 기본으로 안 따라감 → `find -L prod-airflow/dags -name "*.py"`로 찾거나 경로를 직접 Read.

## 작업 라우팅
- DAG 작업은 파일부터 열지 말고 스킬로 라우팅: 
	- 리팩터·개선·리뷰 → dag-audit
	- 신규 → interview
	- 전 과정 → airflow-pipeline
- OS 전체 설계·파이프라인 구조는 OS.md 참고.

## 작성 규칙 (컨텍스트·스킬·서브에이전트)
- **공유 지식은 컨텍스트 파일 한 곳에.** 여러 스킬·서브에이전트가 같은 규칙을 쓰면 `.claude/context/`의 한 파일에 두고 참조한다. 복붙하지 않는다.
- **참조는 이름으로.** 번호·개수·순서로 가리키지 않는다(`(2번)`, `1~7` 금지). 항목 이름(`멱등성`)으로 가리켜야 목록이 바뀌어도 안 깨진다.
- **참조처에 내용을 재나열하지 않는다.** "그 파일 봐라"까지만. 목록을 요약해 다시 적으면 관리 포인트가 둘이 된다.
- **산출물에 편집 사유·해설을 남기지 않는다.** "여기 개수를 박지 않는다" 같은 왜-이렇게-썼는지 주석은 금지. 지시문·지식만 깨끗하게. 결정의 배경은 OS.md나 `learnings/`에.
- **description은 자기 자신만 설명한다.** 다른 스킬·에이전트 이름이나 파이프라인 step 번호(②③⑤)를 넣지 않는다 — 라우터가 모든 description을 보고 조합하므로 서로 가리킬 필요 없다. 누가 누구를 부르는지는 본문·OS.md 몫.
- **본문은 자기가 호출·사용하는 것만 이름 부른다.** 나를 부르는 쪽·내 산출물을 소비하는 쪽·비유는 이름 안 쓴다(그 관계는 상대나 오케스트레이터가 소유). 오케스트레이터만 자기 워커·단계를 이름으로 부른다.
