# airflow-pipeline — Airflow OS 오케스트레이터

`OS.md`의 7단계 파이프라인을 조율하는 **진입점**이다. 사람은 요청과 승인만, 나머지 loop는 이 스킬이 워커들을 시켜 돌린다.

## ⚠️ 스킬 격리 규칙 (반드시 지킴)
- 이 파이프라인은 **이 프로젝트 로컬 `.claude/` 안의 자산만** 사용한다: 스킬 `interview`·`lab`, 서브에이전트 `dag-builder`/`dag-tester`/`dag-reviewer`.
- **전역(`~/.claude/skills`) 스킬을 호출하지 않는다.** 비슷한 이름의 전역 스킬이 있어도 무시하고 로컬 것만 쓴다.
- 워커 서브에이전트들은 `Skill` 도구가 없어 다른 스킬을 부르지 못하도록 이미 격리돼 있다.

## 흐름

```
[사람] 요청
   ↓
① 진입   → [신규]      interview로 설계 합의 (백지 → 질문이 먼저)
   ↓        [수정·리팩터] dag-reviewer로 현재 코드 진단 → 범위 합의 (코드 존재 → 진단이 먼저)
② 구현   → dag-builder 서브에이전트. 설계도/개선목록을 코드로
   ↓
③ 테스트 → dag-tester 서브에이전트. FAIL이면 원인을 담아 ②로 되돌림
   ↓        (PASS까지 ②↔③ 반복)
④ 리뷰   → dag-reviewer 서브에이전트. BLOCKER 있으면 ②로 되돌림
   ↓        (리뷰 통과까지 반복)
⑤ 승인   → 여기서 멈춘다. 설계·코드·테스트·리뷰 결과를 요약해 사람에게 승인 요청 (유일한 수동 게이트)
   ↓
⑥ 배포   → (미구현) 승인 후 자리표시. 배포 정의가 정해지면 dag-deploy 스킬로
⑦ 회고   → retrospective 스킬. 이 작업의 결정·발견을 learnings/에 기록 (재사용 축적)
```

## 단계별 실행 지침

### ① 진입 — 신규는 질문, 수정·리팩터는 진단 (모드 분기)
요청이 **신규 생성**인지 **기존 코드 수정·리팩터**인지 먼저 판별한다. 시작 상태가 다르므로 앞단이 갈린다.

**[신규 생성] — interview 스킬**
백지 상태(소스·목적지·스케줄 미정)라 없는 정보를 질문으로 채운다. `interview`를 실행해 **DAG 설계도에 사용자 OK**를 받는다. interview는 OK 시 **`designs/<dag_id>.md`** 로 설계도를 떨군다 — ②에는 설계도 텍스트가 아니라 **그 파일 경로**를 넘긴다(워커가 Read).

**[수정·리팩터] — dag-reviewer로 진단 먼저**
코드가 이미 있으니 물어볼 게 아니라 봐야 한다. `dag-reviewer`를 **진단 모드**로 호출해 대상 코드의 문제·개선점을 목록화한다(각 항목에 "고치면 동작 보존/변경" 표시). 그 목록을 사람에게 보여주고 **범위만 합의**한다(질문은 최소 — 리팩터에서 되돌리기 어려운 것은 "동작이 바뀌는 수정"이므로 그 경계만 확인). 합의된 개선목록을 **`designs/<dag_id>.md`에 파일로 떨궈** ②에 그 경로를 넘긴다 — 대화 텍스트로만 넘기지 않는다(격리 워커는 대화를 못 봄).

> reviewer를 앞뒤로 쓴다: ①에서 "현재 코드 진단", ④에서 "고친 코드 검증". 같은 리뷰 역량이다.

어느 모드든 **사용자 OK 없이는 ②로 넘어가지 않는다**(게이트).

### ② 구현 — dag-builder
**파일 경로 `designs/<dag_id>.md`**(신규=설계도 / 수정·리팩터=합의된 개선목록)를 dag-builder 서브에이전트에 전달한다. 재검증 루프면 테스터/리뷰어가 돌려보낸 지적을 함께 넘긴다.

### ③ 테스트 — dag-tester
구현된 파일 경로 + 설계도 **파일 경로 `designs/<dag_id>.md`**(신규)를 dag-tester에 넘긴다. dag-tester는 `lab`의 `verify.sh`로 파싱 검증한다.
- **먼저 로컬 env가 준비돼 있어야 한다.** dag-tester가 "env 미구축"으로 반환하면, 여기(메인)서 `lab` 스킬을 실행해 setup한 뒤 ③을 재시도한다(워커는 스킬을 못 부르므로 구축은 오케스트레이터 몫).
- **FAIL이면 실패 내역을 그대로 dag-builder에 다시 넘겨 ②로 되돌린다.** PASS까지 반복. 무한루프 방지: 같은 실패가 3회 반복되면 멈추고 사람에게 상황을 보고한다.

### ④ 리뷰 — dag-reviewer
테스트를 통과한 코드를 dag-reviewer에 넘긴다. **BLOCKER가 있으면 ②로 되돌린다.** WARN은 사람이 승인 단계에서 판단하도록 요약에 남긴다. 리뷰 통과까지 반복(같은 지적 3회 반복 시 사람에게 보고).

### ⑤ 승인 — 사람 게이트 (멈춤)
loop가 끝나면 한 화면에 요약해 승인을 요청한다:
```
## 승인 요청
설계:   <dag_id, 스케줄, task 그래프 요약>
구현:   <작성/수정 파일>
테스트: PASS (<핵심 검증 항목> / 런타임 미검증 항목 있으면 명시)
리뷰:   통과 (남은 WARN/NIT 있으면 목록)
```
승인/반려를 사람이 판단한다. 반려 사유가 있으면 해당 단계로 되돌린다.

### ⑥ 배포 — 미구현
아직 만들지 않았다. "배포는 정의 미정 — 필요 시 별도 진행"이라고 안내한다.

### ⑦ 회고 — retrospective 스킬
승인이 끝나면 `retrospective` 스킬을 **제안**한다(강제 아님). 사용자가 원하면 이 작업의 결정·트레이드오프·발견을 `learnings/`에 기록해 다음 작업이 재사용하게 한다. 남길 게 없는 사소한 작업이면 건너뛴다.

## 원칙
- 사람 개입은 **처음(요청)과 ⑤(승인)** 두 번뿐. 가운데 ②↔③↔④ loop는 워커들이 자체적으로 돈다.
- 되돌림은 항상 **원인을 담아** 이전 단계로. 워커에게 "다시 해"가 아니라 "무엇이 왜 틀렸으니 고쳐라".
- 각 단계는 단독으로도 호출 가능하다. 이 스킬은 "처음부터 끝까지"를 원할 때의 조율자다.
