# sync — OS 자기점검 (작업 ↔ 스킬 대조)

이 OS는 **OS.md(청사진) ↔ 스킬 ↔ 서브에이전트 ↔ 실제 산출물(dags·learnings)** 이 서로 맞물려 있다. 하나를 바꾸면 그걸 참조하는 다른 곳이 조용히 어긋난다. 이 스킬은 그 어긋남을 **작업 전 코드가 아니라 OS 자신을 대상으로** 찾아낸다.

감사 대상이 DAG 코드가 아니라 스킬·에이전트·청사진 사이의 정합성이라는 게 핵심이다.

## 두 종류의 드리프트 (사용자가 잡고 싶어 한 것)

| 종류 | 정의 | 예 |
|---|---|---|
| **불일치** | 산출물과 스킬이 서로 다르게 말함 | 스킬은 "dag-reviewer 진단 모드"를 부르는데 에이전트 파일엔 그 모드가 없음 |
| **미반영** | 작업/구조는 바뀌었는데 스킬에 안 들어감 | retrospective에 "다음엔 이렇게" 남겼는데 어떤 스킬에도 반영 안 됨 / 커밋으로 구조를 바꿨는데 그걸 참조하는 스킬은 그대로 |

## 무엇을 대조하나 (대조 축)

산출물 **전체**를 훑어 아래 축을 교차 점검한다. 각 축은 "A가 말하는 것 == B의 실제인가?"를 본다.

1. **스킬 ↔ OS.md 청사진** — 각 스킬이 OS.md의 단계(①~⑦)·설계결정과 여전히 일치하나? OS.md엔 있는데 스킬로 없는 단계, 스킬엔 있는데 청사진에 없는 개념.
2. **스킬 ↔ 서브에이전트** — 스킬이 부르는 에이전트(dag-reviewer·dag-builder·dag-tester)가 실제로 존재하고, 스킬이 설명하는 역할·모드·도구가 `.claude/agents/*.md`와 맞나? (존재하지 않는 에이전트/모드를 부르면 **높음**.)
3. **스킬 ↔ 스킬 (상호참조)** — A 스킬이 B 스킬을 언급·연결하는데(예: airflow-pipeline→retrospective, dag-audit→airflow-pipeline) 그 설명이 B의 실제와 맞나? 끊긴 참조.
4. **스킬 ↔ 실제 산출물/컨벤션** — 스킬이 규정한 경로·네이밍·규칙(예: retrospective의 `learnings/<date>-<dag_id>.md`)을 실제 파일·폴더가 따르나? dags/tests 구조가 스킬 설명과 맞나?
5. **산출물/변경 ↔ 스킬 미반영** — learnings(특히 `os-improvement`)에 남긴 결정·"다음에 재사용할 것" 중 스킬에 반영됐어야 하는데 안 된 것. (범위를 좁히려면 최근 커밋으로 바뀐 파일을 참조해도 되지만, 기본은 산출물 현재 상태 기준.)

## 흐름

1. **범위 확인** — 기본은 `airflow-os` 전체(OS.md, `.claude/skills/*`, `.claude/agents/*`, `dags/`, `tests/`, `learnings/`). 사용자가 특정 스킬/축만 원하면 좁힌다.
2. **격리된 대조 패스** — `general-purpose` 서브에이전트로 대조를 돌린다. 이 스킬을 부른 메인 컨텍스트의 가정을 그대로 들고 가면 "당연히 맞겠지"로 놓치므로, **분리된 눈**으로 위 5개 축을 훑게 한다. 서브에이전트에는 이 축 목록과 "각 발견마다 두 파일의 실제 문구를 인용하라"를 전달한다.
3. **정리해 보고** — 반환된 발견을 심각도 순으로 리포트(아래 형식). 어긋난 데가 없으면 "드리프트 없음"이라고 명시.
4. **수정 제안** — 발견마다 "어느 파일을, 어느 방향으로" 고치면 되는지 구체적으로 제시한다. **적용은 사람이 승인**한 뒤에만 한다(이 스킬은 제안까지).
5. **다음 안내** — 승인되면 그때 스킬/에이전트/OS.md를 고친다. 구조를 실제로 바꿨으면 `retrospective`(os-improvement)로 남기라고 안내한다.

## 리포트 형식

```
## OS 드리프트 리포트 (범위: <범위>)

### 🔴 높음
- [불일치/미반영] <한 줄 요약>
  - 대상: <파일 A> ↔ <파일 B>
  - 근거: A는 "<인용>", 그런데 B는 "<인용>" (또는 B에 없음)
  - 왜 문제: <끊긴 참조/모순이 부르는 실제 혼란>
  - 수정 제안: <어느 파일을 어떻게>

### 🟡 중간
- ...

### 🟢 낮음
- ...
```

심각도 기준:
- **🔴 높음** — 존재하지 않는 에이전트/모드/스킬 호출, 명백한 모순, 끊긴 상호참조.
- **🟡 중간** — 설명이 실제와 다름, 반영됐어야 할 결정 미반영.
- **🟢 낮음** — 사소한 문구·네이밍·오래된 예시.

## 원칙

- **읽기·제안만.** 스킬/에이전트/OS.md를 마음대로 고치지 않는다. 수정은 사람 승인 뒤.
- **근거 없는 지적 금지.** 발견마다 두 파일의 실제 문구를 인용한다("~일 것 같다"는 안 됨). 애매하면 "판단보류"로 남기고 사람에게.
- **방향을 단정하지 않는다.** 불일치는 산출물이 맞을 수도, 스킬이 맞을 수도 있다. 어느 쪽이 정답인지는 사람이 정한다 — 스킬은 어긋남과 양쪽 문구만 제시.
- **미반영에 특히 민감하게.** "작업했는데 스킬에 안 넣고 넘어간 것"이 이 스킬을 만든 이유다. learnings·구조 변경을 스킬과 꼭 맞대본다.
- 전역 스킬은 쓰지 않는다 — 로컬 산출물만 대조.
