# Interview (Airflow Python 파이프라인 전용)

## 이 스킬이 존재하는 이유

이 사용자는 계획을 길게 세우기보다 아이디어를 빠르게 던지는 스타일이다. "DAG 하나 만들어줘" 수준으로 짧게 요청할 때가 많다. 모호한 채로 바로 DAG 코드를 짜면 → 엉뚱한 소스/적재방식으로 완성 → 사용자가 도중에 끊고 다시 설명 → 재작업, 이 loop가 반복된다.

이 스킬의 목적은 **코드를 짜기 전에** 그 모호함을 몇 개의 정확한 질문으로 걷어내고, "어떤 DAG를 만들지"를 **설계도(task 이름 + 의존성 그래프)로 합의한 뒤** 시작하는 것이다. 인터뷰가 목적이 아니라 **재작업을 없애는 것**이 목적이다. 질문은 적고 날카롭게, 합의는 눈에 보이는 설계도로.

## 전체 흐름

```
1. 조사       코드·기존 DAG·자산 파악. 단 "설계를 좌우하는 발견"은 조용히 채택하지 말 것
2. 인터뷰(게이트)  체크리스트의 빈칸만 객관식으로. 넓게 훑고 → 적재/멱등성/백필은 깊게
3. 설계 제시   spec + DAG task/의존성 그래프 + 참고자산 확인 + 가정을 보여주고 OK 받기
   ─────────  ⛔ 여기가 이 스킬의 끝. 사용자 OK 없이는 절대 개발로 못 넘어감 (명확화 게이트)
4. 개발(호출자)  사용자가 OK → 개발로. 단 개발은 이 스킬이 하지 않는다(아래 참고)
```

이 스킬은 **1~3(설계 합의)까지만** 담당한다. 3단계에서 사용자 OK가 나면 역할은 끝이고, **개발은 호출자가 이어받는다** — 단독 호출이면 그대로 이어서 구현하고, 오케스트레이터가 불렀으면 그 흐름으로 넘어간다. 게이트는 **체크리스트가 다 차고 + 설계도에 OK가 나야** 열린다.

## 언제 쓰고 언제 안 쓰는가

인터뷰는 사용자의 시간을 쓰는 비용이다. 재작업 비용보다 쌀 때만 한다.

**쓴다:**
- Airflow 결과물을 요구하는데 소스/목적지/스케줄/적재방식/실패처리 중 하나라도 안 잡힘
- "이 데이터 적재하는 DAG 만들어줘"처럼 입출력이 여러 갈래로 해석됨
- 기존 방식 중 뭘 따를지 갈림 (증분 vs 풀, catchup on/off 등)

**안 쓴다 (그냥 진행):**
- 요청이 이미 구체적 (어느 DAG의 어느 task를, 무엇으로 바꿀지 명시)
- 오타 수정, 변수명 변경, 로그 한 줄 추가 같은 사소한 1-스텝
- 사용자가 "일단 해봐 / 알아서" 라고 속도를 명시적으로 택함 → 존중하되, 되돌리기 어려운 것(멱등성 깨지는 적재, 운영 DAG 스케줄 변경)만 하나 확인

애매하면: 되돌리기 어려운 결정이 걸렸는가? 걸렸으면 물어라.

## 1단계 — 조사 (묻기 전에 읽어라)

사용자에게 던지기 전에 답이 이미 있는지 본다. 사용자의 시간을 아끼는 게 예의다.

- 기존 유사 DAG, 공용 오퍼레이터/헬퍼, connection·variable을 읽는다. **이 OS의 실제 DAG 소스는 운영 레포 심링크 `prod-airflow/dags`** 이므로 로컬뿐 아니라 거기도 함께 본다
- 프로젝트 CLAUDE.md, DAG 네이밍·폴더 규칙을 확인한다
- 필요하면 `Explore` / `general-purpose` 서브에이전트로 병렬 조사

**핵심 규칙 — 조사는 질문을 줄이는 것이지, 확인을 없애는 게 아니다.** 발견을 두 종류로 나눈다:

- **설계를 좌우하는 발견** (참고할 기존 DAG, 대상 소스 테이블, 따를 오퍼레이터 패턴) → 절대 조용히 채택하지 말 것. 3단계 설계도에 "이거 참고/사용하려는데 맞나요?"로 박아서 확인받는다. 조사로 헛다리를 짚어도 코드 전에 걸러지도록.
- **사소한 발견** (폴더 구조, 파일 네이밍 규칙) → 조용히 따라도 된다.

기준은 "되돌리기 어려운가?"다. 조사로 풀린 항목은 질문 목록에서 빼고, 안 풀린 것만 2단계로 넘긴다.

## 2단계 — 인터뷰 게이트

### 체크리스트 (이게 다 차야 게이트가 열린다)

각 항목은 "안 물으면 나중에 재작업으로 돌아오는 것"이다. 1단계 조사로 이미 풀린 항목은 건너뛴다.

**넓게 — 한 번씩 훑어 골격을 잡는 항목:**
- **소스 → 목적지**: 어디서 어디 테이블·스키마로? (API/DB/파일 → Doris/StarRocks/… 어느 테이블)
- **트리거/스케줄**: 언제 도나? (cron, 다른 DAG 의존, sensor 여부, catchup on/off)
- **정합성·검증**: 완료를 어떻게 확인하나? 스키마/타입 매핑, 소스-타깃 행수 검증 필요 여부
- **재사용 자산**: 참고할 기존 DAG·오퍼레이터·커넥터가 있나? (1단계 발견을 여기서 확인)

**깊게 — 파이프라인 정확성을 좌우해서 끝까지 파야 하는 항목:**
- **적재 방식 (증분 vs 풀)**: 매번 전체를 다시 넣나(풀), 새로 바뀐 것만 넣나(증분)? 증분이면 → 어떤 시간 컬럼 기준(커서)? late 데이터 대비 lookback 며칠?
- **멱등성 (재실행 안전)**: 같은 날짜를 재실행/백필/retry 했을 때 데이터가 중복되면 안 된다. 어떻게 막나? (키 기준 upsert / 파티션 delete-then-insert 등)
- **백필**: 과거 데이터를 채워야 하나? 범위는? catchup 자동 vs 수동 backfill?

> 용어가 부담되면 쉬운 말로 풀어서 물어라. 예: "재실행하면 데이터가 중복될 수 있는데 어떻게 막을까요? (A) 키 기준으로 덮어쓰기 (B) 그 날짜 먼저 지우고 넣기"

### 질문하는 법 — 객관식 우선, 3~5개로 압축

`AskUserQuestion`으로 묻는 것을 기본으로 한다. 선택지를 주면 사용자가 빠르게 고르고, 각 선택지의 trade-off도 미리 보여줄 수 있다.

- 한 번에 **가장 중요한 3~5개**만. 사소한 건 합리적 기본값으로 정하고 설계도에 "이렇게 가정했다"로 적는다.
- 각 질문에 **추천 기본값**을 첫 선택지로 두고 "(추천)"을 붙인다. 사용자가 판단을 위임해도 진행이 멈추지 않게.
- 진행도를 알려주면 게이트가 언제 열리는지 명확하다. 예: "핵심 7개 중 5개 확인됨, 2개만 더요."
- 사용자가 "그냥 네가 정해"라고 하면 즉시 멈추고, 남은 항목은 기본값으로 채워 3단계로 넘어간다.

5개를 넘기고 싶으면, 넘기는 대신 나머지를 기본값으로 정하고 설계도 단계에서 사용자가 반박할 기회를 준다. 너무 많이 묻는 것은 이 스킬의 실패다.

## 3단계 — 설계 제시 (이게 진짜 게이트)

모은 답을 프로즈가 아니라 **DAG 설계도**로 보여준다. 파이프라인에선 task 이름과 의존성 그래프가 곧 spec이다.

**형식은 `.claude/context/dag-design-spec.md`를 그대로 따른다** — 이 스킬은 그 spec의 **생산자**이고, 소비자(워커)가 같은 형식을 기대한다. 형식을 여기서 바꾸지 말고 spec 파일을 Read해서 그 틀로 출력한다. 각 필드(적재·멱등성·백필)의 안전 기준은 `.claude/context/airflow-antipatterns.md`가 근거다.

> `참고 패턴` 필드는 1단계 조사에서 AI가 찾은 후보다 — 조용히 채택하지 말고 `← 이거 참고하는 거 맞나요?`로 반드시 확인받는다.

사용자가 OK → **합의된 설계도를 `designs/<dag_id>.md` 파일로 떨군다** (`.claude/context/dag-design-spec.md` 형식 그대로, 꺾쇠 자리를 실제 값으로 채워서). 이 파일이 소비자(워커)가 Read할 산출물이다 — 대화 텍스트로만 넘기지 않는다(격리 워커는 대화를 못 봄).

그 뒤 **이 스킬의 역할 종료.** 호출자에게 **설계도 파일 경로**를 넘긴다(단독 호출이면 메인이 그 파일을 근거로 구현, 오케스트레이터면 그 흐름으로). 고치라고 하면 반영해 파일을 갱신하고 다시 짧게 확인한다(한 항목이면 전체 재출력 없이 그 부분만).

## 원칙 요약

- 인터뷰는 재작업을 없애기 위한 것. 인터뷰 자체가 목적이 아니다.
- 묻기 전에 읽어라. 단 설계를 좌우하는 발견은 조용히 채택하지 말고 설계도에서 확인받아라.
- 적게·날카롭게 물어라. 3~5개. 나머지는 기본값 + 명시된 가정.
- 증분·멱등성·백필은 파이프라인 정확성의 핵심이라 끝까지(깊게) 판다. 나머지는 넓게 한 번.
- 항상 추천 기본값을 제시해 진행이 멈추지 않게 한다.
- **DAG 설계도(task+의존성)로 합의하고, 사용자 OK 전에는 코드를 짜지 않는다.** 이 게이트가 헛수고를 막는다.
