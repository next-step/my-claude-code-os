## 이터 1 (FAIL)

- 바꾼 것: `app.py`의 `GET /posts`에 `q`(제목/본문 부분일치, 대소문자무시)·`sort`(asc/desc)·
  `page`·`size` 파라미터와 `X-Total-Count` 헤더를 추가했다. 검사 순서는 sort → page →
  size(타입→값), 필터·정렬 후 슬라이스하고 전체 매칭 개수를 헤더에 담는다.
- 지표: ①정확성 PASS — pytest 52 passed (기존 33 + test_search.py 19), 보호 4개 테스트
  파일 sha diff 통과. judge 채점(②~⑤): 엣지케이스 4, 응답일관성 5, 가독성 5,
  테스트커버리지 1(`test_search_extra.py` 파일 자체가 없어서 최저점) — 4개 중 1개가
  3 미만이라 이터 전체는 **FAIL**.
- 교훈: 구현 자체(로직·스타일)는 이미 첫 시도에 매우 탄탄했다(엣지/일관성/가독성 전부
  4점 이상). 유일한 병목은 `test_search_extra.py`를 아예 안 만든 것 — PROMPT.md가
  "선택 허용"이라고 적어놨지만 ⑤테스트커버리지 축은 그 파일이 없으면 무조건 1점으로
  게이트를 못 넘는다. 다음 이터는 코드 품질을 더 다듬으려 하지 말고, 계약
  (`test_search.py`)에 없는 경계를 스스로 찾아 `test_search_extra.py`에 방어적 테스트를
  작성하는 데 집중해야 한다 — 예: 유니코드 검색어, 삭제로 생긴 id 빈틈에서의 페이지네이션,
  size=100 경계, 같은 쿼리 파라미터 중복, page가 매우 큰 값일 때 빈 배열, q에 특수문자.

## 이터 2 (PASS)

- 바꾼 것: `app.py`는 수정하지 않았다(이터 1 구현이 이미 정확했다고 판단). 대신

  페이지네이션, title/body 중복매칭 dedup, q 리터럴 매칭(정규식 아님), 공백/이모지
  검색어, 관대한 정수 표기(`007`,`+2`)와 거부되는 표기(`2e0`), 중복 쿼리 파라미터(첫
  값 사용), size=100 경계, X-Total-Count가 0건/마지막 페이지 초과 시에도 유지되는지,
  q와 잘못된 sort 조합 시 400 우선순위 등 16개 테스트를 추가했다.
- 지표: ①정확성 PASS — pytest 68 passed(기존 52 + 신규 16), 보호 4개 테스트 파일 sha

  4개 전부 3 이상, 이터 전체 **PASS** (streak=1).
- 교훈: 이터 1에서 지적된 유일한 약점(⑤테스트커버리지=1, 파일 없음)을 `app.py`를
  건드리지 않고 테스트 파일만 새로 작성해서 해결했다 — 구현이 이미 탄탄했다면 코드를
  괜히 리팩터링하지 말고 커버리지 갭만 메우는 게 효율적이었다. 다음 이터(연속 PASS
  2회 필요)도 같은 코드/테스트 조합을 유지하되, 혹시 세부 채점이 흔들릴 수 있으니
  기존 계약과 스타일을 그대로 지키는 방향을 유지할 것.
