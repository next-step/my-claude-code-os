# 회고 — 랄프 루프 실습이 sandbox 코드로 편향될 수밖에 없었던 이유

> Day3 도전과제2(5차원 루브릭 + 2시간 이상 랄프 루프) 진행 중 발견한 구조적 제약.
> `board-search`(1회차) 루프 결과([`board-search/result.md`](board-search/result.md))가
> 근거. `OS.md` §7 열린 질문에서 이 파일을 참조한다.

## 무슨 일이 있었나

`board-search` 루프(검색+페이지네이션+정렬, 게이트 임계 3/5점)는 **8분·3이터 만에
연속 PASS 2회로 성공 종료**했다. 목표였던 "2시간 이상 돌리며 이터레이션별 변화를
관찰"에는 크게 못 미쳤다. 원인은 게이트 통과가 쉬워서가 아니라 — 이터 1부터 코드
품질(엣지케이스 4점·응답일관성 5점·가독성 5점)이 이미 탄탄했고, 유일한 병목은
"테스트커버리지 파일을 안 만들었다"는 산출물 누락 하나였다. 그걸 이터 2에서 채우자
바로 만점이 나왔다.

## 왜 이런 일이 생겼나 — sandbox 대상의 구조적 한계

랄프 루프의 지표는 **셸 exit code 로 기계 판정**해야 한다(`ralph/SKILL.md` "하지 말
것 1"). 그러려면 루브릭 대상이 **pytest 로 검증 가능한 결정론적 계약**을 가진
코드여야 하고, 이 저장소에서 그런 대상은 사실상 `sandbox/board` 뿐이다
(`OS.md` 로드맵 Step 1의 "왜 사내 소스가 아니라 목업으로 첫 완주를 했나" 콜아웃과
같은 이유 — Step 2 "사내 유지보수 요청에 OS 적용"이 아직 미착수).

`sandbox/board` 는:

- 단일 파일(`app.py`), 인메모리 dict 저장소, 외부 의존성 없음.
- 실제 사내 시스템에 있는 레거시 제약·불명확한 요구사항·회귀 위험·권한 체계·
  다른 시스템과의 통합이 전혀 없음.

그래서 **루브릭 대상을 고르는 사람(나)이 "결국 pytest로 명확히 검증되고, 결국
성공할 수 있는" 작업 위주로 설계·지시할 수밖에 없다** — 계약이 모호하면 애초에
①정확성 게이트 자체를 못 만든다. 이건 모델의 능력 문제가 아니라 **대상 선정 단계의
구조적 편향**이다: 실제 유지보수 현장이라면 계약이 처음부터 이렇게 깔끔하게
정의되지 않고, 그 모호함 자체가 반복을 늘리는 요인인데, sandbox 실습에서는 내가
계약(`test_*.py`)을 미리 정확하게 써서 게이트를 만들어야 하니 그 모호함이 애초에
제거된 채로 시작한다.

## 어떻게 대응했나

2회차(`board-comments`)는 대상 난이도를 인위적으로 올렸다 — 중첩 리소스(댓글) +
낙관적 동시성 제어(`If-Match`/`X-Version` 헤더, 기존 PATCH 응답 몸통은 안 바꾸는
제약)를 묶어 계약 자체의 복잡도를 키웠다. 다만 이것도 **내가 설계한 인위적
난이도**이지, 실제 유지보수 요청에서 나오는 난이도(레거시 코드 이해, 요구사항 자체의
불명확함, 회귀 없이 고치기)와는 성격이 다르다는 점은 그대로 남는다.

## 부록 — 2회차(`board-comments`)도 2시간을 못 채운 이유는 다르다

2회차는 대상 난이도를 올렸는데도 1회차와 똑같은 패턴(이터 1은 코드 로직이 이미
탄탄하고 ⑤테스트커버리지 축만 미달, 이터 2에서 그 파일만 채우면 만점)이 반복됐다 —
sandbox 대상 자체의 한계가 여전히 유효했다는 신호다. 다만 이번엔 시간을 못 채운
**직접적인 사유가 다르다** — 시간이 남았는데도(경과 0:06/1시간) 대상이 쉬워서 멈춘
게 아니라, **세션 usage 한도(97% 근접)** 때문에 사용자가 이터 2에서 직접 중단시켰다.
즉 "sandbox 대상이 쉬워서 빨리 끝난다"는 구조적 제약과 별개로, **장시간(1~2시간)
멀티 에이전트 루프는 usage 예산이라는 또 다른 실질적 상한을 받는다** — 대상을
아무리 어렵게 만들어도 usage 한도가 먼저 걸리면 못 채운다. 이 저장소에서 랄프
루프를 다시 오래 돌릴 계획이라면 목표 이터 수 × 이터당 실측 토큰(1회차 실측: 약
3.5만 토큰/이터, 코딩+judge 서브에이전트 포함)으로 예산을 먼저 가늠해 볼 것.

## 참고할 사람에게

- `OS.md` Step 2("사내 유지보수 요청에 OS 적용")를 실제로 진행하면 이 회고를
  재평가할 것 — 실 코드에서 랄프 루프를 돌려보면 "쉽게 수렴하는 문제"가 저절로
  해소될 가능성이 높다(대상 자체가 어렵기 때문에).
- sandbox 로 루브릭 루프를 또 돌린다면, 시간을 억지로 채우기보다(예: 게이트 임계를
  비현실적으로 올리는 것) **대상의 계약 복잡도를 올리는 쪽**이 더 정직한 신호를 낸다 —
  `board-comments` 가 그 선택.
