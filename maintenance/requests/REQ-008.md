## 1. 요청 원문

게시글이 새로 작성되면 관리자에게 SMS로 즉시 알림이 가도록 해주세요.

### 추가 확인 (intake-interview → 담당자 응답)

- 목적: 부적절한 글을 빠르게 발견해서 삭제·제재 (모니터링)
- 수신자: 운영 담당자 1~2명의 개인 휴대폰 번호를 그대로 등록
- 발송 수단: **없음 — 새로 계약해야 함** (회사가 계약한 SMS/알림톡 발송 서비스 계정 없음)

## 2. 접수 정리 (/intake)

- 유형: 신규 개발
- 영향 범위: `sandbox/board` `POST /posts` 트리거 + 신규 SMS 발송 연동
- 완료 기준(초안):
  1. 새 게시글 작성 시 등록된 관리자 번호로 SMS 발송
  2. SMS 문구에 제목(+작성자) 포함
  3. 발송 실패 시 로그 남김

### 가정 원장 (interview-method.md §7 — 선택 질문·가정 후보, 묻지 않고 진행)

| - | --- | --- | --- |

| 2 | 발송 실패 시 재시도 로직 없이 1회 시도 후 로그만 | 추정 | 낮음 |

## 4. 스펙 (/spec) — 내부 처리인 경우

- 목표: 새 게시글이 작성되면 등록된 관리자 번호로 SMS 알림을 보낸다.

- 범위 / 범위 밖:
  - 범위: `POST /posts` 성공 후 알림 트리거 + SMS 발송 어댑터 함수 + 실패 로그
  - 범위 밖: 관리자 계정 체계 신설(개인 번호를 설정값으로 직접 등록하는 것으로 대체),
    재시도 로직(§2 가정 원장 #2)

- 영향 파일:
  - `sandbox/board/app.py` — `create_post()` 성공 시 알림 트리거 호출 추가, `send_sms()` 어댑터 함수 신설
  - `sandbox/board/tests/` — 신규 테스트 파일

- 구현 접근:
  - `send_sms(number, message)` 함수를 별도로 분리해 SMS 발송 부분을 격리한다 (어댑터 패턴 —
    나중에 실제 벤더 SDK로 교체하기 쉽게)
  - **실제 발송 API 키·계정이 없으므로**, 이번 구현에서 `send_sms()`는 실제 외부 호출 없이
    "발송 시도했다"는 로그만 남기는 스텁으로 둔다 — 이 지점이 벤더 계약 후 실제 연동으로
    교체돼야 할 자리임을 코드 주석으로 명시

- 완료 기준 (검증 가능하게):
  1. `POST /posts` 성공 시 `send_sms()` 가 호출됨 (로그로 확인 가능)
  2. SMS 문구에 제목이 포함됨 (로그 내용으로 확인)
  3. **관리자가 실제로 SMS를 수신한다** — ⚠️ 실제 SMS 게이트웨이 계약이 없어 **이번 스펙
     범위에서는 검증 불가능**. 벤더 계약 후 별도 후속 작업 필요
  4. 기존 테스트 전부 통과 + 새 케이스 추가

- 위험 / 롤백:
  - 위험: 완료 기준 3번(실제 SMS 수신)을 만족 못 시키는 게 사전에 예견됨 — 벤더 없이는
    "완료"로 볼 수 없는 요청. `/verify` 에서 이 기준은 실패 또는 미실행으로 처리될 것
  - 롤백: 추가한 트리거 호출과 `send_sms()` 함수 제거로 원복

## 5. 구현 로그 (/implement)

- 변경 파일:
  - `sandbox/board/notifications.py` (신규) — `send_sms()`(게이트웨이 없어 항상 로그만 남기고
    `False` 반환), `format_new_post_message()`, `notify_admins()`
  - `sandbox/board/tests/test_notifications.py` (신규) — 위 세 함수 단위 테스트
- 내린 판단 / 스펙에서 벗어난 점: **스펙에서 계획한 `app.py` 연결(트리거)은 이번에 하지 않았다.**
  이유가 스펙 작성 시점엔 없던 것 하나 더 생겼다 — 작업 중 `sandbox/board/app.py`가 **다른
  세션에 의해 실시간으로 계속 수정되고 있는 것**을 확인했다(`git status`상 수정중, mtime이
  방금 전). 같은 파일을 동시에 건드리면 두 작업이 서로 덮어쓸 위험이 있어, 알림 로직 자체는
  `app.py`와 무관한 독립 모듈로 분리해 그 부분만 구현·검증했다. `create_post()`에서 이 모듈을
  호출하는 배선(wiring) 한 줄은 `app.py`가 안전해진 뒤로 미룬다.
  완료 기준 3번(실제 SMS 수신)은 원래 스펙대로 벤더 계약 전까지는 어차피 검증 불가능하다.
- 남은 TODO:
  1. `app.py`가 안전해지면 `create_post()`에 `notify_admins()` 호출 배선
  2. SMS 벤더 선정·계약 → `send_sms()` 내부를 실제 API 호출로 교체
- 실행 결과: `cd sandbox/board && python3 -m pytest tests/test_notifications.py -q` → **3 passed**
  (기존 `app.py` 관련 테스트는 다른 세션 작업 중이라 이번 실행 범위에서 제외)

## 6. 검증 결과 (/verify)

| # | 완료 기준 | 방법 | 결과 |
| - | --- | --- | --- |
| 1 | `POST /posts` 성공 시 알림 함수 호출됨 | (미배선) | ⏭️ 미실행 — `app.py` 연결을 이번 범위에서 보류(아래 이유) |
| 2 | SMS 문구에 제목 포함 | `test_format_message_includes_title_and_author` | ✅ 통과 (모듈 단위로는) |
| 3 | 관리자가 실제로 SMS 수신 | (실행 불가) | ⏭️ 미실행 — SMS 게이트웨이 계약 없음, 검증할 외부 API 자체가 없음 |
| 4 | 기존 테스트 전부 통과 + 신규 케이스 | `pytest tests/test_notifications.py` | ✅ 통과(신규 3건). `app.py` 전체 스위트는 다른 세션 작업 중이라 이번엔 실행 대상에서 제외 |

- 판정: **미실행 포함 → blocked.** 막힌 이유가 두 가지 섞여 있다 —
  1. **진짜 이유(재현 가능)**: 완료 기준 3번(실제 SMS 수신)이 SMS 게이트웨이 계약이라는
     **외부 의존성** 때문에 막힘. 내부 역량 문제가 아니라 조달/외주 성격의 선결 조건.
  2. **이번 세션 한정 이유**: `app.py` 배선(완료 기준 1번)은 다른 세션과의 동시 편집 충돌을
     피하려고 일부러 미룸 — 이건 "역량이 없어서"가 아니라 작업 조율 문제라 다음에 안전할 때
     빠르게 풀 수 있다.
  → **재분류 검토 필요**: "SMS 벤더 선정·계약" 하위 작업을 외주/구매 프로세스로 분리하고,
  계약 완료 + `app.py` 배선까지 마친 뒤 이 REQ를 재개하는 것을 제안한다.
