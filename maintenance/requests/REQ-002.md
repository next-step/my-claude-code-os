## 4. 스펙 (/spec) — 내부 처리인 경우

- 목표: `sandbox/board` API에 `PATCH /posts/<id>` 를 추가해 title만 수정할 수 있게 한다.
  기존 GET/POST/DELETE의 방어 순서·직렬화 관례를 그대로 따른다.

- 범위 / 범위 밖:
  - 범위: `app.py` 에 PATCH 라우트 추가, title만 갱신, 신규 pytest 파일 추가
  - 범위 밖: body 동시 수정(§2 가정 원장 #3), 인증/권한 추가(§2 가정 원장 #4),
    `sandbox/board/README.md` API 명세 표 갱신(요청에 명시 안 됨 — 필요 시 별도 요청)

- 영향 파일:
  - `sandbox/board/app.py` — `delete_post` 아래, `return app` 앞에 라우트 추가
  - `sandbox/board/tests/test_patch.py` — 신규. `test_delete.py` 와 동일한 `client`
    fixture·헬퍼·네이밍 컨벤션(`test_<동작>_<조건>_<기대>`) 따름

- 구현 접근:
  - `@app.patch("/posts/<int:pid>")` 라우트 추가
  - 방어 순서: **404(존재 확인) → 타입 검사(`isinstance(title, str)`) → 값 검사(`strip()` 빈값)
    → 부작용(`posts[pid]["title"]` 갱신)** — DELETE의 "404 먼저" + POST의 "타입→값" 순서를 합친 것
    (`.claude/context/style.md` "방어 순서: 타입 검사 → 값 검사", "부작용은 모든 가드 통과 후")
  - 요청 바디의 title 외 필드(예: `body`)는 무시하고 title만 반영 (§2 가정 원장 #2)
  - 에러 응답은 기존 `jsonify({"error": ...}), <코드>` 컨벤션 재사용, 성공 응답은 `_serialize(pid)` 경유

- 완료 기준 (검증 가능하게 — `.claude/context/dod-patterns.md` 패턴 인용):
  1. `PATCH {"title": "새 제목"}` (존재하는 id) → `200` + `{"id", "title": "새 제목", "body": 원본 그대로}`
     (dod-patterns.md "API 응답" 템플릿)
  2. `PATCH` (없는 id) → `404` + `{"error": "not found"}` (동일 템플릿, GET/DELETE 선례)
  3. `PATCH {"title": ""}` / 공백만 / title 없음 / 비문자열(`123`) → `400` + `{"error": "title is required"}`,
     저장 안 바뀜, 500 아님 (dod-patterns.md "API 응답" + "5xx 방지" 템플릿)
  4. PATCH로 들어온 title은 trim 없이 **바이트 단위로 그대로** 저장 (dod-patterns.md "값 보존" 템플릿,
     POST 선례와 동일)
  5. 요청 바디에 `body` 필드가 같이 와도 무시되고 title만 바뀐다 (§2 가정 원장 #2 검증)
  6. 기존 테스트(`test_board.py`, `test_delete.py`) **코드 수정 없이** 통과 + `test_patch.py` 신규 테스트 추가,
     `cd sandbox/board && python3 -m pytest` 전체 통과 (dod-patterns.md "회귀 없음" + "명령 결과" 템플릿)

- 위험 / 롤백:
  - 위험: 값 검사를 타입 검사보다 먼저 두면 `None`/숫자 title에 `.strip()` 호출로 500 날 수 있음
    (REQ-001에서 겪은 동일 실수 — `style.md` 방어 순서 규칙의 근거) → 타입 검사를 먼저 배치해 방지
  - 롤백: 추가한 PATCH 라우트 블록과 `test_patch.py` 삭제만으로 원상복구 (다른 엔드포인트 무영향)
