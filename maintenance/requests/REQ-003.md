## 1. 요청 원문

게시판(sandbox/board) 글 목록을 관리자가 한눈에 보고 검색·통계 필터링도 할 수 있는 React 기반
SPA 관리자 대시보드를 새로 만들어주세요. 기존 API를 붙여 쓰면 됩니다.

### 추가 확인 (intake-interview → 담당자 응답)

- 업무 문제: 게시글이 늘어나면서 API/DB로 직접 확인하기 번거로움 — 화면으로 보고 싶다
- 통계·검색 기준: 제목/본문 텍스트 검색만 있으면 됨 (작성자·작성일시 통계는 불필요 — 현재 데이터모델로 충분)
- 접근 권한: 아이디/비밀번호 로그인 필요, 관리자만 접근

## 2. 접수 정리 (/intake)

- 유형: 신규 개발
- 영향 범위: 새 프론트엔드(React SPA) + 로그인 엔드포인트 신설. 기존 `sandbox/board` API(GET/POST/PATCH/DELETE)는
  조회용으로 그대로 재사용, 변경 없음
- 재현 방법 / 기대 결과: (해당 없음 — 신규 개발)
- 완료 기준(초안):
  1. 로그인한 관리자만 접근 가능한 화면에서 게시글 목록 조회 가능
  2. 제목/본문 텍스트 검색 가능
  3. 기존 API(GET/POST/PATCH/DELETE)는 무변경 — 화면은 조회용으로만 붙여 씀

     **"SPA(React/Vue 등) 신규 구축, 복잡한 상태관리"가 명시적으로 범위 밖**으로 적혀 있음.

  2. `sizing.md` 루브릭 기준 **L**에 해당: 새 프레임워크(React) 도입 + 로그인/인증 신설 + 관리자 전용
     접근 통제 + 기존 API 연동까지 여러 모듈이 동시에 얽혀 있고 불확실성이 큼.

     "서버 템플릿·바닐라 JS 소규모"만 보유(주니어 1명 겸임)해 SPA 규모를 감당할 캐파가 없음.
- 적용한 기준:
  - `classification-policy.md` §1②③ — 대상 시스템(board) 수행주체 확인 후 team-capability.md 스택 대조 단계 적용
  - `team-capability.md` 부분대응 "안 하는 것" — SPA(React/Vue 등) 신규 구축은 명시적 범위 밖
  - `classification-policy.md` §1③ — "범위 밖 → outsource 쪽으로 강하게"
  - `sizing.md` 루브릭 — 신규 프레임워크 도입 + 인증 + 다중 모듈 → L
  - `knowledge/systems/board.md` — 관리주체 내부, 담당 외주사 없음 → §2 캐파 라우팅 룰은 이 시스템에 적용되지 않음
  - `maintenance/capacity.md` — `updated: 2026-09-15`(오늘), 14일 경과 안 함. 다만 board는 담당 벤더가
    없어 §2 잔여율 계산 자체가 대상 아님
- 확인이 필요한 점:
  - "아이디/비밀번호 로그인, 관리자만 접근" 부분이 `classification-policy.md` §0 "보안 예외 처리,
    권한·계정 정책" 선판정(무조건 internal)에 해당하는지 애매함 — 로그인/인증 백엔드만 internal로
    분리할지는 사람 판단 필요.
  - 규모(L)로 볼 때 `classification-policy.md` §3 스코프 게이팅 상 "별도 프로젝트(Phase 2)" 후보임.

## 7. 외주 요청서 (/outsource) — 외주인 경우

- 배경 / 문제: 사내 게시판(`sandbox/board`) 글이 늘면서 관리자가 매번 API를 직접 호출하거나 DB를
  들여다봐서 목록을 확인하고 있습니다. 관리자가 화면으로 한눈에 보고 검색할 수 있는 도구가 필요합니다.

- 요청 범위:
  1. React 기반 SPA 관리자 대시보드 신규 구축
  2. 아이디/비밀번호 로그인 — 로그인한 관리자만 대시보드 접근 가능
  3. 게시글 목록 조회 화면 (기존 `GET /posts` API 연동)
  4. 제목/본문 텍스트 검색 기능

- 범위 밖:
  - 게시글 수정·삭제 UI — 이번엔 조회·검색까지만 (향후 별도 요청 가능)
  - 날짜별·작성자별 통계 — 현재 데이터모델(`{id, title, body}`)에 작성일시·작성자 필드 자체가 없음
  - 기존 `sandbox/board` API(GET/POST/PATCH/DELETE) 변경 — 그대로 소비만 함

- 산출물:
  - React 프로젝트 소스 코드 전체
  - 배포 가능한 빌드 산출물
  - 배포·실행 가이드 문서
  - 로그인/인증 구현 방식 제안서 — 백엔드 인증 파트를 벤더가 함께 구현할지,
    내부에서 별도로 붙일지는 `(확인 필요)` — 아래 비고 참고

- 완료·인수 기준:
  1. 올바른 아이디/비밀번호로만 대시보드 접근 가능, 그 외에는 접근 거부됨을 시연
  2. 검색어 입력 시 제목 또는 본문에 해당 문자열이 포함된 게시글만 결과로 나옴
  3. 기존 API 응답 스키마(`{id, title, body}`)를 변경 없이 그대로 소비함을 코드 리뷰로 확인
  4. 담당자가 실제 화면에서 로그인·조회·검색을 수행해 승인

- 제약 조건:
  - 프론트: React. 백엔드 기존 Flask API(`sandbox/board`)는 수정 금지, 그대로 사용
  - 로그인 정보 저장 방식(세션/토큰, 비밀번호 해시 등)은 사내 보안 정책 검토 필요 — `(확인 필요)`

- 필요한 접근 권한 / 우리가 제공할 것:
  - `sandbox/board` 저장소 read 권한 (API 스펙 참고용)
  - 배포 환경 정보 — `(확인 필요)`. 별도 인프라가 필요하면 사내 IT팀이 직접 검토·제공
    (`team-capability.md` 주의: "인프라·보안은 사내 IT팀이 직접 수행")

- 일정: `(확인 필요)` — 희망 착수·납기 미정. 규모가 **L**로 분류돼
  `classification-policy.md` §3 스코프 게이팅 상 이번 달 유지보수가 아니라
  **별도 프로젝트(Phase 2)** 로 상정될 가능성이 있음 — 착수 전 사람 판단 필요.

- 커뮤니케이션: `(확인 필요)` — 담당 창구 미정 (요청자 미상)

- 예산 / 비고: 예산 `협의`.
  - **벤더 확인 필요**: `maintenance/capacity.md` 에 등록된 `테크브릿지`(범용 외주, 이번 달 계약 잔여 15%)가
    이 규모(L)를 맡기에 적합한지, 별도 벤더를 새로 찾아야 하는지 확인 필요
    (3. 분류 결과 "확인이 필요한 점" 참고).
  - **인증 파트 소관 확인 필요**: 로그인/계정 정책은 `classification-policy.md` §0상 원래 "보안 예외
    처리·권한 정책 = internal(사내 IT팀 직접)" 대상일 수 있어, 이 외주 범위에서 로그인 백엔드를 뺄지
    포함할지 착수 전 결정 필요.
