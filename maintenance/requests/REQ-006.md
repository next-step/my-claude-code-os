## 1. 요청 원문

게시판을 회사 여러 부서가 각자 독립적으로 쓸 수 있도록 멀티테넌트 구조로 재설계하고,
부서별 접근 권한 관리까지 포함해서 새로 만들어주세요.

### 추가 확인 (intake-interview → 담당자 응답)

- 배경: 새 부서/조직 개편으로 게시판을 분리해야 함
- 대상 시스템: `sandbox/board`는 설계 연습이고, 실제 운영 시스템은 별도(이 저장소 밖)
- 인증/권한: 사내 IT팀이 관리하는 기존 인증 체계(SSO 등)와 연동

## 2. 접수 정리 (/intake)

- 유형: 신규 개발
- 영향 범위: 실제 운영 시스템(이 저장소 밖) — 멀티테넌트 데이터 모델 + 부서별 권한 관리 +
  기존 사내 SSO 연동. `sandbox/board` 코드는 무관(참고용 설계 연습일 뿐)
- 완료 기준(초안):
  1. 부서별로 게시글이 격리되어 보이는 구조 설계·구현
  2. 사내 SSO와 연동된 인증으로 부서 소속을 식별
  3. 신규 조직 개편 반영 가능한 구조

## 3. 분류 결과 (classifier)

## 분류 결과

- 판단: **internal**
- 규모: **L**
- 신뢰도: **낮음**
- 근거:
  1. "부서별 접근 권한 관리"·"사내 SSO 연동"은 `classification-policy.md` §0 "보안 예외 처리,
     권한·계정 정책" 조건에 해당 — 다른 조건과 무관하게 바로 **internal**(사내 IT팀이 직접
     검토·수행)로 선판정된다.
  2. "멀티테넌트 재설계"는 스키마·DB 구조 변경을 동반 — §0 "인프라" 조건에도 해당해 같은
     결론(internal)을 한 번 더 뒷받침.
  3. `sizing.md` 루브릭상 "구조 변경·3일 이상·불확실성 큼"에 해당 — **L**.
- 적용한 기준:
  - `classification-policy.md` §0 — 인프라(DB/스키마 재설계) 해당, 선판정 internal
  - `classification-policy.md` §0 — 보안 예외 처리·권한/계정 정책(부서별 권한 + SSO) 해당, 선판정 internal
  - `team-capability.md` — "인프라·보안은 사내 IT팀이 직접 수행. §0 선판정 참고"
  - `sizing.md` 루브릭 `L`
  - `.claude/knowledge/systems/board.md` — 이 파일은 `sandbox/board`(로컬 전용, 프로덕션 아님)만
    다루며, 이번 요청 대상("저장소 밖 실제 운영 시스템")과는 **다른 시스템**
- 확인이 필요한 점 (**분류를 확정하기 전에 사람 판단 필요**):
  - 대상이 `sandbox/board`가 아니라 저장소 밖 실제 운영 시스템인데, `.claude/knowledge/systems/`에
    이 시스템을 다루는 파일이 없음 — 관리 주체(우리 팀 / 사내 IT팀 / 별도 조직)를 요청자에게
    먼저 확인해야 함 (`classification-policy.md` §1②)
  - §0의 "internal" 결론이 "**우리(이 OS를 쓰는 유지보수팀)가 직접 만든다**"는 뜻인지,
    "**별도 사내 IT팀에 티켓을 넘긴다**"는 뜻인지 구분이 안 됨 — 같은 "internal"이라도
    실제 수행 주체가 달라질 수 있음
  - "우리에게 접근 권한 자체가 없음 → outsource" 조건(§0)도 잠재적으로 해당할 수 있으나
    사실 확인이 안 돼 이번 판단엔 반영하지 않음
  - SSO 연동 대상(사내 IT팀 SSO)의 인터페이스·계약 조건 미확인
- 추천 다음 단계: **형식상 `/spec REQ-006`이지만, 관리 주체·접근 권한 확인이 선행되지 않으면
  스펙 작성 자체가 의미가 없다 — 사람 확인 후 분류를 재확정 권장.**
