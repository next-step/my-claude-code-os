# 테스트 지침 (testing guideline)

이 프로젝트에서 테스트를 **작성·수정**할 때 반드시 지키는 규칙이다.
`test-writer`(테스트 전담) 등 코드를 만드는 서브에이전트와, 직접 테스트를 짜는 모든 작업에 적용된다.

> 💡 **왜 지침을 문서로 분리하나?** 규칙을 사람의 머릿속이나 매 프롬프트에만 두면 매번 달라진다. 문서로 못 박고 CLAUDE.md로 주입하면, **누가·언제 짜든 같은 기준**으로 테스트가 나온다. 이게 "재현 가능한 품질"의 출발점이다.

## 0. 대전제
- **테스트 프레임워크는 표준 라이브러리 `unittest`만 사용한다.** pytest 등 외부 의존성을 추가하지 않는다.
- 테스트는 `tests/` 아래에 `test_*.py`로 둔다. 실행은 `python -m unittest discover -s tests` (또는 `python -m unittest tests.test_모듈`).
- 파일 docstring·클래스 docstring·테스트 메서드명은 **한글**로 쓴다. 이름만 봐도 무엇을 검증하는지 읽혀야 한다. (예: `def test_음수_N은_빈_리스트_slice버그_방어(self):`)

## 1. 무엇을 테스트하는가 — 순수 함수 우선
- **I/O(파일 읽기, 네트워크, 시각)와 로직을 분리하고, 로직은 순수 함수로 뽑아 그 함수를 테스트한다.**
- 순수 함수는 입력→출력이 결정적이라 목(mock) 없이 빠르고 안정적으로 검증된다.

> 💡 **왜?** `count_skills(lines)`처럼 파일 I/O를 밖으로 빼면, 파일을 만들지 않고 리스트만 넘겨 수십 개 케이스를 즉시 돌릴 수 있다. 로직과 I/O가 엉키면 테스트가 느리고 깨지기 쉽다.

## 2. 반드시 커버해야 하는 케이스 (체크리스트)
happy path 하나로 끝내지 않는다. 아래를 **의식적으로** 훑고, 해당되는 것은 모두 테스트한다.

- [ ] **정상 케이스**: 대표적인 입력에서 기대 출력이 정확한가.
- [ ] **빈 입력**: 빈 리스트/빈 dict/빈 문자열에서 안전하게 동작하는가.
- [ ] **경계값**: `0`, `1`, 컬렉션 크기 경계, `n`이 전체보다 클 때 등.
- [ ] **음수·비정상 수치**: 음수를 slice/인덱스에 그대로 넘겨 생기는 버그를 방어하는가. (`ordered[:-1]` 함정)
- [ ] **형식 깨진 입력**: 구분자 없는 줄, 필드 누락, 공백만 있는 줄 등을 무시/처리하는가.
- [ ] **타입 방어**: 순수 함수 단독 사용 시 잘못된 타입을 명확한 `TypeError`로 거부하는가. (`bool`은 `int`의 하위 타입이므로 개수 의미가 아니면 거부)
- [ ] **정렬·동수(tie-break) 규칙**: 정렬 순서가 규칙대로인가. **동수일 때의 순서**까지 고정해 검증한다. (프로젝트 공통 규칙: 횟수 내림차순, 동수면 이름 오름차순)

> 💡 **왜 엣지 케이스가 핵심인가?** 버그는 거의 항상 경계와 예외에서 나온다. happy path만 통과하는 테스트는 "돌아간다"는 착각만 준다. 위 목록은 이 프로젝트에서 실제로 버그가 났던/날 뻔한 지점들을 모은 것이다.

## 3. 테스트를 쓰는 방식
- **AAA 구조**(Arrange–Act–Assert)로 짜고, 한 테스트는 한 가지만 검증한다.
- **각 케이스에 "왜 이 케이스가 필요한지" 한 줄 주석**을 단다. 미래의 독자가 삭제해도 되는지 판단할 수 있어야 한다.
- **결정적으로** 짠다. 랜덤·현재 시각·실행 순서에 의존하지 않는다.
- 에러는 값이 아니라 예외로 확인한다: `with self.assertRaises(TypeError):`

## 4. 회귀 테스트 (버그를 고칠 때)
- 버그를 고치기 전에 **그 버그를 재현해 실패하는 테스트를 먼저 쓴다.** 고친 뒤 그 테스트가 통과하는지 확인한다.
- 이렇게 남긴 테스트가 같은 버그의 재발을 영구히 막는다.

## 5. 완료 기준 (Definition of Done)
- [ ] 위 체크리스트 중 해당 케이스를 모두 테스트로 옮겼다.
- [ ] `python -m unittest`가 **전부 green**이다. (실행해서 눈으로 확인)
- [ ] 새 테스트가 없으면 "테스트 불필요"의 이유를 명시했다.

> 💡 **왜 green 확인까지가 완료인가?** "짰다"와 "통과한다"는 다르다. 실행하지 않은 테스트는 오히려 거짓 안심을 준다. 반드시 돌려서 초록불을 본다.
