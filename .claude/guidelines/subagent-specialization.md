# 서브에이전트 세분화 설계도 (Blueprint)

현재 OS의 서브에이전트를 **더 세부적으로 전문화**하기 위한 설계 문서다.
아직 **구현하지 않았고**, "무엇을·왜·어떻게 나눌지"의 청사진만 담는다.
실제 파일(`.claude/agents/*.md`, `SKILL.md`) 반영은 이 문서 승인 후 진행한다.

> 이 문서는 [OS.md](../../OS.md)의 4개 에이전트 구조를 전제로 한다. 먼저 그 개요를 읽으면 이해가 빠르다.




---

## 0. 세분화 판단 기준 — 언제 쪼개고, 언제 멈추나

아무 기준 없이 나누면 **오케스트레이션 비용**(맥락을 프롬프트로 전달, 호출 지연)만 늘고 품질은 안 는다.
쪼갤 가치가 있는 건 아래 **4가지 정당한 이유** 중 하나에 해당할 때뿐이다.

| 이유 | 설명 | 현재 OS의 사례 |
|------|------|----------------|
| **독립성(편향 제거)** | A가 만든 걸 A가 검증하면 못 믿는다. 만드는 사람과 판정하는 사람을 분리 | writer ↔ reviewer |
| **관점 다양성** | 한 프롬프트에 관점 5개를 담으면 다 얕아진다. 하나씩 전담시키면 깊어진다 | (→ 2장) |
| **병렬성** | 서로 의존 없는 일을 동시에 → 벽시계 시간 단축 | (→ 2장) |
| **최소 권한** | 필요한 도구만 준다. 읽기 전용 에이전트는 실수로도 코드를 못 고침 | reviewer/analyzer의 tools 제한 |

### 멈춰야 할 신호 (과잉 세분화)

- 새 에이전트에 넘길 **맥락 프롬프트가 그 에이전트가 하는 일보다 길다** → 합쳐라.
- 두 에이전트가 **항상 같은 파일을 순서대로만** 건드린다(병렬 불가·독립성 무관) → 합쳐라.
- 관점 A와 B가 **늘 같은 지적**을 낸다(redundant) → 하나로 줄여라.

> 💡 순차 의존이 강하고 맥락을 통째로 넘겨야 하는 일은 쪼개면 손해다.
> 현재 `code-writer`가 "분석→계획→구현"을 한 몸에 묶어둔 게 그 판단의 결과다.

## 1. 방향 A — TDD 내부 분리 (test-writer ↔ impl-writer)

### 1-1. 문제

지금 `code-writer` 하나가 **테스트 작성 + 구현**을 함께 한다.
스스로 짠 테스트는 자기도 모르게 구현에 맞춰 느슨해지고, 최악의 경우
"테스트를 통과시키려고 테스트를 무력화"하는 유혹이 생긴다(원칙으로 금지하지만 **구조적으로는 막지 못한다**).

### 1-2. 핵심 아이디어 — "무엇을(스펙)" vs "어떻게(구현)"

TDD의 본질은 **테스트가 곧 명세(spec)**라는 것이다. 이걸 조직도로 옮기면 분리 지점이 자연히 나온다.

| 에이전트 | 소유하는 질문 | 하는 일 | 권한(tools) | 쓰는 파일 |
|----------|--------------|---------|-------------|-----------|
| **test-writer** | **"무엇이 맞는가"**(스펙) | 요구 분석 → 수용 기준 도출 → **실패하는(red) 테스트** 작성. `testing.md` 지침(정상/빈입력/경계0/음수/형식오류/타입방어/tie-break) 전담 | Read, Grep, Glob, **Write, Edit**, Bash | 테스트 파일 |
| **impl-writer** | **"어떻게 충족하는가"**(구현) | red 테스트를 받아 **green으로 만드는 최소 구현**만 | Read, Grep, Glob, **Write, Edit**, Bash | 구현 파일 |

> 💡 예전 `code-writer`의 "분석" 단계를 어디 둘지 고민할 필요가 없다. **테스트를 쓰려면 요구를 이해해야 하니 분석은 자연히 test-writer 몫**이고, impl-writer는 "테스트라는 완성된 명세"를 받아 구현만 한다. red→green이 곧 자기 실력의 증거다.

### 1-3. 설계 다이어그램

```
 code-analyzer → test-writer → impl-writer → ③ [review-correctness ∥ review-tests] → doc-writer
                  (red 테스트)   (green 구현)         │
                     ▲              ▲                 │ 수정필요 시 지적을 라우팅
                     │              └─ 정확성 🔴 ──────┤ (구현 문제)
                     └─ 테스트 🔴 ──────────────────────┘ (테스트 문제)
                        (테스트 보강→다시 red→impl이 green)
```

### 1-4. impl-writer가 테스트를 못 고치게 하는 법 (교정)

> ⚠️ **초안 교정**: "도구 권한으로 막는다"는 **틀렸다**. Claude Code의 `tools:` frontmatter는 *어떤 도구*(Write/Edit 등)만 정하고 *어떤 경로*에 쓸지는 제한하지 못한다. impl-writer도 Write/Edit가 필요하므로 도구 수준 차단은 불가능하다.

실제 강제는 **규칙 + 사후 검증**으로 이중화한다.

1. **규칙(프롬프트)** — impl-writer 지침에 "테스트 파일은 절대 수정하지 않는다"를 명시.
2. **오케스트레이터 검증(backstop)** — impl-writer 실행 후 스킬이 `git diff --name-only`로 **테스트 파일이 바뀌었는지 확인**. 바뀌었으면 위반이니 되돌리고 재실행하거나 사용자에게 보고.

### 1-5. 핵심 규칙 & 검증 루프 라우팅

- **impl-writer는 테스트 파일을 수정하지 않는다.** red→green이 증거다.
- impl-writer가 "테스트가 틀린 것 같다"고 판단하면 **직접 고치지 말고 오케스트레이터에 반려** → test-writer가 재판단. (writer/reviewer 분리와 **똑같은 철학**: 만든 주체와 고치는 주체를 섞지 않는다.)
- ③ 검증 루프에서 지적을 **누구에게 보낼지 갈라준다**:
  - **review-correctness 🔴 (로직 버그)** → impl-writer가 구현 수정.
  - **review-tests 🔴 (빠진/약한 테스트)** → test-writer가 테스트 보강(다시 red) → **뒤이어 impl-writer가 green**.

### 1-6. 트레이드오프 & code-writer 처리

- 단계 +1, 라우팅 로직 추가, red 테스트를 프롬프트로 넘기는 인계 비용. 작은 프로젝트엔 다소 과하나, **"자기 테스트를 자기가 무력화" 못 하게 구조로 막는 독립성**이 이득.
- `code-writer`는 **은퇴(삭제)**한다. feature-dev가 test/impl로 쪼개지면 어떤 스킬도 code-writer를 부르지 않으므로(quick-review는 원래 writer 없음) 남기면 고아가 된다.
- **feature-dev(큰 기능)에만 적용**, quick-review류엔 미적용.

## 2. 방향 B — 리뷰 관점별 병렬 팬아웃 (fan-out)

### 2-1. 문제

지금 `code-reviewer` **하나**가 정확성·안정성·보안·관습·테스트를 **전부** 본다.
관점 5개를 한 컨텍스트에 담으면 각각 얕아지고, 순차라 **느리다**.

### 2-2. 관점을 몇 개로? — 5개는 과하다

0장의 "멈춰야 할 신호"를 이 프로젝트(로그 파싱 유틸 + 테스트)에 그대로 적용하면 렌즈가 정리된다.

| 관점 | 이 프로젝트에서의 실효성 | 판정 |
|------|------------------------|------|
| **정확성** | 로직·경계·오프바이원·null — 핵심 버그 지점. 항상 일감 | ✅ 채택 |
| **테스트** | `testing.md`가 있고 TDD가 이 OS의 핵심 가치. 정확성과 다른 렌즈 | ✅ 채택 |
| **안정성** | 예외·리소스 누수 — 작은 순수 함수엔 정확성과 거의 겹침 | ⚠️ 정확성에 흡수 |
| **관습** | 스타일·중복 — 실재하나 저수율, `/simplify`류와 겹침 | ❌ 제외 |
| **보안** | 비밀키·주입 — 파싱 유틸엔 대부분 "없음" 반환 | ❌ 제외 |

→ **정확성(+안정성)과 테스트, 2개**만 채택한다. 이 둘은 "코드가 맞나" vs "그걸 실제로 검증했나"로
가장 직교적이고 둘 다 일감이 확실하다. 보안·관습은 필요하면 `code-reviewer`(quick-review용)에 남겨 두거나
민감한 변경일 때만 조건부로 다룬다.

### 2-3. 설계 — 2개 병렬, synthesizer 없음

관점 2개를 **병렬**로 돌리고, 취합(중복 제거·단일 판정)은 **오케스트레이터 스킬이 직접** 한다.
관점이 2개뿐이라 별도 취합 에이전트(synthesizer)는 불필요하다.

```
        ┌─ review-correctness ─┐   (로직·경계·null·예외 = 정확성+안정성)
 diff → ─┤                      ├→  feature-dev 스킬이 취합 → 최종 판정
        └─ review-tests ────────┘   (수용기준 검증·빠진 케이스·green)
           병렬, 서로의 결과를 안 봄
```

| 에이전트 | 렌즈 | 권한 |
|----------|------|------|
| **review-correctness** | 로직 오류, 조건, 오프바이원, 경계값, null/빈 값, 예외·실패 경로 | Read, Grep, Glob, Bash |
| **review-tests** | 수용 기준을 실제로 검증하는지, 빠진 케이스, `testing.md` 커버리지, green 여부 | Read, Grep, Glob, Bash |

### 2-4. 오케스트레이션 변경점 (feature-dev ③단계)

- 기존: "리뷰어 1개 호출 → 판정 확인".
- 변경: **한 메시지에서 관점 에이전트 2개를 동시 호출**(→ 실제 병렬 실행) → 스킬이 두 판정을 취합.
- **취합 규칙**: 둘 중 하나라도 🔴(Blocking)이 있으면 → **수정필요**. 둘 다 🔴이 없으면 → **통과**.
  (기존 단일 reviewer의 판정 규칙과 동일. 입력만 2개로 늘어남.)
- 루프의 종료 조건(통과 / 최대 3회)과 "reviewer는 안 고친다" 원칙은 **그대로 유지**된다.

### 2-5. 설계 원칙

- 관점은 **redundant(같은 검토 N번)가 아니라 diverse(서로 다른 실패 유형)**여야 가치가 있다.
  그래서 겹치는 안정성은 정확성에 흡수하고, 저수율인 보안·관습은 애초에 뺐다.
- 관점 에이전트는 **서로의 결과를 모른다**(맥락 격리) → 사각지대가 겹치지 않는다.
- 취합은 단순 규칙(🔴 하나라도 → 수정필요)이라 **스킬이 코드처럼 처리**한다. 취합 에이전트를 만들지 않는다.

### 2-6. 트레이드오프

- 에이전트 수가 신규 2개 늘어 정의·유지 비용 증가(단, synthesizer가 없어 최소).
- 병렬이라 벽시계 시간은 오히려 **단축**되지만, 토큰 사용량은 늘어난다.
- 작은 diff엔 과하다 → **feature-dev에만**, quick-review는 단일 `code-reviewer` 유지.

---

## 3. 적용 범위 요약

두 방향 모두 **큰 파이프라인(feature-dev)에만** 넣고, 가벼운 흐름(quick-review)은 단순하게 둔다.

| 스킬 | TDD 분리(A) | 리뷰 팬아웃(B) | 이유 |
|------|:-----------:|:--------------:|------|
| **feature-dev** | ✓ | ✓ | 품질·독립성이 중요한 풀 파이프라인 |
| **quick-review** | — | — | 빠르고 가벼운 게 목적. 세분화는 과함 |
