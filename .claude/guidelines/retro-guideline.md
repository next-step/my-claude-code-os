# 일일 회고 지침 (retro guideline)

하루 개발이 끝났을 때 남기는 **회고(retrospective)**의 형식·품질을 정하는 규칙이다.
`retro-writer` 서브에이전트가 이 지침을 따라 회고를 작성한다. 이 문서가 "좋은 회고"의 **단일 출처(SSOT)**다.

> 💡 **왜 회고를 문서 규칙으로 고정하나?** 회고를 매번 즉흥으로 쓰면 어떤 날은 자책만, 어떤 날은 자랑만 남는다. 형식과 기준을 못 박으면 **누가·언제 써도 같은 품질**의 회고가 나오고, 시간이 지나 모았을 때 비교·추세 분석이 가능해진다(= OS의 자기관찰 루프).

## 0. 대전제
- **매일 개발이 완료된 시점**에 그날 작업을 돌아본다.
- **사실에 근거한다.** 그날의 커밋·테스트 결과·변경 파일 같은 결정적 데이터는 `scripts/daily_review.py`가 집계한 값을 근거로 쓰고, 지어내지 않는다.
- **정직하게.** 과장도 자책도 하지 않는다. "무엇이 실제로 좋았고/아쉬웠고, 다음에 무엇을 바꿀지"만 담는다.
- 언어는 **한글**. 간결하게.

## 1. 필수 구성 (이 다섯 섹션을 반드시 포함)

| 섹션 | 담는 것 | 왜 |
|------|---------|----|
| **좋았던 점** | 잘 작동한 것·유지할 습관 | 성공을 재현하려면 무엇이 통했는지 알아야 한다 |
| **아쉬웠던 점** | 막혔던 것·비효율·실수 | 개선의 출발점. 원인까지 짧게 |
| **보완사항 (action items)** | 다음에 할 구체적 행동 | 회고가 실제 변화로 이어지는 유일한 통로 |
| **커밋 요약** | 그날 커밋 수·타입 분포·핵심 변경 | 무엇을 했는지 객관 기록 |
| **지표** | 커밋 N개 / 테스트 통과 / 미해결 액션 수 | 추세를 볼 수 있는 정량 값 |

## 2. 각 섹션 작성법
- **좋았던 점 / 아쉬웠던 점** — 각 항목에 **"왜"**를 한 줄 붙인다. "리뷰 루프가 버그를 잡았다 — 독립 리뷰어가 유령 항목을 발견"처럼.
- **보완사항** — 반드시 **체크박스 마크다운**으로 쓴다: `- [ ] 내용`. 막연한 다짐("더 꼼꼼히") 금지, **검증 가능한 행동**("commits_for_date에 원소 타입 방어 추가")으로.
- **커밋 요약** — `daily_review.py`의 타입 분포(feat/fix/docs…)를 활용.

## 3. 액션아이템 규칙 (회고의 핵심)
- 미완료는 `- [ ]`, 완료는 `- [x]`.
- **이월(carry-forward):** 이전 회고의 미해결(`- [ ]`) 항목을 오늘 회고 맨 위 "이월된 보완사항"에 다시 싣는다. 해결됐으면 `- [x]`로 닫고 근거(커밋 등)를 붙인다.
- 같은 항목이 **3일 이상 이월**되면 별도로 표시해 "왜 안 되고 있는지"를 아쉬웠던 점에 적는다.

> 💡 **왜 이월이 핵심인가?** 아쉬운 점만 나열하는 회고는 감상문이다. 액션아이템을 다음 날로 넘겨 **닫힐 때까지 추적**해야 회고가 개선 루프가 된다.

## 4. 저장 위치
- `.claude/journal/YYYY-MM-DD.md` — 하루 한 파일. 날짜별로 남겨 나중에 주간/기간 집계가 가능하게 한다.

## 5. 완료 기준 (Definition of Done)
- [ ] 다섯 섹션(좋았던/아쉬웠던/보완사항/커밋 요약/지표)을 모두 채웠다.
- [ ] 이전 회고의 미해결 액션아이템을 이월했다(있으면).
- [ ] 보완사항이 체크박스이고 검증 가능한 행동이다.
- [ ] 커밋·테스트 지표가 실제 데이터(daily_review.py)와 일치한다.
