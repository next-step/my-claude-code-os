# 시각 판정 공통어 (rubric)

이 OS의 시각 검증 스킬·서브에이전트가 **공유하는 판정 헌법**이다.
레벨 정의·블라인드 규칙·역할 분담 같은 "판정의 공통어"를 여기 한 곳에 모아,
여러 스킬이 각자 다시 설명하지 않고 **필요할 때(=시각 검증을 실행할 때) 참조**한다.

> **왜 밖에 있나:** 이 지식은 매 턴 필요한 게 아니라 *시각 검증을 돌릴 때만* 필요하다.
> 그래서 CLAUDE.md(매 턴 로딩)에 넣지 않고 밖에 뺐다. 로딩은 lazy 참조("읽어라")가 아니라
> **훅(inject-context)이 판정 스킬 호출·판정 에이전트 스폰 순간 자동 주입**한다 —
> "안 읽을 수도 있다"는 불확실성을 기계적으로 제거한 것. (매핑: `.claude/context/manifest.json`)

---

## 1. 두 개의 눈 — 절대 판정 vs 상대 판정

| | **절대 판정** | **상대 판정** |
|---|---|---|
| 서브에이전트 | `visual-judge` | `visual-comparator` |
| 입력 | 스크린샷 **1장** | before/after **2장** |
| 묻는 것 | "이거 그 자체로 **깨졌나**?" | "before 대비 **딸려서 바뀐 게 있나**?" |
| 레벨 | ok / warn / error | same / expected / unexpected |
| 쓰는 스킬 | visual-check · visual-confidence | visual-regress |

**둘은 서로의 사각지대를 메운다.**
- 절대(1장)는 *혼자 봐도 명백히 깨진 것*을 잡지만, before 대비 미묘하게 바뀐 건 "혼자 보면 정상"이라 놓친다.
- 상대(2장)는 *before 대비 바뀐 것*을 잡지만, **before/after 둘 다에 똑같이 있던 원래부터 깨진 것**은 "변화 없음=통과"로 못 잡는다 → 그건 절대 판정의 몫.
- 그래서 **기준선을 박을 땐 절대 판정으로 검증**하고, 그 뒤 변경마다 상대 판정을 돌린다.

---

## 2. 판정 레벨 정의

### 절대 판정 (`visual-judge`) — "깨졌나?"
- **error(깨짐)** — **처리되지 않은** 넘침(말줄임 없이 바닥·옆으로 뚫음)·요소 겹침·아예 안 읽힘 등 **명백한 기능적 깨짐**.
- **warn(주의)** — 안 깨졌지만 **어색/미묘하게 어긋남**(톤 충돌, 비율 어색, 오버사이즈로 인한 어색한 말줄임, 의도 의심).
- **ok(정상)** — 멀쩡함.

> **판정 경계 둘 (자주 헷갈려 오답 나는 지점):**
> ① **말줄임(…)으로 처리된 잘림은 error 가 아니다.** 그건 정상적 오버플로 처리다 — 어색하면 warn, 멀쩡하면 ok. error 는 *처리 안 된* 넘침(바닥·옆으로 뚫고 나감)·겹침·안 읽힘이다. (그래서 `long-title`은 잘려도 ok, `long-description`은 바닥 뚫어 error.)
> ② **내용량·여백은 판정 대상이 아니다.** 카드 아래 빈 공간이 넓다는 이유만으로 warn 주지 않는다 — 실제 시각적 어긋남(색 충돌·대비 부족·겹침·처리 안 된 잘림)이 **보일 때만** warn/error.

### 상대 판정 (`visual-comparator`) — "의도 외로 바뀌었나?"
- **unexpected(의도 외 변경)** — 의도와 무관한 시각 변화가 보인다(딸려서 바뀜). *의도가 안 주어졌는데 의미 있는 변화가 보이면 이것.* → 회귀 신호.
- **expected(의도된 변경만)** — 바뀌긴 했으나 **전부 의도한 변경으로 설명된다**(의도가 주어졌을 때만 가능).
- **same(변화 없음)** — 의미 있는 차이 없음. 안티앨리어싱·렌더링 노이즈 수준의 미세차는 same.

---

## 3. 블라인드 원칙

판정 서브에이전트에게는 **정답(expected)·코드 수치·다른 판정 결과를 절대 넘기지 않는다.**
그림(과 선택적 한 줄 맥락/의도)만 주고, 스스로 본 대로 판정하게 한다.
→ 정답을 흘리면 "채점"이 아니라 "커닝"이 되어, AI 눈의 진짜 분별력을 못 잰다.

## 4. 본 것만으로 (추측 금지)

- 두 그림/한 그림에서 **실제로 보이는 것만** 근거로 삼는다. diff에 없는 변화를 상상하지 않는다(보이는 게 없으면 same/ok).
- 미세 색차·1px 같이 **사람도 단독으론 못 보는 차이는 AI도 못 본다** — 그건 아래 픽셀 측정의 몫.

---

## 5. 코드 vs AI — 역할 분담과 사각지대

이 OS의 핵심 철학: **"무엇이 바뀌었나(WHAT)"는 코드가, "그게 문제냐(MATTER)"는 AI가.**

| | **코드 (픽셀·측정)** | **AI 눈 (판정)** |
|---|---|---|
| 하는 일 | 사실만 잰다: overflow·대비 수치·색 hex·opacity·크기·픽셀 차이 | 맥락으로 판정한다: 깨짐/어색/정상, 의도 외/의도/변화없음 |
| 강점 | 1px·미세 색차·정밀 수치 | 맥락(같은 대비 1.97이라도 *비활성이면 정상, 본문이면 깨짐*) |
| **사각지대** | **맥락을 모른다** — 수치가 나쁜 게 문제인지 판단 못 함 | **1px·미세 색차·고립된 균일 어긋남을 못 본다** |

- **둘이 어긋나는 칸**(코드는 수치만인데 AI가 깨짐/어긋남, 또는 그 반대)이 **가장 중요한 신호** — 사람이 확인할 곳.
- 서로의 사각지대를 메우므로 **둘을 같이** 쓴다. 픽셀이 *바뀐 변형을 추려주면* AI는 **바뀐 것만** 보고 판정한다(비용↓·노이즈↓).

---

## 6. 비결정성 → 반복·다수결

AI 눈 판정은 이 파이프라인의 **유일한 비결정 요소**다(변형·정답·코드 측정·채점은 고정).
한 번만 돌리면 "운 좋게 맞췄나 / 나쁘게 틀렸나"를 구분 못 한다.
→ 같은 스샷에 **독립 블라인드 판정을 N번** 돌려 **일치율·다수결·flaky(흔들림)**를 본다(`visual-confidence`).
사각지대가 **N번 모두 같은 오답**이면 운이 아니라 "일관된 사각지대"다.

### 6-1. 다수결은 분산만 줄인다 — 편향은 근간 품질로 고친다

투표(N↑)는 **흔들림(분산)**, 즉 *우연히 틀림*만 줄인다. base judge 가 **체계적으로** 틀리면
N 을 아무리 키워도 **확신에 차서 같이 틀린다**(일치율↑인데 정답↓). 다수결로 편향은 못 지운다.

- **증거(우리 데이터):** `tone-c`·`disabled` 는 **일치율 1.0인데 정답률 0** — 안정적으로 틀린 사각지대.
  일치율(자기일관성)과 정답률(정확도)은 **다른 축**이다. 정답 대비 채점은 5장의 코드 몫(`npm run accuracy`).
- **그러므로 투표 수(N)를 늘리기 전에 base judge(눈·rubric)의 품질부터 올린다.**
  N 증설은 *근간이 흔들릴 때만* 유효하고, *근간이 편향됐을 때는* 오답을 더 굳힐 뿐이다.
- **품질을 올리는 수단(우선순위):**
  ① rubric 의 기준·레벨 정의를 더 또렷이(2·3장) → ② `visual-lens` 로 관점을 갈라 좁게 판정 →
  ③ 프레임에 **비교 기준을 공급**(변형 모아보기)해 고립·균일 사각지대를 줄인다.
