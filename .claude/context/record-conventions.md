# 기록 규약 (record-conventions)

> 매일 도는 자동 시뮬레이션 루프가 남기고 읽는 기록물의 공통 규칙. 어떤 기록이 '현재 상태'라
> 제자리 갱신되고, 어떤 기록이 '일어난 사건'이라 append로 박제되는지를 정한다.
> 출처: docs/interviews/2026-07-08-daily-trading-loop.md (S3·Q7·Q11·Q17·Q20·Q27) + 2026-07-08-os-docs-overhaul.md (Q9 재작성).
> 소비자: 루프 스킬 — 아침 수집(`morning-briefing`)·투자 위원회(`investment-committee`)·모의 시뮬 엔진(`sim-engine`)·주간 회고(`weekly-retrospect`).

## 공통 원칙

### 1. 상태(제자리 갱신) vs 사건(로그 append) 분리
기록물은 성격이 둘로 갈린다. 성격이 다르면 저장 방식을 나눈다(S3·Q20).

- **상태 기록 = 하나의 살아있는 문서, 제자리 갱신.** '지금 유효한 것'을 한 곳에서 한눈에
  보여야 하는 것(투자계획서·포트폴리오 상태). OS.md처럼 파일 하나를 계속 수정한다. 이력은
  담지 않는다 — 이력은 사건 로그가 맡는다.
- **사건 기록 = 날짜별 append 로그, 박제.** '일어난 일'(아침 브리핑·위원회 회의록·체결).
  한 번 남기면 수정·삭제하지 않는다. 회고가 성패·판단을 되짚을 원본이기 때문이다.

### 2. append-only 박제
- 사건 로그는 `data/` 아래에 **append-only**로 쌓는다. 과거 기록을 고치지 않는다(판단·예측
  박제 — 주간 회고가 "왜 그 판단을 했고 결과가 어땠나"를 검증할 원본).
- 날짜 파일명은 `YYYY-MM-DD-...md`. **같은 날 재실행은 `-2`, `-3`…** 접미사로 새 파일을
  만든다(과거를 덮지 않음).

### 3. 의도 ↔ 실제 분리, 상태 라벨로만 연결 (D3)
- **투자계획서 = 의도**(진입 대기 주문·목표·손절·목표 비중)만 담는다.
- **포트폴리오 상태 = 실제**(보유·평단·현금·평가손익)의 단일 진실원천이다.
- 둘은 값을 복제하지 않고, 계획서가 종목별 **상태 라벨(대기 / 진행중 / 완료)**로만 실제를
  참조한다. 갱신 주체·주기가 다른 두 데이터(위원회=하루 1회 의도, 시뮬=장중 실시간 실제)를
  한 파일에 섞지 않는다.

## 기록물 5종과 책임

| 기록물 | 경로(예) | 성격 | 작성 주체 | 담는 것 |
|--------|----------|------|-----------|---------|
| 아침 브리핑 | `data/briefings/YYYY-MM-DD.md` | 사건(append 로그) | 아침 수집 스킬 | 국내·미국장·거시·종목 뉴스의 구조화 요약 + 출처 링크. 사실만, 투자 해석은 넣지 않음 |
| 투자계획서 | `data/investment-plan.md` | 상태(살아있는 문서, 제자리 갱신) | 투자 위원회 스킬 | 시장 국면 전제·목표 현금 비중 헤더 + 종목별 진입가·목표가·손절가·목표 비중·주문 수량·근거·상태 라벨 |
| 포트폴리오 상태 | `data/portfolio.md` | 상태(제자리 갱신) | 모의 시뮬 엔진 | 현재 보유·평단·현금·평가손익 — '지금 실제'의 진실원천 |
| 위원회 회의록 | `data/minutes/YYYY-MM-DD.md` | 사건(append 로그) | 투자 위원회 / 긴급위 스킬 | 국면 판단·계획 변경 결정·전문가별 핵심 주장 요약·수렴/미해결 쟁점. 긴급위 소집분은 같은 로그에 **'긴급' 표기**로 append |
| 체결 로그 | `data/fills/YYYY-MM-DD.md` | 사건(append 로그) | 모의 시뮬 엔진 | 매 체결 이벤트(종목·수량·체결가·시각·판정 근거). 정규=한 틱 관통 지정가, 긴급=그 분 현재가 즉시 체결 |

## 세부 규약

- **아침 브리핑(Q7)**: 사실을 추출·중복제거한 구조화 요약만 저장하고 **원본 전문은 링크만**
  둔다. 매매 해석은 브리핑에 넣지 않는다(사실은 수집, 해석은 위원회 토론). 저장은 영구
  append, 위원회 주입은 오늘 + 최근 N영업일(기본 N=5, 튜닝 상수).
- **투자계획서 갱신(Q17)**: 위원회가 **바뀐 종목·필드만 제자리 수정**한다. '무엇을·왜 바꿨나'
  이력은 계획서 안에 쌓지 않고 회의록(append)이 맡는다 — 계획서 본문은 항상 '현재 유효 계획'만.
- **주문 수량(Q25)**: 진입 대기 주문의 수량은 **위원회가 자본·목표 비중·진입가로 정수주까지
  확정**해 계획서에 담는다. 체결 엔진은 그 주문서대로 집행만 하고 수량을 계산하지 않는다.
- **회의록 = 근거 로그(Q11)**: 계획서 본문은 결정 결과만 담고, '왜' 근거는 회의록이 박제한다
  (trading-principles의 "모든 매매 판단에 근거를 남긴다"와 정합).
- **포트폴리오 자산군 표기**: 보유 항목마다 **자산군 칸**(`개별주`·`ETF-헤지`·`ETF-테마`·
  `ETF-채권` — 투자계획서와 동일 값 집합)을 함께 적어, 매수 체결 시 계획서의 자산군 태그를 그대로
  옮긴다(값의 출처는 계획서 — 복제가 아니라 태그 전달). 주식:헤지:현금 배분을 실제 보유 기준으로
  점검하기 위함이다(스키마는 sim-engine SKILL).
- **긴급 반영(Q27)**: 긴급위 결정은 즉시 체결(체결 로그 append)하고 바뀐 보유·손절·비중을
  포트폴리오·계획서에 바로 반영하며, 긴급 회의록을 '긴급' 표기로 append한다(별도 로그를 두지
  않는다).

## 읽을 때 주의

- '지금 무엇을 들고 있나'는 **포트폴리오 상태**가 진실원천이다. 계획서의 상태 라벨은 참조일
  뿐, 실제 보유·평단은 포트폴리오에서 끌어온다.
- 사건 로그(브리핑·회의록·체결)는 그날의 판단·사실을 **박제한 것**이다 — 이후 상황이 달라져도
  당시 기록을 고치지 않는다("그땐 그렇게 판단했다"가 회고가 검증할 진실).
