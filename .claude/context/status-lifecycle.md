# 상태 수명주기 정본 — draft → planned → done

> **이 파일의 역할**: 할일 `status`가 가질 수 있는 값과, **어떤 스킬이 어떤 전이를
> 담당하는지**를 명문화한다. 지금까지 이 계약은 어디에도 적혀 있지 않고 각 스킬이 암묵적으로
> 알고 있었다. 새 스킬을 추가하거나 서브에이전트가 상태를 건드릴 때 "이 전이가 허용되나?"를
> 판단하는 근거가 이 파일이다. 상태값의 스키마는 [`data-model.md`](./data-model.md).

## 상태값

| status | 의미 |
|--------|------|
| `draft` | 캡처만 된 상태. 언제·왜·어떻게가 아직 안 정해짐 |
| `planned` | 구체화 완료. `recurrence`/`due_date`/`time`/`detail`이 채워짐 |
| `done` | 완료 처리됨 |

## 전이 다이어그램

```
        /capture              /plan                 /done
 (없음) ────────▶ draft ──────────────▶ planned ──────────────▶ done
                   │                                              ▲
                   └──────────────────/done───────────────────────┘
                        (planned 안 거치고 draft에서 바로 완료 가능)
```

## 전이 담당 (스킬별 책임)

| 스킬 | 하는 일 | 상태 전이 |
|------|---------|-----------|
| **capture** | 할일 생성 | (없음) → `draft` |
| **plan** | draft를 구체화 인터뷰 | `draft` → `planned` |
| **done** | 완료 처리 | `draft` \| `planned` → `done` |
| **list** | 상태별 조회 | **전이 없음** (읽기 전용) |
| **remind** | draft 알럿 발송 | **전이 없음** (읽기 전용, `draft`만 대상) |

## 불변 규칙

1. **전이는 위 표의 담당 스킬만 수행한다.** 다른 경로에서 status를 바꾸지 않는다.
2. **되돌리는 전이(planned → draft, done → planned 등)는 정의되어 있지 않다.**
   필요해지면 이 파일에 먼저 전이를 추가한 뒤 구현한다.
3. **done은 planned를 건너뛸 수 있다** — 구체화 없이 끝낸 일도 완료 가능.
4. **remind가 대상으로 삼는 것은 `draft`뿐** — 아직 방치된 할일만 알린다.

> capture(생성) → plan(구체화) → done(완료)의 흐름은 여러 SKILL.md 상단에도 요약돼 있다.
> 그 서술과 이 파일이 어긋나면 **이 파일이 정본**이다.
