# 분류 정책 — internal / outsource 판단 규칙

> **성격**: 판단 룰 (임계값). 사실 데이터는 참조만 하고 여기 복사하지 않는다.
> **변경 주기**: 분기~반기. 정책 리뷰 때 사람이 고친다.
> **읽는 쪽**: `classifier` (필수), `intake` (§3 게이팅 초안)

## 참조하는 데이터 (숫자를 이 파일에 박지 말 것)

| 참조 | 파일 | 없거나 오래됐을 때 |
| --- | --- | --- |
| 팀 스택·여력 | [`team-capability.md`](./team-capability.md) | 판단 보류 → 사용자에게 확인 |
| 시스템별 관리주체·외주사 | `.claude/knowledge/systems/<시스템>.md` | 요청자에게 관리주체 확인 |
| 이번 달 잔여 M/M | [`maintenance/capacity.md`](../../maintenance/capacity.md) | **§2 캐파 룰 적용 안 함**, 신뢰도 낮춤 |

`capacity.md` 의 `updated` 가 **14일 이상 지났으면** 숫자를 믿지 않는다.
"캐파 정보 N일 경과 — 사람 확인 필요"를 `확인이 필요한 점` 에 남긴다.

---

## §0. 선판정 — 캐파 계산 전에 즉시 확정

아래에 해당하면 다른 조건을 보지 않고 바로 결론 낸다.

| 조건 | 결론 |
| --- | --- |
| 인프라 (서버, DB 마이그레이션, 네트워크) | **internal** — 사내 IT팀이 직접 검토·수행 |
| 보안 예외 처리, 권한·계정 정책 | **internal** — 사내 IT팀이 직접 검토·수행 |
| 우리에게 접근 권한 자체가 없음 | **outsource** |
| 계약상 그 시스템은 특정 벤더 전담 | **outsource** |

---

## §1. 판단 순서

```
①  §0 선판정 해당? ─ 예 ─▶ 확정, 종료
   │ 아니오
   ▼
②  대상 시스템의 유지보수 수행 주체 확인
   (knowledge/systems/ · 없으면 요청자에게 확인)
   │
   ▼
③  team-capability.md 와 스택 대조
   범위 밖 ─▶ outsource 쪽으로 강하게
   부분대응 ─▶ 규모와 교차 (④)
   주력 ─▶ internal 쪽으로
   │
   ▼
④  규모 S / M / L 산정
   주력 + S·M ─▶ internal
   주력 + L ─▶ 여력 확인, 애매하면 §4
   부분대응 + M 이상 ─▶ outsource 쪽으로
   │
   ▼
⑤  §2 캐파 룰 적용
   │
   ▼
⑥  §3 스코프 게이팅 플래그
   │
   ▼
⑦  결론 + 적용한 기준 인용 (§5)
```

## §2. 캐파 기반 라우팅

> **담당 벤더의 이번 달 계약 M/M 잔여율이 20% 미만**이고,
> 요청이 **단순 문구·설정 수정** 또는 **쿼리 추출** 이면
> → 벤더에 넘기지 않고 **internal** 로 처리한다 (내부 스택으로 충분한 수준).

- 읽을 값: `capacity.md` → `vendors.<담당사>` 의 `contracted_mm` 대비 `used_mm`
  → 잔여율 = `(contracted_mm - used_mm) / contracted_mm`
- **"누구의" 잔여인지**: 팀 공수가 아니라 **그 시스템 담당 벤더의 계약 M/M**.
  벤더의 남은 계약분을 자잘한 건에 소모하지 않고 아껴 두는 것이 목적이다.
- 담당 벤더가 없는(내부 관리) 시스템이면 이 룰은 건너뛴다.

---

## §3. 스코프 게이팅 — 이번 달에 할지 말지

> **신규 기능 추가**이고 **예상 공수가 3 Man-Day 초과**면
> 이번 달 유지보수에서 제외하고 → **차월 이관** 또는 **별도 프로젝트(Phase 2)** 로 상정한다.

- 이것은 `internal` / `outsource` 판단이 **아니다**. "언제 할지"라는 별개 축이다.
- **현재 OS는 2분류만 지원**하므로, 지금은 결론을 바꾸지 말고
  `확인이 필요한 점` 에 `차월 이관 후보 — 신규기능 + 예상 3 M-D 초과` 를 남긴다.
- 3분류(`disposition: this_month | defer_next_month | promote_to_project`) 도입 여부는
  `OS.md` §7 열린 질문에서 결정한다.

---

## §4. 애매할 때

- 기본값은 `internal`, 대신 **신뢰도를 낮추고** `확인이 필요한 점` 을 채운다.
  외주는 조율 비용이 크므로 과잉 외주화를 경계한다.
- 단, **§0 선판정·§2 캐파·§3 게이팅이 서로 충돌**하면 임의로 고르지 말고
  사람 판단을 요청한다.

---

## §5. 인용 규칙 (필수)

판단 결과에 **어느 기준을 적용했는지 출처를 반드시 남긴다.**

```
- 적용한 기준:
  - classification-policy.md §0 — 인프라 해당, 선판정 internal
  - team-capability.md 주력 스택 — Python / Flask
  - capacity.md 2026-09 — 회사A 잔여 15% (< 20%) → §2 발동
```

이 인용이 케이스 파일에 쌓여야 "이 정책이 실제로 쓰였는가"를 나중에 `grep` 으로 감사할 수 있다.
인용이 한 번도 안 되는 항목은 **죽은 지침**이므로 지우거나 고친다.
