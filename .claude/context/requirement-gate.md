# 요청 게이트 — 바꾸기 전에 먼저 묻는다

무언가를 **바꿔 달라는 요청**을 받으면, 곧바로 파일을 고치지 말고 먼저 이 게이트를 통과시킨다. 목적은 질문을 많이 하는 것이 아니라 **합의 없이 구현으로 넘어가는 일을 막는 것**이다. 질문은 수단이다.

`.claude/skills/requirement-interview/SKILL.md`(ATDD 01.5단계)와 같은 판정 기준을 쓴다. 다른 점은 진입 경로다 — 스킬은 불러야 열리고, 이 게이트는 **부르지 않아도 열린다.**

## 1단계 — 이 요청이 게이트 대상인가

**바꾸는 요청에만 적용한다.** 코드·파일·설정을 수정·추가·삭제하는 요청이 대상이다.

조회·질문·설명·검색 요청("이 스킬 뭐 하는 거야", "테스트 몇 개야", "이 함수 설명해줘")은 **게이트를 열지 않고 그냥 답한다.** 이미 명확한 요청에 질문을 붙이는 것이 이 게이트의 가장 흔한 실패다.

## 2단계 — 슬롯 결손을 센다

요청 원문만 읽고 6개 슬롯을 채워 본다. **3개 이상 못 채우면 진입한다. 2개 이하면 그대로 진행한다.**

| 슬롯 | 묻는 것 |
|---|---|
| 목표 | 한 문장으로 무엇을 이루려는가 |
| 현재 상태 | 지금 실제로 무슨 일이 일어나는가 (추측이 아니라 확인된 사실) |
| 기대 동작 | 대신 무슨 일이 일어나야 하는가 |
| 완료 조건 | 무엇이 관측되면 끝인가 |
| 범위 밖 | 이번에 하지 않을 것 |
| 미해결 가정 | 아직 못 정해서 가정으로 둔 것 |

"모호해 보인다"는 감각이 아니라 **슬롯을 세어서** 판정한다. 세어 보면 대개 감각보다 관대하다.

## 3단계 — 경량이냐 본격이냐

|  | **경량** (대화 안에서) | **본격** (`Skill(requirement-interview)`) |
|---|---|---|
| 언제 | 한두 파일에 갇히고, 되돌리기 쉽고, 인수기준이 필요 없는 변경 | 새 기능·새 구조, 여러 파일이나 서브시스템에 걸침, 02단계 `spec-decompose`로 넘길 작업 |
| 절차 | 1라운드 최대 3문항 확인 후 진행 | 스킬의 전체 절차 |
| 산출물 | 없음 — 대화 안의 합의로 끝 | `docs/interview/YYYY-MM-DD-<slug>.md` 브리프 |

- **애매하면 무거운 쪽을 고른다.** 승격은 있고 강등은 없다 — 작업 도중 숨은 복잡도가 드러나면 그 사실을 말하고 본격으로 올린다. 반대로 내리지는 않는다. (superpowers `brainstorming`의 일방향 래칫)
- 무게가 달라지는 것은 **산출물**이지 **합의**가 아니다. 경량이라고 해서 합의 없이 시작해도 된다는 뜻이 아니다.

## 어떻게 묻는가 (경량 경로)

- **한 라운드 최대 3문항.** 선택형이면 `AskUserQuestion`을 쓴다.
- 모든 질문에 **추천안**과 **"지금 안 정함"** 선택지를 넣는다. 모호하게 요청한 이유는 대개 *아직 안 정했기 때문*이지 설명을 안 해서가 아니다.
- **첫 라운드에 항상 "건너뛰고 바로 진행" 탈출구를 넣는다.** 고르면 즉시 멈추고, 못 채운 슬롯을 미해결 가정으로 명시한 뒤 진행한다. 빠져나갈 구멍이 없는 게이트는 반드시 우회당하고, 우회는 기록이 남지 않는다.
- 묻기 전에 저장소를 먼저 읽는다. **코드에서 답할 수 있는 것은 묻지 않는다.** 질문에는 `파일:줄`로 근거를 인용한다.

## 이 게이트가 하지 않는 것

- 인수기준을 만들지 않는다 (02단계 `spec-decompose`의 몫).
- 조회성 요청을 가로막지 않는다.
- 브리프 파일을 경량 경로에서 만들지 않는다 — 본격 경로에서만 남긴다.
