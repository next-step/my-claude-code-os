# 인터뷰 방법론 — 모호함을 구체적으로 바꾸는 절차

> **성격**: 판단 룰 (방법론). 특정 요청의 사실이 아니라 "어떻게 물을지"의 규칙.
> **변경 주기**: 분기~반기. 실제로 써 보고 상한·축이 안 맞으면 고친다.
> **읽는 쪽**: `/interview` 스킬(전 구간), `intake-interview` 서브에이전트(§1·§2·§3·§8만)

## 목표를 먼저 못박는다

**모호함을 0으로 만드는 것이 목표가 아니다. 남은 모호함을 보이게 만드는 것이 목표다.**

완벽하게 아는 대신 모르는 것을 모른다고 적어 둔다. 그러면 나중에 결과가 틀렸을 때
전체를 뒤지지 않고 **가정 원장(§7)부터** 본다. 인터뷰의 진짜 산출물은 답이 아니라
**실패 후보지 목록**이다.

---

## §1. 5축 진단 — 질문하기 전에 조용히 채점한다

요청을 5개 축으로 나누고, 각 축에 눈금을 댄다. **이 단계에서는 아무것도 묻지 않는다.**

| 축 | 묻는 것 |
| --- | --- |
| **Why** 목적 | 왜 하나. 성공하면 무엇이 달라지나 |
| **Who/Where** 대상·범위 | 누가 쓰나. 어디까지가 이번 건인가 |
| **What** 동작 | 무슨 일이 일어나야 하나. 예외·경계는 |
| **Constraint** 제약 | 스택·기한·하면 안 되는 것 |
| **Done** 완료 | 무엇을 보면 끝났다고 하나 |

눈금 3단계:

| 눈금 | 뜻 | 처리 |
| --- | --- | --- |
| `명확` | 요청문 또는 저장소에서 확정된다 | 통과 |
| `추정` | 합리적 기본값이 있다 | 통과하되 **가정으로 기록** (§7) |
| `질문` | 물어봐야 한다. 틀리면 되돌리기 비싸다 | **질문 후보** |

> **게이트** — `질문` 이 하나라도 남은 채로 다음 단계(스펙·구현)로 넘기지 않는다.
> 특히 **Why 축이 `질문` 이면 나머지가 전부 `명확` 이어도 착수하지 않는다.**
> 목적–수단 혼동(해결책을 요청으로 말하는 것)은 요청자 본인도 인지하지 못하므로,
> 이 축을 명시적으로 재지 않으면 걸리지 않는다. 완벽하게 만들고 실패하는 경우가 여기서 나온다.

---

## §2. 질문 우선순위 — 되돌리기 비용 순으로 자른다

`질문` 이 5개여도 다 묻지 않는다. **지금 안 물어서 틀렸을 때 되돌리는 비용**으로 정렬한다.

| 되돌리기 비용 | 예 | 처리 |
| --- | --- | --- |
| **높음** | 목적 자체, 데이터 모델, 대상 사용자, 상태 변경 여부 | **반드시 묻는다** |
| **중간** | 화면 흐름, 예외 처리 정책 | 예산이 남으면 묻는다 |
| **낮음** | 문구, 색상, 파일 이름 | **묻지 않고 가정으로** (§7) |

---

## §3. 묻지 않는 것 두 가지

1. **저장소를 보면 알 수 있는 것** — 스택, 기존 패턴, 파일 위치, 현재 동작.
   먼저 `Grep`·`Glob`·`Read` 로 찾아본 뒤에도 안 나오는 것만 질문으로 만든다.
   이걸 물으면 상대의 시간을 낭비하고 신뢰를 잃는다.
2. **상대가 모를 만한 것** — 업무 담당자에게 "인덱스를 어떻게 걸까요"를 묻지 않는다.
   답할 수 없는 질문은 질문이 아니다. 기술 판단은 우리가 하고, 필요하면 선택지의
   **결과**로 번역해서 묻는다 ("A안은 조회가 빨라지지만 저장이 느려집니다" 처럼).

`team-capability.md` 로 답이 나오는 구현 가능성 질문도 묻지 않는다.

---

## §4. 객관식으로 묻는다

질문마다 **선택지 2~4개 + 기타**를 준다. 서술형만으로 묻지 않는다.

```
Q. 받으신 엑셀 파일로 무엇을 하시나요?
   A) 그대로 팀에 공유한다
   B) 다른 문서에 붙여넣어 월말 보고서를 만든다
   C) 데이터를 검토·수정한 뒤 다시 올린다
   D) 기타
```

**이유는 "고르기 편해서"가 아니다. 부정문이 긍정문보다 정보 밀도가 높기 때문이다.**
백지에 답하면 "음… 잘 되게요"가 돌아오지만, 틀린 보기를 부정할 때는 사람이 근거를
자발적으로 붙인다 — "아니 C는 안 돼요, 그러면 기존 데이터가 다 깨져서."

선택지를 만들 때는 **일부러 틀릴 만한 보기를 넣는다.** 전부 그럴듯하면 반박이 안 나온다.

## §5. 라운드와 상한

```
R0  조용한 진단   요청문 + 저장소 조사 → 5축 채점        질문 0개
R1  핵심 좁히기   되돌리기 비용 높은 것부터 최대 3개
R2  잔여 정리     답 반영해 재채점 → 남은 것 최대 3개
R3  되읽기        조건·행동·결과로 돌려주고 승인          §6
```

**종료 조건 — 셋 중 하나면 멈춘다.**

1. `질문` 눈금이 남아 있지 않다
2. **라운드 3회** 또는 **누적 질문 8개** 도달
3. 상대가 그만하라고 한다 (언제든 우선)

상한이 없으면 인터뷰는 무한히 늘어난다. 멈추는 순간 **남은 모호함은 사라지지 않고
가정 원장(§7)으로 옮겨 적는다.**

---

## §6. 되읽기 — 다른 종류의 실패를 잡는다

질문과 되읽기는 **서로 다른 실패**를 잡는다. 되읽기를 생략하면 오해는 끝까지 살아남는다.

| 실패 | 정체 | 잡는 곳 |
| --- | --- | --- |
| **빠짐** | 안 물어봐서 모른다 | R1·R2 질문 |
| **오해** | 물었고 답도 들었는데 **다르게 알아들었다** | **R3 되읽기** |

이해한 것을 **조건 · 행동 · 결과** 세 문장으로 돌려주고 승인받는다.

```
조건   게시판 목록에서 '2026년 3분기' 필터가 적용된 상태에서
행동   [엑셀 다운로드] 를 누르면
결과   화면에 보이는 컬럼 그대로, 필터된 행만 담긴 xlsx 파일이 받아진다
```

이 형식은 장식이 아니라 **검사기**다. 세 문장으로 안 써지면 아직 모호한 것이고,
써진다면 그대로 `/verify` 가 실행할 수 있는 완료 기준이 된다
(`OS.md` §5 원칙 4 "완료 기준은 검증 가능하게" 를 문법으로 강제).

---

## §7. 가정 원장 — 등급을 붙여서 남긴다

못 정한 것은 사라지지 않는다. 아래 표로 남긴다. **두 출신을 섞지 않는다.**

| # | 가정 | 출신 | 위험 |
| - | --- | --- | --- |
| 1 | 권한별로 보이는 컬럼 차이는 없다 | `추정` — 되돌리기 싸서 일부러 안 물음 | 낮음 |
| 2 | 첨부파일 목록은 포함하지 않는다 | `질문` — 예산 초과로 못 물음 | **높음** |

- **`추정` 출신** — 물을 수 있었지만 되돌리기가 싸서 질문 예산을 쓰지 않기로 **선택**한 것.
- **`질문` 출신** — 원래 물었어야 하는데 상한(§5)에 걸려 **남겨진** 것. 진짜 위험은 여기 있다.

나중에 결과가 틀렸을 때 **`질문` 출신부터 본다.** 이 구분이 실패 후보지 목록에 우선순위를 만든다.

---

## §8. 요청 유형별 축 가중치

유형을 먼저 찍고, 무거운 축에 질문 예산을 몰아준다.

| 유형 | 무거운 축 | 특유 질문 |
| --- | --- | --- |
| 버그 | What, Who/Where | 재현 절차, 기대 vs 실제, 언제부터, 영향 사용자 수 |
| 기능개선 | **Why**, Done | 왜 지금, **지금은 어떻게 우회하고 있나**, 성공 측정 |
| 신규 개발 | 전 축 + Constraint | 데이터 소유, 기존 시스템 연동, 사용자 규모 |
| 문의·조사 | Why, Done | 결과를 어디에 쓰나, 어떤 형태로(표/문서) |
| **스킬·OS 설계** | 트리거, 상태 변경 | 누가 언제 부르나, 무엇을 바꾸나, `## 하지 말 것` 은, 위임할 서브에이전트 |

"UX / 아키텍처 / 구현 가능성"은 별도 축이 아니라 이 가중치의 다른 이름이다 —
UX는 Who/What, 아키텍처는 Constraint + 되돌리기 비용 높은 질문들,
구현 가능성은 [`team-capability.md`](./team-capability.md) 대조로 답한다.
