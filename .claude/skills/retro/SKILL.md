# /retro — 세션 회고 → 개선 제안 (두 렌즈: 스킬·도메인 / 판단만, 적용은 사람)

이 OS를 **쓸수록 좋아지게** 만드는 스킬이다. 방금 굴린 세션을 **두 렌즈**로 돌아본다:
- **렌즈 A — 스킬 개선:** 스킬들이 어디서 **마찰**을 냈는지 보고 **SKILL.md 한 줄 수정 제안**을 뽑는다.
- **렌즈 B — 도메인 점검(개선 또는 신규):** 세션에서 **손댄 서비스 도메인**을 `docs/domain/`과 대조한다. **문서가 있으면** 변경점(아직 없는 새 사실·관계)을 근거와 함께 알리고 **`/domain <slug>` 재실행(개선)**을, **문서가 없으면**(이번에 새로 생겼거나 아직 문서화 안 된 도메인) **`/domain <slug>`로 새로 만들기**를 권장한다. 확인·작성은 /domain 몫. 목차가 커졌으면 세분화도 플래그. (단 **서비스(업무) 도메인**만 — 스킬·훅·도식 같은 OS 인프라 작업은 도메인이 아니다.)

둘 다 **제안·변경점**을 사용자에게 직접 보고하고, 파일로 쌓거나 직접 고치지 않는다.

> 역할 분리 — **관찰·수집은 /retro(오케스트레이터), 개선 판단은 독립 `reviewer`.**
> 이 스킬은 세션의 마찰 신호를 모아 브리프로 만들고, 그 스킬의 프롬프트를 고칠지는
> **격리된 적대적 검토자**에게 던진다(자기 세션을 자기가 미화하지 않도록). `/verify`와 같은 모양이다.
>
> **제안만 한다. 파일을 직접 고치지 않는다.** 반영은 사람이 검토 후 — 스킬은 `/quick` 급으로 SKILL.md,
> **도메인 문서는 `/domain <slug>` 갱신 모드**로. (자동 자기수정은 드리프트를 부른다. 특히 **도메인 문서는
> /prd·/plan에 먹이고 코드 편집 시 자동 주입**되므로, 틀린 한 줄이 널리 전파된다 → 게이트를 더 세게.)

전달된 인자: `$ARGUMENTS`
- 인자가 있으면 → 회고 초점(특정 스킬명 또는 "이번 /impl만" 같은 범위)으로 쓴다.
- 없으면 → **이 세션 전체**를 대상으로 한다.

## 진행 순서

### 1. 세션 브리프 패키징 — ★오케스트레이터(메인)★

이 스킬은 **세션 안에서** 돌기에 대화 기록을 파싱할 필요가 없다 — **너(메인)가 그 세션을 직접 겪었다.**
하지만 다음 단계의 **서브에이전트는 그 맥락을 못 본다(격리)**. 그러니 메인은 **판단하지 말고**,
두 렌즈 에이전트가 볼 **중립 브리프**를 촘촘히 싼다:

1. **세션 서사(주 신호)** — 무엇을 했고, 어디서 막히거나 되돌렸고, 사용자가 뭘 교정했는지 **사실로**.
2. **쓴 스킬** — `.claude/skill-usage.log`(형식 `시각<TAB>스킬명`) + 맥락:
   ```bash
   LOG=".claude/skill-usage.log"   # Bash 도구 cwd=프로젝트 루트. $CLAUDE_PROJECT_DIR는 훅에서만 채워지니 쓰지 말 것.
   test -f "$LOG" && tail -n 40 "$LOG" | cut -f2 | sort | uniq -c | sort -rn
   ```
3. **손댄 도메인** — 이번에 **편집한 코드 파일**을 `docs/domain/_territory.tsv`(경로 글롭 → slug)에 대조해 **두 갈래**로 추린다:
   ```bash
   test -f docs/domain/_territory.tsv && cat docs/domain/_territory.tsv
   ls docs/domain/*.md 2>/dev/null   # 이미 문서가 있는 도메인
   ```
   - **매칭됨** → 이미 문서가 있는 도메인. 렌즈 B가 **변경점(개선)**을 판단.
   - **매칭 안 됨** → `_territory`에 없는 편집 영역. 세션 서사와 함께 **"문서 없는 새 도메인 후보"**로 브리프에 적는다(렌즈 B가 신규 생성 대상인지 판단). 단 **서비스(업무) 도메인**만 후보다 — OS 인프라 작업(`.claude/` 스킬·훅, `docs/diagrams/`·컨텍스트 체계 등)은 도메인이 아니니 후보에서 뺀다.

> 브리프는 **사실만**. 마찰·학습의 **판단은 렌즈 에이전트에게** 넘긴다(자기 세션을 자기가 채점하지 않도록).
> 격리 에이전트는 브리프에 없는 건 못 보니, **브리프를 충분히 실어라.**

### 2. 두 렌즈 병렬 디스패치 — ★오케스트레이터가 서브에이전트 2개 스폰★

메인은 판단하지 않는다. **같은 세션 브리프**를 주고, `Task`로 **독립 `reviewer` 2개를 한 메시지에서 병렬로** 띄운다.
(관련 파일은 각 에이전트가 `Read`로 직접 연다.)

**렌즈 A — 스킬 개선** (`subagent_type: reviewer`, `description: "회고: 스킬 렌즈"`):
- **[대상]** 이번 세션에 쓴 스킬들의 `.claude/skills/<name>/SKILL.md`.
- **[기준]** 세션 브리프(마찰 신호) + 각 스킬의 "수용 기준·안전 규칙".
- **[관점]** "어떤 스킬의 어느 문구가 마찰을 유발/방치했나? **넣거나 고칠 한 줄**은? 근거 없는 개선·무겁게 만드는 제안(원칙 7) 금지. 마찰 없는 스킬은 '깨끗'."
- **[판정 형식]** 스킬별 제안 — 무엇을 / 왜(마찰) / 어떻게(문구). 없으면 "이번엔 없음".

**렌즈 B — 도메인 점검(개선 또는 신규) + 라우팅** (`subagent_type: reviewer`, `description: "회고: 도메인 렌즈"`):
- **[대상]** 도메인 목차 `docs/domain/README.md`(라우팅)로 손댄 **기존** 도메인을 찾아 그 `docs/domain/<slug>.md`(들)을 Read. **목차 자체도** 본다. 브리프의 **"문서 없는 새 도메인 후보"**도 함께 검토한다.
- **[기준]** (개선) 세션 브리프에서 그 도메인에 **새로 드러난 사실**(❓미확인 해소·새 이웃/관계·경계가 코드와 어긋남) + 목차 규모. (신규) 후보가 **문서로 남길 만한 서비스 도메인**인가 — 정체·경계가 잡히고, 일회성/OS 인프라가 아닌가.
- **[관점]** "① **기존 도메인(문서 있음)**: 이번 세션에서 **어떤 변경점**이 드러났나(문서에 아직 없는 사실·관계)? 근거는? ② **새 도메인(문서 없음)**: 후보 중 **정말 서비스 도메인**으로 문서화할 가치가 있는 건? (OS 인프라·일회성은 제외) ③ 목차(README)가 **너무 커졌나** → 세분화 검토가 필요한가? — **완성된 문서 편집은 만들지 마라.** 무엇을 어떻게 담을지는 /domain이 코드 스캔+인터뷰로 확정한다. 여기선 **리드(변경점/후보)와 근거만.**"
- **[판정 형식]** 도메인별 —
  - 기존: `변경점: <드러난 사실·근거> → /domain <slug> 재실행(개선) 권장` 또는 `변경점 없음(문서 최신)`.
  - 신규: `새 도메인 후보: <slug> — <정체 한 줄·근거> → /domain <slug>로 신규 작성 권장` 또는 `해당 없음`.
  - 목차 — `세분화 검토 권장 (근거: …)` 또는 `적정`.

> 왜 감지만 하나: 정확한 문서 내용은 **코드 스캔·인터뷰**로만 확정된다(retro엔 그 입력이 없다). 렌즈 B는 **변경점(리드)을 싸게 알아채는 데** 그치고,
> 확인·작성은 그 입력을 가진 `/domain`에 넘긴다 — **감지 vs 실행 분리**(`/impl`↔`/verify`와 같은 결). 중복도 사라진다.

> 왜 렌즈로 나눠 병렬인가: 두 렌즈는 성격이 다르고(프롬프트 vs 지식) 서로 독립이라 **동시에** 돌 수 있다.
> 왜 서브에이전트인가: 판단을 격리 컨텍스트로 밀어 **메인 맥락을 아끼고**, 자기 세션을 자기가 미화하지 않게 한다.

### 3. 종합·보고 게이트 — ★사용자에게 직접, 멈춤★

두 에이전트 결과를 렌즈별로 묶어 **사용자에게 대화로 직접 보고**하고 멈춘다.
**`docs/retro/` 같은 파일은 만들지 않는다** — retro는 세션 안에서 도는 오케스트레이터이므로 결과를 파일로 쌓지 않고
그 자리에서 사람에게 알린다. **애매하거나 확인이 필요한 건 추측하지 말고 그 자리에서 되묻는다.**

보고 형식(한눈 요약):
```
🔁 회고 완료 — 스킬 제안 M건 · 도메인 변경점 D건

## 렌즈 A — 스킬 개선 제안 (승인 시 /quick 급 반영)
- <스킬>: 무엇을 / 왜(마찰) / 어떻게(SKILL.md 어느 문구)   |  없으면 "이번엔 깨끗"

## 렌즈 B — 도메인 (개선: /domain 재실행 · 신규: /domain 새로 작성)
- <기존 도메인>: 변경점 <드러난 사실·근거> → /domain <slug> 재실행   |  없으면 "변경점 없음(문서 최신)"
- <새 도메인 후보>: <정체 한 줄·근거> → /domain <slug>로 새로 만들기 권장   |  없으면 생략
- 목차(README): 세분화 검토 권장(근거) / 적정

## ❓ 문제·궁금한 점 (있으면)
- 확인이 필요하거나 애매한 것은 여기서 **사용자에게 질문**한다(추측으로 넘기지 않음).
```

- **아무것도 자동으로 고치지 않는다.** 스킬은 승인 후 `/quick`, 도메인 변경점은 `/domain <slug>` 재실행 — 반영은 사람 몫.
- **이월을 파일로 쌓지 않는다.** 근거 약한 1회성 신호는 그냥 **언급만** 한다 — 다음 세션에도 문제면 /retro가 어차피 다시 감지한다(재발 = 자연 승격).
- **스킬도 도메인도 아닌 "일하는 방식"(행동) 교훈**이면 **auto-memory `feedback`** 저장을 사람에게 권한다.

- [ ] 결과를 **렌즈별로 사용자에게 직접 보고**하고, **파일을 만들거나 스킬·도메인 문서를 직접 고치지 않는다**(반영: /quick·/domain).

## 안전 규칙

- **판단만·제안만.** 스킬·도메인 문서를 자동으로 고치지 않는다(드리프트·열화 방지). 반영은 사람 게이트(/quick·/domain).
- **도메인 문서는 더 엄격히.** /prd·/plan에 먹이고 코드 편집 시 자동 주입되므로 틀린 지식이 널리 전파된다 — 추측 관계 금지.
- **셀프 채점 금지.** 판단은 격리된 reviewer(렌즈 에이전트)에게 던진다. 메인은 브리프만 싼다.
- **없는 개선 지어내지 않기.** 근거가 없으면 "이번엔 없음/깨끗". 억지 제안은 문서만 무겁게 한다(원칙 7).
- **얇게 유지 · 기본 2 에이전트.** 오케스트레이터는 렌즈 에이전트 2개만 스폰한다. 한 렌즈가 유난히 무거우면(손댄 스킬·도메인이 아주 많으면) 그 렌즈만 항목별로 더 쪼개도 되지만, 기본은 2개다.
- 서브에이전트가 빈 결과·오류를 돌려주면 그대로 알리고 멈춘다.

## 참고 / 범위 밖

- **지금은 수동 트리거만.** "매 세션 종료마다 자동"으로 돌리려면 SessionEnd 훅이 헤드리스 `claude -p "/retro"`
  를 부르게 하거나 `/schedule`(cron)로 야간 배치하면 된다 — **무한 재귀 가드가 필수**라, 제안 산출물이
  쓸모 있다고 검증된 뒤에 붙인다. (추후 확장)
- **경계 3분할:** 행동 지침(일하는 방식) = auto-memory `feedback` / 스킬 프롬프트 = 렌즈 A(반영 /quick) /
  도메인 지식 = 렌즈 B가 감지(**기존 개선·신규 생성** 둘 다), `/domain`이 반영(갱신 또는 신규 작성). (/retro는 두 렌즈 다 **감지·제안**까지.)
- **파일을 만들지 않는다.** 결과는 세션 중 사용자에게 직접 보고 — 이월/큐 파일이 없다(재발하면 다음 `/retro`가 다시 감지).
