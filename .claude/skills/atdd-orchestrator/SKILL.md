# ATDD 파이프라인 지휘자 (atdd-orchestrator)

`OS.md`에 정의된 ATDD 7단계 파이프라인을 처음부터 끝까지 이어서 실행하는 지휘자 스킬입니다. 이 스킬 자신은 **아무 일도 직접 하지 않습니다** — 인수기준을 분해하지도, 판정하지도, 테스트를 쓰지도, 구현하지도 않습니다. 각 단계를 담당하는 스킬과 서브에이전트를 순서대로 호출·중개하고, 단계 사이에서 결과를 전달하는 역할만 합니다.

```
01 요구사항   사람                          ← (이미지 첨부 시) Skill(ui-spec-from-image)
01.5 인터뷰   → Skill(requirement-interview) ← 슬롯 6개 중 3개 이상 결손일 때만
02 정책 분해  → Skill(spec-decompose)
03 독립 리뷰  → Agent(policy-reviewer)      ← 분해한 쪽과 컨텍스트 차단
04 정책 승인  → AskUserQuestion             ← 사람의 결정
05 실패 테스트 → Skill(acceptance-test-write) → Agent(test-reviewer)
06 TDD 구현   → Skill(tdd-implement)        → Agent(test-reviewer), (UI AC 시) Agent(ui-visual-reviewer)
07 실패 원장  → Skill(failure-ledger)        ← 기록 자체는 훅이 자동 수행
```

## 언제 쓰는가

사용자가 "ATDD 파이프라인 시작해줘", "지휘자 스킬 돌려줘", "요구사항 하나로 파이프라인 진행해줘", "orchestrator 실행해줘" 등을 요청할 때 사용한다.
**이 스킬은 어떤 단계도 직접 수행하지 않는다. 위임할 담당이 정해져 있는 일을 지휘자가 대신 해버리면 이 OS의 구조 자체가 무너진다.**

## 실행 절차

1. **요구사항 접수 (01단계, 사람 담당)**
   - 사용자가 이미 요구사항을 준 경우 그것을 사용한다. 없으면 먼저 물어본다.
   - 앞으로 어떤 순서(01.5→02→03→04)로 진행할지 한 문장으로 미리 안내한다.

1-1. **(조건부) 이미지 스펙 추출 위임 (01.5단계 전 → `ui-spec-from-image` 스킬 호출)**
   - 요구사항에 화면 이미지(목업)가 첨부되어 있는지 확인한다. **없으면 이 단계를 건너뛰고 바로 1-2로 간다.**
   - 있으면 왜 별도 스킬로 먼저 이미지를 분석하는지 한 문장으로 설명한 뒤, `Skill` 도구로 `ui-spec-from-image`를 호출한다.
   - 반환된 `ui-spec.md` 내용과 feature-slug, 저장된 `mockup.*` 경로를 보관한다. **01.5단계와 02단계 양쪽에 전달할 준비물**이다 — 인터뷰가 이미지에 이미 답이 있는 것을 다시 묻지 않게 하려면 인터뷰보다 먼저 확보해야 한다.

1-2. **(조건부) 요구사항 인터뷰 위임 (01.5단계 → `requirement-interview` 스킬 호출)**
   - 요구사항 원문만 읽고 6개 슬롯(목표 / 현재 상태 / 기대 동작 / 완료 조건 / 범위 밖 / 미해결 가정)을 채워 본다. **3개 이상 못 채우면 인터뷰에 들어간다.** 2개 이하면 이 단계를 건너뛰고 바로 02로 간다.
   - 판정 근거(어떤 슬롯이 비었는지)를 한 줄로 사용자에게 보여준다. "모호해 보인다"는 감각이 아니라 결손 슬롯 수로 판정해야 매번 같은 기준이 적용된다.
   - `Skill` 도구로 `requirement-interview`를 호출하고 요구사항 원문을 전달한다. **1-1에서 UI 스펙 문서를 확보했다면 함께 전달**한다.
   - 반환된 **인터뷰 브리프 경로와 내용**을 보관한다. 02단계의 입력은 이제 원문이 아니라 이 브리프다.
   - 사용자가 인터뷰 도중 "건너뛰고 진행"을 선택하면 즉시 존중하고 02로 넘어간다. 못 채운 슬롯은 미해결 가정으로 함께 전달한다.

2. **정책 분해 위임 (02단계 → `spec-decompose` 스킬 호출)**
   - 왜 이 단계를 직접 하지 않고 위임하는지 한두 문장으로 설명한다.
   - `Skill` 도구로 `spec-decompose`를 호출하고, **1-2에서 브리프를 받았으면 원문 대신 브리프를 전달**한다(인터뷰를 건너뛰었으면 원문을 그대로 전달). **1-1에서 UI 스펙 문서를 확보했다면 함께 전달**한다.
   - 반환된 인수기준 목록을 그대로 보관한다(임의로 요약/변형하지 않음).

3. **독립 리뷰 위임 (03단계 → `policy-reviewer` 서브에이전트 호출)**
   - 왜 별도 서브에이전트를 호출하는지, 왜 "독립적"이어야 하는지 설명한다.
   - **핵심 제약**: `Agent` 도구로 `policy-reviewer`를 호출할 때, 프롬프트에는 오직 (a) 요구사항 원문과 (b) `spec-decompose`가 반환한 인수기준 목록만 담는다. **UI AC가 있으면 (c) 원본 이미지(`mockup.*`) 경로와 (d) `ui-spec.md`도 함께 전달한다.** 오케스트레이터 자신의 판단·사전 평가, `spec-decompose`의 분해 근거는 절대 포함하지 않는다.
   - 반환된 PASS/FAIL과 이유를 **원문 그대로** 보관한다.
   - **지적을 지우거나 합치지 않는다.** 리뷰어가 낸 항목은 **개수 그대로** 04단계 승인 화면에 올린다. 구현 지식("이건 이미 커밋됐다", "코드에 이미 반영돼 있다")은 **지적을 지우는 근거가 아니라 항목에 덧붙이는 주석**으로만 쓴다. 무엇을 반영하고 무엇을 넘길지는 **04단계에서 사람이** 정한다 — 호출자가 사람의 결정을 미리 대신하지 않는다.
   - 이 제약이 필요한 이유: gitStatus(브랜치·최근 커밋 5개·변경 파일)는 환경이 주입하며 **서브에이전트에도 그대로 간다.** 저장소 안에서 끌 수 없다. 실측에서 리뷰어 자신은 흔들리지 않았지만, **호출자가 커밋 지식으로 리뷰어의 지적 5~6개를 2개로 깎았다**(`docs/context-ab-test.md` 실험 3). 새는 지점을 못 막으니 **쓰이는 지점**을 막는다.
   - **04단계로 넘기기 전에 기계 검사를 돌린다**(리뷰어 원문과 인계문을 각각 파일로 저장한 뒤):
     ```bash
     node -e "const{checkHandoff}=require('./.claude/lib/review-handoff.js');const fs=require('fs');console.log(JSON.stringify(checkHandoff({reviewerText:fs.readFileSync(process.argv[1],'utf-8'),handoffText:fs.readFileSync(process.argv[2],'utf-8')}),null,1))" <리뷰어원문> <인계문>
     ```
     `warnings`가 나오면 인계문을 고쳐 다시 돌린다. **`ok: true`가 인계가 정직했다는 보증은 아니다** — 항목 개수를 유지한 채 문장만 무력화하면 통과한다(`review-handoff.js` 주석과 AC-12에 명시). 이건 게이트가 아니라 경보다.

4. **정책 승인 게이트 (04단계, 사람 담당)**
   - 원문 요구사항 / 인수기준 목록 / PASS-FAIL 판정과 이유를 한 화면에 정리해서 보여준다. **리뷰어의 지적은 03단계에서 받은 개수 그대로 싣는다.**
   - FAIL이면 먼저 눈에 띄게 알리되, 최종 결정은 사람의 몫임을 분명히 한다.
   - `AskUserQuestion`으로 승인 여부를 묻는다. 선택지: "승인" / "수정 필요(재분해)" / "중단".
   - "수정 필요"면 피드백을 받아 2단계로 돌아간다. "중단"이면 종료.

5. **실패 테스트 작성 위임 (05단계 → `acceptance-test-write` 스킬 호출)**
   - 승인된 AC 목록을 그대로 전달한다. **승인 전에는 절대 이 단계로 넘어가지 않는다.**
   - `Skill` 도구로 `acceptance-test-write`를 호출한다. 이 스킬이 내부에서 `test-reviewer` 서브에이전트를 다시 호출한다는 점을 사용자에게 짚어준다(스킬 → 스킬 → 에이전트의 2단 위임). **UI AC가 포함된 경우 이 스킬이 `dom-lite.js` 기반 구조 검증 테스트도 함께 작성한다는 점을 짚어준다.**
   - 반환된 실패 로그를 보관한다. **테스트가 실패한 상태로 돌아오는 것이 정상**이며, 통과한 채로 돌아왔다면 05단계가 잘못된 것이므로 06으로 넘어가지 않는다.

6. **TDD 구현 위임 (06단계 → `tdd-implement` 스킬 호출)**
   - `Skill` 도구로 `tdd-implement`를 호출하고, 승인된 AC 목록과 05단계의 실패 로그를 전달한다. **UI AC가 포함된 경우 이 스킬이 구조 테스트 통과 후 스크린샷 촬영과 `ui-visual-reviewer`를 통한 시각 비교 게이트까지 추가로 수행한다는 점을 짚어준다.**
   - 이 스킬은 재시도 상한 3회를 스스로 관리한다. 지휘자가 상한을 대신 늘려주지 않는다. **UI AC가 있는 경우 이 3회 상한은 구조 테스트 재시도와 시각 비교 재시도를 합산해 공유한다** — 구현 재시도가 비싸다는 원칙은 UI든 아니든 동일하게 적용된다.
   - 3회 초과로 사람에게 인계되어 돌아오면 되돌아갈 지점을 **두 갈래로 나눠** 사용자에게 묻는다: **AC가 요구사항을 잘못 번역한 것이면 02단계(재분해)로**, **요구사항 자체가 틀렸거나 빠진 것이면 01.5단계(재인터뷰)로**. 01.5 재진입은 사이클당 1회만 허용한다. UI AC가 있었다면 실패 원인이 구조 테스트 문제인지 시각 비교 문제인지도 함께 전달한다.

7. **실패 원장 확인 위임 (07단계 → `failure-ledger` 스킬 호출)**
   - 기록 자체는 `atdd-failure-log.js` 훅이 `node --test` 실행 시 이미 자동으로 남겼다. 지휘자나 스킬이 원장에 직접 쓰지 않는다.
   - `Skill` 도구로 `failure-ledger`를 호출해 이번 사이클에서 무엇이 몇 번 깨졌는지 정리해 보여준다.
   - 같은 AC가 3회 이상 깨졌다는 경고가 나오면 그 사실을 사용자에게 분명히 전달한다.

8. **사이클 종료 보고**
   - 요구사항 → 최종 AC → 재분해 횟수 → 테스트 통과 여부 → 원장 요약을 한 화면으로 정리한다.
   - 어떤 스킬과 어떤 서브에이전트가 각각 몇 번 불렸는지 짚어 준다 — 이 OS가 어떻게 협업했는지 보여주는 것이 이 스킬의 목적이기 때문이다.

## 참고

- 스킬이 스킬을 부르고, 그 스킬이 다시 서브에이전트를 부르는 **2단 위임 구조**를 사용자가 눈으로 보게 하는 것이 이 스킬의 목적이다. 위임 직전 "왜 위임하는지" 설명을 생략하지 않는다.
- `policy-reviewer`·`test-reviewer` 호출 시 컨텍스트 최소화가 가장 어겨지기 쉬운 부분이다 — 리뷰어에게 자기 판단을 흘리지 않았는지 매번 스스로 점검한다.
- **컨텍스트 차단에는 두 종류가 있고 하나만 실재한다.** (a) 호출자가 자기 분해 과정·자기평가를 넘기지 않는 것은 실재하며 이 스킬이 지킨다. (b) 세션 컨텍스트(`CLAUDE.md` 체인·gitStatus)가 서브에이전트에 닿지 않는 것은 **성립하지 않는다** — 전원 상속된다(2026-09-07 실측). 그래서 (b)에 기대는 설계를 세우지 않는다.
- **리뷰 결과를 되돌려 옮길 때가 세 리뷰어 모두의 공통 약점이다.** 05단계(`test-reviewer`)와 06단계(`test-reviewer`·`ui-visual-reviewer`)에서도 같은 규칙이 적용된다 — 지적을 축소하지 않고 개수 그대로 사람에게 올린다.
- `test-reviewer`는 05·06 두 단계에서 모드만 바꿔 재사용되는 **공유 서브에이전트**다.
- 04단계에서 02로 되돌아가는 재분해 횟수에는 상한을 두지 않는다(스펙 논의는 값싸다). 반면 06단계의 구현 재시도는 3회로 제한한다(구현 삽질은 비싸다). **01.5 재인터뷰만 예외적으로 1회 상한**을 둔다 — 요구사항 자체를 다시 여는 일이 반복되면 사이클이 끝나지 않는다.
- 인터뷰 브리프는 **동결된 스냅샷**이다. 04단계에서 사람이 AC를 고쳐도 브리프를 갱신하지 않는다. 진실 원천은 승인된 AC 한쪽이고, 브리프는 '그때 무엇에 합의했는가'의 기록으로만 남는다.

## 예시

```
사용자: "ATDD 파이프라인 시작해줘. 요구사항은 '사용자가 비밀번호를 잊었을 때 이메일로 재설정 링크를 받을 수 있어야 한다'야."

[오케스트레이터] 01.5→02→03→04 순서로 진행하겠습니다.
[오케스트레이터] 슬롯 점검: 목표 ✅ / 현재 상태 ❌ / 기대 동작 ✅ / 완료 조건 ❌ / 범위 밖 ❌ / 미해결 가정 ❌
  → 4개 결손이라 인터뷰를 먼저 돌립니다 → Skill(requirement-interview) 호출
```
