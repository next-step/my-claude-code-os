# ATDD 파이프라인 지휘자 (atdd-orchestrator)

`OS.md`에 정의된 ATDD 7단계 파이프라인을 처음부터 끝까지 이어서 실행하는 지휘자 스킬입니다. 이 스킬 자신은 **아무 일도 직접 하지 않습니다** — 인수기준을 분해하지도, 판정하지도, 테스트를 쓰지도, 구현하지도 않습니다. 각 단계를 담당하는 스킬과 서브에이전트를 순서대로 호출·중개하고, 단계 사이에서 결과를 전달하는 역할만 합니다.

```
01 요구사항  사람                          ← (이미지 첨부 시) Skill(ui-spec-from-image)
02 정책 분해  → Skill(spec-decompose)
03 독립 리뷰  → Agent(policy-reviewer)      ← 분해한 쪽과 컨텍스트 차단
04 정책 승인  → AskUserQuestion             ← 사람의 결정
05 실패 테스트 → Skill(acceptance-test-write) → Agent(test-reviewer)
06 TDD 구현   → Skill(tdd-implement)        → Agent(test-reviewer), (UI AC 시) Agent(ui-visual-reviewer)
07 실패 원장  → Skill(failure-ledger)        ← 기록 자체는 훅이 자동 수행
```

## 언제 쓰는가

사용자가 "ATDD 파이프라인 시작해줘", "지휘자 스킬 돌려줘", "요구사항 하나로 파이프라인 진행해줘", "orchestrator 실행해줘" 등을 요청할 때 사용한다.
**이 스킬은 어떤 단계도 직접 수행하지 않는다. 위임할 담당이 정해져 있는 일을 지휘자가 대신 해버리면 이 OS의 구조 자체가 무너진다.**

## 실행 절차

1. **요구사항 접수 (01단계, 사람 담당)**
   - 사용자가 이미 요구사항을 준 경우 그것을 사용한다. 없으면 먼저 물어본다.
   - 앞으로 어떤 순서(02→03→04)로 진행할지 한 문장으로 미리 안내한다.

1-1. **(조건부) 이미지 스펙 추출 위임 (02단계 전 → `ui-spec-from-image` 스킬 호출)**
   - 요구사항에 화면 이미지(목업)가 첨부되어 있는지 확인한다. **없으면 이 단계를 건너뛰고 바로 02로 간다.**
   - 있으면 왜 별도 스킬로 먼저 이미지를 분석하는지 한 문장으로 설명한 뒤, `Skill` 도구로 `ui-spec-from-image`를 호출한다.
   - 반환된 `ui-spec.md` 내용과 feature-slug, 저장된 `mockup.*` 경로를 보관한다. 02단계에 전달할 준비물이다.

2. **정책 분해 위임 (02단계 → `spec-decompose` 스킬 호출)**
   - 왜 이 단계를 직접 하지 않고 위임하는지 한두 문장으로 설명한다.
   - `Skill` 도구로 `spec-decompose`를 호출하고 요구사항 원문을 전달한다. **1-1에서 UI 스펙 문서를 확보했다면 함께 전달**한다.
   - 반환된 인수기준 목록을 그대로 보관한다(임의로 요약/변형하지 않음).

3. **독립 리뷰 위임 (03단계 → `policy-reviewer` 서브에이전트 호출)**
   - 왜 별도 서브에이전트를 호출하는지, 왜 "독립적"이어야 하는지 설명한다.
   - **핵심 제약**: `Agent` 도구로 `policy-reviewer`를 호출할 때, 프롬프트에는 오직 (a) 요구사항 원문과 (b) `spec-decompose`가 반환한 인수기준 목록만 담는다. **UI AC가 있으면 (c) 원본 이미지(`mockup.*`) 경로와 (d) `ui-spec.md`도 함께 전달한다.** 오케스트레이터 자신의 판단·사전 평가, `spec-decompose`의 분해 근거는 절대 포함하지 않는다.
   - 반환된 PASS/FAIL과 이유를 보관한다.

4. **정책 승인 게이트 (04단계, 사람 담당)**
   - 원문 요구사항 / 인수기준 목록 / PASS-FAIL 판정과 이유를 한 화면에 정리해서 보여준다.
   - FAIL이면 먼저 눈에 띄게 알리되, 최종 결정은 사람의 몫임을 분명히 한다.
   - `AskUserQuestion`으로 승인 여부를 묻는다. 선택지: "승인" / "수정 필요(재분해)" / "중단".
   - "수정 필요"면 피드백을 받아 2단계로 돌아간다. "중단"이면 종료.

5. **실패 테스트 작성 위임 (05단계 → `acceptance-test-write` 스킬 호출)**
   - 승인된 AC 목록을 그대로 전달한다. **승인 전에는 절대 이 단계로 넘어가지 않는다.**
   - `Skill` 도구로 `acceptance-test-write`를 호출한다. 이 스킬이 내부에서 `test-reviewer` 서브에이전트를 다시 호출한다는 점을 사용자에게 짚어준다(스킬 → 스킬 → 에이전트의 2단 위임). **UI AC가 포함된 경우 이 스킬이 `dom-lite.js` 기반 구조 검증 테스트도 함께 작성한다는 점을 짚어준다.**
   - 반환된 실패 로그를 보관한다. **테스트가 실패한 상태로 돌아오는 것이 정상**이며, 통과한 채로 돌아왔다면 05단계가 잘못된 것이므로 06으로 넘어가지 않는다.

6. **TDD 구현 위임 (06단계 → `tdd-implement` 스킬 호출)**
   - `Skill` 도구로 `tdd-implement`를 호출하고, 승인된 AC 목록과 05단계의 실패 로그를 전달한다. **UI AC가 포함된 경우 이 스킬이 구조 테스트 통과 후 스크린샷 촬영과 `ui-visual-reviewer`를 통한 시각 비교 게이트까지 추가로 수행한다는 점을 짚어준다.**
   - 이 스킬은 재시도 상한 3회를 스스로 관리한다. 지휘자가 상한을 대신 늘려주지 않는다. **UI AC가 있는 경우 이 3회 상한은 구조 테스트 재시도와 시각 비교 재시도를 합산해 공유한다** — 구현 재시도가 비싸다는 원칙은 UI든 아니든 동일하게 적용된다.
   - 3회 초과로 사람에게 인계되어 돌아오면, 인수기준 자체가 문제일 수 있으므로 **2단계(재분해)로 되돌아갈지**를 사용자에게 묻는다. UI AC가 있었다면 실패 원인이 구조 테스트 문제인지 시각 비교 문제인지도 함께 전달한다.

7. **실패 원장 확인 위임 (07단계 → `failure-ledger` 스킬 호출)**
   - 기록 자체는 `atdd-failure-log.js` 훅이 `node --test` 실행 시 이미 자동으로 남겼다. 지휘자나 스킬이 원장에 직접 쓰지 않는다.
   - `Skill` 도구로 `failure-ledger`를 호출해 이번 사이클에서 무엇이 몇 번 깨졌는지 정리해 보여준다.
   - 같은 AC가 3회 이상 깨졌다는 경고가 나오면 그 사실을 사용자에게 분명히 전달한다.

8. **사이클 종료 보고**
   - 요구사항 → 최종 AC → 재분해 횟수 → 테스트 통과 여부 → 원장 요약을 한 화면으로 정리한다.
   - 어떤 스킬과 어떤 서브에이전트가 각각 몇 번 불렸는지 짚어 준다 — 이 OS가 어떻게 협업했는지 보여주는 것이 이 스킬의 목적이기 때문이다.

## 참고

- 스킬이 스킬을 부르고, 그 스킬이 다시 서브에이전트를 부르는 **2단 위임 구조**를 사용자가 눈으로 보게 하는 것이 이 스킬의 목적이다. 위임 직전 "왜 위임하는지" 설명을 생략하지 않는다.
- `policy-reviewer`·`test-reviewer` 호출 시 컨텍스트 최소화가 가장 어겨지기 쉬운 부분이다 — 리뷰어에게 자기 판단을 흘리지 않았는지 매번 스스로 점검한다.
- `test-reviewer`는 05·06 두 단계에서 모드만 바꿔 재사용되는 **공유 서브에이전트**다.
- 04단계에서 02로 되돌아가는 재분해 횟수에는 상한을 두지 않는다(스펙 논의는 값싸다). 반면 06단계의 구현 재시도는 3회로 제한한다(구현 삽질은 비싸다).

## 예시

```
사용자: "ATDD 파이프라인 시작해줘. 요구사항은 '사용자가 비밀번호를 잊었을 때 이메일로 재설정 링크를 받을 수 있어야 한다'야."

[오케스트레이터] 02→03→04 순서로 진행하겠습니다.
[오케스트레이터] 인수기준 분해는 별도 스킬(spec-decompose)의 책임이라 위임합니다 → Skill(spec-decompose) 호출
  ↳ AC-1, AC-2, AC-3 수신

[오케스트레이터] 방금 분해 맥락을 모르는 별도 에이전트에게 독립 리뷰를 맡기겠습니다 → Agent(policy-reviewer) 호출
  (전달 내용: 요구사항 원문 + AC-1~3 목록만)
  ↳ 판정: PASS

[오케스트레이터] (요구사항/인수기준/PASS 판정 요약 제시)
[AskUserQuestion] "이 인수기준으로 승인하시겠습니까?" → 사용자: "승인"

[오케스트레이터] 승인됐으니 테스트를 먼저 씁니다 → Skill(acceptance-test-write)
  ↳ 이 스킬이 다시 Agent(test-reviewer, TEST_QUALITY) 호출 — 2단 위임
  ↳ 3 fail / 0 pass (구현 없음) — 정직한 실패 확인

[오케스트레이터] 이제 통과시킵니다 → Skill(tdd-implement)
  ↳ 1회차/3회 → 1 fail, 2회차/3회 → 0 fail ✅
  ↳ 이 스킬도 Agent(test-reviewer, IMPL_HONESTY) 호출 → 판정: PASS

[오케스트레이터] 이번 사이클에 무엇이 깨졌는지 확인합니다 → Skill(failure-ledger)
  ↳ FAIL 2건, RESOLVED 1건 — 현재 🟢

[오케스트레이터] 사이클 완료. 스킬 4회·서브에이전트 3회 호출로 01~07단계를 마쳤습니다.
```
