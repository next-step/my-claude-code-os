# perf-fix · 재현·구현·검증

성능 개선 OS의 **두 번째 스킬**. Stage 3·4·5, 게이트 ②·③, 그리고 실패 라우팅을 담당한다.

## 핵심 원칙

**개선했다는 주장은 인정하지 않는다.**

이 스킬이 성공했다고 말할 수 있는 조건은 두 가지가 모두 충족될 때뿐이다.

1. **수치 개선** — 대상 API의 지표가 측정 가능하게 개선되었다
2. **회귀 방지** — 그 개선을 지키는 테스트가 레포에 남았다

2번 없는 1번은 성공이 아니다. 시간이 지나면 반드시 원래대로 돌아가기 때문이다.

# 0. 입력 — 재개 지점 찾기

입력은 `trace_id` 또는 APM URL. URL이면 `trace_id`만 뽑아 쓴다.

## 진행 거부 조건

```bash
ls .claude/perf-os/cycles/<trace_id>/
```

**`30-decision.md`가 없으면 진행하지 않는다.**

```
❌ 게이트 ①을 통과한 가설이 없습니다.
   먼저 /perf-diagnose <APM URL> 로 진단하세요.
```

무엇을 고칠지 사람이 고르지 않았는데 고치기 시작하면, 이 OS의 게이트 4개 중 첫 번째가 그냥 없는 것이 된다.

## 재개 지점

| 있는 파일 | 재개 지점 |
|---|---|
| `30-decision.md`까지 | Stage 3부터 |
| `40-test.md`까지 (게이트 ② 승인 기록 있음) | Stage 4부터 |
| `50-verify.md`까지 | 게이트 ③부터 |

## `attempts.json`을 먼저 읽는다

```bash
cat .claude/perf-os/cycles/<trace_id>/attempts.json
```

**모든 판단의 전제가 이 파일이다.** 루프 가드 카운터, 반증된 가설, 게이트에 표시할 시도 이력이 전부 여기서 나온다. 대화 맥락으로 세면 세션이 끊기는 순간 카운터가 리셋되어 루프 가드가 있으나 마나가 된다.

```json
{
  "analysis_attempts": [
    { "n": 1, "hypothesis": "...", "outcome": "pending|refuted|confirmed", "reason": null }
  ],
  "implementation_attempts": [
    { "n": 1, "analysis_n": 1, "approach": "...", "outcome": "pending|regression|insufficient|success", "detail": null }
  ]
}
```

`implementation_attempts`의 `analysis_n`은 **어느 가설 하에서의 시도인가**를 가리킨다. 이게 없으면 가설이 바뀌어도 구현 카운터가 이어져, 새 가설의 첫 시도가 곧바로 승격 조건에 걸린다.

**단계가 끝날 때마다 이 파일을 갱신한다.** 나중에 몰아서 쓰지 않는다 — 세션이 끊기면 그 사이 이력이 통째로 사라진다.

# 1. Stage 3 · 재현 테스트 작성

| 항목 | 내용 |
|---|---|
| **입력** | `30-decision.md`의 선택된 가설 |
| **산출** | **실패하는** 테스트 + 실패 로그 |
| **진행 조건** | 테스트가 실제로 실패할 것 |

## 1-1. 환경

**프로덕션과 같은 종류·같은 엔진의 데이터 저장소로 테스트한다.**

인메모리나 경량 대체 DB로는 성능 문제가 재현되지 않는다. 인덱스 사용 여부, 실행 계획, 풀스캔 비용이 프로덕션과 다르기 때문이다. H2로 "N+1을 재현했다"고 말하는 순간 그 테스트는 게이트 ②를 통과할 수 없다.

레포에 이미 Testcontainers 등 실 DB 하네스가 있으면 그것을 쓴다. 없으면 **이 케이스에 필요한 만큼만** 만든다. 범용 성능 테스트 인프라를 선제 구축하지 않는다 — 그것은 이 사이클의 범위 밖이고, 게이트 ②의 판단 대상을 흐린다.

## 1-2. 데이터 규모

문제가 실제로 터지는 규모를 시딩한다. 근거는 `20-hypotheses.md`의 Lane B 산출 **"재현 테스트용 규모 근거"** 절에 있다. 없으면 집계표의 반복 횟수로 역산한다.

## 1-3. 단정은 시간이 아니라 구조로 한다

```
# ❌ 실행 환경에 따라 흔들리는 flaky 단정
assert elapsed < 200ms

# ❌ 구조 단정이지만 취약 — 정당한 쿼리 하나만 늘어도 깨진다
assert queryCount == 2

# ✅ 스케일 불변 단정 — 리팩터링에 강건하고, N+1이 되살아나면 반드시 깨진다
q10  = countQueries { fetchDashboard(seed = 10) }
q100 = countQueries { fetchDashboard(seed = 100) }
assert q10 == q100              # 데이터가 10배여도 쿼리 수는 그대로

# ✅ 실행 계획 단정 — 쿼리를 어떻게 고쳐 쓰든 인덱스를 타면 통과한다
assert plan.hasNoFullScan()
```

시간 단정은 CI 부하에 따라 흔들려 결국 무시되거나 지워진다. 고정 개수 단정(`== 2`)은 정당한 변경에도 깨져서 같은 운명을 맞는다. **살아남는 단정은 "무엇이 참이어야 하는가"를 짚는 것뿐이다.**

Lane C가 실행 계획을 봤다면 단정 형태는 이미 정해져 있다. 무엇이 사실인지 알면 무엇을 단정할지도 안다.

## 1-4. 반드시 먼저 실패해야 한다 (분기점)

테스트를 돌린다. **개선 전에 통과해버리면 진행하지 않는다.**

| 이유 | 의미 |
|---|---|
| **진단이 틀렸다** | 짚은 것이 실제 병목이 아니다 |
| **환경이 프로덕션을 못 흉내 냈다** | 데이터 규모나 스키마가 부족하다 |

먼저 두 번째를 배제한다 — 규모를 프로덕션 상위 구간까지 올려도 통과한다면 첫 번째다.

첫 번째로 판정되면 **§4 실패 라우팅의 "분석 오류" 경로로 간다.** 구현으로 넘어가지 않는다. 이것이 "성능을 개선했다"는 착각을 막는 유일한 장치다.

실패 로그를 `40-test.md`에 **원문 그대로** 남긴다. 게이트 ②의 판단 재료이므로 요약하면 안 된다.

# 2. 🚦 게이트 ② · 이 테스트가 진짜인가 (HARD GATE)

| 항목 | 내용 |
|---|---|
| **판단 주체** | 사람 |
| **판단 재료** | 테스트 **코드 전문** + 개선 전 **실패 로그** |

> **4개 게이트 중 가장 중요하다.**

AI에게 테스트를 시키면 **통과하는 테스트**를 쓰려는 압력이 생긴다. 문제를 실제로 재현하지 않는 가짜 테스트가 만들어지면, 이후 "개선 성공"이라는 **모든 판정이 그 위에 얹힌다.** 틀린 기반 위에 쌓인 확신이 가장 위험하다.

## 제시 형식

```
게이트 ② — 이 테스트가 진짜인가요?

■ 테스트 코드 (전문)
  src/test/.../DashboardPerfTest.kt
  <코드 전문. 요약 금지>

■ 개선 전 실행 결과 (원문)
  <실패 로그>

■ 사람이 확인할 것
  1. 데이터 규모가 프로덕션의 실제 최악 구간에 준하는가
     → 시딩: member 5,000 / attachment 120,000 (근거: Lane B 역산)
  2. 단정이 구조적인가, 시간 기반인가
     → 스케일 불변 단정 (q10 == q100). 고정값에 묶여 있지 않음
  3. 개선 전에 진짜로 실패했는가
     → 위 로그: expected 12, actual 312
  4. 이 테스트가 깨지면 정말 그 문제가 재발한 것인가
     → <답>

승인할까요? (승인 / 반려 + 사유)
```

**코드를 요약해서 제시하지 않는다.** 요약은 사람이 검증할 수 있는 것을 없앤다. 길어도 전문을 보인다.

## 분기

- **승인** → Stage 4. 승인 사실과 시각을 `40-test.md`에 기록한다
- **반려** → Stage 3으로. 수정 후 **이 게이트를 다시 통과해야 한다**

# 3. Stage 4 · 개선 구현

| 항목 | 내용 |
|---|---|
| **입력** | 승인된 가설 + 승인된 테스트 |
| **산출** | 변경 코드 |
| **진행 조건** | 빌드·정적 검사 통과 |

시작할 때 `implementation_attempts`에 항목을 추가한다(`outcome: "pending"`, `analysis_n`은 현재 가설 번호).

**테스트를 고쳐서 통과시키지 않는다.** 게이트 ②를 통과한 테스트는 이 사이클의 기준이다. 기준을 움직이면 측정이 사라진다. 테스트가 잘못됐다고 판단되면 §4의 "테스트 오류" 경로로 가서 게이트 ②를 다시 받는다.

변경 범위는 선택된 가설에 한정한다. 눈에 띄는 다른 성능 문제는 `50-verify.md`의 잔여 리스크에 적고 손대지 않는다. 범위가 번지면 게이트 ③에서 무엇이 개선에 기여했는지 가릴 수 없어진다.

# 4. Stage 5 · 검증

| 항목 | 내용 |
|---|---|
| **담당** | `perf-trace-collector` (`mode: after`) |
| **진행 조건** | 아래 3가지 **모두** 충족 |

1. Stage 3의 재현 테스트가 **통과**한다
2. 기존 테스트 전체가 **무회귀**다
3. before/after 측정치가 기록되었다

## after 측정은 같은 에이전트·같은 축으로

```
mode: after
trace_id: <재현 트레이스의 trace_id>
timeHint: <...>
baseline_digest: <10-baseline.md의 "측정 스냅샷" 절 전체>
```

**`baseline_digest`를 반드시 넘긴다.** 측정 방법이 다르면 before/after 비교 자체가 무의미해지고, 성공 기준 1번("수치 개선")이 성립하지 않는다. collector는 이 필드가 없으면 측정을 거부한다.

결과를 `50-verify.md`에 쓴다. **하나라도 실패하면 아래 실패 라우팅으로 간다.**

# 5. 실패 라우팅

> "테스트가 실패했으니 구현을 고친다"는 AI에게 가장 자연스러운 반응이다. **문제는 분석이 틀렸을 때도 똑같이 반응한다는 것이다.** 병목을 잘못 짚었는데 구현만 계속 바꾸면 다섯 번을 고쳐도 지표는 움직이지 않고 토큰과 시간만 태운다.

## 5-1. 판별 신호 — 지표가 얼마나 움직였는가

| 관측된 현상 | 해석 | 복귀 지점 |
|---|---|---|
| 지표가 **개선됐지만 목표 미달** (쿼리 100 → 40, 목표 2) | 방향은 맞고 정도가 부족 → **구현 오류** | **Stage 4** |
| **다른 테스트가 깨짐** (회귀 발생) | 구현의 부작용 → **구현 오류** | **Stage 4** |
| 지표가 **거의 안 움직임** (쿼리 100 → 98) | 고쳤는데 아무 일도 안 일어남 → **분석 오류** | **Stage 2** |
| **엉뚱한 지표만** 개선됨 | 진단이 다른 문제를 보고 있었음 → **분석 오류** | **Stage 2** |
| 개선 전후 측정이 **완전히 동일**한데 코드는 실제로 달라졌음 | 테스트가 변화를 감지하지 못함 → **테스트 오류** | **Stage 3** |
| 위 어디에도 명확히 해당하지 않음 | 판단 보류 | **사람에게 질문** |

핵심 판별식은 한 줄이다. **"고쳤는데 변화가 없다 = 분석이 틀렸다."**

마지막 행을 실제로 쓴다. 애매한 것을 억지로 위 다섯 줄에 밀어 넣는 것이 이 표를 무력화하는 방법이다.

## 5-2. 세 갈래 모두 스킬 이동은 없다

| 복귀 지점 | 실제로 하는 일 | 스킬 이동 |
|---|---|---|
| Stage 4 | 구현 재작성 | 없음 |
| Stage 3 | 테스트 재작성 + **게이트 ② 재통과** | 없음 |
| Stage 2 | **3-lane 에이전트 재호출 + 게이트 ① 재실행** | **없음** |

복귀 지점이 Stage 2여도 `perf-diagnose`를 호출하지 않는다(R1). **Stage 2는 스킬이 아니라 3-lane 에이전트**이고, 이 스킬이 자기 자리에서 직접 다시 부른다.

## 5-3. → Stage 2 (분석 오류)

### Stage 1은 다시 하지 않는다

트레이스는 이미 일어난 일의 **불변 기록**이므로 재수집해도 같은 데이터가 나온다. 틀린 것은 증거가 아니라 **해석**이다. 재호출 입력으로는 저장된 `10-baseline.md`를 그대로 쓴다.

### 반증을 명시적 입력으로 넣는다

먼저 `attempts.json`을 갱신한다.

```json
{ "n": 1, "hypothesis": "대시보드 조회의 N+1", "outcome": "refuted",
  "reason": "수정 후 쿼리 100→98. 병목 아님" }
```

그 다음 `outcome: "refuted"`인 항목을 뽑아 `refuted_hypotheses[]`를 만들고, 세 레인에 **한 메시지로** 넘긴다.

```
반증 정보: "가설 X(N+1)를 수정했으나 쿼리 수 무변화. 따라서 X는 병목이 아님."
```

**같은 결론을 두 번 내리지 않게 하는 장치다.** 이것이 없으면 세 레인이 매번 같은 답을 내놓는다.

`bp_excerpt`는 Lane B에만 준다(최초와 동일). 새 가설은 `20-hypotheses.md`에 **덧붙인다** — 덮어쓰지 않는다. 반증된 가설의 기록이 남아 있어야 Stage 6의 교훈이 나온다.

### 게이트 ①을 다시 실행한다 — 화면이 달라진다

| 최초 (`perf-diagnose`) | 재진입 (여기) |
|---|---|
| 가설 목록 (5개 항목) | 가설 목록 + **이미 반증된 가설과 그 이유** + **시도 횟수** |

재진입 화면은 최초의 **상위집합**이고, 그 차이는 `attempts.json`이 그대로 결정한다.

```
게이트 ① (재진입 · 분석 시도 2회차) — 무엇을 고칠까요?

■ 이미 반증된 가설
  1. 대시보드 조회의 N+1
     → 수정 후 쿼리 100→98. 병목 아님

■ 새 가설
  [1] ...

⚠️ 분석 시도 1회 실패. 한 번 더 실패하면 파이프라인을 중단하고 에스컬레이션합니다.
```

> **여기가 이 설계의 약한 고리다.** 게이트 ①의 공용 파일을 두지 않았으므로, 이 스킬이 이력 섹션을 빠뜨려도 구조적으로 막히지 않는다. 막는 것은 이 절이 `attempts.json`을 명시적 입력으로 요구하는 것뿐이다. 누락되면 **사람은 "이미 두 번 틀렸다"는 사실을 모른 채 세 번째 선택을 하고**, 아래 루프 가드가 형식만 남는다.

새 가설이 선택되면 `analysis_attempts`에 `n+1` 항목을 `pending`으로 추가하고 Stage 3으로 간다. **테스트도 새로 쓴다** — 가설이 바뀌었으므로 이전 테스트는 다른 것을 재현하고 있다.

## 5-4. → Stage 4 (구현 오류)

가설과 테스트는 유효하다. 구현 방식만 바꾼다. **게이트 재통과는 필요 없다.**

`implementation_attempts`의 현재 항목 `outcome`을 `regression` 또는 `insufficient`로 갱신하고, 새 항목을 `pending`으로 추가한다.

## 5-5. → Stage 3 (테스트 오류)

테스트를 수정한 뒤 **게이트 ②를 반드시 다시 통과해야 한다.**

사람이 승인했던 것은 **수정 전의 테스트**다. 내용이 바뀌었다면 그 승인은 무효다. 재승인 없이 진행하면 게이트 ②는 형식만 남고, **그 순간 이후 모든 "성공" 판정의 근거가 사라진다.**

## 5-6. 루프 가드 — 자동 승격

```
구현 재시도 2회 실패  →  강제로 분석 단계(Stage 2)로 승격
분석 재시도 2회 실패  →  파이프라인 중단, 사람에게 에스컬레이션
```

**카운트는 `attempts.json`의 배열로 센다.**

| 카운터 | 세는 법 |
|---|---|
| 구현 재시도 | `implementation_attempts` 중 **현재 `analysis_n`**이고 `outcome`이 실패인 항목 수 |
| 분석 재시도 | `analysis_attempts` 중 `outcome == "refuted"` 항목 수 |

`analysis_n`으로 범위를 좁히는 것이 핵심이다. 가설이 바뀌면 구현 카운터는 0부터 다시 센다 — 새 가설의 첫 시도가 조기 승격에 걸리면 안 된다.

에스컬레이션 시에는 **중단하고 사람에게 넘긴다.** 세 번째 분석을 자동으로 시작하지 않는다.

```
⛔ 분석 2회 실패. 파이프라인을 중단합니다.

  반증된 가설 2개:
    1. ... → ...
    2. ... → ...

  이 트레이스만으로는 원인에 도달하지 못했습니다.
  다음을 검토해 주세요:
    - 다른 트레이스(더 느린 샘플)로 다시 진단
    - 이 API가 아니라 상류/하류가 원인일 가능성
    - 진단에 필요한 관측 도구가 빠져 있는지 (DBM, 프로파일러)
```

# 6. 🚦 게이트 ③ · 이 구현을 승인하는가 (HARD GATE)

| 항목 | 내용 |
|---|---|
| **판단 주체** | 사람 |
| **판단 재료** | 변경 diff + 측정 결과 + 잔여 리스크 + **되돌리기 방법** |

> **수치가 좋은 것과 방식이 옳은 것은 별개의 판단이다.**

캐시를 덧대 p95는 내려갔지만 정합성 리스크가 생겼다면, 수치만 보고 승인해서는 안 된다. 성능은 종종 다른 무언가와의 교환으로 얻어지며, **무엇을 내주었는지는 사람이 판단해야 한다.**

```
게이트 ③ — 이 구현을 승인하시겠습니까?

■ 변경 diff
  <git diff>

■ 측정 결과 (같은 축·같은 필터)
  | 지표 | before | after | 변화 |
  |---|---|---|---|
  | 쿼리 수 | 312 | 2 | -99.4% |
  | 총 소요 | 1,840ms | 190ms | -89.7% |

■ 테스트
  재현 테스트: 통과
  전체 테스트: 무회귀 (<n>개 통과)

■ 잔여 리스크
  - <무엇을 내주었는가. 없으면 "없음">

■ 되돌리기
  - <이 변경을 되돌리는 방법. 데이터 마이그레이션이 있으면 반드시>

승인할까요? (승인 / 반려 + 사유)
```

**"잔여 리스크: 없음"을 쉽게 쓰지 않는다.** 정말 없는지 한 번 더 본 뒤에 쓴다. 이 칸이 습관적으로 "없음"으로 채워지면 게이트 ③은 수치 확인 절차로 전락한다.

## 분기

- **승인** → 종료. `perf-learn`을 안내한다
- **반려** → Stage 4 (다른 방식으로 재구현). `implementation_attempts`에 반려 사유를 기록한다

## 절대 금지

| 금지 | 이런 생각이 들면 위반 직전 | 실제 |
|---|---|---|
| 테스트를 고쳐 통과시키기 | "단정이 좀 빡센 것 같은데" | 게이트 ②를 통과한 테스트가 이 사이클의 기준이다. 기준을 움직이면 측정이 사라진다 |
| 지표 무변화인데 Stage 4 반복 | "구현을 좀 더 다듬으면" | **고쳤는데 변화가 없다 = 분석이 틀렸다.** 다섯 번 고쳐도 안 움직인다 |
| 테스트 수정 후 게이트 ② 생략 | "사소한 수정이라 재승인은 과하지" | 승인한 건 수정 전 테스트다. 그 순간 이후 모든 성공 판정의 근거가 사라진다 |
| `baseline_digest` 없이 after 측정 | "같은 도구니까 알아서 맞겠지" | 측정 방법이 다르면 before/after가 비교 불가다. collector가 거부한다 |
| 인메모리 DB로 재현 | "빠르고 CI에도 편한데" | 인덱스·실행 계획·풀스캔 비용이 프로덕션과 다르다. 게이트 ②를 통과할 수 없다 |
| 시간 기반 단정 | "제일 직관적이잖아" | CI 부하에 흔들려 결국 무시되거나 지워진다. 회귀 방지 장치가 사라진다 |
| `attempts.json` 갱신 미루기 | "끝나고 한 번에 쓰지" | 세션이 끊기면 이력이 통째로 사라지고 루프 가드가 리셋된다 |
| 재진입 게이트에서 이력 생략 | "가설만 보면 되지 않나" | 사람이 "이미 두 번 틀렸다"를 모른 채 세 번째를 고른다. 이 설계의 약한 고리다 |
| 루프 가드 무시하고 3회차 자동 진행 | "이번엔 될 것 같은데" | 사람이 안 보면 안 끊기는 루프다. 그래서 카운터를 파일에 둔 것이다 |
| 범위 확장 | "보이는 김에 저것도 고치자" | 무엇이 개선에 기여했는지 가릴 수 없어진다. 잔여 리스크에 적고 넘어간다 |
| `git commit` / `push` | "다 됐으니 커밋까지" | 범위 밖이다. 게이트 ③ 승인은 "코드 승인"이지 "커밋 승인"이 아니다 |
