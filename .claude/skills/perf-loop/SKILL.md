# /perf-loop — 게이트 달린 성능 개선 랄프 루프

속도 개선을 **반복(루프)**으로 한다. 단 순수 랄프 루프("같은 프롬프트 무한 반복")가
성능·정산 코드에서 만드는 두 가지 사고를 게이트로 막는다.

> **사고 1 — 측정 안 된 승리.** "빨라 보인다"고 채택하면 착각이 쌓인다. → **측정 게이트**: 숫자 없으면 변경은 0점.
> **사고 2 — 조용한 동작 변경.** 성능 최적화가 결과를 바꾸면 그건 버그다. → **정확성 게이트**: `/verify` 로 확인, 실패면 즉시 되돌림.

전달된 인자: `<대상>` (예: "정산 배치 CALC_METER", "이 함수", 파일/디렉토리 경로)
- 없으면 → "무엇의 속도를 개선할까요? 그리고 어떻게 측정하나요(벤치마크·입력)?"를 묻고 시작한다.

이 스킬은 **속도(latency/throughput)** 만 다룬다. 메모리·정확성·기능 추가는 범위 밖(각각 별 트랙).

## 이 트랙은 /prd → /plan 과 분리된다 (독립 트랙)

성능 개선은 기능 개발 흐름(`/prd → /plan → /impl`)을 **타지 않는다.** 이유:

- prd/plan 은 "무엇을 만들까"(새 동작 정의)가 핵심인데, 성능 개선은 **동작을 바꾸지 않는 게 전제**다.
  요구사항 인터뷰·사용자 시나리오·수용 기준이 대부분 공회전한다.
- 성능 트랙의 승인 기준은 **문서(사람이 스펙 승인)가 아니라 측정 숫자**다.
  게이트가 다르다 — prd/plan 의 "설계 승인" 대신 **측정 게이트 + 정확성 게이트**.

따라서 `/quick` 처럼 **prd·plan 을 건너뛴다.** 대신 정확성은 `/verify` 로, 개선은 벤치마크로 검증한다.
단 **동작을 바꿔야 빨라지는 경우**(예: 캐시 도입으로 일관성 모델 변경, 근사 계산으로 정확도 트레이드오프)는
이 트랙 범위 밖이다 → 그건 새 동작이므로 `/plan` 으로 보낸다.

## 0단계 — 루프를 돌릴 수 있는지부터 확인 (★가장 중요★)

**재현 가능한 벤치마크가 없으면 이 스킬은 시작하지 않는다.** 측정 못 하는 최적화는 랄프 루프가 아니라 도박이다.

착수 전에 사람과 함께 아래를 확정한다:

1. **벤치마크** — 무엇을 어떤 입력으로 재는가? (같은 입력이어야 before/after 비교가 성립)
   - 있으면: 그 명령/스크립트를 확보.
   - 없으면: **먼저 만든다.** 마이크로벤치(단위 함수)든, 대표 입력으로 도는 실행이든, 로그의 `elapsed=..ms`든.
     정산처럼 계측조차 없으면 계측부터 넣는다(이건 별 커밋).
2. **지표** — p50/p95 latency? 총 실행시간? 처리량? 쿼리 수? **하나를 주지표로 못박는다.**
3. **환경 고정** — warm/cold, 데이터 규모, 동시성. 매 라운드 같은 조건이어야 한다.
4. **정확성 기준** — "결과가 같다"를 무엇으로 확인하나? 기존 테스트? 출력 스냅샷? `/verify` 강도?

> 벤치마크가 흔들리면(노이즈가 개선폭보다 크면) 루프가 노이즈를 쫓는다. **최소 3회 측정해 중앙값·분산을 본다.**

## 1단계 — 베이스라인 고정 + 문서 두 개 분리

주지표를 **N회(기본 3, 노이즈 크면 더) 측정**해 중앙값을 베이스라인으로 박는다.

**문서는 두 개로 분리한다** (한 파일에 섞지 마라 — 사용자 요청):
- **`docs/perf/<slug>-loop.md` = 런북** — *루프를 돌리는 방법*: 벤치마크·환경·트리거·VPN 등 주의·루브릭·절차·정리. **라운드 기록은 넣지 않는다.**
- **`docs/perf/<slug>-rounds.md` = 라운드 로그** — *라운드마다 무엇을 왜 바꿨고 결과가 어땠나*(R0, R1, …). 맨 위에 누적 요약 + **루프 총 경과**를 유지.

문서 저장 위치는 프로젝트 관례를 따른다(예: 코드가 batch 저장소라도 문서는 지정된 문서 저장소에). 경로가 gitignore면 게이트에서 알린다.
런북 맨 위에 벤치마크·목표를 고정하고, R0는 라운드 로그의 첫 스냅샷(§R-e 형식)으로 남긴다.

라운드 로그(`<slug>-rounds.md`) 상단:
```markdown
# perf-loop — <대상> · 라운드 로그
> 루프 돌리는 법은 <slug>-loop.md. 이 문서는 라운드별 변경 기록.
한 줄 요약(누적): baseline `<B>` → 현재 `<C>` (누적 <±%>) · 목표 `<T>`
루프 총 경과: <착수 YYYY-MM-DD HH:MM> ~ <현재> · 누적 ~<N>분 · 완료 라운드 <k> (채택 <a> / 폐기 <d>)

## R0 · baseline · <YYYY-MM-DD HH:MM>
- **시간**: 시작 `<HH:MM>` · 종료 `<HH:MM>` · 소요 `~N분`
- **측정** (<지표>, n회 중앙값): `<중앙값>` (n회: [측정치들])  · 환경: <재현 조건>
- **정확성**: <상태>
- **진단**: <병목이 어디로 보이는지 — 다음 후보의 근거>
- **누적**: baseline `<B>`  (목표 `<T>`)
```

## 루프 — 매 라운드 반복

### R-a. 후보 발굴 + 루브릭 채점 (변경 전)

이번 라운드에 시도할 **최적화 후보들**을 뽑는다(프로파일·핫패스·N+1·불필요 반복·배치화 등).
각 후보를 아래 루브릭으로 **점수화**해 **딱 하나** — 기대이득/위험이 가장 좋은 것 — 을 고른다.
(변경 전엔 "속도 목표 달성"을 가설 점수로, 변경 후엔 실측으로 다시 채점한다.)

> **속도 목표**: 대상마다 명시적 목표 시간을 정한다(호출자가 준다). 예: "CALC_METER ≤ 2:30(150초)".
> 목표가 없으면 사람에게 묻는다. 목표 대비로 "속도 목표 달성" 항목을 채점한다.

### 점수 루브릭 — 총점 100, **≥90 만 통과** (정확성은 하드 게이트)

각 후보/변경을 항목별로 채점해 합산한다. **정확성 게이트 실패 시 총점 무관하게 불합격.**

| 항목 | 배점 | 채점 기준 |
|------|-----:|-----------|
| **① 정확성 보존** (하드 게이트) | **30** | `/verify`(동작 보존 핵심이면 full) 통과 **AND** 산출물이 종전과 동일(금액·정산은 수·시각·키까지). **실패 시 전체 불합격.** |
| **② 속도 목표 달성** | **30** | 주지표가 **목표 이하면 30점**. 목표~베이스라인 사이는 선형 부분점. 개선 없음/악화 → 0. (변경 전엔 가설 점수) |
| **③ 측정 신뢰성** | **15** | 같은 조건 N회(≥3) 중앙값, 개선폭 > 노이즈(분산), before/after 숫자 명시. 추측·1회 → 감점. |
| **④ 블라스트 반경 / 되돌리기** | **10** | 변경 범위 좁고 격리됨, revert 쉬움. 공유 base·핫코어 광범위 수정일수록 감점. |
| **⑤ 스케일 지속성** | **10** | 큰 N/운영 규모에서도 유효(알고리즘 O 개선 > 상수배). 장난감 입력에서만이면 감점. |
| **⑥ 유지비** | **5** | 속도당 추가 복잡도·가독성 손실이 낮을수록 만점. |

- **통과 = 총점 ≥ 90 그리고 정확성 게이트 통과.** 5차원 이상 요구를 충족한다(위 6항목).
- 후보 선택 시엔 이 루브릭의 "기대 점수"로 가장 높은 하나를 고르고, R-c/R-d 뒤 실측으로 재채점해 채택/폐기를 정한다.
- 대상에 맞게 항목을 더해도 된다(예: DB 부하, 메모리 트레이드오프) — 배점은 100 합이 되게 재조정.

**후보가 많으면(≥4) 이 채점을 Workflow 판정 패널로 팬아웃**할 수 있다 — 후보마다 독립 채점 에이전트를
병렬로 띄워 루브릭 점수를 받는다(루브릭 = 판정 패널). 후보가 적으면 인라인으로 채점한다.

### R-b. 변경 (하나만)

고른 후보 **하나만** 구현한다. 여러 개를 한 라운드에 섞지 않는다 — 섞으면 어느 게 효과였는지 분리 측정이 안 된다.
큰/광범위 변경이면 `Task`로 구현 에이전트에 던지고, 작으면 인라인.

### R-c. 재측정 (측정 게이트)

베이스라인과 **같은 조건으로 N회 재측정**. 중앙값을 비교한다.

- **개선폭이 노이즈(분산) 안이면 → 효과 없음으로 본다.** "그럴듯한데 숫자가 안 나옴"은 실패다.

### R-d. 정확성 검증 (정확성 게이트)

`/verify` 를 호출한다(0단계에서 정한 강도). 동작 보존이 핵심이면 **full**.
- **통과** → R-e로.
- **구현결함/설계문제** → 이 변경은 **되돌린다**(아래 채택/폐기). 속도가 빨라졌어도 결과가 틀리면 폐기다.

### R-e. 채택 / 폐기 결정 (랄프 루프가 쓰레기를 안 쌓는 핵심)

**R-a 루브릭으로 실측 재채점** → 총점을 낸다. 결정:

| 루브릭 총점 | 정확성 게이트 | 결정 |
|---|---|---|
| **≥ 90** | 통과 | **채택** — 베이스라인 갱신, 로그 기록, 커밋 후보로 |
| < 90 | 통과 | **폐기(되돌림)** — 목표 미달·측정 약함·복잡도 과다 등 |
| — | 실패 | **폐기(되돌림)** — 빨라도 틀리면 버그(하드 게이트) |

폐기는 `git`으로 그 변경만 되돌린다(작업 트리에 다른 미커밋 변경이 있으면 그것까지 날리지 않게 주의).

**매 라운드가 끝날 때마다(채택이든 폐기든) 반드시 아래 스냅샷을 라운드 로그 `docs/perf/<slug>-rounds.md` 에 append 한다** — 런북(`-loop.md`)이 아니라 **라운드 로그**에. 이건 강제다: 한 라운드를 마치면(측정+검증+결정) 다음 라운드로 넘어가기 전에 반드시 기록한다.
폐기 라운드(왜 안 됐는지)도 다음 판단의 자산이다.
스냅샷은 한 라운드의 완결된 기록이라, 나중에·다른 세션이 이 파일만 보고 진행 상황·시도 이력·현재 위치를 파악할 수 있어야 한다.
**append 할 때마다 라운드 로그 상단의 누적 요약 + 루프 총 경과(착수~현재, 총 소요, 완료 라운드 수)도 갱신한다.**

```markdown
## R<n> · 〈채택 | 폐기〉 · <YYYY-MM-DD HH:MM>
- **시간**: 시작 `<YYYY-MM-DD HH:MM>` · 종료 `<YYYY-MM-DD HH:MM>` · 소요 `~N분`
- **후보**: <무엇을 왜 바꿨나 — 한 줄>
- **변경**: <손댄 파일 / 커밋 후보 해시(있으면)>
- **측정** (<주지표>, n회 중앙값): before `<X>` → after `<Y>`  (**<±ZZ%>**)
  - 세부: <구간·프로젝트별 등, 필요 시>  · 환경: <VPN/LAN·규모 등 재현 조건>
- **정확성**: /verify 〈통과|구현결함|설계문제〉 · 산출물 동일성 <확인 방법과 결과>
- **루브릭**: ①정확성 _/30 ②속도 _/30 ③측정 _/15 ④반경 _/10 ⑤스케일 _/10 ⑥유지비 _/5 → **총점 _/100**
- **결정**: 채택(베이스라인 갱신) | 폐기(되돌림 — 사유)
- **누적**: baseline `<B>` → 현재 `<C>`  (누적 **<±%>**, 목표 `<T>`)
```

> R0(베이스라인)도 같은 형식의 첫 스냅샷으로 라운드 로그에 남긴다(후보/결정 칸은 "baseline"). 이후 R1, R2… 순서로 append.
> 런북(`-loop.md`) 맨 위에는 벤치마크·주지표·목표·정확성 기준을 한 번 적어 고정한다(§1). 라운드 기록은 런북에 넣지 않는다.

### R-f. 종료 판정 (수렴)

아래 중 하나면 루프를 멈춘다:
- **정체**: 최근 K라운드(기본 2) 연속 채택된 개선의 합이 임계치 미만(예: 누적 <5%). 남은 후보의 기대이득도 낮음.
- **후보 고갈**: 측정 가능하고 위험 감당되는 후보가 더 없음.
- **라운드 상한**(기본 **100**) 도달. 그 전에 목표 달성·정체·고갈이면 먼저 멈춘다.
- **예산**: 사용자가 토큰/시간 상한을 줬고 근접.

> 상한 100은 폭주 방지용 backstop이다 — 100번을 다 채우는 게 목표가 아니라, 대개 목표 달성이나 정체로 그 전에 끝난다.

멈추지 않으면 R-a로 돌아간다.

## 무인 반복 / 대규모로 돌리려면 (조합)

- 이 스킬은 **한 번 호출 = 여러 라운드**를 돈다. 밤새 자기 페이스로 계속 돌리려면 위에 **`/loop`** 를 얹는다
  (스킬은 *무엇을*, `/loop`는 *언제 반복*). 예: `/loop /perf-loop 정산 배치`.
- 후보 발굴·채점을 대규모 병렬로 하려면 R-a에서 **Workflow** 로 판정 패널을 팬아웃한다(위 R-a 참조).
  단 **변경(R-b)·측정(R-c)·게이트(R-d)는 직렬**이어야 한다 — 동시에 여러 변경을 재면 측정이 오염된다.

## 수용 기준 (이 스킬이 제대로 동작하는지)

- [ ] 재현 가능한 벤치마크·주지표가 없으면 **시작하지 않고** 먼저 만든다(0단계).
- [ ] 베이스라인을 N회 측정 중앙값으로 고정한다.
- [ ] 매 라운드 후보를 **5차원 이상 루브릭**으로 채점해 **하나만** 고른다.
- [ ] 한 라운드에 **변경은 하나** — 분리 측정이 되게.
- [ ] **측정 게이트**(before/after 숫자, 노이즈 대비 유의미)와 **정확성 게이트**(`/verify`)를 둘 다 통과해야 채택.
- [ ] 통과 못 한 변경은 **되돌린다**(랄프 루프가 쓰레기를 안 쌓게).
- [ ] 문서를 **런북(`<slug>-loop.md`, 돌리는 법)** 과 **라운드 로그(`<slug>-rounds.md`, 라운드별 변경)** 로 분리한다.
- [ ] **매 라운드가 끝날 때마다 스냅샷(시작·종료 시각·소요 포함)을 라운드 로그에 남기고, 상단 누적 요약·루프 총 경과를 갱신한다**(채택·폐기 모두).
- [ ] 정체·고갈·상한(**최대 100라운드**)·예산에서 수렴 종료하고 **보고 게이트에서 멈춘다**.
- [ ] 임의 커밋·푸시하지 않는다.

## 안전 규칙

- **측정이 진실이다.** 그럴듯함·직관으로 채택하지 않는다. 숫자 없으면 채택 없다.
- **정확성 > 속도.** 결과를 바꾸는 최적화는 폐기한다. 특히 금액·정산은 `/verify full`.
- **한 번에 하나만.** 여러 변경을 섞으면 무엇이 효과였는지 영영 모른다.
- **되돌림을 아끼지 않는다.** 이득 없는 변경을 "남겨두면 언젠가" 하지 않는다 — 복잡도 부채다.
- **커밋 안 된 남의 변경을 조심.** 되돌릴 때 그 변경까지 날리지 않게 그 파일/헝크만 되돌린다.
- **코드 밖 개선을 코드로 착각하지 않는다.** 인덱스·설정·인프라가 진짜 병목이면 그렇게 보고한다(코드를 억지로 짜지 않는다).
- 서브에이전트/하위 스킬이 빈 결과·오류를 주면 그대로 알리고 멈춘다.
