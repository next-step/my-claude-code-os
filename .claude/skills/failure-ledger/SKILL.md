# 실패 원장 (failure-ledger)

`.claude/hooks/atdd-failure-log.js` 훅이 `node --test` 실행을 감지할 때마다 누적해 온 `.claude/atdd-failure-ledger.json`을 읽어서, **무엇이 언제 왜 깨졌는지**를 사람이 볼 수 있게 정리하는 스킬입니다.

ATDD에서 실패는 지워야 할 오점이 아니라 **남겨야 할 자산**입니다. 같은 AC가 세 번 깨졌다면 그건 구현이 아니라 인수기준이 잘못됐다는 신호입니다.

## 언제 쓰는가

사용자가 "실패 원장 보여줘", "어떤 인수기준이 자꾸 깨지는지 알려줘", "테스트 실패 이력" 등을 요청하거나, `atdd-orchestrator`가 07단계를 위임할 때 사용한다.
**이 스킬은 읽고 분석하기만 한다. 원장 파일에 직접 쓰지 않는다 — 기록은 오직 `atdd-failure-log.js` 훅의 몫이다.**

## 실행 절차

1. **원장 읽기**
   - `.claude/atdd-failure-ledger.json` 을 읽는다.
   - 파일이 없거나 `entries`가 비어 있으면 "아직 기록된 인수 테스트 실패가 없습니다"라고 안내하고 끝낸다.
     (훅이 `node --test` 실행 시 자동 생성하므로, 테스트를 한 번도 안 돌렸다면 없는 게 정상이다.)

2. **이력 정리**
   - `entries`를 시간순으로 정리해 표로 보여준다: 시각 / 상태(FAIL·RESOLVED) / 실패 수 / 통과 수 / 깨진 테스트 이름.
   - 테스트 이름은 `AC-<번호>: ...` 형식이므로 AC 번호를 그대로 추적 단서로 쓴다.

3. **반복 실패 분석**
   - 같은 AC 번호가 **2회 이상** FAIL에 등장하면 눈에 띄게 표시한다.
   - **3회 이상**이면 경고하고, 구현 문제가 아니라 **인수기준 자체를 의심해 02단계(`spec-decompose`)로 되돌아갈 것**을 권한다.
   - 마지막 항목이 `RESOLVED`면 현재 초록불 상태임을 알린다.

4. **결과 보고**
   - 전체 실패 횟수, 가장 자주 깨진 AC, 현재 상태(초록불/빨간불)를 한 줄로 요약한다.
   - **이 저장소는 AI와의 협업(클로드 OS) 학습이 목적**이므로, 필요하면 이 기록이 어떻게 만들어지는지
     (`node --test` 실행 → PostToolUse 훅이 출력 파싱 → JSON 누적 → 이 스킬이 읽어서 표시)를 한두 문장으로 짧게 짚어준다.

## 참고

- 원장이 훅으로 자동 기록되는 이유: AI가 07단계를 기억해서 수행하면 바쁠 때 빼먹는다. 훅으로 만들면 **AI가 깜빡해도 기록은 남는다.** 규율을 사람이나 AI의 성실성이 아니라 시스템에 맡기는 설계다.
- 이 스킬은 `.claude/atdd-failure-ledger.json` 을 절대 수정하지 않는다. `skill-stat`이 `skill-usage-stats.json`을 읽기만 하는 것과 같은 규칙이다.

## 예시

```
인수 테스트 실패 원장 (총 3건, 현재 상태: 🟢 초록불)

| 시각              | 상태     | 실패 | 통과 | 깨진 테스트 |
|------------------|----------|-----|-----|------------|
| 08-27 10:02      | FAIL     | 8   | 0   | AC-1 ~ AC-8 (구현 없음) |
| 08-27 10:07      | FAIL     | 2   | 6   | AC-2, AC-8 |
| 08-27 10:11      | RESOLVED | 0   | 8   | — |

⚠️ AC-2, AC-8이 각각 2회 깨졌습니다 — 동률 처리와 빈 후보 분기가 반복해서 놓친 지점입니다.
→ 마지막 기록이 RESOLVED이므로 현재는 전부 통과 상태입니다.
```
