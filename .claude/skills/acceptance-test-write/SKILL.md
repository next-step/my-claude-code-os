# 실패하는 인수 테스트 작성 (acceptance-test-write)

승인된 인수기준을 실행 가능한 테스트로 옮기는 스킬입니다. ATDD의 핵심 규율인 **"구현보다 테스트가 먼저, 그리고 그 테스트는 반드시 처음에 실패해야 한다"**를 강제합니다.

처음부터 통과하는 테스트는 아무것도 검증하지 못합니다. 실패를 눈으로 확인해야만 그 테스트가 진짜로 무언가를 검사한다는 증거가 생깁니다.

## 언제 쓰는가

사람이 04단계에서 인수기준을 **승인한 뒤**에만 사용한다. 사용자가 "인수 테스트 작성해줘", "실패하는 테스트부터 만들어줘"라고 요청하거나 `atdd-orchestrator`가 05단계를 위임할 때 사용한다.
**이 스킬은 테스트 코드만 작성한다. 테스트를 통과시키는 구현 코드는 한 줄도 쓰지 않는다(06단계의 몫). 인수기준 자체를 고치지도 않는다(02단계의 몫).**

## 실행 절차

1. **승인 확인**
   - 인수기준이 04단계에서 사람에게 승인된 것인지 확인한다. 승인되지 않았으면 진행하지 않고, 먼저 승인이 필요하다고 알린다.
   - 승인된 AC 목록을 그대로 보관한다(임의로 추가·삭제·해석하지 않음).

2. **테스트 대상과 파일 경로 결정**
   - 테스트는 `.claude/tests/<대상>.test.js`에 만든다. 러너는 Node 내장 `node:test` + `node:assert/strict`를 쓴다(별도 설치 불필요).
   - **검증 가능한 대상이 없으면 여기서 짚는다.** 마크다운 지시문은 자동 테스트가 불가능하므로, 검증할 로직을 `.claude/lib/<이름>.js`의 순수 함수로 분리해야 한다고 알리고 그 경로를 정한다.
   - **UI AC(`[UI]` 태그)가 있는 경우**: 검증 대상은 `.claude/lib/ui/<feature-slug>/index.html`(+ `style.css`, `script.js`)이 될 예정이다. 구조 검증에는 jsdom을 도입하지 않고 `.claude/lib/dom-lite.js`(경량 정규식 기반 파서)를 쓴다 — 이 저장소의 "제로 디펜던시" 철학을 유지하기 위함이다.

3. **AC ↔ 테스트 1:1 작성**
   - 각 테스트 이름은 반드시 `AC-<번호>: <내용 요약>` 형식으로 시작한다. 원장·리뷰에서 어떤 AC가 깨졌는지 바로 추적하기 위함이다.
   - 하나의 AC는 하나의 `test()`로 옮긴다. 여러 AC를 한 테스트에 합치지 않는다.
   - 인수기준에 없는 구현 세부사항(내부 자료구조, 정렬 알고리즘)은 단언하지 않는다.
   - **UI AC 작성 패턴**: 구현 파일을 `fs.readFileSync`로 문자열로 읽은 뒤, `dom-lite.js`의 `findElements`/`getText`/`hasClass`로 요소 존재·텍스트를 단언하고, `getCssPropertyForSelector`/`getInlineStyleProperty`로 색상·스타일 값을 단언한다. 예:
     ```js
     const html = fs.readFileSync(path.join(__dirname, "../lib/ui/settings-screen/index.html"), "utf-8");
     const { getText, hasClass } = require("../lib/dom-lite.js");

     test("AC-5: [UI] 헤더에 \"설정\" 텍스트가 노출되어야 한다", () => {
       assert.equal(getText(html, "h1"), "설정");
     });
     ```
     색상 AC는 인라인 스타일이나 CSS 클래스 규칙 문자열에서 값을 추출하는 범위로 한정한다(브라우저가 실제로 계산한 스타일이 아니라 소스 코드에 적힌 값을 그대로 비교하는 것이므로, 상속·우선순위가 얽힌 복잡한 CSS는 검증 범위 밖임을 한계로 인지한다).

4. **실패 확인 — 이 단계를 건너뛰지 않는다**
   - `node --test .claude/tests/` 를 실행한다.
   - **모든 테스트가 실패해야 정상이다.** 통과하는 테스트가 있으면 그 테스트는 아무것도 검증하지 않는 것이므로 다시 쓴다.
   - 실패 사유가 "구현이 없어서"인지 "테스트 자체가 깨져서(오타·import 실패)"인지 구분해 확인한다. 후자면 테스트를 고친다.

5. **독립 리뷰 위임 (→ `test-reviewer` 서브에이전트)**
   - 왜 별도 에이전트에게 맡기는지 한 문장으로 설명한다.
   - `Agent` 도구로 `test-reviewer`를 `모드: TEST_QUALITY`로 호출한다.
   - **전달하는 것**: 승인된 AC 목록, 테스트 코드, 실행 결과(실패 로그). **전달하지 않는 것**: "잘 짰다고 생각한다" 같은 자기 평가.
   - FAIL이면 지적사항을 반영해 3단계로 돌아간다.

6. **멈춤**
   - 실패 로그와 리뷰 판정을 요약해 보고하고 멈춘다. 구현으로 넘어가지 않고, 호출한 쪽이 06단계 진행을 결정하게 넘긴다.

## 참고

- `test-reviewer`는 `tdd-implement`(06단계)와 **공유하는 서브에이전트**다. 같은 전문성을 모드만 바꿔 재사용한다.
- 테스트가 처음에 실패하는 것을 확인하지 않고 넘어가는 것이 이 스킬에서 가장 어기기 쉬운 규율이다 — 항상 실행 로그로 증거를 남긴다.
- `node --test` 실행 결과는 `atdd-failure-log.js` 훅이 자동으로 실패 원장에 기록한다. 여기서 원장을 직접 쓰지 않는다.

## 예시

```
승인된 인수기준: AC-1 ~ AC-8 (skill-stat 최근 사용 스킬 표시)

[05] 검증 대상이 마크다운뿐이라 테스트가 불가능합니다.
     → 집계 로직을 .claude/lib/stats.js 의 summarize() 로 분리하기로 정하고,
       .claude/tests/stats.test.js 를 작성합니다.

[05] node --test .claude/tests/ 실행
     ↳ 8 fail / 0 pass — 전부 "Cannot find module '../lib/stats.js'"
     ↳ 정직한 실패(구현 없음) 확인

[05] 테스트가 AC를 제대로 덮는지는 작성자가 판단하면 안 되므로 위임합니다
     → Agent(test-reviewer, 모드: TEST_QUALITY)
     ↳ 판정: PASS

[05] 여기서 멈춥니다. 구현은 06단계(tdd-implement)의 몫입니다.
```
