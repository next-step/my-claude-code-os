# perf-diagnose · 증거 수집과 진단

성능 개선 OS의 **첫 스킬**. Stage 1·2와 게이트 ①을 담당한다.

## 핵심 원칙

**진단은 여기서 끝난다. 고치지 않는다.**

이 스킬의 산출물은 "개선"이 아니라 **"근거가 붙은 선택지"**다. 무엇을 고칠지는 게이트 ①에서 사람이 정하고, 실제 수정은 `perf-fix`가 한다. 진단 도중 원인이 명백해 보여도 코드를 건드리지 않는다.

---

# 0. 사이클 워크스페이스

모든 산출물은 `trace_id` 이름의 디렉터리 하나에 순서대로 쌓인다.

```
.claude/perf-os/cycles/<trace_id>/
  00-input.md        APM URL 파싱 결과
  10-baseline.md     Stage 1 산출
  20-hypotheses.md   Stage 2 결과 + 교차검증
  30-decision.md     게이트 ① 결과
  attempts.json      시도 이력
```

**시작 전에 이 디렉터리가 이미 있는지 확인한다.**

```bash
ls .claude/perf-os/cycles/<trace_id>/ 2>/dev/null
```

| 상태 | 처리 |
|---|---|
| 없음 | 새 사이클. Stage 1부터 |
| `10-baseline.md`까지 있음 | Stage 1 건너뛰고 Stage 2부터. **트레이스는 불변 기록이라 재수집해도 같다** |
| `30-decision.md`까지 있음 | 진단이 이미 끝났다. 사용자에게 알리고 `perf-fix`를 안내한다 |

번호 접두사는 장식이 아니다. **어디까지 갔는지가 파일 목록으로 드러나는 것이 곧 재개 가능하다는 뜻**이다.

---

# 1. 입력 — URL 파싱

```
https://app.datadoghq.com/apm/trace/6a8ed7d5...5fcc?spanID=6512965886138744892&timeHint=1787746261910
                                    └─ trace_id ─┘        └──── spanID ────┘         └─ timeHint ─┘
```

| 파라미터 | 값의 성격 | 쓰임 |
|---|---|---|
| `trace_id` | 32자리 소문자 hex | collector의 필수 입력. **사이클 ID이기도 하다** |
| `spanID` | 사람이 화면에서 보고 있던 스팬 | **사람이 의심한 지점.** AI 독립 판단과 대조하는 기준점 |
| `timeHint` | epoch millis | 로그·DB·집계 조회의 시간창 고정 |

`trace_id`만 주어졌으면 그것으로 진행하되, `spanID`가 없으므로 **대조는 건너뛴다**(대조 없음을 명시한다). `timeHint`가 없으면 사용자에게 시간대를 묻는다 — 없이 Lane C를 돌리면 다른 시간대 데이터를 근거로 쓰게 된다.

파싱 결과를 `00-input.md`에 적고 시작한다.

# 2. 행동

## Stage 1 · 증거 수집

`perf-trace-collector` 서브에이전트를 호출한다.

```
mode: baseline
trace_id: <...>
timeHint: <...>
suspect_span_id: <spanID>
```

반환된 3축 집계·독립 병목 판정·대조 결과를 **그대로** `10-baseline.md`에 쓴다. 요약하지 않는다 — 이 파일은 Stage 5의 after 측정이 참조할 기준이고, `측정 스냅샷` 절이 통째로 `baseline_digest`가 된다.

수집 실패 시 여기서 멈춘다. 증거 없이 가설로 넘어가지 않는다.

## Stage 2 · 3-lane 병렬 분석

### 2-1. 먼저 축적 지식을 조회한다

`perf-bp-curator`를 `mode: lookup`으로 호출한다.

```
mode: lookup
symptom_summary: <3축 집계 요약 + collector가 지목한 병목 후보>
```

반환은 셋 중 하나다 — 발췌 / "관련 패턴 없음" / "저장소 비어 있음". **셋을 구분해서 기록한다.**

### 2-2. 세 레인을 한 번에 띄운다

**세 에이전트 호출을 반드시 한 메시지에 담는다.** 순차로 부르면 병렬이 아니고, 앞 결과가 뒤 프롬프트에 스며들 여지가 생긴다.

| 레인 | 에이전트 | 넘기는 것 |
|---|---|---|
| A · 일반 원리 | `perf-common-antipattern-matcher` | 공통 입력만 |
| B · 코드베이스 고유 | `perf-codebase-analyst` | 공통 입력 + **`bp_excerpt`** |
| C · 실측 | `perf-runtime-inspector` | 공통 입력만 |

공통 입력: `aggregation`(10-baseline.md의 3축 집계), `service`·`resource`, `timeHint` 시간창, `refuted_hypotheses: []`.

**`refuted_hypotheses`는 빈 배열이라도 반드시 넣는다.** 이 스킬에서는 항상 비어 있지만(재진입은 `perf-fix`의 일이다), 필드를 생략하는 습관이 생기면 재진입 경로에서 조용히 누락된다.

**발췌는 Lane B에만 준다.** A와 C에도 주면 축적된 지식이 세 레인에 동시에 확증 편향을 걸어, "서로 다른 출발점 3개"라는 존재 이유가 사라진다. **무엇을 공유하지 않을지도 공유 설계의 일부다.**

### 2-3. 교차 검증 — 이건 메인이 한다

에이전트는 서로의 결론을 모른다. 합치는 것은 메인의 일이다.

| 판정 | 처리 |
|---|---|
| 여러 레인이 같은 결론 | **증거 강도 상승.** 몇 개 레인이 지지하는지를 숫자로 적는다 |
| 레인 간 결론 충돌 | **충돌 자체를 게이트 ①에 그대로 보고한다.** 임의로 한쪽을 고르지 않는다 |
| Stage 1의 `spanID` 대조와 일치 여부 | 일치는 강도 상승, 불일치는 그 사실을 명시 |

충돌을 메인이 조정하려는 유혹이 크다. 하지 마라. **충돌은 정보다** — 어느 층위의 이해가 어긋나 있는지를 사람에게 보여주는 것이 세 레인을 돌린 값이다.

결과를 `20-hypotheses.md`에 쓴다. 증거 강도 순으로 정렬한다.

# 3. 🚦 게이트 ① · 무엇을 고칠 것인가 (HARD GATE)

| 항목 | 내용 |
|---|---|
| **판단 주체** | 사람 |
| **AI가 하는 일** | 선택지 제시까지. **결정하지 않는다** |

가설 하나하나에 대해 아래 5개 항목을 제시한다. 이 항목들은 새로 정하는 것이 아니라 **3-lane 출력 스키마와 1:1로 대응한다.**

| 제시 항목 | 스키마 필드 |
|---|---|
| 근거 — 어느 스팬 / 어느 실행 계획 / 어느 로그 | `evidence[]` |
| 증거 강도 — 몇 개 레인이 지지하는가 | `confidence` + 레인 수 |
| 예상 개선폭 — 정량 추정 | `expected_gain` |
| 리스크 — 정합성·부작용 | `risk` |
| 작업량 — 대략의 규모 | `effort` |

```
게이트 ① — 무엇을 고칠까요?

[1] 대시보드 조회의 N+1                      ← 3개 레인 모두 지지
    근거    축2 "SELECT * FROM member WHERE id=?" 312회 / 1,840ms
            DashboardService.kt:88 루프 내 조회
            실행 계획: 인덱스 정상 사용, 개별 12행 — 쿼리 자체는 문제 없음
    개선폭  쿼리 312회 → 2회, 총 소요 -1.6s (추정)
    리스크  낮음. 조회 전용
    작업량  S

[2] 첨부 목록 풀스캔                          ← Lane C만 지지
    ...

⚠️ 레인 충돌: Lane A는 [2]를 캐시 미스로, Lane C는 인덱스 부재로 봅니다.
   실행 계획(Lane C)이 더 강한 증거이나, 판단은 맡깁니다.

무엇을 고칠까요? (번호 / 보류)
```

**사용자가 명시적으로 고를 때까지 다음으로 넘어가지 않는다.** 가설이 1개뿐이어도, 3개 레인이 만장일치여도 이 단계를 건너뛰지 않는다. 이 게이트가 없으면 엉뚱한 문제를 며칠 판다.

## 선택된 뒤

`30-decision.md`에 선택된 가설과 선택 이유를 쓰고, **`attempts.json`을 생성한다.**

```json
{
  "analysis_attempts": [
    { "n": 1, "hypothesis": "대시보드 조회의 N+1", "outcome": "pending", "reason": null }
  ],
  "implementation_attempts": []
}
```

**이 파일을 여기서 만드는 것이 중요하다.** `perf-fix`가 만들게 두면 첫 실패 시점에 파일이 없어 "읽기 실패 → 그냥 진행"이 되기 쉽고, 그러면 §7 루프 가드가 형식만 남는다. 게이트 ① 통과가 곧 사이클 시작이므로, 카운터도 여기서 시작한다.

## 보류를 선택하면

종료한다. **진단 보고서는 지운다.** `20-hypotheses.md`까지 남기고 "다시 시작하려면 같은 URL을 주세요"라고 안내한다. 며칠 뒤 돌아와도 Stage 1은 다시 하지 않는다.

---

# 4. 출력 — 무엇을 남기는가

```
진단 완료 — <trace_id 앞 8자>

  선택된 가설: <...>
  근거 레인:   A / B / C 중 <n>개
  기록:        .claude/perf-os/cycles/<trace_id>/

다음: /perf-fix <trace_id>
```

마지막 줄로 이 스킬은 끝난다. **`perf-fix`를 이어서 실행하지 않는다** — 스킬은 다른 스킬을 호출하지 않는다(OS.md §5 R1).

## 절대 금지

| 금지 | 이런 생각이 들면 위반 직전 | 실제 |
|---|---|---|
| 코드 수정 | "원인이 명백한데 고치는 게 빠르지" | 재현 테스트 없이 고친 것은 개선을 증명할 수 없다. 게이트 ②가 존재하는 이유 전체가 무효화된다 |
| 게이트 ① 생략 | "가설이 하나뿐이고 만장일치니까" | 승인한 건 "진단 요청"이지 "이걸 고치기"가 아니다 |
| 세 레인 순차 호출 | "하나씩 봐야 이해가 되지" | 병렬이 아니면 앞 결과가 뒤에 스며든다. 3-lane의 존재 이유가 사라진다 |
| BP 발췌를 A·C에도 주기 | "정보는 많을수록 낫지" | 세 레인에 동시에 확증 편향이 걸린다. 축적할수록 멍청해지는 구조 |
| 레인 충돌을 임의 조정 | "C가 실측이니 C를 따르자" | 충돌은 정보다. 사람에게 그대로 보여주는 것이 세 레인을 돌린 값이다 |
| 느린 스팬만 골라 수집 | "전량은 컨텍스트 낭비" | N+1은 개수로 드러난다. 그리고 전량은 collector 안에서 소멸하므로 낭비가 아니다 |
| `refuted_hypotheses` 생략 | "새 사이클이라 빈 배열인데" | 생략하는 습관이 재진입 경로에서 누락으로 이어진다 |
| `perf-fix` 이어 실행 | "흐름이 끊기니 계속하자" | R1 위반. 게이트 ①과 ② 사이에 사람이 쉴 자리를 남기는 것이 설계다 |
