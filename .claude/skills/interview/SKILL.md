# interview — 구현 전 결정 소진 인터뷰

> 설계 근거: [2026-07-02-interview-skill.md](../../../docs/interviews/2026-07-02-interview-skill.md)
> (Q1–8 설계 · Q9 이유 출처 · Q10–17 개선 · Q18 기록 위치 변경 — 후속 인터뷰는 이 파일에 이어 씀)

목적: 인터뷰가 끝난 시점에 **구현자가 더 이상 판단할(=지어낼) 게 없는 상태**를 만드는 것.
이 스킬은 질문하고 기록할 뿐, **구현하지 않는다**. 구현은 사용자가 별도로 지시한다.

## 실행 절차

### 1단계 — 맥락 파악 (질문하기 전에 스스로 답 찾기)

주제를 받으면 먼저 `docs/OS.md`와 관련 파일·기존 코드를 읽는다.
**코드나 문서로 답할 수 있는 것은 질문하지 않는다.** 질문 대상은 오직:
- 정답이 없고 트레이드오프만 있는 선택 (예: 기록 위치, 발동 조건)
- 사용자의 취향·우선순위에 달린 선택
- 범위를 가르는 선택 (뭘 넣고 뭘 뺄지)

### 2단계 — 재개 확인과 결정 지도

1. **재개 확인**: `docs/interviews/`에 같은 주제의 기록 파일이 있으면(`진행중`이든 `확정`이든),
   지금까지의 결정을 요약해 보여주고 AskUserQuestion으로 **"이어서 / 새로 시작"**을 확인한다.
   - 이어서 → 그 파일 **맨 끝에 새 Q부터 이어 쓴다**(과거 Q 섹션은 절대 수정하지 않는다).
     진행중이었다면 지도의 남은 지점부터 재개하고, 이미 확정된 주제였다면 이번 후속 인터뷰 범위로
     새 결정 지도를 만들어 이어 붙인다. `## 후속 (YYYY-MM-DD)` 소제목으로 재개 배경을 1~2문장 남긴다.
   - 새로 시작 → 기존 파일은 그대로 두고(확정 파일은 이미 박제, 진행중 파일이면 outcome을
     `보류 — 새로 시작으로 마감`으로 갱신), `-2` 파일로 완전히 새로 시작한다.
   - *왜:* 후속 결정마다 파일을 쪼개면(과거 실제로 `-2`, `-3`처럼) Q 번호는 시리즈로 이어지는데
     현재 상태를 보려고 여러 파일을 오가야 했다. 한 파일에 이어 쓰면 박제 원칙(과거 Q 불변)은
     그대로 지키면서 히스토리 전체가 한눈에 보인다. 파일 분리는 과거 결정 자체를 폐기하고
     싶은 드문 경우로 한정한다. (설계 근거: [Q18](../../../docs/interviews/2026-07-02-interview-skill.md#q18-후속-인터뷰의-기록-위치))
2. **결정 지도 작성**: 아래 **결정 체크리스트**를 대조해(1차 대조) 이번 주제에서 물어야 할
   결정 지점 목록(지도)을 뽑는다. 주제에 안 맞는 항목은 건너뛴다.
3. **지도 확인(첫 라운드)**: 지도를 사용자에게 제시하고 AskUserQuestion으로
   **"빠진 결정 지점이 있나요?"**를 묻는다(없음 / '기타'로 추가). 추가분은 지도에 넣는다.
   - *왜:* 전체 그림·분량을 미리 알리고, 누락을 초반에 사용자가 잡을 기회를 만든다.
4. **기록 파일 생성**: 지도가 확정되면 즉시 `docs/interviews/YYYY-MM-DD-주제.md`를
   `outcome: 진행중`으로 생성하고, 지도를 `- [ ]` 체크리스트로 담는다.

### 3단계 — 질문 루프

- **AskUserQuestion**으로 라운드당 2~4개씩 묻는다. 서로 독립인 질문은 한 라운드에 묶고,
  앞 답에 따라 달라지는 질문은 다음 라운드로 미룬다.
- **영향 범위 명시**: 각 질문에 "이 결정이 무엇을 좌우하는지" 한 줄을 반드시 담는다.
  *왜:* 결정의 무게를 알고 답할 수 있게.
- **들러리 선택지 금지**: 실제 고려 가치 없는 구색용 대안을 넣지 않는다. 진짜 대안이 2개면 2개만.
- 각 선택지에는 **트레이드오프(장점과 대가)를 설명에 담는다.** 추천이 있으면 첫 번째에 두고
  라벨에 `(Recommended)`를 붙인다. 선택지 밖 생각은 사용자가 '기타'로 입력한다.
- 답이 새 애매함을 낳으면 후속 라운드로 계속 판다. **애매함이 소진될 때까지 라운드 수 제한 없음.**
  새 결정 지점이 생기면 **"지도에 추가됨"을 알리고** 기록 파일의 지도에도 반영한다.
- 사용자가 '기타'로 직접 쓴 답이나 덧붙인 메모는 **원문 그대로 보존**해 둔다(기록에서 인용해야 함).
- **라운드마다 즉시 저장**: 라운드가 끝날 때마다 확정된 결정을 기록 파일에 Q 섹션으로 append하고
  지도 체크박스를 갱신한다. 이때 이유는 `이유(AI 정리)`로 적는다(아직 승인 관문 전).
  *왜:* 세션이 언제 끊겨도 답변 무손실. Q 섹션 추가는 문자 그대로 append이고, outcome 갱신은
  기존 "status 갱신 = 평가 덧붙임" 논리와 같은 성격이라 박제 원칙과 충돌하지 않는다.

### 4단계 — 종료 판정과 최종 요약

종료 판정 전에 **결정 체크리스트를 다시 대조**해(2차 대조) 빠진 결정이 없는지 스스로 점검한다.
"더 물을 게 없다"고 판단되면, **결정 전체를 표로 요약**해 제시한다
(결정 지점 | 확정 | 기각한 대안과 이유). 이때 **이유는 AI가 정리한 것이니 실제 생각과 다르면
고쳐 달라고 명시적으로 알린다** — 이 요약 확인이 이유의 승인 관문이다.
그리고 AskUserQuestion으로 확정 여부를 묻는다:
- **확정** → 5단계로.
- **수정할 부분 있음** → 해당 지점만 다시 인터뷰 후 요약 재제시.

이 요약 확인이 안전망이다 — AI가 빠뜨린 결정이 있으면 사용자가 여기서 잡는다.

### 5단계 — 확정 기록 (append-only)

최종 확인이 나면 진행중이던 기록 파일을 마감한다(직접 Write/Edit, 스크립트 없음):
- frontmatter `outcome:`을 `확정`(또는 `보류 — 사유`)으로 갱신.
- 본문의 `이유(AI 정리)`를 `이유(AI 정리·확인됨)`으로 **승급** — 요약 확인이 승인 관문을
  통과했다는 표시. (설계 근거: [Q17](../../../docs/interviews/2026-07-02-interview-skill.md#q17-파생-세부-ai-판단-요약-확인으로-승인))
- `## 최종 확인` 섹션을 맨 끝에 append.

기록 규칙:
- 파일명 주제는 짧은 kebab-case. **같은 주제의 후속 인터뷰는 기존 파일 맨 끝에 새 Q로 append**한다
  (과거 Q 섹션은 절대 수정하지 않는다 — 박제). 완전히 처음부터 다시 시작하는 경우에만 `-2`, `-3`
  접미사로 새 파일을 만든다.
- 내용은 **전체 Q&A 원문이 아니라 정제본**: 질문별 결정 + 기각 대안 + 이유.
- **이유의 출처를 정직하게 표기한다.** 이유는 대부분 AI가 선택지에 제시한 트레이드오프이므로
  `이유(AI 정리·확인됨)`으로 명시하고, 사용자가 '기타'·메모로 직접 말한 이유는
  `이유(사용자 원문)`으로 **원문 인용**해 구분한다. *왜:* 미래의 복기자가 추정된 이유를
  본인 판단으로 착각하지 않게. (설계 근거: [Q9](../../../docs/interviews/2026-07-02-interview-skill.md#q9-기록의-이유-란-출처-처리))

템플릿:

```markdown
---
date: YYYY-MM-DD
topic: <주제>
outcome: <진행중 | 확정 | 보류 — 사유>
artifact: <산출물 경로. 아직 없으면 (미구현)>
---

# 인터뷰: <주제>

## 배경
<이 인터뷰를 왜 했는지 1~3문장.>

## 결정 지도
- [x] <물은 결정 지점> → Q1
- [ ] <아직 안 물은 지점>

## Q1. <결정 지점>
- **결정**: <무엇으로 확정했나>
- **기각**: <검토했지만 안 고른 대안들>
- **이유(AI 정리)**: <진행중 표기. 최종 확인 통과 시 '이유(AI 정리·확인됨)'으로 승급>
- **이유(사용자 원문)**: "<사용자가 '기타'·메모로 직접 말한 내용 인용>" ← 있을 때만

## Q2. ...

## 최종 확인
<날짜>, 사용자가 결정 요약을 검토하고 확정. <마감 시에만 추가>

## 후속 (YYYY-MM-DD) — <후속 인터뷰 주제>
<이미 확정된 파일에 후속 인터뷰를 이어 붙일 때만 추가. 재개 배경 1~2문장.>

## Q3. ... (번호는 시리즈로 계속 이어감)

## 최종 확인
<날짜>, 후속 결정 요약을 검토하고 확정.
```

### 6단계 — 마무리 (구현하지 않는다)

1. `docs/OS-log.md` **맨 끝**에 1~2문장 항목 추가(인터뷰 파일 링크 포함).
2. 사용자에게 기록 경로를 알리고 종료. **바로 구현을 시작하지 않는다** —
   구현은 사용자가 별도로 지시하며, 다음 세션이어도 된다.

## 결정 체크리스트 (2단계 지도 작성·4단계 종료 판정, 두 번 대조)

주제에 안 맞는 항목은 건너뛴다. (설계 근거: [Q12](../../../docs/interviews/2026-07-02-interview-skill.md#q12-누락-방지-장치))

| 항목 | 점검 질문 |
|------|-----------|
| 범위 | 무엇을 넣고 무엇을 빼나? 이번 버전(MVP)의 경계는? |
| 발동·트리거 | 언제·어떻게 시작되나? 명시 호출인가 자동인가? 입력은 뭔가? |
| 입출력·기록 | 산출물이 무엇이고 어디에 어떤 형식으로 남나? append-only인가, 갱신인가? |
| 실패·엣지 | 재료가 없거나, 중간에 끊기거나, 같은 것이 이미 있으면 어떻게 되나? |
| 기존 패턴 일관성 | OS 기존 규약(append-only 박제, ref 역참조, 정밀 수치=스크립트 등)과 충돌하지 않나? |
| 수명주기·갱신 | 만든 뒤 언제·누가 갱신하나? 낡거나 폐기되면 어떻게 되나? |

## 구현할 때의 규약 (이 스킬 밖의 일이지만 기록해 둠)

나중에 인터뷰 기반으로 산출물을 만들 때는:
- 산출물(SKILL.md 머리말, 스크립트 주석 등)에 `설계 근거: docs/interviews/....md` **ref 한 줄**을 남긴다.
  (추천 기록이 분석 기록을 ref로 역참조하는 기존 패턴과 동일 — 기록이 묻히지 않게.)
- 인터뷰 기록의 frontmatter `artifact:`가 `(미구현)`이면 산출물 경로로 갱신한다.
  (이 한 줄 갱신은 status 갱신과 같은 '평가 덧붙임'으로, 박제 위반이 아니다. 결정·이유 본문은 불변.)
