# interview

모호한 아이디어나 요구사항을 대화형 질문으로 구체화해 실행 가능한 스펙으로 정리한다.
파이프라인에 자동으로 끼지 않는 **완전 독립 스킬** — 필요할 때 언제든 직접 호출한다.

`/interview` → (기획 위주면 `/ticket-start`, 구현 범위가 이미 명확하면 `/task-impl`)로 이어가는 흐름.

---

## 0단계: 인터뷰 대상 파악

아래 순서로 인터뷰 대상을 찾는다:

1. **인자로 받은 주제/설명**이 있으면 그대로 사용한다.
2. 인자가 없으면 `docs/ticket-briefing.md` 존재 여부를 Read로 확인한다. 있으면 그 내용을 기존 맥락으로 제시하고, 이 브리핑을 더 구체화하고 싶은지 확인한다.
3. 둘 다 없으면 다음을 묻는다:

```
무엇에 대해 모호함을 구체화하고 싶으신가요?
기능 아이디어, 버그, 리팩토링 등 자유롭게 설명해 주세요.
```

---

## 1단계: 모드 선택

AskUserQuestion으로 아래 중 하나를 선택받는다.

- **기획 인터뷰만** — 아직 "무엇을, 왜" 수준이 안 잡힌 경우
- **기술 인터뷰만** — 기획은 끝났고 "어떻게" 구현할지만 불명확한 경우
- **둘 다 (기획 → 기술 순)** — 처음부터 끝까지 구체화가 필요한 경우

추천값: `docs/ticket-briefing.md`가 이미 있으면 **기술 인터뷰만**을, 없으면 **둘 다**를 기본으로 제시한다.

---

## 2단계: 용어 정의 (공통, 항상 실행)

모드 선택과 무관하게 항상 먼저 실행한다.

```
이 작업에서 모호하게 쓰이는 단어가 있나요?
(예: "빠르게" 얼마나 빠르게? "사용자"는 어떤 사용자? "완료"는 무엇을 기준으로?)
```

핵심 용어를 목록화하고 이 맥락에서의 정의를 확정한다. 이후 3~4단계 질문에서 이 정의를 그대로 재사용한다.

---

## 3단계: 기획 인터뷰 (1단계에서 선택한 경우)

| 카테고리 | 질문 예시 |
|---|---|
| 목표 정의 | 해결하려는 문제는? 이해관계자는 누구? 성공 기준은? |
| 범위 정의 | 포함/제외되는 것은? 빠른 수정, MVP, 장기 설계 중 무엇? |
| 정책/규칙 | 적용되는 비즈니스 규칙이 있나? 누가 접근/실행할 수 있나? 어떤 조건에서 허용/차단되나? |
| UX 흐름 | 사용자가 어떤 경로로 진입하나? 화면/상태 흐름은 어떻게 되나? 각 단계에서 무엇을 보고 할 수 있나? |
| 제약 정의 (기획 측면) | 일정, 비즈니스, 법무 제약이 있나? |

---

## 4단계: 기술 인터뷰 (1단계에서 선택한 경우)

| 카테고리 | 질문 예시 |
|---|---|
| 인터페이스 | 입력/출력, API 요청-응답, 함수 시그니처는? |
| 기존 코드 재사용 | 재사용할 컴포넌트/유틸 있나? 새로 만드나? |
| 동작 정의 | 정상 흐름은? 실패/빈 상태/로딩/권한 없음/중복 요청/롤백엔 어떻게 동작해야 하나? |
| 소유권 정의 | 어떤 시스템·모듈·API·사람이 이 상태나 결정을 소유하나? source of truth는 어디? |
| 제약 정의 (기술 측면) | 기술 스택, 호환성 제약이 있나? |
| 검증 방법 | 올바르게 동작함을 어떻게 확인하나? (테스트, QA) |

### 3·4단계 공통 규칙

- 질문은 카테고리당 1~3개씩 배치로 던지고 답변을 받아가며 진행한다 (한 번에 전부 쏟아내지 않는다).
- 코드베이스에서 직접 확인 가능한 것(기존 컴포넌트 유무 등)은 묻지 않고 Read/Grep으로 먼저 확인한 뒤 해당 질문을 스킵한다.
- "모르겠다"/"나중에 정한다"는 답변은 캐묻지 않고 5단계의 "가정" 또는 "미해결 질문"으로 기록한다.
- 사용자가 "그만"/"충분해"/"나중에" 를 입력하면 즉시 5단계(결정으로 변환)로 건너뛰어 지금까지의 답변만으로 정리한다.

---

## 5단계: 결정으로 변환 (공통, 항상 실행)

2~4단계 답변을 종합해 아래 4개 분류로 정리하고 사용자에게 확인받는다.

```
## 결정 요약

**확정된 결정**
- ...

**미해결 질문**
- [ ] ...

**가정** (명시되지 않았지만 진행을 위해 임시로 둔 것)
- ...

**다음 액션**
- ...
```

---

## 6단계: 스펙 문서 저장

아래 형식으로 `docs/interview-spec.md`에 Write로 저장한다 (`docs/` 없으면 `mkdir -p docs` 후 저장).
기존 `docs/interview-spec.md`가 있으면 덮어쓰기 전 사용자에게 확인한다.

````markdown
## 인터뷰 스펙: [주제]
> 생성: /interview | 날짜: YYYY-MM-DD

### 용어 정의
- [용어]: [정의]

### 기획 요약 (진행한 경우)
- 목표: ...
- 범위: ...
- 정책/규칙: ...
- UX 흐름: ...
- 제약 (기획 측면): ...

### 기술 요약 (진행한 경우)
- 인터페이스: ...
- 재사용 대상: ...
- 동작 정의: ...
- 소유권: ...
- 제약 (기술 측면): ...
- 검증 방법: ...

### 결정 요약
**확정된 결정**
- ...

**미해결 질문**
- [ ] ...

**가정**
- ...

**다음 액션**
- ...
````

## 7단계: 다음 단계 안내

파일 저장 후 채팅 하단에 다음을 추가한다:

```
📄 인터뷰 스펙이 docs/interview-spec.md에 저장되었습니다.
기획 위주였다면 /ticket-start로, 구현 범위까지 명확해졌다면 /task-impl로 이어가세요.
```

---

## 주의사항

- 질문은 카테고리당 1~3개, 배치로 진행한다.
- "모르겠다" 답변을 억지로 캐묻지 않는다.
- 코드베이스에서 확인 가능한 정보는 질문하지 않는다.
- 기존 산출물(`docs/interview-spec.md`) 덮어쓰기 전 확인한다.
