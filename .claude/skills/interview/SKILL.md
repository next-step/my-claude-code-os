# interview — 모호함 진단 인터뷰

인터뷰 대상은 스킬 호출 시 인자로 전달된다. 두 가지 형태를 받는다.

| 인자 | 뜻 |
| --- | --- |
| 자유 서술 (`/interview "주간 리포트가 있으면 좋겠다"`) | 아직 접수되지 않은 아이디어 |
| `REQ-XXX` | 이미 접수된 요청을 더 파고들 때 |

인자가 비어 있으면 무엇을 구체화하고 싶은지 먼저 묻는다.

## 0. 선행 조건

- `.claude/context/interview-method.md` 를 **Read 한다.** 이 스킬의 모든 판단은 그 문서를 따른다.
  절 번호(§1~§8)로 참조하며, 이 파일에 방법론을 다시 적지 않는다.
- 인자가 `REQ-XXX` 면 `maintenance/requests/<REQ-ID>.md` 를 읽는다. 없으면 중단하고 알린다.
- `maintenance/interviews/` 가 없으면 만든다.

## 1. 유형 판정

요청을 §8 의 유형 중 하나로 찍는다 — 버그 / 기능개선 / 신규 개발 / 문의·조사 / 스킬·OS 설계.
찍은 유형에 따라 어느 축에 질문 예산을 몰아줄지 정해진다.

## 2. R0 — 조용한 진단 (질문 0개)

**아직 아무것도 묻지 않는다.** 먼저 스스로 답을 찾는다.

- `Grep` · `Glob` · `Read` 로 저장소를 조사한다 (§3 금칙 1 — 저장소로 알 수 있는 건 질문하지 않는다).
- 구현 가능성은 `.claude/context/team-capability.md` 로 대조한다.
- 5축에 눈금(`명확` / `추정` / `질문`)을 매긴다 (§1).

채점표를 사용자에게 먼저 보여준다. 무엇을 이미 알아냈고 무엇이 비었는지 드러내는 것이
이 단계의 산출물이다.

```
## 진단 (R0)
| 축 | 눈금 | 근거 |
| --- | --- | --- |
| 목적 Why | 질문 | 왜 필요한지 원문에 없음 |
| 대상·범위 | 추정 | 목록 화면으로 추정, 상세 포함 여부 미정 |
| 동작 What | 질문 | 대상 컬럼·필터 기준 불명 |
| 제약 | 명확 | 저장소 확인 — 기존 CSV 유틸 있음, 주력 스택 안 |
| 완료 Done | 질문 | "받아지면 끝"인지 서식 요건이 있는지 불명 |
```

## 3. R1~R2 — 질문 (누적 최대 8개)

`질문` 눈금을 §2 의 되돌리기 비용 순으로 정렬하고 위에서부터 자른다.
**한 라운드에 최대 3개**, `AskUserQuestion` 으로 **객관식**(선택지 2~4개)으로 묻는다 (§4).

- 선택지에는 일부러 **틀릴 만한 보기**를 넣는다. 전부 그럴듯하면 반박이 안 나온다.
- 답을 받으면 5축을 **다시 채점**하고, 남은 `질문` 중 상위 최대 3개로 R2 를 돈다.
- §5 종료 조건 중 하나라도 걸리면 즉시 멈춘다. 상한을 넘겨 묻지 않는다.

## 4. R3 — 되읽기와 승인

이해한 것을 **조건 · 행동 · 결과** 세 문장으로 돌려주고 승인받는다 (§6).
세 문장으로 안 써지는 항목이 있으면 아직 모호한 것이므로, 예산이 남아 있으면 그것부터 묻는다.

승인 없이 다음 단계로 넘기지 않는다. 사용자가 고치면 반영하고 다시 보여준다.

## 5. 가정 원장 작성

끝내 못 정한 것을 §7 의 표로 정리한다. **출신(`추정` / `질문`)과 위험도를 반드시 구분한다.**
`질문` 출신은 위험 `높음` 이며, 이것이 1순위 실패 후보지다.

## 6. 산출물 기록

`maintenance/interviews/<오늘>-<주제-slug>.md` 를 만든다.

```markdown
---
subject: (한 줄 요약)
type: 버그 | 기능개선 | 신규 | 문의 | 스킬·OS설계
req: REQ-XXX | -
date: YYYY-MM-DD
rounds: N
questions_asked: N
status: approved
---

## 1. 원문
## 2. 진단 (R0)        — 5축 채점표
## 3. 질문과 답 (R1~R2) — 물어본 것, 받은 답, 그래서 바뀐 눈금
## 4. 되읽기 (R3)      — 조건 · 행동 · 결과
## 5. 가정 원장        — # / 가정 / 출신 / 위험
## 6. 다음 단계
```

인자가 `REQ-XXX` 였으면 케이스 파일 **"2. 접수 정리"** 끝에
`- 인터뷰: maintenance/interviews/<파일명>` 한 줄을 덧붙이고 `updated` 를 오늘로 갱신한다.
케이스 파일의 다른 섹션은 건드리지 않는다.

## 7. 보고

- 만든 파일 경로
- 조건·행동·결과 요약
- **가정 원장에서 위험 `높음` 인 항목** (여기를 특히 짚어 준다)
- 다음 단계 안내:
  - 접수 안 된 요청 → `/intake "<되읽기 요약>"`
  - 이미 `REQ-XXX` → `/spec REQ-XXX`
  - 스킬·OS 설계였다면 → 되읽기 결과를 새 `SKILL.md` 초안의 재료로

## 하지 말 것

1. **저장소를 보면 알 수 있는 것을 묻지 않는다.** R0 에서 먼저 찾아본다.
2. **상대가 답할 수 없는 것을 묻지 않는다.** 기술 판단은 우리가 하고, 필요하면 결과로 번역해서 묻는다.
3. **누적 8개를 넘겨 묻지 않는다.** 남은 것은 가정 원장으로 넘긴다 — 더 묻는 것으로 해결하지 않는다.
4. **서술형만으로 묻지 않는다.** 선택지를 준다.
5. **되읽기 승인 없이 산출물을 `approved` 로 적지 않는다.**
6. **가정을 사실처럼 적지 않는다.** 출신과 위험도를 반드시 붙인다.
7. 코드를 수정하지 않는다 — 이 스킬은 이해를 만드는 단계다.
8. 케이스 파일의 스펙·구현·검증 섹션을 건드리지 않는다.
