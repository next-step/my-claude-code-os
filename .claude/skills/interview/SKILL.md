# interview

모호한 요청을 받았을 때 스스로 판단·추측해서 채우지 않고, 질문을 통해 사용자의 사고 과정을 명시화한 뒤 작업한다. 별도 요구사항 문서를 만들지 않고, 대화에서 확보한 맥락만으로 원래 작업을 바로 수행하는 것이 목표다.

## 모호함의 판단 기준

모호함은 "설명이 부족하다"가 아니라 **사용자만 답할 수 있는 선택지(갈림길)가 둘 이상 존재하고, 그중 무엇을 고르느냐에 따라 결과물이 달라지는 상태**를 뜻한다. 선택지가 하나뿐이거나 상식적으로 명백하면, 정보가 적어도 모호한 것이 아니다 — 그때는 조사(0단계)나 합리적 기본값으로 채우고 바로 진행한다.

## 발동 조건

| 구분 | 조건 |
|---|---|
| 명시적 | 사용자가 `/interview`로 직접 호출 |
| 암묵적 | 비trivial한 생성/설계성 요청인데, 아래 중 하나라도 **실제 선택지가 둘 이상** 존재: 핵심 용어가 여러 뜻으로 해석 가능 / 결과물의 형태·범위에 복수의 가능성 / 완성 기준으로 삼을 만한 기준이 여럿 / 요청 배경(목적)에 따라 접근 방식이 갈림 |
| 발동 안 함 | 선택지가 하나뿐이거나(상식적으로 명백), 단순 조회·버그 수정·오탈자 수정 등 결과물이 이미 하나로 정해지는 작업 — 과도한 질문으로 사용자를 피곤하게 하지 않는다 |

## 절차

### 0단계 — 조사 우선
질문하기 전에 리포지토리/기존 파일을 먼저 읽어 답을 유추할 수 있는 것은 스스로 확인한다. 코드나 문서에 이미 답이 있는 것을 사용자에게 묻지 않는다.

### 1단계 — 질문 설계
남은 모호함을 아래 카테고리에 대입해 질문 목록을 만든다.
- **용어 정의**: 사용자가 쓴 핵심 단어(예: "context")가 구체적으로 뭘 가리키는지
- **현재 이해**: 사용자가 지금 이 프로젝트/대상을 어떻게 이해하고 있는지
- **의도·배경**: 왜 이 요청을 하게 됐는지, 어떤 문제를 해결하려는지
- **범위·형태**: 결과물이 어떤 모습이어야 하는지 (파일? 대화 답변? 구조?)
- **완성 기준**: 무엇이 채워지면 "충분하다"고 볼 수 있는지

### 2단계 — 질문 실행
`AskUserQuestion` 도구로 한 번에 최대 4개 질문을 묶어서 물어본다. 선택지로 답할 수 있는 것은 옵션으로 구성하고(옵션에는 항상 "기타" 자유 서술이 자동 포함됨), 옵션으로 좁히기 어려운 것은 서술형 질문으로 병행한다.

### 3단계 — 자가 평가
답변을 받은 후 "이제 원래 작업을 사용자 의도대로 정확히 수행할 수 있는가"를 스스로 점검한다. 용어 정의·범위·완성 기준 같은 핵심 의사결정 지점에 빈틈이 남아있다면 추가 라운드 질문을 이어간다.

### 4단계 — 확인 후 종료
충분하다고 판단되면, 지금까지 파악한 이해를 1~3문장으로 요약해 사용자에게 보여주고 맞는지 확인받는다. 확인을 받으면 별도 문서 없이 바로 원래 작업을 수행한다.

## 가드레일

- 핵심 의사결정(정의·범위·완성 기준·의도)은 절대 임의로 추측해서 채우지 않는다.
- 이미 파일·코드에서 확인 가능한 사실은 사용자에게 묻지 않는다 (0단계 조사 우선).
- 무한 질문 방지: 통상 1~2라운드 안에 핵심 갭이 좁혀지지 않으면, "이대로 가정하고 진행할지 더 좁혀볼지"를 사용자에게 직접 물어 루프가 무한히 늘어지지 않게 한다.
- 인터뷰 종료 후 별도 요구사항 문서는 만들지 않는다 — 확보한 맥락은 대화 내에서만 유지하고 바로 실행에 사용한다.
