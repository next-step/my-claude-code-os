# Commit — 검토 후 커밋, 그리고 내 포크로 푸시

`git add -A && git commit -m "update" && git push` 는 스킬이 필요 없다. 그건 한 줄이면 된다.
이 스킬이 존재하는 이유는 그 한 줄이 **되돌리기 어려운 사고**를 내기 때문이다.

## 0. 이 스킬이 막는 네 가지 사고

| 사고 | 어떻게 일어나는가 | 방어 규칙 |
|---|---|---|
| 공용 저장소 오염 | `upstream`(next-step)은 수십 명이 공유한다. 여기에 푸시하면 남의 작업에 영향을 준다 | 푸시 대상은 **항상 `origin`**. `upstream` 푸시는 금지 |
| 쓰레기 파일 커밋 | `.idea/`, `.DS_Store`, `node_modules/`를 `add -A`가 통째로 삼킨다 | `add -A`·`add .` 금지. 파일을 **명시적으로** 스테이징 |
| 비밀정보 유출 | `.env`, 토큰, 키가 diff에 섞인다. 푸시된 뒤엔 삭제해도 히스토리에 남는다 | 커밋 전 비밀정보 스캔. 발견 시 **중단하고 보고** |
| 의미 없는 히스토리 | "update", "수정" 같은 메시지. 리뷰어가 무슨 변경인지 알 수 없다 | diff를 읽고 **무엇을·왜**를 쓴다 |

이 중 앞의 세 개는 푸시 후 되돌리기가 매우 어렵다. 속도보다 이 순서를 지키는 것이 우선이다.

## 1. 상황 파악 — 한 번에 조회한다

아래를 **한 응답에서 병렬로** 실행한다. 순차 실행하면 느려지고, 중간에 판단이 흔들린다.

```bash
git status --short                 # 무엇이 바뀌었나
git branch --show-current          # 어느 브랜치인가
git remote -v                      # origin / upstream 구분
git log --pretty=format:'%s' -15   # 이 저장소의 메시지 컨벤션
git diff                           # 워킹트리 변경 내용
git diff --cached                  # 이미 스테이징된 변경 내용
```

### 브랜치 확인 (여기서 멈출 수 있다)

- `main`(또는 `master`)에 있다면 **커밋하지 않는다.** 작업 브랜치가 필요한 이유를 말하고
  `git switch -c <브랜치명>`을 제안한 뒤 사용자 확인을 받는다.
- 이 저장소의 흐름은 `README.md`에 있다: 주차별 요구사항 구현 → 내 GitHub 아이디 브랜치로 PR → 리뷰 반영.
  따라서 작업 브랜치는 `stepN` 같은 진행 단위 브랜치다.

## 2. 스테이징 — 명시적으로만

```bash
git add <파일1> <파일2>    # ✅ 의도한 파일만
git add -A                 # ❌ 금지
git add .                  # ❌ 금지
```

`git status`에 **추적되지 않은(untracked) 파일**이 있으면 각각 판단한다.

- 작업 산출물인가 → 스테이징한다
- IDE·OS·의존성 생성물인가(`.idea/`, `.vscode/`, `.DS_Store`, `node_modules/`, `dist/`, `*.log`) →
  **커밋하지 않는다.** `.gitignore`에 추가할 것을 제안한다 (제안이지, 임의 수정이 아니다)
- 판단이 안 서는 파일이 있으면 커밋에서 빼고 사용자에게 물어본다. 애매한 파일은 넣지 않는 쪽이 안전하다

`.gitignore`가 없거나 IDE 항목이 빠져 있으면 그 사실을 한 줄로 알린다. 매번 같은 쓰레기 파일을 손으로 걸러내는 건 낭비다.

## 3. 안전 점검 — 통과하지 못하면 커밋하지 않는다

스테이징 후 커밋 직전에 확인한다.

```bash
git diff --cached --stat                    # 파일 수·변경량 확인
git diff --cached --name-only               # 커밋될 파일 목록 확정
```

1. **비밀정보** — 스테이징된 diff에서 아래 패턴을 찾는다.

   ```bash
   git diff --cached -U0 | grep -nEi '(api[_-]?key|secret|password|passwd|token|private[_-]?key|BEGIN [A-Z ]*PRIVATE KEY|sk-[A-Za-z0-9]{16,}|ghp_[A-Za-z0-9]{20,})'
   ```

   걸리면 **커밋을 멈추고** 해당 위치를 보고한다. 스스로 값을 지우거나 마스킹해서 진행하지 않는다.
   테스트용 더미 값이라 무해할 수도 있지만, 그 판단은 사용자가 한다.

2. **파일 이름** — `.env`, `*.pem`, `*.key`, `id_rsa`, `credentials*`가 목록에 있으면 같은 방식으로 멈춘다.

3. **범위 이탈** — 이번 작업과 무관한 파일이 섞여 있지 않은지 본다. 있으면 4번으로 간다.

4. **대용량 파일** — 1MB를 넘는 바이너리가 있으면 의도한 것인지 확인한다.

## 4. 커밋 단위 — 섞이면 쪼갠다

한 커밋은 **하나의 논리적 변경**이다. 리뷰어가 커밋 하나를 보고 "이건 X를 했구나"라고 말할 수 있어야 한다.

쪼개야 하는 신호:
- 서로 무관한 기능이 함께 들어 있다 (스킬 추가 + 문서 오타 수정)
- 리팩터링과 기능 변경이 섞여 있다
- 메시지에 "그리고", "및"을 두 번 이상 쓰게 된다

쪼갤 때는 계획을 먼저 사용자에게 보여준다. 예:

```
2개 커밋으로 나눕니다.
1) .claude/skills/commit/ — feat: 커밋 스킬 추가
2) .gitignore — chore: IDE 설정 파일 제외
```

반대로, 억지로 쪼개지 않는다. 스킬 파일과 그 스킬이 쓰는 참조 문서는 한 커밋이 맞다.

## 5. 메시지 작성

### 컨벤션 — 타입 프리픽스를 붙인다

제목은 **`<type>: <한국어 요약>`** 형식이다. 타입은 아래 일곱 개만 쓴다.

| type | 언제 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서의 수정 |
| `style` | (코드의 수정 없이) 스타일(style)만 변경(들여쓰기 같은 포맷이나 세미콜론을 빼먹은 경우) |
| `refactor` | 코드를 리펙토링 |
| `test` | Test 관련한 코드의 추가, 수정 |
| `chore` | (코드의 수정 없이) 설정을 변경 |

요약은 한국어 명사형으로 쓴다. 예: `feat: 커밋 스킬 추가`

**타입이 헷갈리면** "이 변경이 없으면 무엇이 안 되는가"로 고른다.

- 없던 동작이 생긴다 → `feat` (스킬·훅 추가가 여기 해당한다)
- 동작은 그대로고 설정만 바뀐다 → `chore`
- 읽는 사람만 영향을 받는다 → `docs`

한 커밋에 두 타입이 걸리면 타입을 고르는 문제가 아니라 **커밋을 쪼갤 신호다.** 4번으로 돌아간다.

### 과거 히스토리를 근거로 타입을 빼지 않는다

`git log`에는 이 컨벤션 이전에 만들어진 커밋(`미션 진행 방식 추가` 등)이 남아 있다.
1단계에서 그것을 보더라도 **관측을 근거로 타입을 생략하지 않는다.** 위 표가 기준이다.
다만 주차 미션 커밋의 `🚀 N주차 - ...` 형식은 별도 관례이므로 그대로 둔다.

### 형식

```
<type>: <제목: 무엇을 했는가 — 50자 내외, 마침표 없음>

<본문: 왜 했는가 / 어떤 판단을 했는가 — 필요할 때만>

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

- 제목만으로 충분한 변경(오타 수정, 파일 하나 추가)에는 본문을 쓰지 않는다
- 본문은 **왜**를 쓴다. **무엇**은 diff에 이미 있다
- 커밋 메시지에 검증하지 않은 사실을 쓰지 않는다. 테스트를 돌리지 않았다면 "테스트 통과"라고 쓸 수 없다
- `Co-Authored-By` 트레일러는 이 환경의 기본 규칙이다. 원치 않으면 사용자가 빼라고 하면 된다

### 커밋 실행

```bash
git commit -m "$(cat <<'EOF'
type: 제목

본문

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
EOF
)"
```

`--no-verify`는 **쓰지 않는다.** pre-commit 훅이 실패했다면 훅이 옳고 코드가 틀렸을 가능성이 크다.
훅 실패 시: 출력을 읽고 → 원인을 고치고 → 다시 커밋한다. 고칠 수 없으면 사용자에게 훅 출력을 그대로 보여준다.

커밋 후 `git log -1 --stat`으로 실제로 무엇이 들어갔는지 확인한다.

## 6. 푸시 — 확인을 받고, origin으로만

푸시는 **외부로 나가는 행위**다. 사용자가 "커밋하고 푸시해줘"처럼 명시했거나
이 대화에서 이미 승인한 흐름이 아니라면, 푸시 전에 무엇을 어디로 보낼지 알리고 확인을 받는다.

```bash
# 업스트림 추적이 없는 첫 푸시
git push -u origin <현재-브랜치>

# 이후
git push
```

**금지:**
- `git push upstream ...` — 공용 저장소다. 절대 하지 않는다
- `git push --force` / `-f` — 공유 브랜치의 히스토리를 지운다.
  꼭 필요하면 `--force-with-lease`를 쓰고, 사용자 확인을 먼저 받는다
- 이미 푸시된 커밋을 `git commit --amend`로 고치기 — 강제 푸시가 뒤따르게 된다.
  푸시 전이라면 amend는 괜찮다

푸시가 거절되면(non-fast-forward) 강제 푸시로 뚫지 않는다. `git fetch && git log origin/<브랜치>..HEAD`로
원격에 무엇이 있는지 확인하고 상황을 보고한다.

## 7. 보고, 그리고 다음 단계

끝나면 **사실만** 짧게 보고한다.

```
커밋 2개, origin/step1에 푸시 완료
  a1b2c3d feat: 커밋 스킬 추가
  e4f5g6h chore: .gitignore에 IDE 설정 제외
```

PR 생성은 이 스킬의 범위가 아니다. 사용자가 PR을 원하면 `gh pr create`가 가능하다는 것만 알리고,
베이스 브랜치(이 저장소는 내 GitHub 아이디 브랜치)와 본문을 확인받은 뒤 진행한다.

## 인자

| 인자 | 동작 |
|---|---|
| (없음) | 1~7단계 전체. 푸시 전 확인 |
| `--no-push` | 커밋까지만. 푸시하지 않음 |
| `--push` | 푸시 확인 절차 생략 (사용자가 미리 승인한 것으로 본다) |
| 자유 텍스트 | 커밋 메시지 힌트로 사용. 단, diff와 어긋나면 diff를 따르고 차이를 알린다 |

## 출력 전 자기 점검

- [ ] `main`이 아닌 작업 브랜치에서 커밋했는가
- [ ] `git add -A` / `git add .`를 쓰지 않았는가
- [ ] 커밋된 파일 목록을 눈으로 확인했는가 (`.idea/` 같은 것이 섞이지 않았는가)
- [ ] 비밀정보 스캔을 돌렸는가
- [ ] 제목이 `<type>: <한국어 요약>` 형식인가 (타입 일곱 개 중 하나)
- [ ] 메시지에 검증하지 않은 주장(테스트 통과 등)이 없는가
- [ ] 푸시 대상이 `origin`인가 (`upstream`이 아닌가)
- [ ] `--no-verify`, `--force`를 쓰지 않았는가
- [ ] 보고한 커밋 해시와 브랜치가 실제 명령 출력과 일치하는가
