# git 커밋

## 핵심 원칙

**계획을 보여주고 승인받기 전에는 커밋하지 않는다.**

커밋은 히스토리에 남고, 잘못 묶인 커밋은 되돌리기 비싸다. 
이 스킬의 산출물은 "커밋"이 아니라 **"사용자가 승인한 커밋"**이다.

---

# 1. 입력 — 무엇을 읽는가

한 번에 병렬 실행한다.

```bash
git status --short
git diff HEAD
git log --oneline -10
```

| 명령 | 얻는 것 |
|---|---|
| `git status --short` | 파일 목록, 스테이징 여부(좌열=index, 우열=worktree), untracked |
| `git diff HEAD` | 스테이징 + 미스테이징 변경의 **합집합** 내용 |
| `git log --oneline -10` | 이 레포의 기존 메시지 톤 |

**읽지 말아야 할 것**

- **`git diff`와 `git diff --staged`를 습관적으로 덧붙이지 마라.** 대부분 `git diff HEAD`의 부분집합이라 토큰 낭비다.
- **예외:** `git status --short`에 `MM`처럼 좌우 열이 모두 채워진 파일(부분 스테이징)이 있을 때만 두 diff를 따로 실행한다.

**입력의 사각지대**

- untracked(`??`) 파일은 **어떤 diff에도 잡히지 않는다.** 내용이 필요하면 파일을 직접 읽어라.
- 변경사항이 하나도 없으면 여기서 즉시 종료한다.

---

# 2. 행동 — 무엇을 하는가

## 2-1. 논리적 단위로 그룹핑

성격이 다른 변경은 나눈다.

- 기능 추가 / 버그 수정 / 문서 / 테스트 / 설정은 각각 다른 커밋
- 판별 질문: **"이 커밋 하나만 revert할 수 있는가?"** 답이 "아니오"면 잘못 묶은 것이다

## 2-2. 부분 스테이징 확인 (`MM`이 있을 때만)

계획을 세우기 **전에** 물어본다.

> `src/auth/login.ts`에 이미 스테이징된 변경과 그렇지 않은 변경이 섞여 있습니다.
> 스테이징된 것만 커밋할까요, 전체를 커밋할까요?

답을 듣기 전에는 그 파일을 건드리지 않는다.

## 2-3. 커밋 계획 제시 → 승인 대기 (HARD GATE)

```
제안된 커밋 계획:

1. feat: 로그인 API 추가
   - src/auth/login.ts
   - src/auth/token.ts

2. test: 로그인 API 테스트 추가
   - test/auth/login.test.ts

이대로 진행할까요?
```

메시지 작성 규칙은 아래 **커밋 메시지 규칙** 참조.

**사용자가 명시적으로 승인할 때까지 `git add`도 `git commit`도 실행하지 않는다.** 그룹이 1개뿐이어도 이 단계를 건너뛰지 않는다. 짧게 제시하되, 제시는 한다.

## 2-4. 순차 커밋

그룹별로 실행한다.

```bash
git add src/auth/login.ts src/auth/token.ts
git commit -m "$(cat <<'MSG'
feat: 로그인 API 추가
MSG
)"
```

- 한 그룹이 실패하면 **멈추고 보고**한다. 다음 그룹으로 넘어가지 않는다.
- hook이 파일을 수정했으면 `git status`로 확인하고 사용자에게 알린다.

# 3. 출력 — 무엇을 남기는가

먼저 확인한다.

```bash
git log --oneline -<생성한 커밋 수>
git status --short
```

그다음 아래 **세 부품을 이 순서대로** 출력하고 종료한다.

```
생성된 커밋:
  a1b2c3d feat: 로그인 API 추가
  e4f5g6h test: 로그인 API 테스트 추가

남은 변경: 없음        ← 있으면 파일 목록과 이유를 적는다

푸시할까요?
```

| 부품 | 내용 |
|---|---|
| 생성된 커밋 | 해시 + 메시지 제목. 실제 `git log` 출력에서 가져온다 |
| 남은 변경 | 커밋하지 않고 남긴 것. 없으면 "없음", 있으면 파일과 이유 |
| 푸시 질문 | 마지막 줄. 이 문장으로 스킬이 끝난다 |

**푸시는 이 스킬의 범위 밖이다.** 사용자가 "응"이라고 답해도, 그 시점부터는 이 스킬이 아니라 사용자의 새 지시로 처리한다.

## 커밋 메시지 규칙

형식: `<type>: <한국어 요약>`

| type | 용도 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `style` | 포맷팅, 동작 변화 없음 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드/설정/의존성 |
| `perf` | 성능 개선 |
| `build`, `ci` | 빌드 시스템, CI 설정 |

- 제목 50자 이내, 마침표 없음
- 명사형 종결: `로그인 API 추가` (O) / `로그인 API를 추가했다` (X)
- 본문은 **"왜"**가 필요할 때만 쓴다. "무엇을"은 diff가 말해준다
- 현재 harness가 커밋 트레일러(`Co-Authored-By` 등)를 지정하고 있으면 그 규칙을 따른다

## 절대 금지

가운데 열의 생각이 떠올랐다면 **이미 위반 직전이다.** 실행하기 전에 오른쪽 열을 읽어라.

| 금지 | 이런 생각이 들면 위반 직전 | 실제 |
|---|---|---|
| `git push` 실행 | "커밋했으니 푸시까지 해주는 게 친절하겠지", "사용자가 어차피 푸시할 거니까" | 공유 브랜치에 올라간 커밋은 사실상 되돌릴 수 없다. 이 스킬은 **묻기만** 한다 |
| `git add -A`, `git add .` | "결과는 같은데 이게 빠르니까" | 같지 않다. 빌드 산출물·IDE 설정·시크릿이 딸려온다. 항상 명시적 경로만 |
| 승인 없이 커밋 | "변경이 작으니 계획은 생략하자", "'커밋해줘'라고 했으니 이미 승인한 것" | 승인한 건 "커밋 행위"지 "커밋 분할안"이 아니다. 그룹 수와 무관하다 |
| 부분 스테이징(`MM`) 파일 통째로 `add` | "어차피 다 커밋할 텐데" | 사용자가 손으로 고른 hunk 범위가 뭉개진다. 먼저 물어라 |
| hook 실패 시 `--no-verify` | "hook이 자꾸 막으니 한 번만" | 우회 금지. 원인을 고치고 재시도한다 |
| `--amend`, `rebase`, `reset --hard`, `checkout --` | "정리하는 김에 깔끔하게" | 히스토리·작업물 파괴 |
| `.env`, `*.key`, `credentials*` 커밋 | "설정 파일도 있어야 돌아가니까" | 시크릿 유출. 계획에서 제외하고 경고한다 |
| `git diff` + `git diff --staged` 습관적 실행 | "안전하게 같이 보자" | `git diff HEAD`가 합집합이다. `MM`이 없으면 순수 낭비 |
