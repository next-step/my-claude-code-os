# spec — 내부 처리 스펙 작성

대상 REQ-ID 는 스킬 호출 시 인자로 전달된다 (예: `/spec REQ-001`). 이하 `<REQ-ID>` 로 표기.

## 0. 선행 조건 확인

- `maintenance/requests/<REQ-ID>.md` 를 읽는다. 없으면 중단하고 알린다.
- frontmatter `classification` 이 `internal` 이 아니면 중단한다.
  `outsource` 면 "이 요청은 외주 대상입니다. `/outsource <REQ-ID>` 를 쓰세요" 라고 안내.

## 1. context-loader 호출

`Task` 툴로 **context-loader** 서브에이전트를 실행한다. 입력: `REQ-ID=<REQ-ID>`, `phase=spec`.
돌려받은 "컨텍스트 팩" 을 스펙 작성의 기준선으로 삼는다 (부족하면 보완 조사 가능).

## 2. 스펙 작성 → 케이스 파일 "4. 스펙" 섹션

다음 항목을 채운다:

- **목표**: 한 문단. 무엇을 달성하면 되는가.
- **범위 / 범위 밖**: 건드릴 것과, 명시적으로 안 건드릴 것.
- **영향 파일**: context-loader 가 지목한 파일·라인 기준.
- **구현 접근**: 방법 개요(알고리즘/흐름). 대안이 있으면 한 줄씩, 그리고 고른 이유.
- **완료 기준 (검증 가능하게)**: `/verify` 가 하나씩 체크할 수 있는 형태로.
  예: "잘못된 토큰으로 로그인 시 3회까지 재시도 후 401 반환", "관련 유닛테스트 통과".
- **위험 / 롤백**: 회귀 위험 지점, 되돌리는 방법.

## 3. spec-reviewer 서브에이전트 호출

`Task` 툴로 **spec-reviewer** 서브에이전트를 실행한다. 입력: `REQ-ID=<REQ-ID>`.
돌려받은 `## 스펙 검토 결과` 를 처리한다:

- **판정: 통과** → 다음 단계로.
- **판정: 보완 필요** → 지적 사항을 "4. 스펙" 에 반영하고, 다시 spec-reviewer 를 호출한다.
  2회 반복해도 통과가 안 나오면 남은 지적을 사용자에게 보고하고 판단을 구한다.

## 4. 상태 갱신

- frontmatter `status: spec`, `updated` 오늘로 갱신
- `변경 이력` 에 `<오늘> 스펙 확정 (spec, 리뷰 통과)` 추가

## 5. 보고

스펙 요약·완료 기준 목록과 spec-reviewer 판정을 보여주고,
다음 단계로 `/implement <REQ-ID>` 를 안내한다.

## 하지 말 것

1. 코드를 수정하지 않는다 — 스펙 문서만 작성한다.
2. 완료 기준을 "잘 동작함" 같이 모호하게 쓰지 않는다 — 측정 가능해야 한다.
3. 요청 범위를 임의로 키우지 않는다 — 커지면 사용자에게 확인받고 "범위 밖" 에 기록한다.
4. spec-reviewer 지적을 무시하고 `status: spec` 으로 넘기지 않는다.
