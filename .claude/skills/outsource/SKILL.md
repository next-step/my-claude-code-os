# outsource — 외주 요청서 작성

대상 REQ-ID 는 스킬 호출 시 인자로 전달된다 (예: `/outsource REQ-001`). 이하 `<REQ-ID>` 로 표기.

## 0. 선행 조건

- `maintenance/requests/<REQ-ID>.md` 를 읽는다.
- frontmatter `classification` 이 `outsource` 가 아니면 중단한다.
  `internal` 이면 "내부 처리 대상입니다. `/spec <REQ-ID>` 를 쓰세요" 라고 안내.

## 1. 외주 요청서 작성 → 케이스 파일 "7. 외주 요청서"

받는 쪽(외부 업체/담당자)이 **이 문서만 보고도 착수**할 수 있어야 한다. 항목:

- **배경 / 문제**: 지금 무엇이 왜 문제인가 (내부 용어·약어는 풀어서 설명).
- **요청 범위**: 해줘야 하는 일. 목록으로.
- **범위 밖**: 명시적으로 포함하지 않는 것.
- **산출물**: 코드 / 문서 / 배포본 등 구체적으로.
- **완료·인수 기준**: 우리가 무엇을 확인하면 받는가 (검증 가능하게).
- **제약 조건**: 기술 스택, 보안 / 컴플라이언스, 코딩 규칙, 라이선스.
- **필요한 접근 권한 / 우리가 제공할 것**: 저장소, 계정, 문서, 담당자.
- **일정**: 희망 착수 / 납기, 마일스톤.
- **커뮤니케이션**: 채널, 보고 주기, 우리 쪽 창구.
- **예산 / 비고**: 알면 범위, 모르면 `협의`.

## 2. 상태 갱신

- frontmatter `status: outsourced`, `updated` 오늘로 갱신
- `변경 이력` 에 `<오늘> 외주 요청서 발행 (outsourced)` 추가

## 3. 보고

요청서 전문을 사용자에게 보여주고, `(확인 필요)` 로 남은 칸을 짚어 준다.
외부로 보내기 전에 사용자가 검토·보완하도록 안내한다.

## 하지 말 것

1. 확정되지 않은 일정·예산을 임의로 지어내지 않는다 — 모르면 `(확인 필요)`.
2. 내부 시크릿(키, 내부 URL, 개인정보)을 요청서에 넣지 않는다.
3. 코드를 구현하지 않는다 — 이 요청은 외주 대상이다.
