# TDD 구현 루프 (tdd-implement)

실패하는 인수 테스트를 초록불로 바꾸는 스킬입니다. ATDD 파이프라인 06단계를 담당하며, **테스트를 고쳐서 통과시키는 것을 금지**하는 것이 이 스킬의 존재 이유입니다.

테스트를 손대는 순간 ATDD는 무너집니다. 통과시킬 수 없다면 그것은 구현이 부족하거나 인수기준이 잘못된 것이지, 테스트가 까다로운 게 아닙니다.

## 언제 쓰는가

`acceptance-test-write`(05단계)가 실패하는 테스트를 남기고 멈춘 뒤에 사용한다. 사용자가 "이제 구현해줘", "테스트 통과시켜줘"라고 요청하거나 `atdd-orchestrator`가 06단계를 위임할 때 사용한다.
**이 스킬은 구현 코드만 수정한다. 테스트 코드와 인수기준은 읽기 전용으로 취급한다.**

## 실행 절차

1. **출발점 확인**
   - `node --test .claude/tests/` 를 실행해 **지금 실패하고 있는지** 확인한다.
   - 이미 전부 통과 중이면 05단계가 제대로 안 된 것이므로, 구현하지 않고 그 사실을 알린다.
   - 실패한 테스트 이름(`AC-<번호>: ...`)을 목록으로 정리한다.

2. **최소 구현 (재시도 1회차)**
   - 실패한 테스트를 통과시킬 **최소한의** 코드만 작성한다. 인수기준에 없는 기능을 미리 만들지 않는다.
   - **절대 금지**: 테스트 파일 수정, 단언(assert) 완화·삭제·주석 처리, `skip`/`todo` 표시, 테스트 입력값에만 맞춘 하드코딩.

3. **재실행 · 재시도 (상한 3회)**
   - `node --test .claude/tests/` 를 다시 실행한다.
   - 여전히 실패하면 실패 메시지를 근거로 구현을 고치고 다시 실행한다.
   - **재시도 상한은 3회다.** 매 시도마다 "n회차 / 3회" 를 명시해 사용자가 남은 횟수를 볼 수 있게 한다. **UI AC가 있는 경우 이 3회는 구조 테스트 재실행과 5-4의 시각 비교 재실행을 합산한 상한이다.**

4. **상한 초과 시 — 사람에게 인계**
   - 3회 안에 통과하지 못하면 **더 시도하지 않고 멈춘다.** 계속 찌르는 대신 다음을 정리해 보고한다:
     - 어떤 AC가 계속 실패하는지
     - 매 시도에서 무엇을 바꿨고 왜 실패했는지
     - 구현 문제로 보이는지, 인수기준 자체가 모순되어 02단계로 돌아가야 하는지에 대한 판단
     - **UI AC가 있었다면**: 구조 테스트 문제였는지 시각 비교 문제였는지, 시각 비교 문제라면 이미지 해석(`ui-spec-from-image`) 자체가 잘못된 것인지 구현이 잘못된 것인지 구분해 보고한다.
   - 실패 이력은 `atdd-failure-log.js` 훅이 원장에 자동 기록하므로 여기서 직접 쓰지 않는다.

5. **독립 리뷰 위임 (→ `test-reviewer` 서브에이전트)**
   - 전부 통과했더라도 **바로 끝내지 않는다.** 초록불이 정직하게 얻어진 것인지는 구현한 쪽이 판정할 수 없다.
   - `Agent` 도구로 `test-reviewer`를 `모드: IMPL_HONESTY`로 호출한다.
   - **전달하는 것**: 승인된 AC 목록, 테스트 코드, 구현 코드, 통과 로그. **전달하지 않는 것**: 구현 과정의 자기 변호.
   - FAIL(우회·하드코딩 지적)이면 2단계로 돌아간다. 이때도 재시도 상한을 함께 센다.

5-1. **(조건부) UI 존재 확인**
   - 이번 사이클에 UI AC(`[UI]` 태그)가 있는지 확인한다. **없으면 6번(결과 보고)으로 바로 간다.**

5-2. **(조건부) 스크린샷 촬영 (→ `claude-in-chrome` 스킬)**
   - `Skill` 도구로 `claude-in-chrome`을 호출해 `.claude/lib/ui/<feature-slug>/index.html`을 렌더링하고, `.claude/tests/fixtures/<feature-slug>/screenshot.png`로 저장한다.
   - 스크린샷 촬영은 이 스킬(06단계)의 책임이다. `ui-visual-reviewer`는 촬영하지 않는다.

5-3. **(조건부) 시각 비교 위임 (→ `ui-visual-reviewer` 서브에이전트)**
   - 왜 별도 에이전트에게 시각 비교를 맡기는지 한 문장으로 설명한다.
   - `Agent` 도구로 `ui-visual-reviewer`를 호출한다.
   - **전달하는 것**: 원본 목업 이미지(`mockup.*`) 경로, 방금 촬영한 스크린샷(`screenshot.png`) 경로 **두 개뿐**. **전달하지 않는 것**: 구현 코드, AC 목록, 구조 테스트 결과, 자기 평가.

5-4. **FAIL 처리**
   - `ui-visual-reviewer`가 FAIL을 내면 2단계(최소 구현)로 되돌아가 CSS/레이아웃을 수정한다.
   - **이 재시도는 3단계의 3회 상한 카운터를 공유한다.** 별도로 3회를 더 주지 않는다.

6. **결과 보고**
   - 통과한 AC 목록, 총 재시도 횟수, `test-reviewer` 판정(과 UI AC가 있었다면 `ui-visual-reviewer` 판정)을 요약한다.
   - 07단계(실패 원장 확인)로 넘어갈 수 있음을 알리고 멈춘다.

## 참고

- 재시도 상한 3회는 온보딩 자료의 "3회 상한" 규칙을 따른 것이다. 무한히 시도하는 AI보다 빨리 손드는 AI가 낫다는 판단이다.
- `test-reviewer`는 `acceptance-test-write`(05단계)와 **공유하는 서브에이전트**다. 05는 `TEST_QUALITY`, 06은 `IMPL_HONESTY` 모드로 같은 전문성을 재사용한다.
- 이 스킬이 가장 어기기 쉬운 규율은 "막히면 테스트를 살짝 고치기"다. 막히면 고칠 대상은 언제나 구현이거나 인수기준이다.
- `ui-visual-reviewer`의 FAIL은 `node --test` Bash 출력이 아니므로 `atdd-failure-log.js` 훅이 자동 기록하지 않는다 — `policy-reviewer`/`test-reviewer`의 FAIL이 원장에 안 남는 것과 같은 기존 설계와 일관된 동작이다(새로운 갭이 아니다).

## 예시

```
[06] 출발점 확인: node --test .claude/tests/
     ↳ 8 fail / 0 pass — 구현 없음 확인

[06] 1회차 / 3회 — .claude/lib/stats.js 에 summarize() 최소 구현
     ↳ 6 pass / 2 fail (AC-2 동률 정렬, AC-8 유효 시각 전무)

[06] 2회차 / 3회 — 동률 처리와 빈 후보 분기 추가
     ↳ 8 pass / 0 fail  ✅

[06] 초록불이 정직한지는 구현자가 판정할 수 없으므로 위임합니다
     → Agent(test-reviewer, 모드: IMPL_HONESTY)
     ↳ 판정: PASS — 테스트 수정 흔적 없음, 하드코딩 없음

[06] 총 2회 재시도로 AC-1~8 전부 통과. 07단계로 넘어갈 수 있습니다.
```
