# Skill Forge — 스킬을 만드는 오케스트레이터

이 저장소의 첫 오케스트레이터다. 지휘 구조는 `OS.md` 4절에서 상속받고, 이 문서는 그것을
**스킬 만들기**라는 한 워크플로우에 적용한다.

왜 첫 워크플로우가 이것인가. `OS.md` 원칙 3은 "손으로 두 번 반복하면 스킬로 승격한다"고 말한다.
스킬 만들기는 이 저장소에서 **이미 세 번 반복된**(`commit`, `news`, `skill-stat`) 유일한 워크플로우다.
대상 제품이 정해지기 전에 오케스트레이터를 태워볼 수 있는 것도 이것뿐이다.

## 0. 이 스킬의 실패 모드

스킬 파일을 만드는 일은 쉽다. 어려운 것은 **그 파일이 실제로 불리고, 실제로 사고를 막는 것**이다.

혼자 만들면 내가 쓴 초안을 내가 검토한다. 같은 착각을 두 번 하고, 초안은 늘 통과한다.
그래서 이 스킬의 실패는 "초안이 나쁘게 나와서"가 아니라 **"내 초안을 추인하는 검토가 돌아서"** 일어난다.

| 실패 | 어떻게 일어나는가 | 방어 |
|---|---|---|
| 추인 검토 | 검토자에게 "이렇게 썼는데 괜찮아?"라고 묻는다 | 검토자는 **초안만** 받는다. 작성 의도·이유를 주지 않는다 |
| 시끄러운 지적 | 검토자 지적을 전부 반영해 스킬이 부풀고 끝나지 않는다 | 지적마다 **반박자**를 붙이고, 애매하면 지적을 버린다 |
| 안 불리는 스킬 | 트리거 문구가 내가 실제 쓰는 말과 다르다 | 1단계에서 **실제 쓰는 말**을 받고, `lint.py`가 3개 이상을 강제한다 |
| 통과 착각 | 서브가 "잘 됐다"고 말한 것을 통과로 쓴다 | 관문은 `lint.py`의 **종료 코드**다. 자연어 판정은 통과가 아니다 |

## 1. 지휘 규칙 — `OS.md` 4절을 그대로 적용한다

| # | 이 스킬에서의 의미 |
|---|---|
| 1 | **메인은 초안을 쓰지 않고, 지적의 타당성도 판정하지 않는다.** 부르고, 받고, 넘긴다 |
| 2 | 검토자·반박자에게 **결론을 미리 주지 않는다** |
| 3 | 서브의 입력은 자기 판단에 필요한 만큼만 자른다. 이 대화 전체를 넘기지 않는다 |
| 4 | 검토자 3명은 **병렬**, 단계 사이는 **순차** |
| 5 | `lint.py` 실패는 다음 단계로 넘기지 않는다. 2단계로 되돌린다 |
| 6 | 파일 쓰기는 사람 승인 후. **커밋·푸시는 이 스킬이 하지 않는다** |
| 7 | 서브의 "통과" 발언을 통과로 채택하지 않는다. `lint.py`에 걸어본다 |

## 2. 흐름

```
사람 ──요구──▶ [메인: 지휘만]
                   │
                   │ ① 요구 수집 (사람과 직접) ── 막을 사고를 못 대면 여기서 중단
                   │
                   ├─▶ ② 초안 작성자 (서브 1)
                   │        │ 초안
                   │        ▼
                   ├─▶ ③ 검토자 3명 (서브, 병렬) ── 초안만 받는다
                   │        │ 지적 N건
                   │        ▼
                   ├─▶ ④ 반박자 (서브, 지적당 1명) ── 지적자의 근거는 받지 않는다
                   │        │ 살아남은 지적만
                   │        ▼
                   ├─▶ ⑤ lint.py (기계 채점기) ──FAIL──▶ ②로 되돌림 (최대 3회)
                   │        │ PASS
                   │        ▼
                   └─▶ ⑥ 사람 승인 ──▶ 파일 쓰기 (커밋은 commit 스킬에 넘긴다)
```

## 3. 단계

### ① 요구 수집 — 메인이 사람과 직접 한다 (서브 없음)

세 가지를 받는다. 하나라도 비면 다음 단계로 가지 않는다.

| 받을 것 | 없으면 |
|---|---|
| 이 스킬이 **막아야 할 사고** 1개 이상 | 스킬을 만들지 않는다. 막을 사고가 없으면 그건 스킬이 아니라 한 줄 지시다 |
| **실제로 쓸 말** 3개 이상 (트리거 후보) | 만들어도 불리지 않는다 |
| 필요한 **도구** 목록 | 전부 열지 않는다. 모르면 최소로 시작한다 |

"막을 사고"를 물을 때 기능을 묻지 않는다. **"이게 없으면 무슨 사고가 나는가"** 를 묻는다.
답이 "편해진다"뿐이면 스킬 대신 한 줄 지시로 충분하다는 뜻이고, 그 사실을 알린다.

### ② 초안 작성자 — 서브에이전트 1명

메인은 초안을 쓰지 않는다. 아래만 넘긴다.

- 막을 사고 목록, 트리거 문구, 도구 목록 (①의 산출물)
- 스타일 참조로 기존 스킬 **1개**의 경로 (내용을 붙여넣지 않고 경로만 준다)
- `lint.py`가 검사하는 항목 (구조 요건)

넘기지 않는 것: 내가 머릿속에 그린 초안, "이런 식으로 써줘" 같은 지시된 결론.

### ③ 검토자 — 서브에이전트 3명, 병렬, 관점을 나눈다

같은 초안을 세 번 읽히는 것이 아니라 **다른 자리에서** 읽힌다. 동일 프롬프트 3개는 의미가 없다.

| 관점 | 이 검토자가 찾는 것 |
|---|---|
| 트리거 | 이 스킬이 **안 불릴 이유**. description이 실제 쓰는 말을 담고 있는가 |
| 방어 | ①의 사고 목록 각각이 본문 규칙으로 **실제로 막히는가**. 안 막히는 사고를 지목한다 |
| 유발 | 이 스킬을 그대로 따르면 **새로 생기는 사고**. 과잉 권한, 되돌릴 수 없는 조작 |

세 검토자 모두 **초안 본문만** 받는다. 누가 썼는지, 왜 그렇게 썼는지, 앞 단계에서 무슨 말이 있었는지 주지 않는다.
각 검토자에게 **"지적할 것이 없으면 없다고 답하라"** 를 명시한다. 지적 개수를 채우게 만들면 시끄러워진다.

### ④ 반박자 — 지적 하나당 서브에이전트 1명

- 받는 것: 지적 문장 하나 + 초안
- 받지 않는 것: 지적자의 근거, 관점 이름, 다른 지적들
- 돌려주는 것: 반박 성공 / 실패, 한 줄 근거

**애매하면 반박 성공으로 본다** — 즉 지적을 버린다. 스킬 만들기의 실패 모드는 "틀려서"가 아니라 **"시끄러워서"** 이고,
부풀어 끝나지 않는 스킬이 지적 하나 놓친 스킬보다 나쁘다. 버린 지적은 **개수와 요지를 사람에게 보고**한다.

반박에 실패한 지적만 초안에 반영한다. 반영은 메인이 한다(판정이 아니라 적용이므로).

### ⑤ 관문 — `lint.py`

```bash
python3 .claude/skills/skill-forge/lint.py <스킬-디렉터리>
```

**종료 코드 0이 아니면 통과가 아니다.** 서브가 무슨 말을 했는지와 무관하다.

FAIL이면 실패 항목의 `→ 고칠 것` 문장을 그대로 ②에 되돌린다. 같은 초안에 대해 **최대 3회**까지 돌리고,
3회에도 통과하지 못하면 멈추고 사람에게 lint 출력을 그대로 보여준다. 무한 루프를 도는 것보다 낫다.

`lint.py`를 우회하거나 검사 항목을 지워서 통과시키지 않는다. 검사가 틀렸다고 판단되면
**근거를 대고 스크립트를 고칠 것을 제안**한 뒤 사람 승인을 받는다.

### ⑥ 확정

파일 쓰기 전에 사람에게 보여준다.

- 새 스킬이면 `.claude/skills/<name>/SKILL.md` (`CLAUDE.md` 규칙 1 — 반드시 프로젝트 안)
- 기존 스킬을 고치는 경우 덮어쓰기 전에 diff를 보여주고 확인받는다
- `lint.py` 기록 한 줄(`기록: <name> PASS 10/10`)을 결과에 함께 보고한다

커밋과 푸시는 **하지 않는다.** `commit` 스킬의 일이다.

## 4. 서브에이전트 프롬프트 규격

읽을 때 중요한 열은 "돌려주는 것"이 아니라 **"절대 받지 않는 것"** 이다. 그 열이 이 오케스트레이터의 독립성 전부다.

| 서브 | 받는 것 | 절대 받지 않는 것 | 돌려주는 것 |
|---|---|---|---|
| 초안 작성자 | 사고 목록, 트리거, 도구, 참조 스킬 경로, 구조 요건 | 내가 그린 초안, 지시된 결론 | SKILL.md 초안 전문 |
| 검토자 (트리거) | 초안 본문 | 작성 의도, 작성자, 앞 단계 대화 | 안 불릴 이유 목록 (없으면 "없음") |
| 검토자 (방어) | 초안 본문 + 사고 목록 | 초안이 그 사고를 막으려 했다는 설명 | 안 막히는 사고 목록 |
| 검토자 (유발) | 초안 본문 | 작성 의도 | 새로 생기는 사고 목록 |
| 반박자 | 지적 하나 + 초안 본문 | 지적자의 근거·관점, 다른 지적 | 반박 성공/실패 + 한 줄 근거 |

## 5. 금지

- 메인이 초안을 직접 쓰기 — 서브를 부른 의미가 사라진다
- 메인이 지적의 타당성을 판정하기 — 반박자의 일이다
- 검토자에게 작성 의도를 알려주기 — 추인 검토가 된다
- 검토자 3명에게 같은 프롬프트 주기 — 관점을 나누지 않으면 3배 느린 1명이다
- `lint.py` 실패를 손으로 우회하기, 검사 항목 삭제로 통과시키기
- 사람 승인 없이 기존 파일 덮어쓰기
- 이 스킬에서 커밋·푸시하기

## 6. 인자

| 인자 | 동작 |
|---|---|
| (없음) | ①~⑥ 전체 |
| 자유 텍스트 | 만들 스킬의 요구로 사용. ①에서 부족한 것만 되묻는다 |
| `--fix <스킬명>` | 기존 스킬 수정. ②의 입력이 현재 파일이 된다 |
| `--review <스킬명>` | ③④⑤만. 파일을 고치지 않고 지적과 lint 결과만 보고 |
| `--reviewers N` | 검토자 수 (기본 3). 3보다 줄이면 관점 중 무엇을 뺐는지 밝힌다 |
| `--dry-run` | ⑥의 파일 쓰기를 하지 않는다 |

## 출력 전 자기 점검

- [ ] 초안을 서브에이전트가 썼는가 (메인이 직접 쓰지 않았는가)
- [ ] 검토자에게 초안만 주고 작성 의도를 주지 않았는가
- [ ] 검토자 3명의 관점이 서로 다른가
- [ ] 반박자에게 지적자의 근거를 주지 않았는가
- [ ] `lint.py`를 실제로 돌렸는가 (통과했다고 말만 하지 않았는가)
- [ ] lint 실패 항목을 우회하거나 검사를 지우지 않았는가
- [ ] 버린 지적의 개수와 요지를 보고했는가
- [ ] 파일 쓰기 전에 사람 승인을 받았는가
- [ ] 커밋·푸시를 하지 않았는가
