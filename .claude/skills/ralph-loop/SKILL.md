# 랄프 루프 (ralph-loop)

목표에 닿을 때까지 같은 과제를 **매번 빈 컨텍스트로** 다시 던지는 루프입니다. `context-ab`가 "지침 구성을 바꾸면 뭐가 달라지나"를 한 번 재는 도구라면, 이 스킬은 "목표 수치에 닿을 때까지 자동으로 고쳐 보는" 도구입니다.

## 왜 있는가

이 저장소의 기존 루프는 전부 상한이 걸린 유한 재시도입니다(`OS.md:282-291`). 사람이 고칠 방향을 알고 있을 때는 그것으로 충분합니다. 그런데 "응답을 절반으로 줄여라" 같은 목표는 무엇을 고쳐야 하는지를 미리 알 수 없고, 고쳐 보고 재 봐야 압니다. 그 시행착오를 사람이 돌리면 회차마다 앞 회차의 맥락이 쌓여서 판단이 오염됩니다. 랄프 루프는 회차마다 컨텍스트를 버려서 그 오염을 없앱니다.

## 절차

| 단계 | 무엇을 | 도구 |
|---|---|---|
| 1 | 목표 정의를 고른다 | `experiments/ralph/goals/*.json` |
| 2 | dry-run으로 세션 수와 예상 비용을 본다 | `node .claude/lib/ralph-run.js --goal <경로>` |
| 3 | **사람에게 승인을 받는다** | AskUserQuestion — 세션 수와 예상 비용을 그대로 보여준다 |
| 4 | 실제로 돌린다 | 같은 명령에 `--go` |
| 5 | 결과 패치를 사람에게 제출한다 | `experiments/ralph/runs/<목표id>/final.patch` |
| 6 | 한계를 함께 말한다 | `summary.json`의 `caveat` |

### 2단계 — dry-run이 기본이다

```bash
node .claude/lib/ralph-run.js --goal experiments/ralph/goals/brevity-50.json
```

세션 수와 예상 비용만 찍고 끝납니다. `--go` 없이는 절대 세션이 뜨지 않습니다(테스트 AC-9가 이걸 잠급니다). 세션 수는 `1 + 과제수 × repeats` 곱하기 이터레이션 수에 베이스라인을 더한 값이며, AC-15가 이 산식을 잠급니다.

### 4단계 — 실제 실행

```bash
node .claude/lib/ralph-run.js --goal <경로> --go
```

옵션: `--max-iterations N`(목표 정의의 상한을 낮춰 잡을 때), `--work-dir <경로>`, `--model <id>`, `--per-run-usd <숫자>`, `--root <결과 경로>`.

사본은 `TMPDIR` 아래에 만듭니다. 저장소 안에서 돌리면 회차마다 `git status`가 달라져 `os-retro-check.js`와 `big-change-commit-check.js`가 계속 되묻습니다. 같은 사고가 `.gitignore:21-27`에 기록돼 있습니다.

### 사본이 둘인 이유

| 사본 | `.git` | 훅 | 쓰임 |
|---|---|---|---|
| `work/` | 있음 | 없음 | 작업 세션이 `editable` 파일을 고칩니다. 회차마다 커밋을 남겨 마지막에 패치를 뽑습니다 |
| `probe/` | 없음 | 없음 | 측정 세션이 고정 과제에 답합니다. 회차마다 `editable` 파일만 `work/`에서 옮겨 심습니다 |

측정 사본에서 `.git`을 빼는 것은 취향이 아닙니다. gitStatus(최근 커밋)가 세션 시작 시 주입되므로, 회차마다 커밋이 쌓이면 측정 세션이 지침이 아니라 커밋 로그에 반응하게 됩니다. `context-ab.js:101`이 실험 3에서 같은 누수를 겪었다고 적어 뒀습니다.

### 고칠 파일이 `work/ralph-edit/`에 따로 깔리는 이유

헤드리스 세션은 `.claude/**`를 민감 파일로 분류합니다. 편집 승인이 자동으로 서는 모드(`--permission-mode acceptEdits`)에서도 사람에게 되묻고 멈춥니다. 루프에는 되물을 사람이 없으므로 작업 세션이 그 자리에서 끝납니다. 2026-09-11 실제 실행에서 회차 두 번이 통째로 이렇게 날아갔습니다.

그래서 보호를 끄는 대신 **작업하는 자리를 옮깁니다.**

| 시점 | 경로 |
|---|---|
| 작업 세션이 고치는 곳 | `work/ralph-edit/claude__context__response-brevity.md` |
| 측정 직전 옮겨 심는 곳 | `probe/.claude/context/response-brevity.md` |
| 최종 패치에 적히는 경로 | `.claude/context/response-brevity.md` |

측정 사본에서는 원래 자리로 돌아가므로 측정은 그대로 성립하고, 패치도 저장소에 바로 적용됩니다(AC-22·23이 잠급니다). 작업 세션에만 `--permission-mode acceptEdits`를 붙이고 측정 세션에는 붙이지 않습니다 — 측정까지 권한 설정을 바꾸면 재는 대상이 평소 세션과 달라집니다(AC-24).

### 5단계 — 결과를 적용하는 법

루프는 저장소를 고치지 않습니다. 산출물은 다음과 같습니다.

- `final.patch` — 사람이 읽고 적용합니다. `git apply`로 바로 넣지 말고 먼저 읽으십시오. **`editable`에 적힌 경로만 담깁니다.** 한정하지 않으면 사본에서 뺀 훅과 `settings.json`이 삭제로 잡혀, 적용하는 순간 훅이 전부 사라집니다(AC-17이 잠급니다).
- `summary.json` — 결과(`done` / `stalled` / `exhausted` / `aborted`), 회차별 지표 추이, `caveat`, 그리고 `strayChanges`. 루프가 `editable` 밖을 만졌으면 그 경로 이름이 여기 남습니다. 패치에는 넣지 않지만 조용히 버리지도 않습니다.
- `RALPH-NOTES.md` — 루프가 무엇을 시도했고 무엇이 안 통했는지.
- `iteration-N/` — 회차별 프롬프트, 작업 응답, 측정 응답 원문, `metrics.json`.

## 목표 정의를 어떻게 쓰나

```json
{
  "id": "<영숫자와 _- 만>",
  "goal": "무엇을 이루려는지 한 문장",
  "editable": ["고쳐도 되는 파일 목록"],
  "probes": [{ "id": "...", "prompt": "측정용 고정 과제" }],
  "targets": [{ "id": "...", "kind": "response", "extract": "median_chars", "op": "<=", "relative_to_baseline": 0.5 }],
  "guards":  [{ "id": "...", "kind": "command", "cmd": "node --test ...", "extract": "fail", "op": "<=", "relative_to_baseline": 1 }],
  "repeats": 3, "max_iterations": 8, "stall_after": 3
}
```

- **`targets`는 달성할 것, `guards`는 무너지면 안 될 것입니다.** target을 전부 달성해도 guard가 하나 깨지면 실패로 칩니다. 분량만 재는 루프는 "아무 말도 안 하는" 방향으로 최적화되기 때문입니다(AC-5).
- `kind`는 `response`(측정 세션의 응답을 잰다)와 `command`(작업 사본에서 셸 명령을 돌린다) 두 가지입니다.
- 목표값은 `absolute` 또는 `relative_to_baseline` 중 **정확히 하나**입니다. 둘 다 주면 어느 쪽이 이기는지가 정의에서 안 보입니다.
- `max_iterations`는 생략할 수 없습니다. `repeats`를 생략하면 3이 채워집니다.
- **셸 가드는 `absolute: 0`보다 `relative_to_baseline: 1`이 안전합니다.** 작업 사본은 훅을 뺀 상태라 목표와 무관하게 이미 깨져 있는 테스트가 있습니다. 절대값 0으로 걸면 그 가드는 처음부터 만족될 수 없어, "망가뜨리지 마라"가 아니라 "시작부터 실패"가 됩니다. 배수 1을 주면 고치기 전에 잰 값이 기준이 됩니다. 베이스라인에서 못 잰 가드는 통과가 아니라 위반으로 칩니다(AC-19·20·21).
- **`editable`에 지표를 산출하는 코드를 넣지 마십시오.** 루프가 채점기를 고칠 수 있으면, 목표를 달성하는 가장 짧은 경로가 "탐지를 무력화하는 것"이 됩니다. 예를 들어 "`docs/*.md`의 미등록 수치를 0으로 줄여라"라는 목표에 `.claude/lib/freshness.js`를 `editable`로 주면, 루프는 문서를 고치는 대신 탐지 함수가 아무것도 못 찾게 만들어 즉시 0을 달성합니다. `guards`의 `cmd`가 부르는 파일에도 같은 원칙이 적용됩니다.

## 세션이 실패한 측정은 세지 않는다

측정 세션은 실패할 수 있습니다(API 오류, 타임아웃). 그때 응답 본문은 오류 문자열이라 **아주 짧습니다.** 분량을 줄이는 목표에서는 그것이 개선처럼 보입니다 — 네트워크가 끊긴 것을 목표 달성으로 보고하게 됩니다. 실제로 `context-slim-30` 두 번째 실주행에서 6회 중 4회가 78자짜리 `API Error: ENOTFOUND`였는데 분량 가드가 초록불을 냈습니다.

그래서 세 가지를 겁니다.

1. `ok === false`인 측정은 집계에서 뺍니다. 몇 개를 뺐는지는 `failedRuns`로 남기고 `caveat`이 말합니다(AC-27).
2. 한 과제의 측정이 **과반 실패하면 지표를 통째로 `null`로** 냅니다. 남은 한 개의 중앙값은 대표값이 아닙니다. `null`은 통과로 치지 않으므로 못 잰 회차가 조용히 성공으로 넘어가지 않습니다(AC-29·30).
3. **베이스라인을 못 재면 회차를 하나도 시작하지 않고 `aborted`로 끝냅니다**(AC-31). 기준값이 없으면 배수 목표가 서지 않고 노이즈 폭도 못 구하는데, 그래도 루프는 상한까지 돌며 회차마다 실비를 씁니다. 2회차 실주행이 그렇게 28세션을 태웠습니다.

**못 잰 것보다 잘못 잰 것이 나쁩니다.** 못 쟀다는 사실은 `null`로 드러나지만, 잘못 잰 값은 정상적인 숫자로 위장합니다.

## 노이즈를 개선으로 착각하지 않는 장치

같은 지침과 같은 과제로 돌려도 응답 길이는 실행마다 흔들립니다. 그래서 세 가지를 겁니다.

1. 과제를 `repeats`회씩 돌립니다. 기본 3회입니다.
2. 대표값은 평균이 아니라 **중앙값**입니다. 한 번 유난히 긴 응답이 나와도 판정이 통째로 흔들리지 않습니다.
3. 베이스라인 반복 측정에서 **과제 안의 산포**를 구해 노이즈 폭으로 삼고, 그 폭을 넘어서 줄었을 때만 개선으로 셉니다(AC-14). 과제를 가로질러 재지 않는 이유는, 과제가 다르면 응답 길이도 원래 다르기 때문입니다.

`repeats`를 1로 두면 노이즈 폭이 0이 되어 정체 판정이 사실상 꺼집니다. 그때는 `summary.json`의 `caveat`이 그 사실을 말합니다.

## 하지 않는 것

- **사람 승인 없이 실행하지 않는다.** 실비가 나갑니다. dry-run으로 세션 수와 예상 비용을 먼저 보여줍니다.
- **결과를 저장소에 자동으로 적용하지 않는다.** 패치를 제출하고 멈춥니다. 개인 지침이 검토 없이 바뀌면 되돌리기 전까지 모든 세션에 영향을 줍니다.
- **목표 정의를 스스로 고치지 않는다.** 목표에 못 닿았다고 목표값을 낮추는 것은 실험을 조작하는 것입니다. `evals.json`이 "루브릭은 결과를 보기 전에 고정한다"고 적어 둔 것과 같은 이유입니다.
- **상한 없이 돌리지 않는다.** `max_iterations`는 필수입니다. `OS.md:291`의 "무한히 시도하는 AI보다 빨리 손드는 AI가 낫다"를 폐기하는 것이 아니라, 상한이 있는 자율 루프라는 예외를 두는 것입니다.
- **실행 결과를 커밋하지 않는다.** `experiments/ralph/runs/`는 `.gitignore`에 있습니다. 재현을 가능하게 하는 것은 결과가 아니라 목표 정의이고, 그쪽은 커밋됩니다.

## 이 루프가 보지 못하는 것

`summary.json`의 `caveat`을 **초록불일 때도 반드시 같이 말합니다.** 초록불을 품질 보증으로 읽는 것이 이 저장소가 반복해 겪은 실패입니다.

- **품질을 직접 재지 못합니다.** guard는 인용 개수와 셸 명령 결과만 봅니다. 응답이 짧아지면서 실제로 쓸모가 줄었는지는 사람이 패치를 읽고 판단해야 합니다. 자동 채점을 종료 판정에 물리지 않은 이유는 `.claude/context/context-experiment.md`에 있습니다. 이 저장소는 세 실험 연속으로 채점 기준이 대상보다 부정확했고, 그런 기준을 루프에 물리면 루프가 잘못된 기준을 최적화합니다.
- **작업 사본에는 훅이 없습니다.** 훅을 넣으면 회차마다 Stop 훅이 되물어 루프가 진행되지 않습니다. 따라서 훅이 관여하는 동작은 루프 안에서 재현되지 않습니다.
- **목표를 달성해도 그 지침이 다른 과제에서 잘 동작한다는 보장은 없습니다.** 루프는 `probes`에 적힌 과제만 봅니다. 과제 두세 개에 맞춰 최적화된 지침일 수 있습니다.
- **측정 세션의 모델과 실제 사용 모델이 다르면 결과가 옮겨지지 않습니다.** `--model`을 쓸 때 유의하십시오.
- **측정 실패를 짧은 응답과 구분하지 못합니다.** 세션이 오류 문자열 한 줄을 돌려주면 그것이 "아주 짧은 응답"으로 집계됩니다. 2026-09-11 실행에서 실행 중 컴퓨터가 절전에 들어가 측정 3개 중 2개가 90자짜리 오류 문자열로 기록됐고, 그 값이 중앙값을 끌어내렸습니다. 지표가 갑자기 크게 좋아지면 `runs/iteration-*/probes/*.txt`를 먼저 열어 보십시오. 장시간 실행 중에는 절전을 꺼 두는 편이 안전합니다.
