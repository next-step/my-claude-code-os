# 기능 개발 파이프라인 (feature-dev)

기능 하나를 **4단계**로 개발하는 오케스트레이터 스킬이다. 각 단계는 전용 서브에이전트(`.claude/agents/`)에게 맡기고, 이 스킬은 그 사이를 잇고 **검증 루프**를 돌린다.

```
① code-analyzer → ②a test-writer → ②b impl-writer → ③ [review-correctness ∥ review-tests] ⇄ (라우팅) → ④ doc-writer
```

> 💡 **왜 이렇게 나누나?** 한 에이전트가 전부 하면 맥락이 뒤섞이고, 자기가 짠 코드를 자기가 리뷰하는 "확증 편향"이 생긴다. 단계를 나누고 **리뷰어를 구현자와 분리**하면, 독립적인 시선으로 품질을 검증할 수 있다. 이게 이 파이프라인의 핵심이다.
>
> 💡 **왜 테스트 작성과 구현을 나누나(②a/②b)?** TDD에서 **테스트가 곧 명세**다. `test-writer`가 "무엇이 맞는가"(수용 기준 → red 테스트)를 소유하고, `impl-writer`가 "어떻게 충족하는가"(green 구현)를 소유한다. 이렇게 분리하면 impl-writer가 **자기 테스트를 자기가 무력화하는 일을 구조적으로 막을 수 있다** — 남이 쓴 테스트를 통과시켜야 하니까.
>
> 💡 **왜 리뷰어가 2개인가?** 한 리뷰어가 정확성·테스트를 다 보면 각 관점이 얕아진다. "코드가 맞나(review-correctness)"와 "그걸 실제로 검증했나(review-tests)"는 서로 다른 실패 유형을 잡는 직교적 렌즈라, 각각 전담시켜 **병렬로** 돌리면 더 깊고 빠르다. 두 판정의 취합은 이 스킬이 직접 한다(별도 취합 에이전트 없음).

## 사용 시점
- "~기능 만들어줘/개발해줘/구현해줘" 같은 새 기능·변경 요청을 받았을 때

## 절차

### ① 코드베이스 파악
- `code-analyzer` 서브에이전트를 호출한다. 사용자 요구사항을 함께 전달한다.
- 결과: 관련 파일 지도, 프로젝트 관습, 변경 진입점, 주의점.

> 💡 **왜 먼저?** 어디를 어떻게 고칠지는 코드베이스의 기존 규칙에 달렸다. 파악 없이 짜면 프로젝트와 안 맞는 코드가 나온다.

### ② 개발 (테스트 → 구현, 2스텝)

TDD를 **"스펙 작성"과 "구현"으로 분리**해 순서대로 호출한다.

**②a. test-writer — 스펙(red 테스트)**
- `test-writer` 서브에이전트를 호출한다. **①의 지도 + 사용자 요구사항**을 전달한다.
- 요구 분석 → 수용 기준 도출 → 실패하는(red) 테스트 작성 → `testing.md` 커버리지 확인.
- 결과: 수용 기준, 작성한 테스트 파일, red 확인 결과, impl-writer에게 넘길 스펙 요약.

**②b. impl-writer — 구현(green)**
- `impl-writer` 서브에이전트를 호출한다. **②a의 red 테스트 + ①의 지도 + 요구사항**을 전달한다.
- red 테스트를 통과시키는 최소 구현 → green 확인. 구현은 `coding-style.md` 컨벤션을 따른다. **테스트 파일은 수정하지 않는다.**
- 결과: 통과시킨 테스트, 변경한 **구현** 파일, 테스트 결과(green).

> 💡 **backstop 검증**: impl-writer 실행 후 `git diff --name-only`로 **테스트 파일이 바뀌지 않았는지** 확인한다(Claude Code는 도구 권한으로 경로를 제한하지 못하므로, 규칙 위반을 스킬이 사후에 잡는다). 테스트가 바뀌었으면 규칙 위반이니 되돌리거나 사용자에게 보고한다.
>
> 💡 **impl-writer가 "테스트가 틀렸다"고 반려하면**, 직접 고치게 두지 말고 `test-writer`를 다시 호출해 재판단시킨다. 만든 주체와 고치는 주체를 섞지 않는다.

### ③ 검증 루프 (핵심)
아래를 **판정이 "통과"가 될 때까지, 최대 3회** 반복한다.

1. **관점 리뷰어 2개를 병렬로 호출한다.** `review-correctness`와 `review-tests`를 **한 메시지에서 동시에** 호출해야 실제로 병렬 실행된다. 둘 다 변경된 코드(git diff)를 각자의 렌즈로 리뷰한다.
   - `review-correctness`: 로직·경계·null·예외 (코드가 맞나)
   - `review-tests`: 수용 기준 검증·빠진 케이스·`testing.md` 커버리지·green 여부 (검증했나)
   두 리뷰어는 심각도·판정을 `.claude/guidelines/review-criteria.md`의 공통 기준으로 매긴다.
2. **두 판정을 취합하고, 지적을 알맞은 작성자에게 라우팅한다(스킬이 직접).**
   - **둘 다 "통과"** → 루프 종료, ④로 간다.
   - **하나라도 "수정필요"** → 지적을 **누가 고칠지 갈라서** 넘긴다:
     - **review-correctness 🔴 (로직 버그)** → `impl-writer`가 구현 수정.
     - **review-tests 🔴 (빠진/약한 테스트)** → `test-writer`가 테스트 보강(다시 red) → **뒤이어 `impl-writer`가 green**.
   - 수정 후 1번으로 돌아가 다시(2개 병렬) 리뷰.
3. 3회를 돌아도 둘 다 "통과"가 안 나오면, 남은 지적을 사용자에게 요약해 보고하고 어떻게 할지 묻는다. (무한 루프 금지)

> 💡 **왜 루프인가?** 한 번 고친다고 다 해결되지 않는다. "리뷰 → 수정 → 재리뷰"를 반복해야 품질이 수렴한다. 사람이 매번 개입하지 않아도 되도록, 반복 상한(3회)과 종료 조건(판정=통과)을 명확히 둔다.
>
> 💡 **왜 지적을 갈라 보내나?** writer가 둘(test/impl)이라, "코드가 틀렸다"는 impl-writer가, "테스트가 부족하다"는 test-writer가 고쳐야 각자의 책임 경계가 유지된다. 테스트를 보강하면 새 red가 생기므로 **반드시 impl-writer가 뒤이어 green**을 만든다.
>
> 💡 **취합 규칙은 단순하다.** 두 렌즈 중 🔴이 하나라도 있으면 수정필요, 둘 다 없으면 통과. 이 규칙이 코드처럼 단순해서 별도 취합 에이전트(synthesizer) 없이 스킬이 직접 판정한다.

### ④ 문서화
- 검증을 통과한 뒤 `doc-writer` 서브에이전트를 호출한다.
- 변경 내용을 프로젝트 스타일(`.claude/guidelines/doc-style.md`)에 맞춰 문서(README/사용법/CHANGELOG 등)로 남긴다.

### ⑤ 최종 보고
사용자에게 아래를 정리해 보고한다.
- 무엇을 만들었는지(요구사항 대비)
- 바뀐 파일과 테스트 결과
- 검증 루프 결과(몇 회 만에 통과했는지, 남은 🟡/🟢 있으면 언급)
- 문서화한 내용
- 커밋이 필요하면 `git-commit` 스킬을 안내한다.

## 오케스트레이션 팁
- **단계 사이는 순서대로**(①→②a→②b→③→④) 호출하고, 앞 단계 출력을 다음 단계 입력으로 명시적으로 넘긴다. 특히 ②a의 **red 테스트를 ②b impl-writer의 프롬프트에 담아** 넘겨야 한다(에이전트는 맥락을 공유하지 않음).
- **예외: ③단계의 두 리뷰어는 병렬이다.** `review-correctness`와 `review-tests`는 서로 의존이 없으므로 **한 메시지에서 동시에** 호출한다(순차로 부르면 병렬 이점이 사라진다).
- ③에서 재수정 시, 지적을 **작성자별로 갈라** 넘긴다(정확성→impl-writer / 테스트→test-writer→impl-writer). 두 리뷰어의 🔴을 뭉뚱그려 한 명에게 보내지 않는다.
- **impl-writer 실행 직후 `git diff --name-only`로 테스트 파일 미변경을 확인**한다(backstop). 위반이면 되돌린다.
- ①에서 요구사항이 너무 모호하면, 개발을 시작하기 전에 사용자에게 먼저 확인한다.

## 주의사항
- **검증 루프는 반드시 종료 조건이 있어야 한다.** 두 리뷰어 판정=통과 또는 3회 도달. 그 외에는 멈추지 않는다.
- 리뷰어가 "통과"를 줬는데 테스트가 실패 상태면, 그건 모순이니 다시 확인한다.
- 범위를 벗어난 큰 변경이 필요해지면 멈추고 사용자에게 알린다.
