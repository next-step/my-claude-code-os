# Refactor Loop — 동작을 고정하고 구조만 바꾸는 오케스트레이터

`feature-loop`가 **없던 동작을 만드는** 루프라면, 이 스킬은 **있는 동작을 그대로 둔 채 구조만 바꾸는** 루프다.
둘의 차이는 관문에 있다. `feature-loop`는 테스트가 늘어나야 통과하고, 여기는 **테스트가 한 줄도 바뀌지 않아야** 통과한다.

**대상 제품** — `projects/review-scheduler` (Spring Boot + JUnit). 빌드는 `projects/<제품>/app` 안에서 돈다.
대상 제품 디렉터리가 확인되지 않으면 ①에서 중단한다.

**메인은 코드를 고치지 않는다.** 그래서 `allowed-tools`에 `Write`·`Edit`이 없다.
`Grep`도 없다 — 코드를 뒤지는 것은 서브의 일이고, 메인이 뒤지기 시작하면 판정에 편향이 생긴다.
메인이 하는 일은 **지휘와 관문 실행** 둘뿐이다.

## 0. 이 스킬의 실패 모드

리팩토링을 못 하는 일은 거의 없다. 실패는 전부 **리팩토링이 아닌 것이 리팩토링이라는 이름으로 통과하는 것**이다.
셋 다 초록불 뒤에서 일어나기 때문에 조용하다.

| 사고 | 어떻게 일어나는가 | 방어 |
|---|---|---|
| **1. 동작이 바뀐다** | 구조를 고치다 동작을 바꾸고 나중에 발견한다. 구조 변경과 기능 변경이 한 커밋에 섞여 **어느 쪽이 깨뜨렸는지 모른다** | 기준선 초록불에서만 시작하고 **관문 A**로 판정. ③의 **회귀 관점**이 diff에서 동작이 달라질 지점을 찾는다. ④에서 두 종류 변경을 한 커밋에 섞지 않는다 |
| **2. 테스트를 고쳐 초록불을 만든다** | 리팩토링하다 테스트가 깨지자 테스트 쪽을 손본다. 그 순간 **동작 보존을 판정하던 유일한 장치가 사라진다** | **관문 B** — 테스트 파일이 한 줄이라도 바뀌면 FAIL. ②의 되돌림 규칙: 깨지면 되돌릴 것은 **방금 한 변경**이지 테스트가 아니다 |
| **3. 범위가 번져 끝이 안 난다** | 한 곳을 고치다 옆을 고치고, 그것이 또 옆을 부른다. **어디서 멈췄는지가 기록되지 않는다** | ①의 **범위 계약**(파일 단위 목록) + Developer의 **번짐 목록**(손대고 싶었으나 남긴 것을 손대지 않은 채 돌려준다) + ③의 **범위 관점** |
| 초록불이 아무것도 지키지 않는다 | 기준선이 이미 빨간불이었다. 뭘 해도 원래대로 빨갛다 | ①에서 기준선 초록불을 확인하지 못하면 **중단한다.** 빨간불에서 시작하는 것은 리팩토링이 아니라 버그 수정이다 |
| 리팩토링이 사양 변경으로 미끄러진다 | "이 테스트가 틀렸다"고 판단하고 테스트를 고친다 | 그 판단이 맞을 수 있다. 맞아도 **이 스킬의 일이 아니다.** 멈추고 사람에게 가져간다 |
| 추인 리뷰 | Reviewer에게 "이렇게 리팩토링했는데 봐줘"라고 준다 | Reviewer는 **diff와 관점 하나만** 받는다 |
| 리뷰 도중 대상이 바뀐다 | 리뷰어가 발견한 것을 그 자리에서 고친다 | 판정하러 간 서브는 **읽기만 한다.** 고칠 것은 지적으로 돌려주고 ②가 고친다 |

## 1. 지휘 규칙 — `OS.md` 4절을 그대로 적용한다

| # | 이 스킬에서의 의미 |
|---|---|
| 1 | **메인은 고치지 않고, 지적의 타당성도 판정하지 않는다.** 부르고, 관문을 돌리고, 넘긴다 |
| 2 | Reviewer에게 **왜 그렇게 고쳤는지 주지 않는다.** 주면 구현자의 가정을 물려받아 그 밖을 때리지 않는다 |
| 3 | **서브는 넘긴 것만 본다.** 이 대화도, `OS.md`·`README.md`·`loops/`도 스스로 읽게 두지 않는다 |
| 4 | 구간 사이는 **순차**. 같은 diff를 보는 세 관점은 **병렬** — 그래서 리뷰 중에 코드가 바뀌면 안 된다 |
| 5 | 관문 실패는 다음 구간으로 넘기지 않는다. 그 구간에서 멈추고 되돌린다 |
| 6 | 커밋은 사람이 방아쇠를 당긴다. 커밋·푸시는 `commit` 스킬에 넘긴다 |
| 7 | 서브의 "동작은 그대로입니다" 발언을 통과로 채택하지 않는다. **관문 A·B의 종료 코드와 출력**만 통과다 |

## 2. 흐름

```
사람 ──요구──▶ [메인: 지휘와 관문 실행만]
                   │
                   │ ① 범위 계약 (사람과 직접) ── 대상 제품이 없으면 중단
                   │    · 손댈 파일 목록 · 하지 않을 것 · 기준선 BASE
                   │    · 기준선 초록불 확인 ──FAIL──▶ 중단 (고칠 것이 먼저 있다)
                   │
                   ├─▶ ② Developer  `refactor-developer` ── 범위 계약만 받는다
                   │        │ 변경 목록 + 동작 보존 근거 + 번짐 목록
                   │        ▼
                   │     관문 A  ./gradlew test          ─┐
                   │     관문 B  테스트 파일 diff 비었나  ─┴─FAIL──▶ ②로 되돌림 (최대 3회)
                   │        │ 둘 다 PASS
                   │        ▼
                   ├─▶ ③ Reviewer  `refactor-reviewer` ×3 ── diff + 관점 하나만
                   │        │ 구조 · 회귀 · 범위
                   │        ▼
                   │     반영 여부는 사람이 결정 ── 고쳤으면 ②의 관문부터 다시
                   │        │
                   └─▶ ④ 사람이 커밋 버튼 ──▶ 번짐 목록 = 다음 루프의 입력
```

## 3. 단계

### ① 범위 계약 — 메인이 사람과 직접 한다 (서브 없음)

| 받을 것 | 없으면 |
|---|---|
| 대상 제품 (`projects/<제품>/app`) | **중단한다.** 관문이 돌 곳이 없다 |
| **손댈 파일 목록** — 클래스가 아니라 파일 단위로 | 범위가 없으면 사고 3을 막는 것이 아무것도 없다. 대상이 흐리면 후보를 보여주고 고르게 한다 |
| **하지 않을 것** — 이번에 건드리지 않기로 한 인접 영역 | 번짐 목록의 판정 기준이 사라진다 |
| 새 파일이 필요한 변경인가 (클래스 추출 등) | 아래를 본다 |

**작업 트리가 깨끗해야 시작한다.** 커밋되지 않은 변경이 남아 있으면 기준선이 잡히지 않고,
관문 B가 이번 루프의 변경과 남아 있던 변경을 구분하지 못한다.

```bash
git status --porcelain                       # 비어 있어야 한다
BASE=$(git rev-parse HEAD)                   # 기준선. 루프 내내 바꾸지 않는다
cd projects/<제품>/app && ./gradlew test     # 시작점이 초록불인가
```

**기준선이 빨간불이면 중단한다.** 통과하지 않는 테스트가 있는 상태에서는 관문 A가 무엇을 판정하는지 알 수 없다.

**새 파일이 필요하면 사람이 만든다.** `refactor-developer`에게는 `Write`가 없다 — 새 파일을 만드는 것은
리팩토링이 아니라 설계 결정이기 때문이다. 클래스 추출처럼 없던 파일이 필요한 경우, **빈 껍데기 파일은 사람이 만들고**
그 파일도 범위 계약 목록에 넣는다. 그 뒤 내용은 Developer가 채운다(원칙 2 — 구조 신설의 방아쇠는 사람).

### ② Developer — `refactor-developer` 1명

- 받는 것: 범위 계약(파일 목록 · 하지 않을 것), 사람이 말한 리팩토링 요구, 프로젝트 경로, `BASE`
- 받지 않는 것: 내가 짠 리팩토링 설계, "이 순서로 해라", 테스트를 고쳐도 된다는 여지

**작업 방식·되돌림 규칙·돌려줄 형식은 에이전트 파일이 들고 있다.** 프롬프트에 다시 적지 마라 —
두 곳에 있으면 어긋나고, 어긋나면 어느 쪽이 규격인지 알 수 없다.

**관문 — 둘을 함께 건다**

```bash
cd projects/<제품>/app && ./gradlew test               # 관문 A · 종료 코드 0
git diff --name-only $BASE -- ':(top)*/src/test/*'           # 관문 B · 출력이 비어 있어야 한다
```

**`:(top)` 을 빼지 마라.** git의 pathspec은 **명령을 실행한 위치 기준**이다. 관문 A의 `cd .../app` 뒤에
`app/` 안에서 그냥 `*/src/test/*` 로 돌리면 **아무것도 매치하지 않아 빈 출력 = PASS** 가 된다 —
테스트를 고쳐도 통과한다. `:(top)` 은 저장소 루트 기준으로 고정해 **어디서 돌리든 같은 답**을 내게 한다.

**관문 B가 없으면 관문 A는 아무것도 판정하지 못한다.** 깨진 테스트를 고치면 언제나 초록불이기 때문이다.
사고 1을 A가, 사고 2를 B가 잡는다. **사고 3은 기계가 잡지 못한다** — 그건 ①의 범위 계약과 ③의 범위 관점이 잡는다.

FAIL이면 출력을 그대로 ②에 되돌린다. **최대 3회.** 3회에도 통과하지 못하면 멈추고 사람에게 출력을 그대로 보여준다.
관문 B가 FAIL이면 **테스트 파일을 원상 복구하는 것부터** 시키고, 이것도 되돌림 1회로 센다.

기록은 한 줄로 남긴다. 종료 코드가 아닌 것을 통과로 채택하지 않는다.

```
기록: refactor <대상> · test PASS(0 failed) · test-diff CLEAN(0 files)
기록: refactor <대상> · test FAIL(3 failed) · test-diff DIRTY(2 files) → ②로 되돌림 1/3
```

**새 파일이 생기지 않았는지도 함께 본다.** `git diff --name-status $BASE`에 `A`(추가)나 `D`(삭제)가 있으면
①에서 사람이 승인한 파일인지 확인한다. 아니면 되돌린다.

### ③ Reviewer — `refactor-reviewer`를 관점 수만큼 병렬로

- 받는 것: diff, **관점 하나**, (범위 관점이면) 범위 계약, (회귀 관점이면) 손댄 파일과 맞닿은 기존 테스트 목록
- 받지 않는 것: **왜 그렇게 고쳤는지, Developer가 돌려준 동작 보존 근거**
- 관점마다 **다른 호출**이다. 같은 프롬프트 셋은 리뷰가 아니라 중복이다

| 관점 | 이 리뷰어가 찾는 것 |
|---|---|
| 구조 | 테스트는 통과하지만 **나아지지 않은** 지점. 중복이 사라진 것이 아니라 옮겨 간 곳, 사용처 하나를 위해 생긴 추상 |
| 회귀 | 관문이 통과했는데도 **동작이 달라질 수 있는** 지점. 기존 테스트가 덮지 않는 경계 |
| 범위 | 범위 계약 **밖의 변경**, 구조 변경에 섞여 들어온 **기능 변경** |

리뷰어에게는 쓰기·실행 도구가 없다(4절). 그래도 **리뷰 도중 코드가 바뀌지 않는 것은 메인이 지킨다** —
셋이 병렬로 도는데(규칙 4) 그사이 손을 대면 셋이 서로 다른 코드를 본다.
지적을 받아 ②에서 고쳤으면 **②의 관문 A·B부터 다시 돈다.**

지적이 많아 반영이 끝나지 않으면 **반박자를 떼어낼 신호**다(`OS.md` 2절). 지금은 반영 여부를 사람이 결정한다.

### ④ 커밋 — 사람이 방아쇠

- **구조 변경과 기능 변경을 한 커밋에 섞지 않는다.** 섞이면 사고 1이 나중에 터졌을 때 되돌릴 단위가 없다
- 커밋·푸시는 **이 스킬이 하지 않는다.** `commit` 스킬에 넘긴다
- **번짐 목록을 보고와 커밋 메시지 본문에 남긴다.** 어디서 멈췄는지가 남지 않으면 사고 3은 다음 루프에 그대로 다시 온다
- 관문 기록 한 줄도 함께 넘긴다

## 4. 서브에이전트 — 규격은 `.claude/agents/`에 있다

역할의 불변 규칙(**받지 않는 것 · 읽는 범위 · 쓰는 범위 · 돌려줄 형식**)은 **에이전트 파일이 가진다.**
메인이 매 루프 프롬프트에 옮겨 적지 않는다 — 옮겨 적어야 작동하는 것은 "안 불러도 실행되는 것"이 아니라
**내가 기억해야 실행되는 것**이고, 한 번 잊으면 그대로 사라진다(`OS.md` 원칙 4).

| 구간 | `subagent_type` | 도구로 잠긴 것 | 메인이 매 루프 넘기는 것 | 받아서 확인할 것 |
|---|---|---|---|---|
| ② | `refactor-developer` | **`Write` 없음** — 새 파일을 만들 수단이 없다 | 범위 계약, 리팩토링 요구, 프로젝트 경로, `BASE` | 변경 목록 + **동작 보존 근거** + **번짐 목록** |
| ③ | `refactor-reviewer` | 쓰기·실행 **없음** (읽기만) | diff, **관점 하나**, (범위면) 범위 계약, (회귀면) 기존 테스트 목록 | 지적 (없으면 "없음") |

**`Write`를 뺀 것이 이 표의 축이다.** `git diff`는 추적되지 않는 새 파일을 보지 못하므로,
Developer가 새 테스트 파일을 만들면 관문 B가 그것을 놓친다. 그 구멍을 명령을 늘려 막지 않고 **수단째로** 막았다.
`cat >`·`tee`·`cp`·`touch`로 Bash를 우회하는 것은 에이전트 파일이 문장으로 금지한다.

**읽기 쪽 절반은 아직 문장이 지킨다.** `tools:`는 경로를 구분하지 못한다 — `app/`을 읽어야 하는 둘은
`OS.md`·`README.md`·`loops/`도 읽을 수 있다. 그 경계는 에이전트 파일이 들고 있다.

### 메인이 여전히 손으로 지키는 것

| | 왜 파일로 못 옮기나 |
|---|---|
| **의도를 넘기지 않기** | Reviewer에게 "왜 이렇게 고쳤는지"를 프롬프트에 넣지 않는다. 에이전트 파일은 "왔으면 무시하라"까지만 할 수 있고, 애초에 안 넣는 것은 부르는 쪽의 일이다 |
| **관점 하나씩 나눠 주기** | `refactor-reviewer` 하나를 셋으로 띄우되 관점을 각각 다르게 준다. 같은 프롬프트 셋은 리뷰가 아니라 중복이다 |
| **기준선 고정** | `BASE`를 ①에서 찍고 루프 내내 바꾸지 않는다. 중간에 커밋하면 관문 B가 이미 섞인 변경을 보지 못한다 |
| **`description`(라벨)** | `Developer: …` · `Reviewer: …`로 시작하게 쓴다. `loop-view`가 이 접두사로 구간을 가르므로, 라벨이 어긋나면 그 왕복이 `기타`로 빠진다 |

## 5. 금지

- 메인이 코드를 직접 고치기 — 서브를 부른 의미가 사라진다
- **역할 서브를 `general-purpose`로 띄우기** — `tools:` 제한이 걸리지 않아 격리가 통째로 풀린다
- **역할 규칙을 프롬프트에 다시 적기** — 에이전트 파일과 어긋나면 어느 쪽이 규격인지 알 수 없다
- 서브가 저장소 문서를 자유롭게 읽게 두기 — 격리가 프롬프트를 우회해 파일로 새어 들어온다
- **테스트 파일을 고치기** — 한 줄도, 공백 하나도. 동작 보존을 판정하는 유일한 장치다
- **테스트가 틀렸다고 판단해 테스트를 고치기** — 판단이 맞아도 이 스킬의 일이 아니다. 멈추고 사람에게 간다
- **관문 B 없이 관문 A만 돌리고 통과라고 보고하기** — 깨진 테스트를 고치면 언제나 초록불이다
- **빨간불 기준선에서 시작하기** — 무엇이 통과했는지 알 수 없다
- 범위 계약에 없는 파일을 고치기, 고치고 나서 계약을 늘리기
- 기능 추가·버그 수정·성능 개선을 리팩토링에 섞기
- **Reviewer가 코드를 고치게 두기** — 판정 대상이 판정 도중에 바뀌고, 병렬 리뷰어가 서로 다른 코드를 본다
- Reviewer에게 구현 의도나 동작 보존 근거를 알려주기
- 관문 실패를 손으로 우회하기, 테스트를 `@Disabled`로 꺼서 통과시키기
- 사람 승인 없이 커밋하기, 이 스킬에서 커밋·푸시하기
- 번짐 목록을 남기지 않고 루프 완료라고 보고하기
- 구조 변경과 기능 변경을 한 커밋에 담기

## 6. 인자

| 인자 | 동작 |
|---|---|
| (없음) | ①~④ 전체 |
| 자유 텍스트 | 리팩토링 요구로 사용. ①에서 부족한 것만 되묻는다 |
| `--project <제품명>` | 대상 제품 (기본 `review-scheduler`). `projects/<제품명>` 을 가리킨다 |
| `--base <ref>` | 기준선 (기본 현재 `HEAD`). 관문 B의 비교 대상이다 |
| `--reviewers N` | 리뷰 관점 수 (기본 3 = 구조·회귀·범위). 줄이면 **어떤 관점을 뺐는지 밝힌다** |
| `--no-commit` | ④에서 커밋을 넘기지 않는다. 번짐 목록은 그대로 보고한다 |

## 출력 전 자기 점검

- [ ] 대상 제품 디렉터리와 `app/`을 확인했는가
- [ ] 시작 전 작업 트리가 깨끗했고, 기준선에서 `./gradlew test`가 **초록불**이었는가
- [ ] `BASE`를 ①에서 찍고 루프 내내 바꾸지 않았는가
- [ ] 범위 계약을 사람과 확정했는가 (손댈 대상이 **파일 단위**로 적혀 있는가)
- [ ] `./gradlew test`를 실제로 돌렸는가 (종료 코드를 봤는가, 말로 때우지 않았는가)
- [ ] `git diff --name-only $BASE -- ':(top)*/src/test/*'` 출력이 **비어 있는가** (한 줄이라도 있으면 통과가 아니다)
- [ ] 테스트가 깨졌을 때 되돌린 것이 **테스트가 아니라 방금 한 변경**이었는가
- [ ] `git diff --name-status $BASE`에 승인되지 않은 `A`나 `D`가 없는가
- [ ] 리뷰어마다 **관점을 하나씩 다르게** 주었는가 (같은 프롬프트 셋을 띄우지 않았는가)
- [ ] Reviewer에게 구현 의도나 동작 보존 근거를 주지 않았는가
- [ ] **모든 서브를 `.claude/agents/`의 역할 타입으로 띄웠는가** (`general-purpose`로 띄우면 도구 제한이 안 걸린다)
- [ ] 서브 라벨(`description`)이 `Developer:` · `Reviewer:` 로 시작하는가
- [ ] **리뷰 도중 코드가 바뀌지 않았는가** (바뀌었으면 ②의 관문부터 다시 돌았는가)
- [ ] **번짐 목록**(손대지 않고 남긴 것)을 보고에 남겼는가
- [ ] 구조 변경과 기능 변경을 한 커밋에 섞지 않았는가
- [ ] 커밋·푸시를 `commit` 스킬에 넘겼는가
