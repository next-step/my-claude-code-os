# 인수기준 — 커밋 전 테스트 초록불 확인 훅

## 요구사항 원문

> 커밋 전에 테스트가 초록불인지 확인하고 빨간불이면 되묻는 훅을 만들려고 해.

## 인수기준

AC-1. Given 커밋을 시도하는 시점에, When 훅이 실행되면, Then 훅은 먼저 테스트 스위트를 실행해 그 결과(통과/실패)를 확인해야 한다.

AC-2. Given 테스트 실행 결과가 초록불(전부 통과)이면, When 훅이 판정을 내리면, Then 커밋을 막지 않고 그대로 진행되어야 한다.

AC-3. Given 테스트 실행 결과가 빨간불(하나 이상 실패)이면, When 훅이 판정을 내리면, Then 커밋을 곧바로 차단하지 않고 사용자에게 계속 진행할지 되물어야 한다.

AC-4. Given 되묻는 질문에 사용자가 "그래도 커밋 진행"을 선택하면, When 훅이 그 응답을 받으면, Then 커밋이 진행되어야 한다.

AC-5. Given 되묻는 질문에 사용자가 "커밋 중단"을 선택하면, When 훅이 그 응답을 받으면, Then 커밋이 중단되고 실패한 테스트 내역이 함께 안내되어야 한다.

AC-6. Given 테스트 실행 자체가 오류로 끝나(예: 테스트 명령을 찾을 수 없음, 타임아웃) 통과/실패 판정이 불가능하면, When 훅이 이를 감지하면, Then 이를 "빨간불"과 구분되는 별도 상황으로 사용자에게 알리고 되물어야 한다.

AC-7. Given 훅이 사용자의 되묻는 응답을 기다리는 동안, When 응답이 오지 않거나 시간이 초과되면, Then 훅은 커밋을 임의로 자동 진행시키지 않아야 한다.

## 분해 근거

- AC-1~AC-2는 정상 경로(초록불이면 방해 없이 진행)를 담아, 훅이 평소에는 눈에 띄지 않아야 한다는 요구를 반영했다.
- AC-3~AC-5는 요구사항의 핵심인 "빨간불이면 되묻는다"를 판정(AC-3)과 그 이후 두 갈래 응답(진행/중단, AC-4~AC-5)으로 나눴다. 하나의 AC가 하나의 조건만 검증하도록 쪼갠 것이다. AC-5에 실패 내역 안내를 넣은 이유는, 중단만 시키고 왜 중단됐는지 알려주지 않으면 "되묻는 훅"이 아니라 그냥 "막는 훅"이 되기 때문이다.
- AC-6은 요구사항 원문에 없는 경계 상황이다. "빨간불"은 테스트가 실행되어 실패했다는 뜻이고, 테스트 자체가 돌지 않는 것은 다른 상황이라 별도로 분리했다.
- AC-7도 원문에 명시되지 않은 경계 상황이다. 되묻는 도중 응답이 없을 때 자동으로 커밋을 진행시키면 "되묻는다"는 목적이 무력화되므로, 안전 방향(자동 진행 금지)을 명시했다.
- AC-6, AC-7은 요구사항 원문에서 직접 확인되지 않는 확장이므로, 사람 승인(04단계) 시 이 두 항목이 실제로 필요한 범위인지 별도로 확인이 필요하다.

## 셀프 체크 (policy-reviewer 독립 리뷰)

판정: **PASS**

근거(policy-reviewer 응답 원문):
- 정상 경로(초록불 → 진행, AC-2)와 예외 경로(빨간불 → 되묻기, AC-3)를 모두 다룬다.
- 되묻기 이후 두 갈래 응답(진행/중단)을 각각 AC-4, AC-5로 검증 가능하게 명시했고, AC-5는 실패 내역 안내까지 포함해 요구사항의 "되묻는 훅"이라는 목적을 살렸다.
- 원문에 명시되지 않았지만 암묵적으로 따라오는 경계 상황(테스트 실행 자체의 오류 AC-6, 응답 무응답/타임아웃 AC-7)까지 포괄해 누락을 방지했다.
- 각 AC가 Given-When-Then으로 관측 가능한 형태이며 요구사항 범위(커밋 전 테스트 확인·되묻기)를 벗어나지 않는다.
