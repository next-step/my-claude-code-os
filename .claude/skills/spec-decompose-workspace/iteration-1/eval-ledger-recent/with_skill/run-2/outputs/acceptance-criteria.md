# 인수기준 — 실패 원장 최근 7일 조회 스킬

요구사항: "실패 원장에서 최근 7일치만 뽑아 보여주는 스킬이 필요해. 인수기준으로 나눠줘."

## 인수기준

AC-1. Given `.claude/atdd-failure-ledger.json` 파일이 존재하고 `entries`가 1개 이상이면, When 스킬을 실행하면, Then 각 entry의 `recordedAt`이 "실행 시점으로부터 7일 이내"인 것만 걸러서 보여줘야 한다.

AC-2. Given 파일이 없거나 `entries`가 비어 있으면, When 스킬을 실행하면, Then "아직 기록된 인수 테스트 실패가 없습니다" 안내를 보여주고 끝내야 한다.

AC-3. Given `entries`는 있지만 모두 recordedAt이 7일보다 오래됐으면, When 스킬을 실행하면, Then "최근 7일 이내 기록된 실패가 없습니다" 안내를 보여주고, 7일보다 오래된 항목은 하나도 노출하지 않아야 한다.

AC-4. Given recordedAt이 정확히 "지금-7일" 경계에 걸치는 entry가 있으면, When 필터링하면, Then 경계값(지금으로부터 7일 이내 = 포함)을 명시적으로 정의한 규칙대로 포함/제외가 일관되게 적용되어야 한다.

AC-5. Given 필터링된 entries가 여러 개면, When 보여주면, Then 각 entry를 시간순(오래된 것 → 최신)으로 정렬하고, 원장에 이미 기록된 정보(예: 시각·상태·결과 요약)를 사람이 알아볼 수 있는 형태로 노출해야 한다.

AC-6. Given 어떤 실행이든, When 스킬이 동작하면, Then `.claude/atdd-failure-ledger.json` 파일을 절대 수정하지 않고 읽기만 해야 한다.

## 분해 근거

- AC-2와 AC-3을 분리한 이유: "파일/entries 자체가 없음"과 "entries는 있지만 7일 필터 결과가 0건"은 원인이 다르고 사람에게 줄 안내 문구도 달라야 한다.
- AC-4를 별도 항목으로 둔 이유: "최근 7일"은 자연어로는 명확해 보이지만 경계(정확히 7일 전 항목의 포함 여부)를 코드로 옮기면 반드시 선택이 필요한 지점이라 명시했다.
- AC-6은 요구사항 문면에는 없지만 "뽑아 보여주는" 조회 스킬이라는 성격에서 나오는 암묵적 제약으로 포함했다(기존 `failure-ledger` 스킬도 동일 원칙 — 원장 수정은 훅의 몫).

## 셀프 체크 (policy-reviewer, 단독 호출이므로 실행)

- 1차 판정: **FAIL** — 반복 실패 강조·spec-decompose 회귀 권고·RESOLVED 초록불 보고(당시 AC-6~AC-8)는 "뽑아 보여준다"는 요구사항 범위를 넘어선 분석·권고 기능이며, 당시 AC-5의 표 컬럼 구성도 원장 스키마를 전제로 과도하게 구체적이라는 지적을 받음.
- 반영: 범위를 벗어난 3개 항목(반복 실패 분석, 3회 이상 회귀 권고, RESOLVED 요약 보고)을 제거하고, 표시 형식(AC-5)을 컬럼을 규정하지 않는 수준으로 완화함.
- 2차 판정: **PASS** — 정상 경로·빈 원장·기간 밖 전량·경계값·정렬 표시·읽기 전용 제약까지 요구사항의 핵심 동작과 예외/경계를 빠짐없이 다룬다고 판정됨.
- 리뷰어가 별도로 남긴 참고(FAIL 사유는 아님): 원장 JSON 파싱 실패, entry에 `recordedAt` 필드 자체가 없는 손상 데이터 케이스는 이번 인수기준에서 다루지 않음 — 요구사항 문면에 없는 암묵적 견고성 항목이라 범위 밖으로 남김.
