# Feature Loop — 기능 하나를 한 루프로 돌리는 오케스트레이터

`OS.md` 3절의 네 구간을 그대로 실행한다. 지휘 규칙은 4절에서 상속받는다.
`skill-forge`가 **스킬 만들기**를 지휘하듯, 이 스킬은 **기능 만들기**를 지휘한다.

**대상 제품** — `projects/review-scheduler` (학습 기록 + 복습 스케줄러, Spring Boot + JUnit).
OS는 `.claude/` 안에, 제품은 `projects/` 안에 있다. 경계와 디렉터리 규약은 `projects/README.md`에 있다.
대상 제품 디렉터리가 확인되지 않으면 ①에서 중단한다.

## 0. 이 스킬의 실패 모드

기능을 못 만드는 일은 거의 없다. 가장 흔한 실패는 **루프가 한 번 돌고 멈추는 것**이다.
리뷰까지 하고 배포를 안 하거나, 배포는 했는데 관측이 돌아오지 않으면 다음 루프의 입력이 없다.
그러면 이건 파이프라인이 아니라 일회성 작업이다(`OS.md` 3절).
다른 한 부류는 **관문이 통과시켰는데 아무것도 판정되지 않은 것**이다 — 이쪽은 초록불이라 훨씬 조용하다.

| 실패 | 어떻게 일어나는가 | 방어 |
|---|---|---|
| 루프가 닫히지 않는다 | 3구간까지 하고 배포를 미룬다. 관측 항목을 정하지 않았다 | ④를 통과하기 전까지 **루프 미완**으로 보고한다. 관측 항목은 ①에서 미리 정한다 |
| 기능이 커서 끝나지 않는다 | 한 루프에 수용 기준이 열 개 들어간다 | ①에서 기준이 **5개를 넘으면 쪼갠다.** 루프 단위는 기능 하나다 |
| 기준을 무르게 쓴다 | `criteria-lint.py`를 통과시키려고 숫자만 끼워 넣는다 | 채점기를 만족시키려 내용을 왜곡한 것이다. 사람 승인이 형식이 되면 **기준 검증자를 떼어낼 신호**(`OS.md` 2절) |
| 추인 리뷰 | Reviewer에게 "이렇게 구현했는데 봐줘"라고 준다 | Reviewer는 **diff와 수용 기준만** 받는다 |
| 통로가 절반만 선다 | 상태를 만드는 기능인데 그 상태를 되돌리거나 다시 보는 통로가 기준에 없다 | ②에서 **통로를 짝으로 센다.** 기준에 없으면 관문도 리뷰도 그것을 찾지 않는다 |
| 초록불이 아무것도 지키지 않는다 | 구현자가 쓴 테스트가 애초에 빨간불이 될 수 없다 | ③의 **빨간불 확인** — 구현을 일부러 깨서 그 테스트가 실제로 실패하는지 보고 되돌린다 |
| 리뷰 도중 대상이 바뀐다 | Reviewer가 발견한 것을 그 자리에서 고친다 | 판정하러 간 서브는 **읽기만 한다.** 고칠 것은 지적으로 돌려주고 ③이 고친다 |

## 1. 지휘 규칙 — `OS.md` 4절을 그대로 적용한다

| # | 이 스킬에서의 의미 |
|---|---|
| 1 | **메인은 구현하지 않고, 지적의 타당성도 판정하지 않는다.** 부르고, 받고, 넘긴다 |
| 2 | PM에게 **내 결론을 주지 않는다.** Reviewer에게 **구현 의도를 주지 않는다** |
| 3 | **서브는 넘긴 것만 본다.** 이 대화도, 저장소 문서도 스스로 읽게 두지 않는다 |
| 4 | 구간 사이는 **순차**. 같은 diff를 보는 리뷰 관점은 **병렬** — 그래서 리뷰 중에 diff가 바뀌면 안 된다 |
| 5 | 관문 실패는 다음 구간으로 넘기지 않는다. 그 구간에서 멈추고 되돌린다 |
| 6 | 배포는 사람이 방아쇠를 당긴다. 커밋·푸시는 `commit` 스킬에 넘긴다 |
| 7 | 서브의 "통과" 발언을 통과로 채택하지 않는다. **관문의 종료 코드**만 통과다 — 단 초록불은 그 테스트가 **빨간불이 될 수 있을 때만** 통과를 뜻한다(③) |

## 2. 흐름

```
사람 ──요구──▶ [메인: 지휘만]
                   │
                   │ ① 요구 수집 (사람과 직접) ── 대상 프로젝트가 없으면 중단
                   │
                   ├─▶ ② PM  `feature-pm` ── 내 결론 없이 받는다
                   │        │ 수용 기준 + 통로 표
                   │        ▼
                   │     criteria-lint.py ──FAIL──▶ ②로 되돌림 (최대 3회)
                   │        │ PASS
                   │        ▼
                   │     PM ⇄ Developer 문의  `feature-developer-advisor` ── 관문 아님
                   │        │ 개발 쪽이 사실만 답하고 PM이 기준을 고친다 · PM이 확정하면 끝
                   │        ▼
                   │     사람 승인 ("이게 필요한가"만 · 통로 표를 함께 본다)
                   │        │
                   │        ▼
                   ├─▶ ③ Developer  `feature-developer` ── 수용 기준만 받는다
                   │        │ 코드 + 테스트
                   │        ▼
                   │     ./gradlew test → 빨간불 확인 ──FAIL──▶ ③으로 되돌림 (최대 3회)
                   │        │ PASS
                   │        ▼
                   ├─▶ ④ Reviewer  `feature-reviewer` ×N ── diff + 관점 하나만 받는다
                   │        │ 지적 + 회귀 결과
                   │        ▼
                   │     회귀 없음 + 반영 여부는 사람이 결정
                   │        │
                   └─▶ ⑤ 사람이 배포 버튼 ──▶ 관측 항목 기록 (다음 루프의 입력)
```

## 3. 단계

### ① 요구 수집 — 메인이 사람과 직접 한다 (서브 없음)

| 받을 것 | 없으면 |
|---|---|
| 대상 제품 (`projects/<제품>`) | **중단한다.** 제품이 없으면 2·3구간 관문이 돌 곳이 없다 |
| 이 루프에서 만들 **기능 하나** | 여러 기능이면 하나를 고르게 한다. 루프 단위는 기능 하나다 |
| 배포 후 **무엇을 볼 것인가**(관측 항목) | 루프가 닫히지 않는다. ⑤에서 기록할 것을 여기서 정한다 |

기능이 여러 개로 들리면 그대로 진행하지 않고 **쪼갠 목록을 보여주고 하나를 고르게 한다.**

정해지면 루프 디렉터리를 만든다. 번호는 기존 디렉터리 수 + 1이다(`projects/README.md` 규약 1).

```bash
ls -1 projects/<제품>/loops                                          # 지금까지 몇 번째인가
cp -r projects/_loop-template projects/<제품>/loops/00N-<기능명>     # 템플릿 복사
```

### ② PM — `feature-pm` 1명

메인은 수용 기준을 쓰지 않는다. `feature-pm`을 띄우고 4절 표의 「넘기는 것」만 넘긴다 — ①의 기능 설명,
지난 루프의 관측(있으면), `criteria.md` 경로, 기존 도메인 코드의 **경로**(내용을 붙여넣지 않는다).
넘기지 않는 것: 내가 생각한 구현 방식, "이렇게 만들면 될 것 같다" 같은 결론.

기준의 **형식 요건 · 자동충족 판별 · 통로 표 · 5개 상한**은 에이전트 파일이 이미 들고 있다.
프롬프트에 다시 적지 마라 — 두 곳에 있으면 어긋나고, 어긋나면 어느 쪽이 규격인지 알 수 없다.

**관문**

```bash
python3 .claude/skills/feature-loop/criteria-lint.py projects/<제품>/loops/00N-<기능명>/criteria.md
```

종료 코드 0이 아니면 통과가 아니다. FAIL이면 `→ 고칠 것` 문장을 그대로 ②에 되돌린다.
**최대 3회**까지 돌리고, 3회에도 통과하지 못하면 멈추고 사람에게 출력을 그대로 보여준다.

**통로 표는 받아서 확인한다 — 쓰는 것은 PM이다**

**상태를 만드는 기능**(숨긴다·보관한다·잠근다·표시한다)은 그 상태를 **되돌리거나 다시 보는 통로**가 함께 있어야
완성된다. 빠진 절반은 **기준에 없으므로 관문도 리뷰도 그것을 찾지 않는다.**

표가 오지 않았으면 ②를 다시 부른다. **없음**이 이유 없이 남은 줄은 사람 승인 전에 PM에게 되돌린다 —
기준을 채우거나, 이번 루프 밖이라고 적게 한다. **빈 채로 승인을 구하지 않는다** —
리뷰까지 안 걸리면 배포 직전에 발견된다.

**PM ⇄ Developer 문의 — 관문이 아니다**

`criteria-lint.py`는 문장의 꼴만 본다. **기술적으로 무의미한 기준**은 형식이 멀쩡해도 통과한다.
그래서 통과한 기준을 개발 쪽에 물어본다. 아래 다섯 가지만 답하게 한다.

**이것은 관문이 아니라 협의다.** 통과·실패도, 되돌림 횟수도 없다. 개발 쪽이 사실을 답하고 **PM이 기준을 고친다.**
리뷰어와 같은 자리다 — 지적을 낼 뿐 통과를 정하지 않으므로 `OS.md` 6절의 채점기 요건을 들이대지 않는다.
네 번 오가도 고장이 아니라 설계 논의다. 좁혀지지 않으면 사람에게 가져간다.

| 물을 것 | 예 |
|---|---|
| **자동 충족**되는가 | "응답 시간 2초 이하" — 서버가 떠 있으면 항상 참이라 아무것도 막지 못한다 |
| **검증 불가능**한가 | 테스트로 옮길 수 없거나, 옮기면 flaky해지는가 |
| **서로 모순**인가 | 두 기준이 동시에 참일 수 없는가 |
| **이미 있는 것의 반복**인가 | 앞 루프에서 이미 통과한 동작을 다시 세우는가 |
| **통로가 정말 없는가** | 표에서 **없음**으로 적힌 통로가 코드에 이미 있지는 않은가 |

「자동 충족」의 정의와 판별 방식, 근거에 코드 경로를 적게 하는 규칙은 **에이전트 파일이 들고 있다.**
메인은 다시 설명하지 않고 위 다섯 가지만 물어 온다.

**개발 쪽은 판정하지 않고, 메인도 중계만 한다.** 받은 사실을 그대로 PM에게 넘기고 어느 기준이 남아야 하는지는
말하지 않는다. 구현자가 기준을 지울 수 있으면 **어려운 기준을 기술적으로 무의미하다고 회피할 유인**이 생긴다.
기준의 주인은 계속 PM이다.

**자문은 구현과 다른 호출로, 구현 전에만 한다.** `feature-developer-advisor`와 `feature-developer`는
파일이 나뉘어 있지만 **한 호출에 이어 붙이면 같은 사고**다 — "내가 무의미하다고 한 기준"이라는 편향이
구현에 남는다(규칙 3의 연장).

**사람 승인 — 여기가 두 번째 관문이다**

형식 관문을 통과하고 문의가 끝난 뒤에 받는다. 사람은 **"이 기준이 필요한가"** 만 본다 —
형식은 스크립트가, 기술적 사실은 문의가 앞에서 처리했다. **통로 표를 기준 목록과 함께 보여준다.**
기준이 **5개를 넘으면** 승인을 구하기 전에 쪼갤 것을 제안한다.

### ③ Developer — `feature-developer` 1명

- 받는 것: 승인된 수용 기준, 대상 프로젝트 경로
- 받지 않는 것: 구현 방법 지시, 내가 짠 설계 초안, **자문 때 오간 말**

**관문**

```bash
cd projects/<제품>/app && ./gradlew test
```

종료 코드 0이 아니면 통과가 아니다.
FAIL이면 실패한 테스트 출력을 그대로 ③에 되돌린다. **최대 3회.**

**초록불만으로는 통과가 아니다 — 빨간불 확인 표를 받는다**

**실패할 수 없는 테스트**는 언제나 초록불이고, **관문은 이것을 잡지 못한다.** 그래서 Developer가
새 테스트마다 구현부를 일부러 깨보고 `테스트 | 무엇을 깼나 | 빨개졌나` 표로 돌려준다(방법은 에이전트 파일에 있다).

**이 표가 없으면 ③은 통과가 아니다.** 빨개지지 않은 테스트는 **통과로 세지 않고** ③을 다시 돌린다(3회 한도에 포함).
깬 것을 되돌린 뒤 `./gradlew test`가 다시 초록불인 것까지 확인하고 ④로 넘긴다.

### ④ Reviewer — `feature-reviewer`를 관점 수만큼 병렬로

- 받는 것: diff, **관점 하나**, (기준 대조면) 수용 기준, (회귀면) 기존 테스트 목록
- 받지 않는 것: **구현 의도 설명, 구현자가 왜 그렇게 했는지**
- 관점마다 **다른 호출**이다. 같은 프롬프트 셋은 리뷰가 아니라 중복이다

| 관점 | 이 리뷰어가 찾는 것 |
|---|---|
| 기준 대조 | 수용 기준 중 코드로 **덮이지 않은 것** |
| 구조 | 테스트는 통과하지만 **이렇게 만들면 안 되는** 지점 |
| 회귀 | 이 변경으로 **깨질 수 있는 기존 동작** |

리뷰어에게는 **쓰기 도구가 없다**(4절). 그래도 **리뷰 도중 코드가 바뀌지 않는 것은 메인이 지킨다** —
관점 셋은 병렬로 도는데(규칙 4) 그사이 메인이나 다른 서브가 손을 대면 셋이 서로 다른 코드를 본다.
지적을 받아 ③에서 고쳤으면 **③의 관문(빨간불 확인 포함)부터 다시 돈다.**

지적이 많아 반영이 끝나지 않으면 **반박자를 떼어낼 신호**다(`OS.md` 2절). 지금은 반영 여부를 사람이 결정한다.

### ⑤ 배포 — 사람이 방아쇠

- 배포 전에 되돌릴 수 있는지 확인한다
- 커밋·푸시는 **이 스킬이 하지 않는다.** `commit` 스킬에 넘긴다
- ①에서 정한 **관측 항목을 `loops/00N-<기능명>/observation.md`에 기록한다.** 이것이 다음 루프 ②의 입력이다
- 이 제품을 만들며 `OS.md`가 바뀌었으면 제품 README의 **「OS로 되먹인 것」** 에 한 줄 남긴다(바깥 루프)

`observation.md`가 비어 있으면 루프가 닫히지 않는다. 이 단계를 건너뛰고 완료라고 보고하지 않는다.

## 4. 서브에이전트 — 규격은 `.claude/agents/`에 있다

역할의 불변 규칙(**받지 않는 것 · 읽는 범위 · 쓰는 범위 · 돌려줄 형식**)은 **에이전트 파일이 가진다.**
메인이 매 루프 프롬프트에 옮겨 적지 않는다 — 옮겨 적어야 작동하는 것은 "안 불러도 실행되는 것"이 아니라
**내가 기억해야 실행되는 것**이고, 한 번 잊으면 그대로 사라진다(`OS.md` 원칙 4).

| 구간 | `subagent_type` | 도구로 잠긴 것 | 메인이 매 루프 넘기는 것 | 받아서 확인할 것 |
|---|---|---|---|---|
| ② | `feature-pm` | 읽기 **없음** · 쓰기는 `criteria.md`뿐 | 기능 설명, 지난 루프의 관측, `criteria.md` 경로 | 수용 기준 + **통로 표** |
| ② | `feature-developer-advisor` | 쓰기·실행 **없음** (읽기만) | 기준 문장 목록, 통로 표, 제품 한 줄, 스택, `app/` 경로 | 다섯 물음의 **사실과 근거** |
| ③ | `feature-developer` | — (쓰기·실행이 일이다) | 승인된 수용 기준, 프로젝트 경로 | 코드 + 테스트 + **빨간불 확인 표** |
| ④ | `feature-reviewer` | 쓰기·실행 **없음** (읽기만) | diff, **관점 하나**, (기준 대조면) 수용 기준, (회귀면) 기존 테스트 목록 | 지적 (없으면 "없음") |

**「도구로 잠긴 것」이 이 표의 축이다.** 예전에는 `저장소의 다른 파일을 읽지 마라` · `코드를 고치지 마라`
두 줄을 메인이 프롬프트마다 손으로 넣었다. 지금은 `tools:` 프론트매터가 그중 **쓰기 쪽을 수단째로** 막는다 —
Reviewer와 자문 Developer에게는 쓰기 도구가 없고, PM에게는 읽기 도구가 없다.
잊어서 새는 일이 없어지고, 새는지 보려고 로그를 뒤질 일도 없어진다.

**읽기 쪽 절반은 아직 문장이 지킨다.** `tools:`는 **경로를 구분하지 못한다** — `app/`을 읽어야 하는 셋은
`OS.md`·`README.md`·`loops/`도 읽을 수 있다. 그 경계는 에이전트 파일이 문장으로 들고 있고,
지켜졌는지는 `log-agent-handoff.sh`가 **관측만** 한다(막지 않는다). 여기가 다음에 조일 자리다.

### 메인이 여전히 손으로 지키는 것 — 파일이 대신해 줄 수 없다

| | 왜 파일로 못 옮기나 |
|---|---|
| **결론을 넘기지 않기** | PM에게 구현 방식을, Reviewer에게 구현 의도를 프롬프트에 넣지 않는다. 에이전트 파일은 "왔으면 무시하라"까지만 할 수 있고, 애초에 안 넣는 것은 부르는 쪽의 일이다 |
| **자문과 구현을 다른 호출로** | 파일이 나뉘어 있어도 **한 호출에 이어 붙이면 같은 사고**다. 자문 때의 판단이 구현에 편향으로 남는다 |
| **관점 하나씩 나눠 주기** | `feature-reviewer` 하나를 셋으로 띄우되 관점을 각각 다르게 준다. 같은 프롬프트 셋은 리뷰가 아니라 중복이다 |
| **`description`(라벨)** | `PM: …` · `Developer 자문: …` · `Developer: …` · `Reviewer: …`로 시작하게 쓴다. `loop-view`가 이 접두사로 구간을 가르므로, 라벨이 어긋나면 그 왕복이 `기타`로 빠진다 |

쪼개면 이 표에 행이 늘어난다 — `기준 검증자`·`반박자`·`QA`는 `OS.md` 2절의 신호가 발동할 때
각자 에이전트 파일을 얻는다. **어느 것도 미리 만들지 않는다.**

## 5. 금지

- 메인이 수용 기준이나 코드를 직접 쓰기 — 서브를 부른 의미가 사라진다
- **역할 서브를 `general-purpose`로 띄우기** — `tools:` 제한이 걸리지 않아 격리가 통째로 풀린다
- **역할 규칙을 프롬프트에 다시 적기** — 에이전트 파일과 어긋나면 어느 쪽이 규격인지 알 수 없다
- 서브가 저장소 문서를 자유롭게 읽게 두기 — 격리가 프롬프트를 우회해 파일로 새어 들어온다
- **Reviewer나 자문 Developer가 코드를 고치게 두기** — 판정 대상이 판정 도중에 바뀌고, 병렬 리뷰어가 서로 다른 코드를 본다
- PM에게 구현 방식을 알려주기, Reviewer에게 구현 의도를 알려주기
- 자문 Developer에게 "이 기준을 뺄까요"를 묻기 — 구현자가 자기 일을 줄이게 된다
- 자문과 구현을 같은 컨텍스트에서 시키기 — 자문 때의 판단이 구현에 편향으로 남는다
- 관문 실패를 손으로 우회하기, 검사 항목을 지워서 통과시키기
- `./gradlew test`를 돌리지 않고 통과라고 보고하기
- **빨간불 확인 없이 초록불을 통과로 채택하기** — 실패할 수 없는 테스트는 아무것도 지키지 않는다
- **통로 표에 「없음」을 남겨둔 채 승인을 구하기** — 채우거나, 이번 루프 밖이라고 적는다
- 사람 승인 없이 배포하기, 이 스킬에서 커밋·푸시하기
- 관측 항목을 기록하지 않고 루프 완료라고 보고하기
- 한 루프에 기능 여러 개를 담기

## 6. 인자

| 인자 | 동작 |
|---|---|
| (없음) | ①~⑤ 전체 |
| 자유 텍스트 | 만들 기능의 요구로 사용. ①에서 부족한 것만 되묻는다 |
| `--project <제품명>` | 대상 제품 (기본 `review-scheduler`). `projects/<제품명>` 을 가리킨다 |
| `--criteria-only` | ②까지만. 수용 기준과 관문 결과만 보고 |
| `--no-deploy` | ⑤의 배포를 하지 않는다. 관측 항목은 그대로 기록한다 |
| `--reviewers N` | 리뷰 관점 수 (기본 3). 줄이면 어떤 관점을 뺐는지 밝힌다 |

## 출력 전 자기 점검

- [ ] 대상 제품 디렉터리를 확인했는가 (`projects/<제품>/app` 이 있는가)
- [ ] 수용 기준을 `criteria-lint.py`에 실제로 걸었는가 (통과했다고 말만 하지 않았는가)
- [ ] 기준이 5개 이하인가 (한 루프에 담기는 크기인가)
- [ ] **통로 표에 「없음」이 남아 있지 않은가** (상태를 만드는 기준마다 되돌리거나 다시 보는 통로가 있는가)
- [ ] **PM ⇄ Developer 문의를 거쳤는가** (별도 컨텍스트로, 판정이 아니라 사실만 받고 통과·실패를 세지 않았는가)
- [ ] PM에게 구현 방식을, Reviewer에게 구현 의도를 주지 않았는가
- [ ] 리뷰어마다 **관점을 하나씩 다르게** 주었는가 (같은 프롬프트 셋을 띄우지 않았는가)
- [ ] 서브 라벨(`description`)이 `PM:` · `Developer 자문:` · `Developer:` · `Reviewer:` 로 시작하는가 (`loop-view`가 이것으로 구간을 가른다)
- [ ] **모든 서브를 `.claude/agents/`의 역할 타입으로 띄웠는가** (`general-purpose`로 띄우면 도구 제한이 안 걸린다)
- [ ] `./gradlew test`를 실제로 돌렸는가 — 그리고 **새 테스트마다 빨간불 확인을 하고 되돌렸는가**
- [ ] **리뷰 도중 코드가 바뀌지 않았는가** (바뀌었으면 ③의 관문부터 다시 돌았는가)
- [ ] 관문 실패를 우회하거나 검사를 지우지 않았는가
- [ ] 배포 전에 사람 승인을 받았는가
- [ ] 이번 루프의 관측을 `observation.md`에 기록했는가
- [ ] 커밋·푸시를 `commit` 스킬에 넘겼는가
