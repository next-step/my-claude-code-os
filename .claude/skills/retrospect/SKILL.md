# Retrospect — 사이클 회고와 OS 반영

## Overview

실험 사이클에서 배운 것을 다음 사이클의 입력으로 바꾼다. **에이전트 없음 —
메인이 직접 한다.** 회고의 재료는 대화 맥락 자체이므로 분리하면 오히려 손해다.

## 절차

| # | 담당 | 단계 |
|---|------|------|
| 1 | 🟢 메인 | **재료 수집** — 이번 사이클의 대화 맥락 + 최신 실험 기록의 "배운 것"·측정자/적용자 특이사항을 훑는다 |
| 2 | 🟢 메인 | **교훈 분류** — 아래 2계층으로 나눈다 |
| 3 | 🟢 메인 | **갱신안 제시** — 계층별 반영안을 diff 수준으로 구체화해 제시 |
| 4 | 🔵 사람 | **확인** — 반영할 항목을 사람이 고른다 |
| 5 | 🟢 메인 | **반영** — 승인된 것만 적용. 통증 목록은 `private/notes/os-pains.md`에 append |

## 교훈 2계층

| 계층 | 예 | 반영처 |
|---|---|---|
| **대상 수준** — 색상 추출 도메인의 교훈 | 판정 기준의 허점, 측정 셋에 없는 실패 유형, 검증된/기각된 기법 | `metrics.md` 갱신안, `knowledge/` 갱신 제안(갱신 자체는 /research·curator 경로 권장), 다음 실험 후보 보강 |
| **하니스/OS 수준** — 체계 자체의 통증 | 스킬 절차의 마찰, 에이전트 반환 계약 위반 사례, 반복된 수동 작업 | `private/notes/os-pains.md`에 통증 항목 적재 (해결은 /os 몫 — 여기서 고치지 않는다) |

## 불변 규칙

1. **사용자 확인 전 SSOT(metrics.md·knowledge/·OS.md) 수정 금지** — 3단계는
   제안까지다.
2. **metrics.md의 기존 케이스·판정 기준을 삭제하지 않는다** — 회귀 감지 보존.
   기준 변경은 추가·버전 업 방식으로.
3. **통증 적재와 통증 해결을 섞지 않는다** — 이 스킬은 적재까지. OS 파일 수정은
   `/os` 경로로만.
4. 통증 항목 형식: `- [ ] YYYY-MM-DD <통증 한 줄> (출처: 실험 NNNN / 세션)` —
   해결되면 체크하고 해결 커밋·ADR을 링크.

## Common Mistakes

| 실수 | 해결 |
|---|---|
| 회고를 서브에이전트에 위임 | 대화 맥락이 재료 — 메인이 직접 |
| 제안과 동시에 metrics.md를 고쳐버림 | 4단계 확인 후에만 반영 |
| 통증을 발견한 김에 스킬 파일까지 수정 | 적재만 하고 수정은 /os로 |
| 도메인 교훈을 knowledge/에 직접 작성 | knowledge 작성은 curator 경로 — 여기선 "갱신 제안"으로 남긴다 |
