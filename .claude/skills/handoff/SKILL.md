# handoff — 배포 노트 & 담당자 통보문

대상 REQ-ID 는 스킬 호출 시 인자로 전달된다 (예: `/handoff REQ-001`). 이하 `<REQ-ID>` 로 표기.

## 0. 선행 조건

- `maintenance/requests/<REQ-ID>.md` 를 읽는다.
- `status` 가 `done` 이어야 한다. 아니면 중단하고 `/verify <REQ-ID>` 를 먼저 하라고 안내한다.

## 1. 배포 노트 작성 → 케이스 파일 "8. 배포·핸드오프"

- **바뀐 것**: 요청 대비 무엇이 어떻게 달라졌나 (사용자가 체감하는 표현으로).
- **변경 파일 / 커밋**: "5. 구현 로그" 와 git 로그 기준.
- **확인 방법**: 담당자가 직접 눈으로 확인하는 절차 ("6. 검증 결과" 를 사용자용으로 바꿔 서술).
- **적용 범위 / 주의**: 영향받는 화면·기능, 배포 시 주의점.
- **롤백**: 문제 시 되돌리는 법 ("4. 스펙" 의 롤백 항목 기준).

## 2. 담당자 통보문 초안

받는 사람이 개발 맥락을 몰라도 이해되게, 짧게:

```
[유지보수 완료] <요청 제목>

요청하신 <한 줄> 건이 반영되었습니다.
- 무엇이 바뀌나: ...
- 확인 방법: ...
- 반영 시점: ...
이상이 있으면 회신 부탁드립니다.
```

## 3. 상태 갱신

- frontmatter `status: handed_off`, `updated` 오늘로 갱신
- `변경 이력` 에 `<오늘> 핸드오프 (handed_off)` 추가

## 4. 보고

배포 노트와 통보문 초안을 보여주고, 내부 용어·미확정 값(`(확인 필요)`)을 짚어 준다.
실제 발송 전 사용자가 검토·보완하도록 안내한다.

## 하지 말 것

1. 검증(`/verify`)을 통과하지 않은 요청에 핸드오프하지 않는다.
2. 통보문에 내부 시크릿(키, 내부 URL, 개인정보)을 넣지 않는다.
3. 코드를 수정하지 않는다 — 이미 완료된 요청의 문서화·전달 단계다.
