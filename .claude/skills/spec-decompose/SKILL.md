# 요구사항 → 인수기준 분해 (spec-decompose)

자연어 요구사항 한 개를 받아, 검증 가능한 인수기준(acceptance criteria) 목록으로 쪼개는 스킬입니다. ATDD 파이프라인의 02단계("정책으로 분해 후 멈춤")를 담당하며, `atdd-orchestrator` 스킬이 이 스킬을 호출해 위임하는 경우가 많습니다.

## 언제 쓰는가

사용자가 직접 "요구사항을 인수기준으로 나눠줘", "인수 조건 뽑아줘" 등을 요청하거나, `atdd-orchestrator`가 02단계를 위임할 때 사용한다.
**이 스킬은 인수기준 목록을 제시하고 멈추는 것까지만 한다. 인수기준이 요구사항을 충분히 커버하는지 판정하지 않고(그건 03단계의 몫), 테스트/구현 코드도 작성하지 않는다(05~06단계의 몫).**

## 실행 절차

1. **요구사항 확인**
   - 입력 요구사항을 읽는다. 모호하면 무엇이 불명확한지 짚고, 합리적 가정을 명시한 뒤 진행한다(가정은 결과에 함께 적는다).
   - UI 스펙 문서(`ui-spec.md`, `ui-spec-from-image`의 산출물)가 함께 주어졌는지 확인한다.

2. **인수기준으로 분해**
   - 독립적으로 검증 가능한 단위로 쪼갠다. 하나의 인수기준은 하나의 조건만 검증한다.
   - 가능하면 `Given <상황>, When <행동>, Then <기대 결과>` 형태로, 자연스럽지 않으면 "~해야 한다" 평서문도 허용.
   - `AC-1`, `AC-2`... 형태로 번호를 매긴다.
   - **UI 스펙 문서가 있는 경우**: 레이아웃/컴포넌트 존재/텍스트 콘텐츠/색상 등 이미지에서 검증 가능한 조건도 같은 번호 체계 안에서 뽑되, `[UI]` 태그를 붙여 구분한다(예: `AC-5. [UI] Given 설정 화면을 열면, Then 헤더에 "설정" 텍스트가 노출되어야 한다`). 별도 번호 체계(`AC-U1` 등)를 새로 만들지 않는다 — `acceptance-test-write`의 `AC-<번호>:` 네이밍 규칙과 `atdd-failure-log.js` 훅이 이미 이 패턴만으로 동작하므로 호환성을 그대로 유지하기 위함이다.
   - UI AC는 이미지에서 실제로 확인 가능한 근거만 사용한다. 이미지에 없는 내용을 상상해서 AC로 만들지 않는다.

3. **분해 근거 설명**
   - 각 인수기준을 왜 그렇게 나눴는지, 특히 경계/예외 상황을 어떻게 반영했는지 한두 문장으로 설명한다.

4. **셀프 체크 (사람이 직접 호출한 경우에만 → `policy-reviewer` 서브에이전트)**
   - `atdd-orchestrator`가 위임한 경우에는 **건너뛴다** — 지휘자가 03단계에서 어차피 같은 리뷰를 돌리므로 중복이다.
   - 사람이 이 스킬만 단독으로 부른 경우에는, 분해 결과를 그대로 내보내기 전에 `Agent` 도구로 `policy-reviewer`를 호출해 한 번 검증받는다.
   - **전달하는 것**: 요구사항 원문 + 인수기준 목록. **전달하지 않는 것**: 3단계에서 쓴 분해 근거. 분해한 쪽의 논리를 같이 주면 리뷰어가 거기에 끌려가 독립 리뷰가 성립하지 않는다.
   - FAIL이면 지적사항을 반영해 2단계로 돌아간다.

5. **멈춤**
   - 목록(과 셀프 체크 결과)을 제시한 뒤 구현/테스트 작성으로 넘어가지 않고 멈춘다. 호출한 쪽(사람 또는 `atdd-orchestrator`)이 다음을 결정하게 넘긴다.

## 참고

- 이 스킬의 출력(요구사항 원문 + 인수기준 목록)이 03단계 독립 리뷰에 그대로 전달될 수 있으므로, 목록과 "왜 이렇게 나눴는지" 설명은 구분해서 제시한다.
- `policy-reviewer`는 `atdd-orchestrator`(03단계)와 **공유하는 서브에이전트**다. 지휘자를 거치든 이 스킬을 단독으로 쓰든 동일한 판정 기준이 적용되게 하려고 같은 에이전트를 재사용한다.
- UI AC는 `policy-reviewer`가 UI 스펙 문서가 아니라 **원본 이미지 자체**와 대조해 판정할 것이므로, 이미지에서 확인 가능한 근거만 AC로 만든다(상상으로 채우지 않는다).

## 예시

```
요구사항: "사용자가 비밀번호를 잊었을 때 이메일로 재설정 링크를 받을 수 있어야 한다."

인수기준:
AC-1. Given 가입된 이메일 주소를 입력하면, When "비밀번호 재설정"을 요청하면, Then 해당 이메일로 재설정 링크가 발송되어야 한다.
AC-2. Given 가입되지 않은 이메일 주소를 입력하면, When 재설정을 요청하면, Then 시스템은 이메일 존재 여부를 노출하지 않는 일반 안내 메시지를 보여줘야 한다.
AC-3. Given 재설정 링크를 받았으면, When 유효 시간(예: 30분)이 지난 뒤 접속하면, Then 링크 만료 안내와 재요청 유도를 해야 한다.

→ AC-2, AC-3은 정상 경로만으로는 드러나지 않는 보안/예외 케이스라서 별도 항목으로 분리했습니다.
```
