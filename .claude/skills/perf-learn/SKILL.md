# perf-learn · 교훈 추출과 축적

성능 개선 OS의 **마지막 스킬**. Stage 6과 게이트 ④를 담당한다.

## 핵심 원칙

**OS는 쓸수록 똑똑해져야 한다.**

이 스킬이 없으면 이 체계는 그냥 잘 만든 체크리스트다. 매 사이클의 교훈이 축적되고 다음 사이클의 Lane B에 자동 투입되어야, 5번째 개선이 앞선 4번을 이미 알고 시작한다. **이 피드백 루프가 "도구"와 "OS"를 가른다.**

그리고 그 반대편에 함정이 있다. 케이스마다 파일을 하나씩 추가하면 1년 뒤 50개가 되고, 그 시점에 전부 읽을 수 없으니 **결국 아무것도 읽지 않게 된다.** 그래서 저장 규칙이 추가가 아니라 **병합**이다.

# 0. 입력

## `trace_id`가 주어진 경우

```bash
ls .claude/perf-os/cycles/<trace_id>/
```

**`50-verify.md`가 없으면 진행하지 않는다.**

```
❌ 검증이 끝나지 않은 사이클입니다.
   먼저 /perf-fix <trace_id> 로 개선·검증을 마치세요.
```

검증 전 교훈은 "무엇이 통했는지 모르는 채 쓴 교훈"이다. 그것이 축적되면 다음 사이클을 오염시킨다.

## `trace_id`가 없는 경우 — 미처리 사이클 목록

```bash
ls -d .claude/perf-os/cycles/*/ 2>/dev/null
```

각 디렉터리에서 `50-verify.md`는 있고 `60-lesson.md`는 없는 것이 **미처리 사이클**이다. 목록을 제시하고 고르게 한다.

```
교훈을 뽑을 사이클을 고르세요.

  [1] 6a8ed7d5  대시보드 N+1        검증 완료 2026-08-30
  [2] 91f0c22a  첨부 목록 풀스캔     검증 완료 2026-08-28

번호를 고르세요.
```

미처리가 없으면 그렇다고 말하고 끝낸다.

# 1. Stage 6 · 교훈 추출

| 항목 | 내용 |
|---|---|
| **입력** | 이번 사이클 전체 기록 (**실패 이력 포함**) |
| **산출** | 베스트 프랙티스 초안 → `60-lesson.md` |

## 1-1. 실패 이력이 1급 재료다

```bash
cat .claude/perf-os/cycles/<trace_id>/attempts.json
```

**"왜 처음에 틀리게 진단했는가"는 성공 사례보다 값지다.** 성공은 상황이 달라지면 재현하기 어렵지만, 실패의 원인은 다음번에 곧바로 피할 수 있다.

| `attempts.json`에서 뽑을 것 | 교훈의 어느 절이 되는가 |
|---|---|
| `outcome: "refuted"` 가설과 `reason` | **틀리기 쉬운 지점** |
| `outcome: "regression"` 구현과 `detail` | 해결 방식의 "이 방법은 피하라" |
| 배열 길이 | 이 증상이 얼마나 까다로웠는지의 지표 |

`attempts.json`에 실패가 하나도 없다면 그것도 정보다 — 한 번에 맞힌 증상은 체크리스트로 만들기 좋다.

## 1-2. 초안에 담을 것

읽을 파일: `10-baseline.md`(증상), `20-hypotheses.md`(가설과 반증), `40-test.md`(재현 방법), `50-verify.md`(측정), `attempts.json`(실패 이력).

```markdown
# 교훈 초안 — <trace_id>

## 증상
- 스팬 트리 모양 / 어떤 지표로 드러났는가
- **다음에 이 모양을 보면 이 패턴을 의심하라**에 쓸 수 있게 적는다

## 원인
## 해결 방식
- 무엇을 내주고 얻었는가 (게이트 ③의 잔여 리스크)

## 재현 방법
- 어떤 규모로 시딩했고 어떤 단정을 썼는가
- 다음에 같은 패턴을 만나면 그대로 베낄 수 있게

## 이번에 틀렸던 가설과, 왜 틀렸는지
| 가설 | 반증 근거 | 왜 그렇게 생각했는가 |
|---|---|---|

## 다음에 같은 증상을 봤을 때의 체크리스트
- [ ] ...

## 일반화 판단
- 이 레포 어디서나 재발할 수 있는가, 이번 코드 경로에만 있는 특수 상황인가
```

마지막 절이 게이트 ④의 입력이다. **초안을 쓰면서 미리 판단해 두면 사람의 판단 비용이 낮아진다.** 다만 판단을 대신하지는 않는다.

## 1-3. 자기 검열 — 이건 교훈이 아니다

| 초안에 쓰지 말 것 | 이유 |
|---|---|
| "성능 문제는 측정부터 하자" 같은 일반론 | Lane A가 이미 안다. 발췌 노이즈만 늘린다 |
| 이번 트레이스에서만 참인 수치 | `member 테이블 5,000행`은 6개월 뒤 거짓이다 |
| 코드 스니펫 통째 복사 | 코드는 바뀐다. **판단 기준**을 적어야 오래 산다 |
| 사이클 진행 과정 서술 | 그건 `cycles/`에 이미 있다 |

**"이 레포에서만 참이고, 6개월 뒤에도 참인 것"만 남긴다.** 이 두 조건을 동시에 통과하는 문장은 생각보다 적다.

초안을 `60-lesson.md`에 쓴다. **여기까지는 저장이 아니다.**

# 2. 🚦 게이트 ④ · 베스트 프랙티스로 남길 것인가 (HARD GATE)

| 항목 | 내용 |
|---|---|
| **판단 주체** | 사람 |
| **핵심 질문** | **"이건 새 패턴인가, 기존 패턴의 사례인가?"** |

이 게이트가 없으면 틀린 교훈이 영구 축적되어 다음 사이클을 오염시킨다. 게이트 4개 중 유일하게 **미래에 영향을 주는** 게이트다.

## 제시 형식

먼저 `perf-bp-curator`에게 `mode: lookup`으로 기존 지식을 조회한다. **사람이 "새 패턴인가"를 판단하려면 기존에 무엇이 있는지 알아야 한다.**

```
게이트 ④ — 베스트 프랙티스로 남길까요?

■ 교훈 초안
  증상    루트 아래 동일 SELECT가 컬렉션 크기만큼 반복
  원인    lazy 연관을 루프에서 접근
  해결    배치 페치 (in-clause)
  틀렸던 것  처음엔 인덱스 부재로 봤음 → 실행 계획상 인덱스 정상
  체크리스트 3항목

■ 기존 지식 (큐레이터 조회)
  - n-plus-one.md  (사례 3건) ← 증상 모양 일치
  - missing-index.md (사례 1건)

■ AI의 일반화 판단
  기존 패턴의 사례로 보입니다. 다만 "인덱스 부재로 오진했다"는
  n-plus-one.md의 "틀리기 쉬운 지점"에 없는 내용입니다.

어떻게 할까요?
  [1] 기존 패턴의 사례      → n-plus-one.md 에 사례 절 추가 (파일 수 증가 없음)
  [2] 새 패턴               → 새 md 생성 + INDEX.md 갱신
  [3] 폐기                  → 일반화 불가. 남기지 않음
```

**폐기를 선택지에서 빼지 않는다.** 이번 사이클에만 해당하는 특수 상황이었다면 남기지 않는 것이 옳고, 그것이 저장소를 소음에서 지킨다.

## 승인 후 — 저장은 큐레이터가 한다

`perf-bp-curator`를 `mode: merge`로 호출한다.

```
mode: merge
gate4_decision: existing_case | new_pattern | discard
cycle_record: <60-lesson.md 내용 + 측정치 + attempts.json 요약>
```

**`gate4_decision`은 사람의 답을 그대로 옮긴다.** 이 필드가 게이트 ④의 유일한 물리적 흔적이고, 큐레이터는 이 필드가 없으면 쓰기를 거부한다.

**스킬은 저장 경로를 모른다.** 저장소를 직접 열지도, 이 문서에 경로를 적지도 않는다 — 경로가 두 곳에 적히는 순간 캡슐화가 무너진다(OS.md §5 R3). 어디에 어떤 형식으로 쓰이는지는 전적으로 큐레이터의 소관이다.

큐레이터가 **판단 불일치**를 보고할 수 있다. 예컨대 `new_pattern`으로 넘겼는데 거의 같은 파일이 이미 있다는 보고다. 그러면 **사람에게 다시 묻는다.** 사람은 INDEX 전체를 보지 않고 판단했을 수 있다.

게이트 ④ 결과를 `60-lesson.md` 하단에 기록한다.

# 3. 출력

```
사이클 완료 — <trace_id 앞 8자>

  교훈:    기존 패턴의 사례로 병합
  갱신:    n-plus-one.md (사례 4건), INDEX.md
  환류:    다음 사이클의 Lane B가 이 교훈을 받습니다

  기록:    .claude/perf-os/cycles/<trace_id>/
```

`best-practices/`는 **팀 지식이므로 커밋 대상**이다(`cycles/`는 `.gitignore`). 커밋은 이 스킬의 범위 밖이지만, 커밋할 것이 생겼다는 사실은 알린다.

## 절대 금지

| 금지 | 이런 생각이 들면 위반 직전 | 실제 |
|---|---|---|
| 검증 전 사이클에서 교훈 추출 | "원인은 이미 알잖아" | 무엇이 통했는지 모르는 채 쓴 교훈이 다음 사이클을 오염시킨다 |
| `best-practices/` 직접 읽기·쓰기 | "큐레이터 부르는 게 번거로운데" | R3 위반. 경로가 두 곳에 적히면 저장 구조를 못 바꾼다 |
| `gate4_decision` 없이 merge 호출 | "사용자가 승인했으니 됐지" | 그 필드가 승인의 유일한 흔적이다. 큐레이터가 거부한다 |
| 실패 이력 생략 | "성공 사례만 정리하면 깔끔하지" | 실패 이력이 1급 재료다. "왜 틀렸는가"가 다음번을 구한다 |
| 사례마다 새 파일 만들기 | "각각 상황이 다르니까" | 1년 뒤 50개가 되면 아무도 안 읽는다. 이 OS가 명시적으로 막는 실패 모드다 |
| 폐기 선택지 빼기 | "기왕 뽑았는데 남기는 게 낫지" | 특수 상황을 남기면 저장소가 소음이 된다 |
| 일반론 축적 | "원론적으로도 맞는 말이니까" | Lane A가 이미 안다. 발췌 노이즈를 늘려 Lane B의 가치를 깎는다 |
| 틀린 기존 항목 방치 | "지우는 건 좀 부담스러운데" | 축적은 추가만이 아니다. 모순된 조언이 공존하면 저장소 신뢰가 0이 된다 |
