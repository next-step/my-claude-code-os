# verify — 완료 기준 검증

대상 REQ-ID 는 스킬 호출 시 인자로 전달된다 (예: `/verify REQ-001`). 이하 `<REQ-ID>` 로 표기.

## 0. 선행 조건

- `maintenance/requests/<REQ-ID>.md` 를 읽는다.
- "4. 스펙" 의 **완료 기준** 목록이 있어야 한다. 없으면 중단한다.

## 1. context-loader 호출

`Task` 툴로 **context-loader** (`REQ-ID=<REQ-ID>`, `phase=verify`) 를 실행한다.
각 완료 기준을 무엇으로 확인하는지(테스트 명령, 재현 절차)를 파악한다.

## 2. 기준별 검증

완료 기준을 하나씩 처리한다. 가능하면 실제로 실행한다:

- 테스트: 프로젝트 명령 (`npm test`, `pytest` 등)
- 빌드 / lint
- 버그 재현 절차를 따라가서 기대 결과가 나오는지 확인

## 3. 결과 표 → 케이스 파일 "6. 검증 결과"

```
| # | 완료 기준 | 방법 | 결과 |
| - | --- | --- | --- |
| 1 | ... | `npm test auth` | ✅ 통과 |
| 2 | ... | 수동 재현 | ❌ 실패 — <무엇이 안 됐는지> |
```

실행하지 못한 항목은 `⏭️ 미실행 (사유)` 로 남긴다.

## 4. 판정 & 상태

- 전부 통과 → `status: done`. `변경 이력` 에 `<오늘> 검증 통과 (done)` 추가.
- 하나라도 실패 / 미실행 → `status: blocked`. 실패 항목과 필요한 후속 작업을 "6." 에 적고,
  `변경 이력` 에 `<오늘> 검증 실패 (blocked)` 추가.
- `updated` 를 오늘로 갱신.

## 5. 보고

결과 표를 요약한다. 실패면 다음 액션(무엇을 고쳐 `/implement` 를 재실행할지)을 제시한다.
통과면:

- 필요 시 `git-commit` 스킬로 커밋을 권한다.
- 담당자에게 결과를 전달하려면 `/handoff <REQ-ID>` 를 안내한다 (배포 노트 + 통보문).

## 하지 말 것

1. 실행하지 않은 검증을 "통과" 로 적지 않는다.
2. 완료 기준을 검증 중에 몰래 완화하지 않는다 — 기준을 바꾸려면 `/spec` 으로 돌아가
   스펙을 고치고 그 사실을 남긴다.
3. 여기서 코드를 고치지 않는다 — 수정은 `/implement` 로 되돌아가서 한다.
