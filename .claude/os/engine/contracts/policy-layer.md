# 소유 정책 레이어 계약

이 OS에는 정책이 두 벌 있다. 섞으면 안 된다.

| 구분 | 위치 | 누가 쓰는가 | 재생성 |
|---|---|---|---|
| **소유 정책** | `.claude/os/attributes/<프로필ID>/policy/` | 사람이 직접 쓴다 | 안 됨. 지우면 끝 |
| **가져온 스냅샷** | `.claude/os/runs/<프로필ID>/policy/` | import 어댑터가 쓴다 | 매 사이클 덮어씀 |

`runs/`는 언제든 지우고 다시 만들 수 있어야 한다. 그래서 손으로 쓴 정책을 거기 두지 않는다.
스냅샷은 "지금 프로덕션이 실제로 쓰는 문장"이고, 소유 정책은 "우리가 옳다고 정한 문장"이다.
둘이 다르면 그 차이가 곧 개선 대상이다.

## 디렉터리 구조

```
.claude/os/
  engine/templates/
    policy.md              새 속성 정책의 뼈대
    precedent.md           새 판례의 뼈대
  attributes/<프로필ID>/
    policy/
      policy.md            정책 원본 (사람 소유)
      precedents/
        <판례ID>.md        경계 판정 1건 = 파일 1개
```

## policy.md 계약

프론트매터에 `id`(프로필 ID와 같아야 함), `version`, `owner`, `updatedAt`을 둔다.
본문에는 아래 네 개의 `##` 섹션이 **반드시** 있어야 한다. 하나라도 없으면 사이클이 실패한다.

| 섹션 | 내용 | 없으면 생기는 일 |
|---|---|---|
| `## 허용값` | 닫힌 목록. `` - `LABEL` — 설명 `` 형식 | 열린 목록이면 평가가 불가능하다 |
| `## 근거 우선순위` | 근거가 충돌할 때의 결정 규칙 | 같은 입력에 다른 답이 나온다 |
| `## 판정 불가 조건` | 언제 판정 불가 값을 내는가 | 억지 추출이 가장 흔한 오류원이다 |
| `## 판례` | 경계 판정 파일 링크 | 같은 질문을 두 번 묻게 된다 |

허용값은 `` - `MALE` — 설명 `` 처럼 첫 백틱 토큰을 라벨로 읽는다.

## 규칙에 이름을 붙인다

`## 근거 우선순위`와 `## 판정 불가 조건`의 각 항목은 **대문자 토큰으로 시작한다.**
허용값과 같은 모양이고, 있는 자리가 다르다.

```markdown
1. `P1_DIRECT_TEXT` — **직접 상품 성별 문구.** 대상 상품을 직접 수식하는 …
- `U1_SIGNAL_CONFLICT` — 여성 신호와 남성 신호가 충돌한다
```

이름이 없으면 「어느 규칙의 판례인가」를 물을 수 없다. 물을 수 없으면 다음 실행의 판독기가
그 판례를 골라 읽을 수 없고, 그때 판례는 정책 폴더 안의 문서로만 남는다 —
**사람이 답한 경계가 다음 판독에 한 번도 닿지 않는다.**

규칙은 이 두 섹션에서만 읽는다. 계약 밖의 자유 섹션은 훑지 않는다 — 훑으면 「근거 유형」
같은 값 목록이 규칙으로 둔갑한다. 규칙 본문의 형식은 강요하지 않는다. 첫 토큰만 이름이고
나머지는 사람이 읽을 문장이다. 본문을 형식으로 묶으면 정책이 형식에 맞춰 얇아진다.

## 판례 계약

판례는 **사람이 한 번 답하면 닫히는 경계 질문 하나**를 담는다. 케이스 라벨이 아니다.

| 프론트매터 | 필수 | 값 |
|---|---|---|
| `id` | 예 | 파일명과 같아야 한다 |
| `profile` | 예 | 프로필 ID |
| `status` | 예 | `OPEN` · `DECIDED` · `SUPERSEDED` |
| `applies` | 아니오 | `EVIDENCE` · `RULING`. 없으면 `RULING` |
| `rule` | `EVIDENCE`일 때 예 | 걸리는 정책 규칙 ID (쉼표 구분) |
| `signals` | 아니오 | 이 판례를 기다리는 큐 신호 (쉼표 구분) |
| `answers` | 아니오 | 닫는 정책 질문 ID (쉼표 구분) |
| `acknowledges` | 아니오 | 알고도 남겨둔 위반 코드 (쉼표 구분) |
| `decision` | `DECIDED`일 때 예 | 확정된 판정 |
| `decidedBy` / `decidedAt` | `DECIDED`일 때 예 | 누가 언제 |
| `supersedes` | 아니오 | 대체한 이전 판례 ID |

### 판례는 스스로 걸린다 — 코드가 아니라

`rule`과 `signals`가 이 판례가 **어디에 걸리는지**를 선언한다. 엔진이 그 선언을 읽어
심판의 `blockedBy`를 채우고, 규칙 브리프에 실을 판례를 고른다.

전에는 이 이음이 어댑터 코드에 상수로 있었다(`blockedBy: ["BG-0001"]`). 그러면 판례를
새로 써도 심판은 모르고, 판례를 닫아도 코드를 고쳐야 했다 — **판례가 자산이 아니라
코드의 상수였다.** 지금은 판례 파일 하나를 더하는 것만으로 다음 실행이 달라진다.

### `applies` — 판례에는 두 종류가 있다

| 값 | 묻는 것 | 판독기에게 |
|---|---|---|
| `EVIDENCE` | **무엇이 근거인가** (몇 묶음이 겹쳐야 결합이 성립하는가) | 규칙 브리프에 실려 간다 |
| `RULING` | **근거가 이러할 때 무엇으로 정할 것인가** (GT를 뒤집을 것인가) | 가지 않는다 |

선언하지 않으면 `RULING`이다. 모르는 것을 판독기에게 주는 쪽이 안 주는 쪽보다 나쁘다 —
판정 규칙을 읽은 판독기는 「무엇이 보이는가」를 답해야 할 자리에서 「무엇이 답인가」를
먼저 정한다.

`EVIDENCE`인데 `rule`이 없으면 그 판례는 어느 브리프에도 실리지 않아 **다음 실행에
영원히 닿지 못한다.** 그래서 그때만 규칙이 필수다. `RULING`은 규칙 없이 설 수 있다 —
「두 GT 소스 중 무엇이 정본인가」는 어떤 근거 규칙 위에도 서지 않는다.

`OPEN`은 질문만 있고 답이 없는 상태다. 이걸 파일로 남기는 이유는, 답하지 않은 질문의
개수가 곧 **이 속성의 정책이 얼마나 미완성인지를 보여주는 지표**이기 때문이다.

`status`는 표시가 아니라 관문이다. 사람이 GT 정정을 승인할 때 근거로 가리킨 판례가
`OPEN`이면 그 판정은 원장에 남되 골든셋에는 반영되지 않는다 — 경계가 열려 있는데
개별 건을 확정하면 그 건들이 곧 답이 되어 버린다. `DECIDED`로 바꾸는 순간 기다리던
건이 한꺼번에 나가므로, **판례를 닫는 일이 곧 밀린 정정을 푸는 일**이다.
계약은 [gt-layer.md](gt-layer.md)에 있다.

## 검증과 위반 등급

`build_policy_index.py`가 매 사이클마다 검사하고 `runs/<프로필ID>/policy/policy-index.json`과
`runs/<프로필ID>/reports/policy-status.md`를 만든다.

| 등급 | 뜻 | 사이클 |
|---|---|---|
| `BLOCKING` | 계약 위반. 파일이 없거나 형식이 깨졌다 | 중단 (exit 1) |
| `REVIEW` | 정책과 프로필·질문이 어긋난다 | 계속. 다만 기록에 남는다 |

`REVIEW` 위반은 어떤 판례가 `acknowledges`로 그 코드를 선언하면 `tracked`가 된다.
tracked는 "알고 남겨둔 것", untracked는 "아무도 모르는 것"이다. 이 둘을 구분하는 것이
이 레이어의 핵심이다. 정책 공백 자체는 죄가 아니지만, 추적되지 않는 공백은 죄다.

| 코드 | 등급 | 언제 |
|---|---|---|
| `POLICY_FILE_MISSING` | BLOCKING | `policy.owned` 경로에 파일이 없다 |
| `POLICY_ID_MISMATCH` | BLOCKING | 프론트매터 `id`가 프로필 ID와 다르다 |
| `POLICY_SECTION_MISSING` | BLOCKING | 필수 `##` 섹션이 없다 |
| `POLICY_LABELS_EMPTY` | BLOCKING | 허용값을 하나도 못 읽었다 |
| `PRECEDENT_MALFORMED` | BLOCKING | 판례 프론트매터가 계약을 어겼다 |
| `LABEL_NOT_IN_PROFILE` | REVIEW | 정책 허용값이 프로필 `labels`에 없다 |
| `LABEL_NOT_IN_POLICY` | REVIEW | 프로필 `labels`가 정책 허용값에 없다 |
| `QUESTION_WITHOUT_PRECEDENT` | REVIEW | 정책 질문에 답할 판례 파일이 없다 |
| `UNKNOWN_QUESTION` | REVIEW | 판례가 존재하지 않는 질문을 가리킨다 |
| `UNKNOWN_RULE` | REVIEW | 판례가 정책에 없는 규칙을 가리킨다 |
| `PRECEDENT_WITHOUT_RULE` | REVIEW | `EVIDENCE` 판례가 규칙을 안 걸어 브리프에 못 실린다 |

## 규칙 브리프 — 판례가 다음 실행에 닿는 길

`build_precedent_brief.py`가 규칙마다 한 장씩 굽는다.
`runs/<프로필ID>/policy/rule-briefs/<규칙ID>.md`이고, 목차는 같은 폴더의 `index.json`,
주소는 `run-summary.json`의 `artifacts.ruleBriefs`가 가리킨다.

| 브리프에 실리는 것 | 왜 |
|---|---|
| 그 규칙이 속한 정책 섹션 **통째로** | 자를 자리가 없으면 잘리지 않는다 |
| 걸린 `EVIDENCE` 판례의 질문과 확정된 답 | 사람이 답한 경계가 다음 판독에 닿는 자리 |
| 그 판례로 실제 확정한 사례 몇 건 | 말이 아니라 어떻게 적용됐는가 |
| 판례 없이 그 규칙 위에서 내린 판단 수 | 쌓이면 **판례를 열 자리**다 |

판독기는 정책 파일 경로를 받지 않는다. 브리프 **내용만** 받는다. 경로를 주면 옆 파일을
열어 판정 규칙까지 읽는다. 발췌를 손으로 뜨지 않는 이유는 사고 기록이 있기 때문이다 —
2순위 묶음 표의 마지막 줄이 발췌에서 빠져 판독기가 그 묶음을 못 본 적이 있다.
**발췌에 없는 것은 판독기에게 존재하지 않는다.**

## 새 속성에 정책 레이어 붙이기

1. `.claude/os/attributes/<프로필ID>/policy/`를 만들고 `engine/templates/policy.md`를 복사한다.
2. 프로필 JSON에 `policy` 블록(`owned`, `precedents`, `imported`)을 추가한다.
3. `attributes/<프로필ID>/run.sh`를 돌린다. 위반 목록이 곧 첫 할 일 목록이다.

`policy` 블록이 없는 프로필은 이 단계를 건너뛴다. 정책 레이어는 선택이지, 강제가 아니다.
