# 카탈로그 감사 HTML 보고서

```bash
python3 .claude/os/engine/scripts/render_catalog_report.py --profile '<profile.json>'
```

`runs/<프로필ID>/reports/`에 네 장이 생긴다.

| 파일 | 무엇 | 단위 |
|---|---|---|
| `catalog-audit.html` | 표지. 두 목록의 크기, 분리된 실행 결함 표, 신호가 어느 목록으로 갔는지 | — |
| `gt-fixes.html` | GT 정정 후보. 한 제안이 한 장의 조서. `현재 GT → 제안`과 그 주장이 딛고 선 사진 | 제안 |
| `suspect-gt.html` | 의심되는 GT 찾기. 심판이 골든셋을 지목했거나 판례 답을 기다리는 사례 | 건 |
| `policy-gaps.html` | 빈 정책 찾기. 답을 기다리는 판례별로 사례를 접어 둔 목록 | 군집 |

`gt-fixes.html`과 `suspect-gt.html`은 **같은 행을 본다.** 다른 것은 묻는 질문이다 — 정정 후보는
"이 GT를 이렇게 고칠까"를, 사례 보고서는 "판독기가 어떤 단계를 거쳐 저 답에 닿았나"를 묻는다.

정정 후보 한 장은 조서다. 주문(`현재 GT → 제안`)과 GT 출처, 판독기가 쓴 문장과 리뷰어가 쓴 문장,
그리고 **판독기가 인용한 사진**이 한 화면에 있다. 인용된 장면에는 «근거» 표시가 붙는다 —
그 사진을 반박할 수 있으면 제안은 무너지므로, 사람이 어디를 봐야 하는지가 먼저 보여야 한다.
나머지 타일은 접어 둔다. 사라진 원본은 빈 액자로 남기지 않고 "못 불러왔다"고 적는다.
빈 액자는 "근거가 없다"로 읽히는데 그건 사실이 아니다.

제안 도장(확신 · 정책적용 · 판단필요 · 미확정)은 손으로 고른 확신도가 아니라 심판이 낸 귀책과
근거 강도에서 나온다. 그래서 정정 후보에는 **손으로 적은 숫자도, 손으로 고른 분류도 없다.**

### GT를 묻는 화면에 실행 품질을 싣지 않는다

`gt-fixes.html`과 `suspect-gt.html`의 계기판에는 표면 정확도·처리 건수·정책 버전이 없다.
"이 GT가 틀렸나"에 답을 주지 않는 숫자이기 때문이다. 답에 기여하지 않는 지표를 판단 화면 옆에
두면 사람은 그것으로도 판단하게 된다 — 정확도가 높으면 GT를 덜 의심하고, 낮으면 더 의심한다.
둘 다 근거가 아니다. 대신 GT에 관한 것만 센다: 사진이 붙은 건, 인용 장면이 찍힌 건,
현재 GT의 출처 종류, 다른 GT 소스와 갈린 건. 실행 건강은 표지(`catalog-audit.html`)의 일이다.

사례 보고서는 상품마다 GT·실행·정책 답·귀책을 나란히 놓고, 판단기가 본 단계(1차 대표 이미지 →
2차 상세 이미지 → 최종)와 근거 문장, 그리고 프로필 `gallery`가 가리키는 대표 이미지·상세 타일 전부를
밀집해 싣는다. 근거로 채택된 장면은 강조된다.

보고서는 프로필의 대상·속성·신호 표시명을 사용한다. 렌더러에 라벨 값이나 속성 규칙을 추가하지
않는다. 어느 상품이 어느 보고서에 가는지는 `review/verdicts.jsonl`의 귀책이 정한다. 심판이 없으면
프로필 신호의 `lane`, 그것도 없으면 미확정이라 두 보고서에 모두 나온다.

정책 질문의 의미를 풀어야 할 때는 공유 `catalog-golden-adjudicator` 서브에이전트를 사용한다.
