# 인터뷰 규약

모호함을 구체로 바꾸는 절차. 네 단계이고, 각 단계는 다음 단계의 입력을 만든다.

```
분류 ──▶ 위치 ──▶ 질문 ──▶ 검사
 무슨    어디에    어떻게    통과했나
 종류인가 쌓이나   묻나      아닌가
```

## 0단계 — 자료 접수: 받아서 슬롯별로 인용해 둔다

대개 PRD·LLD·라벨링 가이드가 인터뷰보다 먼저 있다. 그래서 첫 동작은 질문이 아니라 **접수**다.
다만 "받는 것"으로 끝나지 않는다 — 받아서 **슬롯별로 분류하고 인용해 두는 것**까지가 0단계다.

```
자료 후보 ──▶ 큐레이터가 고른다 ──▶ 사람이 확인 ──▶ 스냅샷 + 해시 ──▶ 슬롯 × 자료 커버리지 표
```

자료가 있으면 질문의 모양이 바뀐다. 백지 질문("사용처가 뭡니까")이 **확인 질문**("LLD §스코프는
사용처를 검색 필터라고 합니다. 추천에도 쓰나요?")이 된다. 확인은 생성보다 싸고, 이미 있는
"백지 금지" 규칙의 가장 좋은 재료가 자료다. 특히 PRD는 왜·누가·무엇을 다루므로 목표층(`A0`)에 강하다.

지켜야 할 경계는 하나다. **자료는 답이 아니라 답의 후보다.** "여성스러운 디자인이면 FEMALE"이
PRD에 있어도 관찰 가능 검사를 못 넘는다. 자료 문장도 사람 답과 같은 세 관문을 지난다.
자료는 질문을 짧게 만들 뿐 게이트를 우회하지 않는다.

| 산출물 | 위치 | 성격 |
|---|---|---|
| 참조 목록 | 프로필 `references` | 사람이 확인해 넣는다 |
| 스냅샷·해시 | `runs/<id>/interview/sources/` + `manifest.json` | 접수 시점의 사본. 정책 import와 같은 원리 |
| 커버리지 표 | `runs/<id>/interview/coverage.json` | AI 산출물. 슬롯별 인용. 자료가 바뀌면 `STALE` |

커버리지 표에서 **자료가 답하지 못하는 빈 열**이 곧 진짜 인터뷰 대상이다.
절차는 `catalog-source-intake` 스킬, 고르는 기준은 `catalog-source-curator` 에이전트에 있다.

## 1단계 — 분류

모호함에 이름을 붙인다. 종류마다 이름(`A0`~)과 그것을 푸는 도구가 있고,
목록은 [ambiguity-taxonomy.md](ambiguity-taxonomy.md)에 있다. 여기서는 개수를 세지 않는다 —
종류가 늘 때마다 이 문장이 조용히 틀리기 때문이다.

## 층 순서 — 목표 → 정책 → 판례

슬롯 순서는 취향이 아니라 [engine/goal.md](../../engine/goal.md)의 레이어 서열
**목표 > 정책 > GT**를 그대로 옮긴 것이다.

| 층 | 슬롯 | 이 층이 비면 |
|---|---|---|
| 목표 | `SLOT-PURPOSE` · `SLOT-VERDICT` · `SLOT-QUALITY` | 판정표의 ①을 아무도 채울 수 없고, 언제 끝나는지도 아무도 모른다. 정책과 GT가 갈릴 때 그 자리에 있던 사람의 취향이 결정한다 |
| 아는 것 | `SLOT-PROVENANCE` | 이미 답이 있는 걸 다시 묻고, 근거 없는 규칙이 정책에 들어간다 |
| 정책 | `SLOT-SCOPE` · `SLOT-LABELS` · `SLOT-ABSTAIN` · `SLOT-PRIORITY` · `SLOT-BLAME` | 사이클이 시작되지 않는다 (`BLOCKING`) |
| 판례 | `SLOT-PRECEDENT` · 열린 `OPEN` 판례 | 같은 질문을 두 번 묻는다 |

### 목표를 묻는 법 — 목표를 묻지 않는다

"이 속성의 목표가 무엇입니까"는 슬로건을 부른다. "정확도를 올린다", "데이터 품질을 높인다".
슬로건으로는 상품 하나를 판정할 수 없다. 대신 셋을 묻는다.

1. **사용처** — 이 값을 실제로 읽는 화면·기능. 하나도 못 대면 이 속성은 목표가 없다
2. **실패 장면** — 값이 틀렸을 때 **누가 무엇을 못 하게 되는가**. 장면 하나를 구체적으로
3. **판정 한 문장** — "이 값이 옳다"가 무슨 뜻인지 한 문장. 이 문장만 읽고 판정할 수 있어야 한다

셋이 모이면 목표가 문장이 된다. 뼈대는 [engine/templates/goal.md](../../engine/templates/goal.md)다.

### 품질을 묻는 법 — 정확도를 묻지 않는다

"정확도 몇 %"를 물으면 95가 반사적으로 나온다. 근거 없는 숫자는 달성해도 끝나지 않는다.
대신 위에서 받은 **실패 장면에 숫자를 붙인다** — "그 장면이 100건 중 몇 건까지면 버팁니까."
방향(어느 쪽 오류를 몇 건까지), 분해 단위(전체 평균 금지), 기준 품질(GT를 얼마나 믿어야
이 숫자가 유효한가)을 함께 받는다. 숫자 없는 답은 `RESOLVED`가 되지 않는다.

이 OS는 정확도를 완료 조건으로 두지 않는다. 목표 품질은 속성의 **운영 목표**이고,
이 OS는 그 목표를 잴 수 있는 기준(GT)을 만든다. 그래서 표의 첫 줄은 기준 품질이다.

### 아는 것을 묻는 법 — 어디에 적혀 있나, 누가 정했나

"우리는 정책을 안다"는 두 가지를 뜻할 수 있고, 둘을 섞는 것이 이 OS가 막으려는 실수다.
그래서 **모든 답에 출처와 확신도 꼬리표를 붙인다.**

| 출처 | 확신도 |
|---|---|
| `OWNED` 소유 정책에 적혀 있다 | `DECIDED` 누가 언제 정했다 |
| `SNAPSHOT` 프로덕션 프롬프트에만 있다 | `CUSTOM` 그냥 그렇게 해왔다 |
| `DOCUMENT` PRD·LLD·가이드에 적혀 있다 — `--cite` 필수 | `GUESS` 답변자도 추측이다 |
| `TACIT` 아무 데도 없다 | |
| `NEW` 이번에 처음 정했다 | |

핵심 질문은 한 줄이다 — **"이건 누가 정한 건가요, 아니면 그냥 그렇게 해온 건가요?"**
`GUESS`는 `RESOLVED`가 될 수 없다. 확신도가 낮은 답이 아니라 아직 답이 아니기 때문이다.
소유자를 찾을 때까지 `OPEN`으로 둔다. `CUSTOM`은 쓰되 판례로 승격시켜 근거를 남긴다.

정책 전체의 지도는 `SLOT-PROVENANCE`가 들고 있다 — 소유 정책의 `## 출처와 확신도` 표다.

## 2단계 — 위치: 슬롯이 질문을 만든다

**도착지가 없는 질문은 하지 않는다.** 답을 받아도 쌓을 곳이 없으면 그 대화는 대화로 끝난다.
그래서 질문은 사람의 궁금증에서 나오지 않고 **비어 있는 슬롯**에서 나온다.

슬롯은 [slots.json](slots.json)에 선언되어 있고, 전부 **엔진이 이미 검증하는 빈칸**이다.
인터뷰가 끝나면 `build_policy_index.py`의 `BLOCKING` 위반이 0이 된다는 뜻이다.
인터뷰의 완료 조건이 느낌이 아니라 종료 코드인 이유가 여기 있다.

```bash
python3 .claude/os/interview/scripts/scan_ambiguity.py --profile '<profile.json>'
```

스캐너는 슬롯 상태를 셋으로 나눈다.

| 상태 | 뜻 | 예 |
|---|---|---|
| `EMPTY` | 파일이나 섹션 자체가 없다 | `policy.md`를 아직 안 만들었다 |
| `THIN` | 자리는 있는데 템플릿 자리표시자뿐이다 | `- <조건 1>`, `_(아직 없음)_` |
| `FILLED` | 판정에 쓸 수 있는 문장이 있다 | |

슬롯마다 질문 모양도 정한다 — 자료 후보가 있으면 `CONFIRM`, 없으면 `OPEN`.
`CONFIRM`이면 `nextQuestion`에 인용이 붙어 나온다.

스캐너는 사이클을 막지 않는다. 세는 것까지가 기계의 몫이다.

그리고 모드를 하나 정한다. `EMPTY`가 하나라도 있으면 `NEW` — 계약이 아직 안 섰으므로
정의부터 묻는다. 전부 자리를 잡았으면 `GAP` — 남은 일은 자리표시자와 열린 판례,
그리고 사이클이 올린 미답 정책 질문을 닫는 것이다. 두 모드는 질문 재료만 다르고
3·4단계는 똑같다.

## 3단계 — 질문: 다섯 규칙

1. **케이스가 아니라 경계를 묻는다.** "이 상품은 뭔가요"가 아니라 "어디부터 갈리나요".
   케이스를 물으면 답 하나가 케이스 하나를 닫고, 경계를 물으면 답 하나가 군집을 닫는다.
2. **백지 금지.** 선택지 2~3개, 각 선택지의 대가, 권고안과 이유를 함께 낸다.
   백지 질문은 답이 늦고, 늦은 답은 대개 안 온다.
3. **한 번에 하나.** 스캐너는 후보를 여럿 내지만 사람에게는 상위 하나만 묻는다.
4. **값을 미리 보여준다 — 큐에 이미 있는 상품으로.** "이 답이면 X는 이렇게, Y는 저렇게 됩니다."
   답변자는 규칙을 상상해서 검토하지 못한다. 결과를 봐야 자기 기준이 드러난다.
   그 X·Y는 지어내지 않는다. 스캐너가 `ambiguousProducts`로 첨부한 **큐의 실제 상품**에서 고른다.
   사이클이 이미 "모르겠다"고 말한 상품이 가장 많은 것을 가르고, 그 상품만 다음 사이클에서
   답이 맞았는지 검증할 수 있다. 큐가 비어 있으면(`NEW`) 지어낸 사례를 쓰되 원장에 `queued: false`로 남는다.
5. **모르면 '미정'이 정답이다.** 추측으로 슬롯을 채우지 않는다. 미정은
   `status: OPEN` 판례로 남는다. 답하지 않은 질문의 개수가 이 속성의 미완성도다.

질문 예산은 한 세션 7문항이다. 취조가 되면 답의 품질이 떨어진다.
넘치면 남은 슬롯을 `OPEN`으로 남기고 세션을 닫는다.

## 4단계 — 검사: 세 관문

답이 왔다고 구체가 된 것이 아니다. 세 검사를 전부 통과해야 `RESOLVED`다.

| 검사 | 묻는 것 | 떨어지는 답의 예 |
|---|---|---|
| **관찰 가능** | 답에 나오는 술어를 상품 데이터에서 확인할 수 있는가 | "고급스러우면 여성용" |
| **재현 가능** | 반례 쌍 2건에 서로 **다른 값**이 나오는가 | 두 사례에 같은 값이 나오면 그 답은 경계를 가르지 못했다 |
| **닫힘** | 모든 입력이 허용값 또는 판정 불가로 떨어지는가 | "그 외에는 상황에 따라" |

슬롯 계약이 `answerMustContain: number`를 선언한 슬롯(`SLOT-QUALITY`)은 답에 숫자가 있어야
`RESOLVED`다. 숫자 없는 품질 목표는 슬로건이다.

여기에 출처 관문이 하나 더 붙는다. `--source`와 `--confidence`가 없으면 기록되지 않고,
`--confidence GUESS`는 `RESOLVED`가 되지 않는다. 어디서 왔는지 모르는 규칙은
다음 사이클에서 **근거 없는 일치**의 원인이 된다.

떨어지면 후속 질문을 **한 개** 만든다. 같은 슬롯에서 3회 되묻지 않는다.
3회에 못 닫히면 그건 답변자가 모르는 게 아니라 **아직 조직이 정하지 않은 것**이다.
`OPEN`으로 내리고 판례 파일로 남긴다.

재현 검사의 기준은 이 저장소가 이미 쓰는 기준과 같다 — *사람 2명이 같은 상품에 같은 라벨*.
반례 쌍은 그 검사를 두 건으로 축소한 것이다.

## 기록 계약

`<outputRoot>/interview/answers.json` · `schemaVersion: catalog-interview-v1`.

```bash
python3 .claude/os/interview/scripts/record_interview_answer.py \
  --profile '<profile.json>' --slot SLOT-ABSTAIN \
  --question '<물은 것>' --answer '<사람이 답한 규칙 문장>' \
  --answered-by '<이름>' --status RESOLVED \
  --observable --closed \
  --counter-example '<사례 A> => <값>' --counter-example '<사례 B> => <다른 값>' \
  --source OWNED --confidence DECIDED --owner '<확정할 수 있는 사람>' \
  --option 'A: <선택지>' --option 'B: <선택지>' --reason '<왜 이 답인가>' \
  --session '<세션ID · 기본 오늘 날짜>' --applies-to '<답이 들어갈 파일>'
```

- **사람이 명시적으로 확정한 답만 기록한다.** AI가 만든 질문·선택지·권고는 기록 대상이 아니다.
  판정 원장(`review/decisions.json`)과 같은 규칙이다.
- `RESOLVED`는 세 검사를 전부 통과해야 기록된다. 반례 쌍이 같은 값을 내면 스크립트가 거절한다.
  **방법을 문서가 아니라 게이트로 둔 것이다.** 문서로만 있는 규칙은 바쁠 때 가장 먼저 생략된다.
- 같은 슬롯을 다시 답할 때는 `--supersedes`로 이전 `answerId`를 명시한다. 과거 답은 지우지 않는다.
  왜 기준이 바뀌었는지가 나중에 가장 궁금해지는 정보다.

## ADR — 세션 하나가 문서 한 장

원장은 기계가 읽는 쪽이고, 사람이 읽고 리뷰하는 쪽은 ADR이다. Q&A 형식이다 —
질문, 놓였던 선택지, 답, 이유, 반례, 출처, 적용처가 답마다 한 덩어리로 남는다.

```bash
python3 .claude/os/interview/scripts/render_interview_adr.py --profile '<profile.json>'
```

`attributes/<id>/adr/ADR-<NNNN>-<세션>.md`로 렌더한다. 모양은 [templates/adr.md](../templates/adr.md)다.
전부 `RESOLVED`면 `ACCEPTED`, 열린 답이 하나라도 있으면 `PROPOSED`다.
**이미 있는 ADR은 덮어쓰지 않는다.** 사람이 손본 문장을 기계가 지우면 안 되기 때문이다.
다시 쓰려면 `--force`를 명시한다.

ADR이 `attributes/`에 사는 이유는 판례와 같다 — 지워지면 안 되는 사람의 결정이다.
원장은 `runs/`에 있지만 판정 원장과 같은 규칙으로 재실행에도 보존된다.

## 적용

ADR은 기록이지 반영이 아니다. 답은 두 곳 중 하나로 옮겨져야 산출물이 된다.

| 답의 성격 | 옮기는 곳 |
|---|---|
| 사용처·실패 장면·판정 기준·목표 품질 | `attributes/<id>/goal.md`의 앞 세 섹션 |
| 어느 쪽을 고칠지의 원칙 | `attributes/<id>/goal.md`의 `## 귀책 원칙` |
| 규칙의 출처와 확신도 | `attributes/<id>/policy/policy.md`의 `## 출처와 확신도` |
| 정책 문장으로 옮길 수 있는 규칙 | `attributes/<id>/policy/policy.md` · `policy/precedents/<ID>.md` |

옮긴 뒤 스캐너를 다시 돌린다. 슬롯이 `FILLED`로 바뀌지 않았다면 그 답은 아직 문장이 아니다.
