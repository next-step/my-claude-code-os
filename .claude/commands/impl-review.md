`$ARGUMENTS`는 작업 폴더(`$DIR`)다. `<프로젝트>/tasks/NNN-작업명` 형태라는 전제에서 프로젝트 루트(`$PROJECT`)를 도출한다.

## 원칙

- **고도화지 수리가 아니다.** 시작 시점에 테스트를 통과하지 못하는 코드는 이 스킬의 대상이 아니다 — 멈추고 `/impl`로 돌려보낸다.
- **테스트가 정의한 동작은 불변이다.** 어떤 개선도 테스트를 깨뜨리거나 수정할 수 없다. 정책 밖 신규 기능 추가도 하지 않는다.
- **작성자와 검토자를 분리한다.** 지적은 새 컨텍스트의 서브에이전트가 만들고, 적용 여부 판단과 적용은 이 세션이 한다.
- **모든 적용은 검증으로 닫는다.** 개선을 적용할 때마다 전체 테스트를 다시 통과해야 한다. 깨지면 그 변경을 되돌린다.

## 실행 순서

### 1단계: 전제 확인

`$DIR/spec.md`를 읽는다.

- 파일이 없거나 `status: approved`가 아니면 "승인된 spec이 없습니다. /spec → /spec-review → 승인 → /test → /impl 순서를 먼저 진행하세요."라고 출력하고 종료한다.
- `$DIR/test-plan.md`가 없으면 "/test가 아직 실행되지 않았습니다."라고 출력하고 종료한다.
- `변경 범위`에 명시된 파일이 실제로 존재하는지 확인한다. 없으면 "/impl이 아직 실행되지 않은 것으로 보입니다."라고 출력하고 종료한다.

### 2단계: 기준선 검증

test-plan.md에 매핑된 테스트 전체를 실행한다.

- 하나라도 실패하면 **개선하지 말고 멈춘다.** 실패한 테스트와 대응 정책 ID를 보고하고 "/impl로 먼저 수리하세요."라고 안내한 뒤 종료한다.
- 실행한 명령을 기록해 둔다 — 4단계에서 같은 명령으로 재검증한다.

### 3단계: 서브에이전트 리뷰

general-purpose 서브에이전트를 **동기로(run_in_background: false)** 하나 띄운다. 프롬프트는 아래 템플릿을 그대로 쓰되 `{...}` 부분만 채운다:

```
너는 코드 검토자다. 이 코드는 네가 쓴 것이 아니다. 통과시키는 것이 목적이 아니라 더 나은 코드로 만들 지점을 찾는 것이 목적이다.

- spec: {spec.md 절대 경로} — 정책(P-…)이 코드가 지켜야 할 동작의 전부다.
- 테스트: {test-plan.md 절대 경로}와 거기 매핑된 테스트 파일 — 동작의 실행 가능한 정의다.
- 코드: {변경 범위의 파일 절대 경로 목록}

세 관점으로 검토하라:
1. 정확성 — 테스트는 통과하지만 깨지기 쉬운 지점. 테스트가 덮지 않는 엣지 입력(빈 파일, 손상된 데이터, 경계값, 중복 실행)에서 정책 위반이나 크래시가 나는 경로를 실제 코드를 따라가며 찾아라.
2. 단순화 — 중복 로직, 죽은 코드, 불필요한 상태, 더 짧고 명확하게 같은 동작을 하는 구현. 기존 코드의 관용구를 따르는 방향으로.
3. 견고성·가독성 — 오해를 부르는 이름, 삼켜지는 예외, 부적절한 자료구조.

각 지적을 아래 형식으로 작성하라:
- 분류: 결함(엣지에서 정책 위반/크래시 가능) 또는 개선(동작 동일, 품질 향상)
- 관련 정책: P-… (해당 없으면 "일반")
- 근거: {파일}:{줄} 과 문제 시나리오 한 문장 (결함이면 구체 입력 → 잘못된 결과를 명시)
- 제안: 어떻게 바꿀지 한두 문장

금지: 정책 밖 신규 기능 제안, 테스트 파일 수정 제안, 근거 없는 추측성 지적, 순수 취향 문제(포맷팅 등), 라이브러리 교체 같은 대수술.
지적이 없으면 "지적 없음"이라고 답하라. 파일은 수정하지 마라.
```

### 4단계: 적용과 재검증

서브에이전트의 지적을 하나씩 판단해 적용한다:

- **결함**은 전부 적용한다. 단, 지적의 문제 시나리오를 먼저 실제로 재현해 확인하고, 재현되지 않으면 적용하지 말고 보류로 분류한다(사유 기록).
- **개선**은 동작 보존이 확실한 것만 적용한다. 확신이 서지 않으면 보류로 남긴다.
- 적용할 때마다 2단계의 테스트를 다시 실행한다. 실패하면 그 변경을 되돌리고 보류로 분류한다.
- 보류 사유가 **스펙 결함**(정책이 모호해 옳은 동작을 판단할 수 없음)이면 `$PROJECT/docs/failures.md`에 원장 항목(원인: 스펙-모호 등)을 추가한다.
- 적용·보류와 별개로, 지적 중 **이번 작업에 국한되지 않고 다음 impl에서도 반복될 교훈**(예: 이 코드베이스 특유의 함정, 반복된 구현 습관)이 있으면 원장에 원인 분류에 맞춰 기록한다 — 다음 impl이 시작할 때 읽는 것은 개별 impl-review.md가 아니라 원장이다.

### 5단계: impl-review.md 작성

`$DIR/impl-review.md`에 기록한다. 최상단 프론트매터:

```yaml
---
reviewed: YYYY-MM-DD
applied: {적용 건수}
deferred: {보류 건수}
---
```

본문은 아래 4개 섹션만 포함한다:

1. **요약** — 무엇을 검토했고 코드가 어떻게 달라졌는지 한 문단.
2. **검증** — 적용 전/후 테스트 결과 (`전 {통과}/{전체} / 후 {통과}/{전체}`)와 실행 명령.
3. **적용한 변경** — 각 항목: 분류, 관련 정책 ID, 무엇을 왜 바꿨는지, 근거 파일 경로.
4. **보류한 지적** — 적용하지 않은 지적과 그 사유(재현 실패 / 동작 변경 위험 / 판단 필요). 사람이 결정할 것이 있으면 여기서 드러난다. 없으면 "없음".

### 6단계: 멈춤

사용자에게 다음을 보고하고 종료한다:

- 적용 N건 / 보류 M건, impl-review.md 경로
- 테스트 최종 결과 (전부 통과해야 정상 종료다)
- 보류 중 사람 판단이 필요한 항목이 있으면 그 목록
