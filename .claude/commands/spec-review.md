name: spec-review
description: 지정한 폴더의 spec.md를 새 컨텍스트의 서브에이전트로 검토합니다. 기존 정책(ID 인용)과의 충돌, 각 정책(P-작업번호-순번)의 견고성을 검사해 같은 폴더의 spec-review.md에 PASS/FAIL 판정을 남깁니다. spec.md를 수정하지 않습니다.
---

`$ARGUMENTS` 폴더의 `spec.md`를 검토하고 같은 폴더에 `spec-review.md`를 작성한다.

## 원칙

- **작성자와 검토자를 분리한다.** 검토는 반드시 새 컨텍스트의 서브에이전트가 수행한다. 이 세션에서 spec을 작성했더라도, 현재 컨텍스트에서 직접 검토하지 않는다.
- **spec.md를 수정하지 않는다.** 지적사항은 spec-review.md에만 기록한다. 반영 여부는 사람이 결정한다.
- **근거 없는 지적을 하지 않는다.** 충돌 지적에는 반드시 근거 파일 경로가 있어야 한다.

## 실행 순서

### 1단계: spec.md 확인

`$ARGUMENTS/spec.md`를 읽는다.

- 파일이 없으면 "해당 폴더에 spec.md가 없습니다. 먼저 /spec으로 작성하세요."라고 출력하고 종료한다.
- 프론트매터가 `status: approved`이면 "이미 승인된 spec입니다. 검토가 필요하면 status를 draft로 되돌린 뒤 다시 실행하세요."라고 출력하고 종료한다.

### 2단계: 검토 대상 소스 수집

서브에이전트에게 넘길 **파일 경로 목록**을 만든다. 내용은 여기서 읽지 않는다 (검토자가 직접 읽는다).

`$ARGUMENTS`가 `<프로젝트>/tasks/NNN-작업명` 형태라는 전제에서:

1. **기존 정책**: 같은 프로젝트의 다른 작업 폴더(`<프로젝트>/tasks/*/spec.md`) 중 `status: approved`인 것 전부. 프론트매터 확인을 위해 status 줄만 확인한다.
2. **설계 문서**: `<프로젝트>/docs/design/` 아래 문서 전부 (있는 경우).
3. **코드**: `<프로젝트>/src/` 경로 (있는 경우 — 경로만 알려주고 탐색은 검토자에게 맡긴다).
4. **실패 원장**: `<프로젝트>/docs/failures.md` (있는 경우).

### 3단계: 서브에이전트 검토 실행

general-purpose 서브에이전트를 **동기로(run_in_background: false)** 하나 띄운다. 프롬프트는 아래 템플릿을 그대로 쓰되 `{...}` 부분만 채운다:

```
너는 스펙 검토자다. {spec.md 절대 경로}를 읽고 아래 두 검사를 수행하라.
이 spec은 네가 쓴 것이 아니다. 통과시키는 것이 목적이 아니라 구멍을 찾는 것이 목적이다.

## 검사 A: 기존 정책 충돌
다음 소스를 읽고, 신규 spec의 정책·요약과 모순되거나 중복되는 규칙이 있는지 조사하라:
- 승인된 기존 spec: {경로 목록}
- 설계 문서: {경로 목록}
- 코드: {src 경로} (신규 정책과 관련된 부분만 검색해서 확인)
- 실패 원장: {failures.md 경로 또는 "없음"}
충돌 지적에는 반드시 근거 파일 경로와 해당 문장/코드를 인용하고, 기존 spec의 정책은 정책 ID(P-…)로 인용하라. 추측으로 지적하지 마라.
실패 원장이 있으면 먼저 읽고, `원인` 분류 중 2회 이상 반복된 유형이 있으면 신규 spec이 같은 유형의 결함을 갖는지 집중 검사하라 (예: `숨은-의존` 반복 → 정책 간 의존 관계를 우선 확인, `스펙-모호` 반복 → 규칙의 해석 여지를 우선 확인).

## 검사 B: 정책 견고성
먼저 형식을 검사하라: 모든 정책이 `P-{작업번호}-{순번}` 형식의 ID를 갖고, ID가 폴더의 작업 번호와 일치하며, 프로젝트 내 다른 spec의 ID와 중복되지 않는가.

그다음 정책 각 항목(ID로 지칭)에 대해 채점하라:
1. 검증 가능 — 참/거짓을 판별할 수 있는 규칙인가? 테스트 하나로 옮길 수 있는가?
2. 원자적 — 규칙 하나만 담고 있는가? "그리고/또한"으로 묶인 복합 규칙이 아닌가?
3. 비중복 — 다른 정책(기존 승인 spec 포함)과 겹치거나 포함 관계가 아닌가?
4. 미결정 존중 — spec 본문의 `결정 필요(미결정)` 사항을 정책이 특정 선택지로 몰래 확정하지 않았는가?
5. 예시 정합 — 정책의 예시가 규칙과 실제로 일치하는가? 숫자가 있으면 검산하라.

그다음 **반례 시나리오 3개**를 만들어라: 모든 정책을 만족하면서도 사용자 의도를 배반할 수 있는 구현 시나리오, 또는 spec이 답을 주지 못하는 입력 상황. 각 시나리오에 대해 spec이 답을 주는지 판정하라.

## 판정 기준
다음 중 하나라도 해당하면 FAIL, 아니면 PASS:
- 기존 정책과의 모순이 하나라도 발견됨
- ID 형식 위반 또는 ID 중복이 있음
- 검증 불가능한 정책이 있음
- 반례 시나리오 중 spec이 답을 주지 못하는 것이 있음
중복·복합 규칙·예시 불일치 등 그 외 지적은 판정을 바꾸지 않는 개선 제안으로 분류하라.

## 출력
판정(PASS/FAIL), 검사 A 결과, 검사 B의 정책 ID별 채점표(O/X만 기입), 반례 시나리오 3개와 각 판정,
지적사항 목록(각각 "차단"/"개선" 분류, 관련 정책 ID 명시)을 마크다운으로 반환하라. 파일은 쓰지 마라.
```

### 4단계: spec-review.md 작성

서브에이전트가 반환한 검토 결과를 `$ARGUMENTS/spec-review.md`에 기록한다. 최상단 프론트매터:

```yaml
---
verdict: PASS 또는 FAIL
reviewed: YYYY-MM-DD
---
```

본문은 아래 4개 섹션만 포함한다:

1. **판정 요약** — 판정과 그 이유를 한 문단으로.
2. **정책 충돌 검사** — 검사 A 결과. 기존 정책은 ID(P-…)로 인용한다. 충돌이 없으면 "없음"과 함께 무엇을 확인했는지(읽은 소스 목록) 명시한다.
3. **정책 검수** — 정책 ID별 채점표(O/X)와 반례 시나리오 3개 및 각 판정.
4. **지적사항** — `차단`(FAIL 사유, 승인 전 반드시 해소)과 `개선`(권고)으로 나눈 목록. 각 항목에 관련 정책 ID를 명시한다. 없으면 "없음".

### 5단계: 멈춤

`spec-review.md` 작성을 완료하면 멈춘다. **spec.md를 수정하지 않는다.** 사용자에게 다음을 보고하고 종료한다:

- 판정(PASS/FAIL)과 차단 지적사항 개수, spec-review.md 경로
- **FAIL인 경우**: 차단 지적사항 목록 — "spec.md를 수정한 뒤 /spec-review를 다시 실행하세요."
- **PASS인 경우**: "검토를 통과했습니다. 개선 제안을 확인하고, 이상 없으면 spec.md의 `status`를 `approved`로 바꿔주세요. 승인 후 `/test`로 진행합니다."
