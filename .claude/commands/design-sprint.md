# design-sprint

도메인 설계 파이프라인 오케스트레이터. PRD 작성부터 설계 문서까지 서브 에이전트를 순서대로 실행하며, 3개의 사람 검수 게이트를 거쳐 산출물을 완성한다.

## 실행 방법

```
/design-sprint <프로젝트 폴더> [기능 아이디어]
```

예시: `/design-sprint sandbox/subscription-tracker` (기존 prd.md 재사용)
예시: `/design-sprint sandbox/pomodoro 작업별 포모도로 세션을 기록하는 앱`

산출물은 `<프로젝트 폴더>/docs/design/`에 저장된다.

---

## 오케스트레이터 지침

아래 단계를 순서대로 실행한다. 각 단계의 산출물은 반드시 지정된 파일에 저장한다.

### 준비: 워크스페이스 초기화

1. `$PROJECT`를 첫 번째 인수(프로젝트 폴더)로 정한다. 인수가 없으면 `sandbox/` 아래 디렉토리를 나열해 `AskUserQuestion`으로 선택받는다. 나머지 인수는 기능 아이디어(선택)다
2. `$DESIGN` = `$PROJECT/docs/design/` 디렉토리를 생성한다
3. `$DESIGN/prd.md`도 없고 기능 아이디어 인수도 없으면, `$PROJECT/README.md`에서 아이디어를 추출하거나 사용자에게 묻는다
4. 아래 흐름을 시작한다고 사용자에게 알린다

### Step 1 — PRD 초안 생성 [Auto]

**인터뷰 산출물 재사용:** `$DESIGN/prd.md`가 이미 존재하면
(`/interview` 스킬 산출물) Step 1을 건너뛰고 Gate 1로 간다. 이 경우 Gate 1은
핵심 행위가 이미 인터뷰로 검증되었으므로 가벼운 최종 확인만 받는다.

Agent tool을 사용해 서브 에이전트를 실행한다.

**서브 에이전트 프롬프트:**
```
다음 기능 아이디어를 바탕으로 PRD를 작성해라.

기능: {사용자 입력}

아래 형식을 반드시 준수한다:

## [PRD] {기능명}

### 배경
(이 기능이 왜 필요한가)

### 목표
(이 기능으로 달성하려는 것)

### 사용자 / 이해관계자
(누가 이 기능을 사용하는가)

### 핵심 행위
(동사 중심으로 작성. 형식: "Actor가 Command를 실행한다")
- ...

### 제약 / 비기능 요구사항
- ...

### 성공 지표
- ...

### 미결 질문
- ...
```

서브 에이전트 출력을 `$DESIGN/prd.md`에 저장한다.

### 🧑 Gate 1 — 핵심 행위 승인

`$DESIGN/prd.md`의 **"핵심 행위" 섹션만** 사용자에게 보여준다.

사용자에게 다음을 묻는다:
> "핵심 행위가 실제 비즈니스 작동 방식과 맞는지 확인해주세요.
> 수정할 부분이 있으면 알려주시고, 없으면 '계속'이라고 말씀해주세요."

- 수정 요청이 있으면 → prd.md에 반영하고 핵심 행위 섹션을 다시 보여준다
- '계속' 또는 승인 시 → Step 2로 진행한다

### 🧑 Gate 2 — Aggregate 경계 승인  ← ROI 최고

`$DESIGN/domain-model.md`의 **Aggregate 섹션만** 사용자에게 보여준다.

사용자에게 다음을 묻는다:
> "Aggregate 경계가 팀 구조, 배포 단위, 트랜잭션 요건과 맞는지 확인해주세요.
> 이 경계는 나중에 바꾸는 비용이 크므로 신중하게 검토 부탁드립니다.
> 수정할 부분이 있으면 알려주시고, 없으면 '계속'이라고 말씀해주세요."

- 수정 요청이 있으면 → domain-model.md에 반영하고 Aggregate 섹션을 다시 보여준다
  - 반영 후, 그 수정이 `docs/design-principles.md`의 기존 기준(A1~B4)으로 설명되는지 확인한다.
    설명되지 않으면 새 기준 추가 또는 기존 기준 수정을 사용자에게 제안한다
    (기준 없이 반복되는 수정은 기준 문서의 버그다)
- '계속' 또는 승인 시 → Step 4로 진행한다
