# interview

모호한 기능 아이디어를 인터뷰로 구체화해 PRD를 산출한다.
design-sprint의 Step 1(PRD 초안 생성) + Gate 1(핵심 행위 승인)을 대체하는 입력 장치다:
AI가 지어낸 PRD를 사람이 검수하는 대신, 사람에게 물어서 얻은 사실로 PRD를 만든다.

방법론: 메타인지 확인(0층) + 3층 깔때기 — Why(Impact Mapping) → What(스토리 워크스루) → Rule(Example Mapping).
Rule 층의 질문은 설계 판단 기준 문서(docs/design-principles.md)에서 도출한다.
질문을 시작하기 전에 모호함 유형을 진단해 질문 예산을 배분한다.

## 실행 방법

```
/interview <프로젝트 폴더> <기능 아이디어>
```

예시: `/interview sandbox/subscription-tracker 구독 서비스를 등록하고 갱신일과 지출을 관리하는 CLI`

산출물은 `<프로젝트 폴더>/docs/design/`에 저장된다.

---

## 인터뷰어 지침

### 원칙 (모든 층에 적용)

1. **한 번에 질문 하나.** AskUserQuestion 도구로 객관식을 제시한다.
   "모르겠음 / 나중에 결정" 선택지를 항상 포함한다.
2. **열린 질문 대신 가설 제시형.** AI가 그럴듯한 답을 추측해 선택지로 내민다.
   틀린 추측이 진짜 답을 끌어낸다 ("둘 다 아니고 사실은…").
   유일한 예외는 2층의 시나리오 질문 — 이야기는 열린 형식으로 받는 게 낫다.
3. **과거 행동을 묻는다 (Mom Test).** 의견·미래 가정 질문은 듣기 좋은 거짓말을 유도한다.
   - ❌ "알림 기능 쓰실 건가요?" / "이 기능 유용할까요?"
   - ✅ "지난달에 갱신일을 놓친 적이 있나요? 그때 어떻게 됐나요?"
   - 과거 사례가 없는 주제(신규 기능의 규칙 등)는 가설 제시형으로 대체한다
4. **질문 예산: 총 12개.** 사용자가 "그만"이라고 하면 어느 층에 있든 즉시 종료 단계로 간다.
5. **질문은 사람만 아는 것에만 쓴다.** 빈칸을 3종류로 분류한다:
   - 사용자 머릿속에만 있는 것 (문제, 성공 기준, 비즈니스 규칙) → 묻는다
   - 아무도 아직 모르는 것 → 한 번 묻고 "모르겠음"이면 Questions에 기록, 파고들지 않는다
   - AI가 정해도 되는 것 (기술 선택, 형식, 관례적 기본값) → 묻지 않고 기본값을 정한 뒤 산출물에 `(기본값)` 표기
   - **How(기술·구현 방식)는 인터뷰 대상이 아니다.** 이 인터뷰는 Why와 What의 모호함만 다룬다.
     구현 구조는 design-sprint 이후의 몫이다
6. **이미 말한 것은 다시 묻지 않는다.** 시작 시 사용자 입력에서 확정 가능한 사실을 먼저 채운다.
7. **답변 즉시 반영.** 모든 답변은 interview.md에 바로 기록하고,
   층이 끝날 때마다 채워진 내용을 요약해 보여준 뒤 다음 층으로 내려간다.
8. **판정 가능성 테스트.** PRD에 적는 모든 문장은
   "제3자가 지켜졌는지/아닌지 판정할 수 있는가"를 통과해야 한다.
   통과하지 못하는 문장(예: "편리하게 주문할 수 있다")은 구체화 질문을 하거나 Questions로 보낸다.

### 준비

1. `$PROJECT`를 첫 번째 인수(프로젝트 폴더)로 정한다. 폴더 인수가 없으면 `sandbox/` 아래 디렉토리를 나열해 `AskUserQuestion`으로 선택받는다. 나머지 인수가 기능 아이디어다
2. `$DESIGN` = `$PROJECT/docs/design/` 디렉토리를 생성한다. `$DESIGN/interview.md`가 이미 있으면 읽고, "진행 상태"에 기록된 지점부터 이어서 진행한다 (새로 시작하지 않는다)
3. `$DESIGN/interview.md` 골격을 생성한다 (아래 산출물 형식 참조). Story에 사용자 입력 원문을 기록한다
4. `docs/design-principles.md`를 읽는다 (자동 주입되지 않았다면 직접 읽는다) — 3층 질문 도출에 쓴다
5. 사용자 입력에서 이미 답이 된 빈칸을 채우고, 남은 빈칸으로 질문 어젠다를 만든다
6. **모호함 유형 진단 (질문 소비 없음):** 남은 빈칸이 어느 층에 몰려 있는지 판단해
   질문 예산을 배분한다.
   - 문제·성공이 불분명 → 1층에 예산 집중
   - 문제는 명확한데 행위·범위가 불분명 → 2층에 집중
   - 행위는 명확한데 규칙·엣지가 불분명 → 3층에 집중
   - 진단 결과를 interview.md 상단에 한 줄로 기록한다 (예: "모호함 집중: Rule 층 — 행위는 입력에 명시됨")

---

### 0층 — 메타인지: 추측 목록 확인 (질문 1개)

목표: AI가 지금 추측으로 메꾸려는 가정을 **사용자 눈에 보이게** 꺼내고, 한 번에 검증한다.
가정 하나당 질문 하나를 쓰면 예산이 바닥나므로, 목록으로 묶어 1개 질문으로 처리한다.

1. 입력과 컨텍스트에서 AI가 세운 가정을 6~8개 목록으로 제시한다
   (예: "본인 혼자 쓴다 / 통화는 KRW / 월간 구독만 다룬다 / 알림은 CLI 실행 시점에만 가능하다")
2. 복수 선택으로 묻는다: **"이 중 틀린 것을 골라주세요"** (전부 맞으면 "전부 맞음" 선택지)
3. 틀린 가정 → 즉시 정정 질문 1개를 이어서 하거나, 복잡하면 해당 층 어젠다에 추가
4. 맞은 가정 → Rules에 `출처: 가정 확인`으로 기록. 더 이상 묻지 않는다

이 단계의 효과: 이후 층에서 확인된 가정 위에서 질문할 수 있고,
사용자도 "내가 뭘 안 정했는지"를 목록으로 보게 된다 (메타인지).

---

### 1층 — Why: 문제와 성공 (질문 2~3개)

목표: PRD의 배경·목표·사용자·성공 지표를 **사용자 입에서 나온 사실**로 채운다.
기능 아이디어는 대부분 해결책의 모습으로 오므로, 한 층 파서 문제를 꺼낸다.

질문 소재:
- 문제: "이 기능이 없으면 지금 무슨 일이 일어나나요? 지금은 어떻게 하고 있나요?"
- 사용자: 액터 후보를 추측해 객관식으로 (예: "B2C 쇼핑몰 고객 / 사내 발주 담당자 / 본인용")
- 성공: "3개월 뒤 성공했다고 말하려면 뭐가 보여야 하나요?"
  (사이드 프로젝트면: "뭐가 되면 만족하고 멈출 건가요?")

**층 종료 확인:** 배경·목표 요약을 보여주고 확인받는다.
여기가 틀리면 아래층 답이 전부 무효이므로 반드시 확인 후 진행한다.

---

### 2층 — What: 시나리오 워크스루 (질문 2~4개)

목표: 핵심 행위(Actor-Command)와 범위 경계를 확정한다.

1. 행위 목록을 직접 묻지 말고 **이야기를 시킨다** (열린 질문 허용 지점):
   > "사용자 한 명이 이 기능을 처음부터 끝까지 쓰는 장면을 이야기해주세요.
   > 어디서 시작해서 뭘로 끝나나요?"
2. 이야기에서 Actor-Command 쌍("Actor가 Command를 실행한다")을 추출해 목록으로 확인받는다.
   이야기에 없지만 있을 법한 행위는 추측해 포함 여부를 묻는다
3. **범위 협상:** 인접 기능을 추측해 명시적으로 밀어낸다
   (예: "결제도 포함인가요? 재고 관리는요?") → **"안 한다" 목록**을 만든다.
   범위의 음영이 명시돼야 하위 단계의 추측이 막힌다
4. **숨겨진 제약 발굴:** 사용자가 말하지 않았지만 설계를 뒤집을 수 있는 제약을 찌른다.
   기능이 아니라 **조건**을 묻는 것이다:
   - 시간: "언제까지 써야 하나요? 1~2주 안에 끝나야 하는 이유가 있나요?"
   - 환경: "어디서 실행되나요? 오프라인에서도 돼야 하나요?"
   - 우선순위: "행위들 중 하나만 남긴다면 뭘 남기나요?"
   - 데이터: "기존에 관리하던 데이터(스프레드시트 등)를 가져와야 하나요?"
   해당 없어 보이는 항목은 묻지 않는다 — 이 목록은 체크리스트지 설문지가 아니다

**층 종료 확인:** 핵심 행위 목록 + "안 한다" 목록 + 발굴된 제약을 보여주고 확인받는다.

---

### 3층 — Rule: 행위별 규칙과 경계 (질문 3~5개, Example Mapping)

목표: 핵심 행위마다 규칙(Rule)과 구체 예시(Example)를 확보하고, 모르는 것은 Question으로 남긴다.
이 층의 답이 design-sprint Step 3에서 Aggregate 경계 판단(A1~B4)의 원재료가 된다.

질문은 설계 판단 기준에서 도출한다:
- **A1 탐침 (불변식):** "X와 Y가 항상 함께 만족해야 하는 규칙이 있나요?"
  (예: "주문 총액은 항목 합계와 항상 일치해야 하나요?")
- **A4 탐침 (동시 수정):** "이걸 누가 수정하나요? 서로 다른 주체가 동시에 건드릴 수 있나요?"
- **A5 탐침 (일관성 허용치):** "이 값이 1분 늦게 갱신돼도 비즈니스가 괜찮나요?"
- **B1 탐침 (용어):** "이 단어가 맥락마다 같은 뜻인가요? 정의를 두 문장으로 써야 하나요?"

진행 규칙:
- 규칙 가설을 객관식으로 제시한다
  (예: "담아둔 사이 가격이 바뀌면? A) 담을 때 가격 B) 주문 시점 가격 C) 모르겠음")
- 확정된 규칙마다 **숫자·날짜가 든 구체 예시 1개**를 제안해 확인받는다
  (예: "3/1에 월 구독 결제, 3/15에 해지 → 3/31까지 활성. 맞나요?")
- 경계 사례를 찌른다: 실패하면? 중간에 그만두면? 이미 있으면? 동시에 하면?
- "모르겠음" 응답 → Questions에 기록하고 즉시 다음 질문으로. 파고들지 않는다

---

### 수렴 — 종료 판정과 산출

**종료 조건** (하나라도 충족 시):
- 정상 종료: 모든 PRD 섹션에 사용자 발 사실 ≥ 1개, 그리고 모든 핵심 행위에 규칙 또는 예시 ≥ 1개
- 예산 소진: 질문 12개 사용
- 사용자 중단: "그만"

**수렴 확인 (readback):** 산출물을 쓰기 전에, 확정된 사실 전체를
"문제 → 행위 → 규칙 → 미결" 순서로 한 화면에 요약해 보여주고 마지막 확인을 받는다.
층별 확인은 부분 검증이고, 이것은 전체 정합성 검증이다 —
1층 답과 3층 답이 모순되면 여기서 드러난다 (예: "지출 파악이 목적"이라더니 금액 규칙이 전부 미결).
모순이 보이면 산출 전에 정정 질문 1개를 쓸 수 있다 (예산 외 허용).

**산출물 2개**를 저장한다:

1. `$DESIGN/interview.md` — 인터뷰 원자료:

```
# Interview: {기능명}

## Story
(사용자 입력 원문과 1층에서 확정된 문제 정의)

## Rules
(확정된 비즈니스 규칙. 각 규칙에 출처 표기: 사용자 답변 / 기본값)
- ...

## Examples
(규칙을 검증하는 구체 사례. 숫자·날짜 포함)
- ...

## Questions
(답을 얻지 못한 것. 어느 층/어느 탐침(A1 등)에서 나왔는지 표기)
- ...

## 안 한다 (Out of Scope)
- ...
```

2. `$DESIGN/prd.md` — design-sprint Step 1과 동일한 형식:

```
## [PRD] {기능명}

### 배경
(이 기능이 왜 필요한가)

### 목표
(이 기능으로 달성하려는 것)

### 사용자 / 이해관계자
(누가 이 기능을 사용하는가)

### 핵심 행위
(동사 중심. 형식: "Actor가 Command를 실행한다". 각 행위 아래 관련 규칙·예시를 부기)
- ...

### 제약 / 비기능 요구사항
(Rules + "안 한다" 목록 반영. AI가 정한 기본값은 "(기본값)" 표기)
- ...

### 성공 지표
- ...

### 미결 질문
(interview.md의 Questions 전체)
- ...
```

prd.md 작성 규칙:
- **사용자 답변에서 나온 사실만 쓴다.** 답을 얻지 못한 빈칸은 지어내지 말고 미결 질문에 남긴다
- AI가 정한 기본값은 반드시 `(기본값)` 표기로 구분한다
- 모든 문장에 판정 가능성 테스트를 적용한다

**종료 리포트:**
> "인터뷰 완료: 질문 {N}개 사용, 규칙 {R}개, 예시 {E}개, 미결 질문 {Q}개.
> 산출물: `$DESIGN/interview.md`, `prd.md`
> 다음 단계: `/design-sprint $PROJECT` 실행 시 이 prd.md를 재사용합니다."

- Q ≥ R이면 경고를 덧붙인다:
  > "미결 질문이 규칙만큼 많습니다. 설계 스프린트 전에 미결 질문을 먼저 줄이는 것을 권합니다."
