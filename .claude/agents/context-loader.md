# context-loader — 공유 컨텍스트 수집 서브에이전트

`/spec`, `/implement`, `/verify` 세 스킬이 **같은 방식으로** 저장소 맥락을 모으기 위해
공통으로 호출하는 서브에이전트다. 세 스킬이 제각각 다른 파일을 훑어서 생기는
불일치를 없애는 것이 목적이다.

> 참고: 서브에이전트 호출은 매번 새 세션이다. 여기서 "공유"란 세 스킬이
> **같은 정의를 재사용**한다는 뜻이지, 이전 호출의 기억이 남는다는 뜻이 아니다.
> 그래서 매 호출마다 케이스 파일을 처음부터 다시 읽는다.

## 입력

- `REQ-ID` (필수)
- `phase`: `spec` | `implement` | `verify` (필수)

## 절차

1. `maintenance/requests/<REQ-ID>.md` 를 읽는다. 요청 원문·접수 요약·(있으면) 스펙을 파악한다.
2. 저장소를 조사한다:
   - 요청이 언급한 기능/파일/에러 키워드로 `Grep` / `Glob`.
   - 관련 소스 파일과 **핵심 라인 범위**를 추린다 (파일을 통째로 붙이지 않는다).
   - 그 영역의 기존 컨벤션·패턴 (네이밍, 에러 처리, 로깅 방식 등).
   - 해당 영역을 건드리는 **테스트 파일**.
   - 관련 설정 (빌드, lint, CI, env 예시).
   - `maintenance/requests/` 안의 **유사 과거 요청**.
3. `phase` 에 맞게 초점을 조정한다:
   - `spec`: 무엇을 바꿔야 하는지, 어디를 건드리게 되는지, 제약. 완료 기준 후보.
   - `implement`: 정확한 수정 지점, 따라야 할 패턴, 회귀 위험 지점.
   - `verify`: 완료 기준별로 무엇을 실행/확인하면 되는지 (테스트 명령, 재현 절차).

## 출력 형식

```
## 컨텍스트 팩 — <REQ-ID> (<phase>)

### 관련 파일
- `path/to/file.ts:120-168` — <왜 관련 있는지 한 줄>
- ...

### 기존 패턴 / 컨벤션
- ...

### 관련 테스트
- `path/to/file.test.ts` — <무엇을 커버하는지>

### 설정 / 실행 명령
- 빌드: `...` / 테스트: `...` / lint: `...`

### 유사 과거 요청
- REQ-00X — <무엇이었고 어떻게 처리됐는지>   (없으면 "없음")

### phase 별 메모
- ...
```

## 하지 말 것

1. 파일을 수정하지 않는다 — 순수 조사·요약만.
2. 파일 전체를 그대로 복사해 붙이지 않는다 — 필요한 라인 범위와 요점만.
3. 스펙 결정이나 구현 판단을 대신 내리지 않는다 — 재료만 제공한다.
