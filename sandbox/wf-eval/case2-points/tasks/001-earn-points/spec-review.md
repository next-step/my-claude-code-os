## 요약

general-purpose 서브에이전트에게 `spec.md`를 새 컨텍스트에서 검토시켰다. 이 프로젝트는 `001-earn-points`가 최초 작업이라 기존 정책 충돌은 없었으나, 정책 견고성 검사에서 차단 3건(버림 연산을 적용하는 시점 미정의, 정의되지 않은 등급 값에 대한 무답, 쿠폰 이외 결제수단이 섞인 경우의 기준 금액 범위 무답)과 개선 4건이 나왔다. 차단 3건은 모두 spec.md에 새 기본값과 정책(P-001-8 신설)으로 반영했고, 개선 중 저위험 2건(용어 정의 선지정, 함수 입력 파라미터 명시)을 적용했다. 정책 개수가 8개(P-001-1~8)에 이르러 "8개 초과 시 범위 분리 검토" 기준에 근접했으므로, 나머지 개선 2건(P-001-4 분리, 등급 정책 통합)은 정책 개수를 더 늘리지 않기 위해 보류했다.

### 반례 시나리오 3개

1. **연산 순서 미정의(필수 항목)** — 실버 회원, 결제 1,060원, 이벤트 기간. 등급율 단계에서 먼저 버림(`floor(1060×0.01)=10`, `×2=20`)과 최종값 1회 버림(`floor(1060×0.02)=21`)이 둘 다 조문을 만족하지만 결과가 다르다. **판정: spec 무답 → 차단.**
2. **정의되지 않은 회원 등급** — 등급 값이 "브론즈"이거나 등급 정보가 없는 결제. P-001-1~3은 실버/골드/VIP만 다룬다. **판정: spec 무답 → 차단.**
3. **쿠폰 이외 결제수단 혼합** — 정가 30,000원을 카드 25,000원 + 보유 포인트 5,000원으로 결제(쿠폰 아님). P-001-4는 쿠폰 케이스만 정의한다. **판정: spec 무답 → 차단.**

## 반영 내역

**적용 (차단 해소)**
- [P-001-1, P-001-2, P-001-3, P-001-5] 버림 적용 시점 미정의(반례 1) — `## 정책` 섹션 도입부에 `포인트 = floor(결제 금액 × 등급 기본율 × 이벤트 배수)`라는 단일 수식을 명시하고, 등급율·이벤트 배수 각 단계에서 개별 버림하지 않음을 못박았다. P-001-5 예시에 1,060원 소수 발생 사례를 추가해 최종 1회 버림 규칙을 검증 가능하게 했다. 정책 충돌 섹션 항목 2도 이 수식과 근거로 재작성했다.
- [P-001-8 신설] 정의되지 않은 등급 무답(반례 2) — 등급이 실버/골드/VIP가 아니면 예외를 발생시키는 정책을 신설했다. 정책 충돌 섹션에 선택지 A(예외)/B(0포인트)/C(최저등급 취급)를 제시하고 A를 기본값으로 채택한 근거(등급 오기입을 조용히 은폐하지 않기 위함)를 기록했다.
- [P-001-4] 쿠폰 이외 결제수단 혼합 시 기준 금액 무답(반례 3) — 정책 충돌 섹션에 항목 4를 추가해 "본 spec은 쿠폰 할인만 다루며 포인트 사용 등 다른 결제수단 조정은 범위 밖"이라고 명시적으로 배제했고, `## 정책` 도입부와 변경 범위 섹션에도 이 정의를 반영했다.

**확정 (기본값)**
- 없음으로 집계. 위 3건의 차단 해소가 실질적으로는 새 기본값(버림 1회 적용 시점, 등급 예외 처리, 결제수단 범위 제한)을 확정하는 형태였지만, 서브에이전트가 별도 "결정 대기" 항목을 찾지 못했다고 명시했으므로(spec.md에 `결정 필요(미결정)` 표식 없음) 이 절의 "확정" 건수에는 포함하지 않고 위 "적용" 항목에 함께 기록했다.

**보류**
- [P-001-4] 복합 규칙 분리 개선 — "적립 대상 포함 여부"와 "기준 금액 정의"를 별도 정책 ID로 분리하는 개선을 제안받았으나, 분리하면 정책이 9개가 되어 spec-review 자체 기준("8개 초과 시 범위 분리 검토")에 걸린다. 두 문장을 명확히 구분해 표기하는 것으로 대체하고 ID 분리는 보류했다. 사유: 정책 개수 상한 근접.
- [일반] 정책 개수 여유 부족(등급별 정책 P-001-1~3을 표 기반 단일 정책으로 통합하는 리팩터링 제안) — 개수를 8개로 유지하는 현재로선 시급하지 않아 보류했다. 사유: 판단 필요(향후 정책 추가 시 재검토 권장).
- 용어 정의 순서(정책 목록 앞에 "결제 금액" 정의 선배치)와 함수 입력 파라미터 스키마 명시(변경 범위에 등급/결제금액/이벤트여부 명시)는 동작을 바꾸지 않는 명확한 개선으로 판단해 적용했다(위 "적용" 참조 대상은 아니지만 실제로 `## 정책` 도입부와 변경 범위 섹션에 반영됨).
