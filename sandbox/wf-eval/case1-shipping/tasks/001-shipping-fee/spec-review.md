## 요약

`spec.md`를 새 컨텍스트의 general-purpose 서브에이전트(검토자)로 1회 검토했다. 기존 정책·설계 문서·코드·실패 원장이 프로젝트에 전혀 없어 정책 충돌은 없었으나, 정책 견고성 검사에서 반례 시나리오 2건이 spec의 답을 얻지 못하는 것으로 드러났다: (1) `order`의 키 누락 시 동작이 서술로만 남아 검증 불가능했던 점, (2) `is_express`에 non-bool 값이 들어왔을 때 엄격 식별과 truthy 판정 중 무엇을 쓸지 P-001-5가 답을 주지 못했던 점. 두 건 모두 차단으로 분류해 각각 새 정책(P-001-8)과 P-001-5 규칙 문구 수정으로 해소했다. `subtotal` 타입 미검증에 대해서는 원래 선택했던 기본값(선택지 B)을 유지하되 "타입 위반 시 발생하는 예외는 정책 위반이 아니다"라는 문구를 추가해 범위를 명확히 했다. 정책 서술 중복 지적(P-001-3/4/5의 반복 문구)은 동작에 영향이 없는 순수 편집 사안이라 이번 회차에서는 보류했다.

**반례 시나리오 3개**

1. `subtotal=-1000, region="부산", is_express=False` (P-001-6·P-001-7 동시 발동) → spec이 답을 줌: 두 정책 모두 `ValueError` 발생만 요구하고 메시지는 검증 대상이 아니므로 검사 순서와 무관하게 결과가 동일.
2. `order`에 `is_express` 키 자체가 없는 경우 → **spec 무답** (검토 당시). `.get()`으로 조용히 기본값을 채우는 구현도 기존 정책을 전부 만족했다. → P-001-8 신설로 해소.
3. `is_express="False"` (문자열) → **spec 무답** (검토 당시). 엄격 식별(`is True`)과 truthy 판정이 서로 다른 결과(2,000원 부과 여부)를 낳는데 둘 다 기존 정책을 만족했다. → P-001-5 규칙 문구 수정으로 해소.

## 반영 내역

**적용**
- P-001-8 신설 (관련: 반례 2) — `order`에 `subtotal`/`region`/`is_express` 중 키가 없으면 조용히 기본값으로 치환하지 않고 `KeyError`가 그대로 전파되어야 한다는 규칙을 명문화. 서술로만 존재하던 "정책 충돌" 섹션 항목 1의 결정을 검증 가능한 정책으로 승격.
- P-001-5 규칙 문구 수정 (관련: 반례 3) — "`is_express`가 `True`이면" → "`is_express is True`(정확히 `bool` 타입의 `True`)이면 … `bool`이 아닌 값이 들어온 경우의 동작은 정의하지 않는다"로 명확화해 엄격 식별을 기본값으로 확정.

**확정**
- `subtotal` 타입 미검증 (관련: 정책 충돌 섹션 항목 2) — 기존 선택(선택지 B, 값 비교만 수행)을 유지하되 "타입 위반으로 파이썬이 자체적으로 발생시키는 예외(`TypeError` 등)는 정책 위반이 아니며 테스트 대상도 아니다"를 명문화. 근거: request가 타입 조건을 요구하지 않았고, 새 정책을 추가하면 오히려 request에 없는 요구를 만드는 것이 되어 범위를 벗어난다.

**보류**
- P-001-3/4/5의 "무료배송 여부와 무관하게 항상 부과된다" 문구 반복 축약 (개선 지적 4) — 동작에는 영향이 없는 순수 편집·구조 변경이며, 정책 3개를 동시에 손대는 리스크 대비 이득이 낮아 이번 회차에서는 보류. 필요 시 별도로 spec.md를 수정.
