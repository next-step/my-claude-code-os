## 요약

사용자별 API 호출 빈도를 제한하는 rate limiter를 추가한다. 사용자 식별자(`user_id`)와 요청 시각(`now`)을 받아 요청 허용 여부를 판정하는 `RateLimiter.allow(user_id, now)`를 제공하며, 고정 1분 윈도우 안에서 사용자당 최대 10회까지 요청을 허용하고 초과 요청은 거부한다. 거부된 사용자가 차단 기간 중에도 계속 요청하면 차단 시간이 늘어나는 페널티를 적용하고, 판정마다 구조화된 로그를 남긴다. "응답이 빨라야 한다"와 "운영자가 보기에 자연스럽다"는 요구는 그 자체로는 참/거짓 판별이 불가능하므로, 아래 정책 충돌 절에서 검증 가능한 대체 기준으로 치환한 결과만 정책에 반영한다.

## 정책 충돌

기존 코드/문서 조사 결과: 이 프로젝트(`sandbox/wf-eval/case5-ratelimit`)에는 `README.md`와 `request.md`만 존재하고 `src/`, `tests/`, 기존 `spec.md`가 전혀 없다(확인: 프로젝트 루트 및 하위 디렉터리 파일 목록에 다른 파일 없음). 따라서 기존 승인 정책과의 충돌은 **없음**.

다만 request.md 자체의 해석이 갈리는 지점이 여러 곳 있어 각각 기본값을 선택한다. 아래 쟁점 번호(A~I, G~I는 spec-review 반영분)는 정책 ID(P-001-N)와 다른 별도 목록이다 — 혼동 방지를 위해 알파벳으로 표기한다:

쟁점 A. **윈도우 방식(고정 vs 슬라이딩)** — "1분에 최대 10회"만 명시하고 윈도우가 고정 구간인지 이동 구간인지는 정의하지 않는다.
   - 선택지 A: 슬라이딩 윈도우(최근 60초 내 요청 타임스탬프를 모두 기록해 카운트). 더 정교하지만 사용자당 요청 이력을 무한정 보관해야 하고 구현·테스트가 복잡해진다.
   - 선택지 B (기본값): 고정 윈도우(첫 요청 시각 기준 60초 구간 동안 카운트, 60초 경과 시 카운트 리셋). 구현이 단순하고 메모리 사용이 O(1)이며 결정적 테스트가 쉽다.
   - 근거: request는 정밀한 이동 윈도우를 요구하지 않았고, 4번(응답 속도) 요구와 결합하면 상태를 적게 유지하는 고정 윈도우가 유리하다.

쟁점 B. **페널티(차단 시간 증가) 공식** — "패널티로 제한 시간이 늘어나야 한다"만 명시하고 증가폭·시작값을 정의하지 않는다.
   - 선택지 A: 선형 증가(매 위반마다 +60초).
   - 선택지 B (기본값): 지수 증가(첫 위반 시 차단 60초, 차단 중 재요청마다 차단 시간을 2배로 연장). 반복 남용에 대해 억제 효과가 빠르게 커지는 것이 "패널티"라는 표현의 취지에 더 부합한다.
   - 근거: request가 "계속 요청하면" 늘어난다고 했으므로 위반이 반복될수록 가중되는 지수 방식이 자연스러운 기본값이다. 근거 파일: `request.md` 2번째 항목.

쟁점 C. **"응답이 빨라야 한다"(성능 요구)** — 지연시간 수치(SLA)가 없어 참/거짓 판별이 불가능하다.
   - 선택지 A: 임의의 지연 시간 임계값(예: 1ms 이내)을 정하고 벤치마크 테스트로 검증한다. 실행 환경(CI 머신 성능)에 따라 결과가 흔들려 신뢰할 수 없는 테스트가 된다.
   - 선택지 B (기본값): 절대 시간 임계값 대신 **판정 로직이 외부 I/O·인위적 지연(sleep, 네트워크 호출, 파일 접근)을 포함하지 않고 인메모리 연산만으로 O(1)에 동작**하는 것을 대체 기준으로 삼는다. 이는 코드 검토와 "다량 호출이 즉시 반환되는지"를 확인하는 테스트로 검증 가능하다.
   - 근거: request의 "체감상 지연이 없어야" 한다는 표현은 절대 벤치마크가 아니라 "불필요한 블로킹이 없어야 한다"는 구조적 요구로 해석하는 것이 합리적이다.

쟁점 D. **"로그를 보기 좋게"(로그 형식)** — 가독성은 주관적이라 그 자체로는 검증 불가능하다.
   - 선택지 A: 사람이 읽기 좋은 자유 형식 문자열만 남긴다. 문구 검증이 어렵고 테스트가 불안정해진다.
   - 선택지 B (기본값): **구조화된 로그**를 남긴다 — 매 판정마다 `user_id`, `decision`("allow"/"deny"), `reason`, `request_count`, `now` 필드를 포함한 로그 레코드 1건을 표준 `logging` 모듈로 기록한다. `reason`은 `"within_limit"`(한도 이내 허용) / `"limit_exceeded"`(한도 초과로 신규 차단) / `"blocked"`(차단 중 재요청 거부) / `"window_reset"`(자연 윈도우 리셋 후 첫 허용) 중 하나로 고정한다. "보기 좋음"을 필드가 누락 없이 구조적으로 남는지로 치환해 테스트 가능하게 만든다.
   - 근거: 자유 형식 문구는 테스트로 고정할 수 없으므로, 필드 존재 여부와 고정된 `reason` 값 집합을 검증 가능한 대리 지표로 삼는다.

쟁점 E. **"운영자가 보기에 자연스러운 방식으로 동작"** — 위 정책들을 만족하는 것 이상의 추가 요구를 특정할 수 없다.
   - 선택지 A: 별도 정책을 신설해 모호한 기준(예: "동작이 직관적이어야 한다")을 그대로 옮긴다. 참/거짓 판별이 불가능해 테스트로 옮길 수 없다.
   - 선택지 B (기본값): 별도 정책을 만들지 않는다. P-001-1~7(윈도우, 초과 거부, 페널티, 차단 해제 리셋, 자연 리셋, 무지연, 구조화 로그)을 모두 만족하면 이 요구가 충족된 것으로 간주한다.
   - 근거: 검증 불가능한 요구를 그대로 정책화하면 "정책은 참/거짓 판별 가능한 규칙 하나"라는 제약을 어기게 된다.

쟁점 F. **`now`(현재 시각) 주입 방식** — request는 시간 처리 방식을 명시하지 않는다.
   - 선택지 A: `RateLimiter` 내부에서 `time.time()`을 직접 호출한다. 실사용에는 간편하지만 결정적 테스트(윈도우 경계, 차단 연장 시점)를 작성하기 어렵다.
   - 선택지 B (기본값): `allow(user_id, now)`가 호출자로부터 `now`(초 단위 float)를 인자로 받는다. 실사용 시 호출부에서 `time.time()`을 넘기면 되고, 테스트에서는 임의의 시각을 주입해 결정적으로 검증할 수 있다.
   - 근거: P-001-2·3(윈도우 리셋, 페널티 연장)은 시간 경계값 테스트가 필수적이므로 주입 가능한 구조가 필요하다.

### spec-review 반영 (차단 해소)

spec-review에서 아래 두 공백이 차단으로 지적되어 이 절에 기본값을 추가로 확정한다.

쟁점 G. **차단 이력 없이 자연 경과한 윈도우의 리셋** — P-001-4는 "차단 해제 후" 리셋만 다루고, 애초에 한 번도 차단되지 않은 사용자가 윈도우 시간(60초)만 자연히 경과시킨 뒤 재요청하는 경우를 다루지 않았다(spec-review 반례 시나리오 2).
   - 기본값: 차단 여부와 무관하게, 현재 윈도우 시작 시각으로부터 `window_seconds`가 지나면 다음 요청은 새 윈도우의 첫 요청으로 취급한다. → 신규 정책 P-001-7로 반영.

쟁점 H. **차단 사이클이 반복될 때 페널티 배수(차단 지속 시간) 리셋 여부** — 이전 차단이 이미 완전히 만료되고 사용자가 정상적으로 요청을 이어가다가 다시 한도를 초과한 경우, 새 차단이 이전 차단의 배가된 지속 시간(예: 120초)에서 이어지는지 기본값 60초로 새로 시작하는지 spec이 답하지 않았다(spec-review 반례 시나리오 1).
   - 기본값: 차단 지속 시간(페널티 배수) 상태는 P-001-2(신규 차단 시작)가 발동할 때마다 항상 `base_block_seconds`로 초기화된다. 배수 연장은 오직 같은 차단이 끝나지 않은 채 재요청되는 P-001-3 경로에서만 발생한다. → P-001-2에 반영.

쟁점 I. **차단 중 반복 거부 시 `request_count` 로그 값** — 차단 상태에서 짧은 간격으로 반복 요청하면 매 거부마다 `request_count`가 계속 증가하는지, 차단을 유발한 값에 고정되는지 정의되지 않았다(spec-review 반례 시나리오 3).
   - 기본값: 차단 중 거부(`reason="blocked"`)는 `request_count`를 증가시키지 않고, 차단을 유발한 시점의 값(예: 11)을 그대로 로그에 남긴다. → P-001-3·P-001-6에 반영.

## 정책

### P-001-1: 윈도우 내 허용 한도
- 규칙: 고정 1분 윈도우 안에서 사용자의 누적 요청 횟수가 10회 이하이면 요청이 허용된다.
- 예시: `limit=10, window_seconds=60`인 `RateLimiter`에 사용자 `"u1"`이 `now=0,1,2,...,9`(1초 간격, 10회)에 요청 → 매 호출 `allow("u1", now)`이 `True`를 반환한다(누적 카운트 1~10, 윈도우 시작 0초로 60초 미경과).

### P-001-2: 한도 초과 시 거부와 차단 시작 (기본값)
- 규칙: 같은 윈도우 안에서 11번째 이상 요청이 들어오면 그 요청은 거부되고, 그 시점부터 `base_block_seconds`(기본값 60초) 동안 해당 사용자는 차단 상태가 된다. 이때 사용자의 차단 지속 시간(페널티 배수) 상태는 이전 차단 이력과 무관하게 항상 `base_block_seconds`로 초기화된다(쟁점 H 기본값).
- 예시: 사용자 `"u1"`이 `now=0..9`에 10회 요청(모두 허용) 후 `now=10`에 11번째 요청 → `allow("u1", 10)`이 `False`를 반환하고, 내부 차단 종료 시각은 `10 + 60 = 70`, 차단 지속 시간은 `60`으로 설정된다.

### P-001-3: 차단 중 재요청 시 페널티 연장 (기본값)
- 규칙: 사용자가 차단 상태(현재 시각이 차단 종료 시각 이전)에서 다시 요청하면 그 요청은 거부되고, 차단 지속 시간이 이전 값의 2배로 늘어나 차단 종료 시각이 `요청 시각 + 새 지속 시간`으로 갱신된다. 이 거부는 `request_count`를 증가시키지 않으며, 차단을 유발한 시점의 `request_count` 값이 그대로 유지된다(쟁점 I 기본값).
- 예시: P-001-2 상태(차단 지속 시간 60초, 차단 종료 70초, `request_count=11`)에서 사용자 `"u1"`이 `now=15`에 요청 → `allow("u1", 15)`이 `False`를 반환하고, 새 지속 시간은 `60 * 2 = 120`초, 새 차단 종료 시각은 `15 + 120 = 135`가 되며 `request_count`는 `11`로 유지된다.

### P-001-4: 차단 해제 후 윈도우 리셋
- 규칙: 현재 시각이 차단 종료 시각 이상이 되어 차단이 풀리면, 그 이후 요청은 새 윈도우의 첫 요청으로 취급되어 카운트가 1부터 다시 시작하고 정상적으로 허용된다.
- 예시: P-001-3 상태(차단 종료 135)에서 사용자 `"u1"`이 `now=140`에 요청 → `allow("u1", 140)`이 `True`를 반환한다(140 ≥ 135이므로 차단 해제, 새 윈도우 시작, 카운트 1).

### P-001-5: 무지연 인메모리 판정 (기본값)
- 규칙: `allow()` 판정 로직은 `time.sleep` 등 인위적 지연이나 네트워크·파일 I/O를 호출하지 않고 인메모리 상태만으로 즉시 반환한다.
- 예시: 서로 다른 사용자 1,000명에 대해 `allow(f"user-{i}", 0)`를 순차 호출해도 각 호출은 블로킹 호출 없이 즉시 반환되어 전체 호출이 지연 없이 끝난다(코드에 `sleep`/네트워크/파일 호출이 없음을 코드 검사로 확인 가능).

### P-001-6: 구조화된 판정 로그 (기본값)
- 규칙: `allow()`가 호출될 때마다 `user_id`, `decision`("allow" 또는 "deny"), `reason`(`"within_limit"`/`"limit_exceeded"`/`"blocked"`/`"window_reset"` 중 하나), `request_count`, `now` 필드를 포함하는 로그 레코드가 정확히 1건 기록된다. 차단 중 거부(`reason="blocked"`)의 `request_count`는 P-001-3에 따라 차단을 유발한 시점 값에서 고정된다.
- 예시: 사용자 `"u1"`이 `now=0`에 첫 요청 → 로그 레코드 1건이 남고, 그 레코드는 `user_id="u1"`, `decision="allow"`, `reason="within_limit"`, `request_count=1`, `now=0` 정보를 포함한다.

### P-001-7: 차단 이력 없이 자연 경과한 윈도우의 리셋 (기본값)
- 규칙: 사용자가 차단 상태가 아닌 채로 현재 윈도우 시작 시각으로부터 `window_seconds`(기본값 60초)가 경과한 뒤 요청하면, 그 요청은 새 윈도우의 첫 요청으로 취급되어 카운트가 1부터 시작하고 허용된다.
- 예시: 사용자 `"u2"`가 `now=0,5,10,...,45`(1분 이내 10회, 모두 허용, 한도 미초과라 차단 없음) 이후 `now=65`에 요청 → `allow("u2", 65)`가 `True`를 반환한다(`65 - 0 = 65 ≥ 60`이므로 윈도우 리셋, 새 윈도우 카운트 1).
