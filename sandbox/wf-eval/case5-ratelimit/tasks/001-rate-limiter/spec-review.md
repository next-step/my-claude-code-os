## 요약

`spec.md`를 새 컨텍스트의 general-purpose 서브에이전트에게 검토자로 위임해, 기존 정책 충돌 여부와 정책 6개(P-001-1~6)의 견고성(형식·검증가능·원자성·비중복·예시정합)을 검사하고 반례 시나리오 3개를 만들도록 했다. 기존 승인 spec·설계 문서·코드·실패 원장이 프로젝트에 전혀 없어 충돌은 없었지만, 반례 시나리오를 통해 spec이 답하지 못하는 공백 3건(차단 이력 없는 자연 윈도우 리셋, 차단 재발 시 페널티 배수 리셋 여부, 차단 중 반복 거부의 `request_count` 값)이 차단으로 지적되었다. 이 세션이 세 건 모두를 기본값으로 확정해 반영했다: 신규 정책 `P-001-7`을 추가하고, `P-001-2`에 페널티 배수 초기화 규칙을, `P-001-3`·`P-001-6`에 `request_count` 고정 규칙을 추가했다. 개선 지적 중 `reason` 값 도메인 미정의와 예시 불완전은 즉시 반영했고, 정책 충돌 절의 번호(1~6)와 정책 ID(P-001-N)가 혼용되던 부분은 알파벳 쟁점 라벨(A~I)로 분리해 해소했다. 정책의 "판정/상태전이 분리" 리팩터링은 동작 변경 없이 하기엔 구조 개편 폭이 커서 보류했다. 정책은 6개에서 7개(P-001-1~7)로 늘었고, 상태를 `approved`로 승격했다.

### 반례 시나리오 3개와 판정

1. **차단 사이클 재발생 시 페널티 배수 리셋 여부** — 차단(60초)→연장(120초)→자연 리셋 후 정상 요청 10회→재차 한도 초과 시, 새 차단이 60초로 시작하는지 이전 배수(120)에서 이어가는지 spec이 답하지 않음. **판정: 무답 (차단)** → 쟁점 H로 해소.
2. **차단 없이 자연 경과한 윈도우** — 차단당한 적 없이 한도 이내로 요청하다가 60초가 지난 뒤 재요청하면 카운트가 리셋되는지 spec이 답하지 않음(P-001-4는 "차단 해제 후"만 규정). **판정: 무답 (차단)** → 쟁점 G, 신규 P-001-7로 해소.
3. **차단 중 반복 거부의 `request_count` 로그 값** — 차단 중 반복 요청 시 `request_count`가 계속 증가하는지 고정되는지 P-001-6이 정의하지 않아, 모든 정책을 만족하면서도 "운영자가 보기에 자연스러운 로그"라는 취지를 배반하는 구현(예: `request_count=137`)이 가능함. **판정: 무답 (차단)** → 쟁점 I로 해소.

## 반영 내역

**적용**
- (P-001-2, P-001-3, 신규 P-001-7) 반례 시나리오 1·2에서 지적된 두 공백을 해소하기 위해 P-001-2에 페널티 배수 초기화 문장을 추가하고, P-001-7을 신설해 차단 이력 없는 자연 윈도우 리셋 규칙을 명문화했다. ID는 재부여하지 않고 기존 마지막 순번(6) 다음인 7을 사용했다.
- (P-001-3, P-001-6) 반례 시나리오 3에서 지적된 `request_count` 값 모호성을 해소하기 위해 두 정책에 "차단 중 거부는 request_count를 증가시키지 않는다" 규칙과 그 예시 수치(11 유지)를 추가했다.
- (P-001-6) 개선 지적 "reason 값 도메인 미정의"·"예시 불완전"을 반영해 `reason`을 4개 값(`within_limit`/`limit_exceeded`/`blocked`/`window_reset`)으로 고정하고 예시에 `reason="within_limit"`을 추가했다. 동작(정책의 참/거짓 판정 자체)은 바뀌지 않고 검증 가능한 값 집합만 명확해졌다.
- (정책 충돌 절 전체) 개선 지적 "번호 체계 혼동"(정책 충돌 절의 목록 번호 1~6과 정책 ID P-001-1~6이 같은 숫자로 혼용됨)을 반영해 정책 충돌 절의 목록을 쟁점 A~I(알파벳)로 재라벨링했다. 문서 서술만 바뀌고 정책 내용은 변경되지 않았다.

**확정 (기본값)**
- 쟁점 H: 차단 지속 시간(페널티 배수)은 새 차단이 시작(P-001-2)될 때마다 항상 `base_block_seconds`(60초)로 초기화된다. 근거: 배수 연장은 "같은 차단이 끝나지 않은 채 반복 요청"하는 경우(P-001-3)에만 발동하는 것이 "패널티"라는 표현의 취지(반복 남용에 대한 억제)에 맞고, 이미 정상적으로 요청을 재개한 사용자에게 과거 배수를 그대로 적용하는 것은 사용자 의도에 반한다.
- 쟁점 G: 차단 여부와 무관하게 현재 윈도우 시작 시각으로부터 `window_seconds`가 경과하면 다음 요청은 새 윈도우로 취급된다(신규 P-001-7). 근거: P-001-1이 "1분 윈도우"를 전제로 하므로, 차단된 적이 없어도 시간이 지나면 카운트가 리셋되는 것이 "1분에 최대 10회"라는 request.md 원문의 자연스러운 해석이다.
- 쟁점 I: 차단 중 거부(`reason="blocked"`)는 `request_count`를 증가시키지 않고 차단을 유발한 시점 값을 유지한다. 근거: 반복 거부마다 카운트가 계속 올라가면 로그가 실제 유효 요청 수와 무관한 값을 보여 운영자에게 오해를 주므로, 페널티 발동 시점의 값을 고정하는 것이 request.md의 "로그를 보기 좋게" 요구에 더 부합한다.

**보류**
- (P-001-2·3·4·7) "판정/상태전이 분리" — 검토자는 P-001-2·3·4가 "허용/거부 판정"과 "차단 상태 갱신"을 한 문장에 묶어 엄격한 원자성 기준에서 X라고 지적했다. 규칙 자체의 의미(테스트로 옮길 내용)는 이미 명확하고 각 정책이 예시로 검증 가능하므로 당장 기능적 결함은 아니라고 판단했다. 다만 이를 분리하려면 정책 재구성(신규 ID 배정, 예시 재작성)이 필요해 "동작이 바뀌지 않는 명확화"의 범위를 넘어선다고 보아 보류한다. `/test`에서 정책당 테스트를 나눌 때 이 구조를 참고할 수 있다.
