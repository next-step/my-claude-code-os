# /gs:implement-loop — 개인 프로젝트 구현 오케스트레이터

한 번 호출하면 아래를 **끝까지** 돈다. 사람에게 묻는 자리는 ★ 세 곳뿐이고, 나머지는 멈추지 않는다.

```
/gs:idea ─→ 기획 확정 ─→ /gs:design ─→ 설계서 + 확정 도장
                                                      │
[사람] design ⑥에서 승인 ◄────────────────────────────┘
   │
   ▼
① 구현            TDL의 [BE] → Agent: gs:backend-dev
                  TDL의 [FE] → Agent: gs:frontend-dev
                  ────────────── ★ 에이전트가 "막힌 지점"을 반환하면 즉시 묻는다
② 셀프 QA         /gs:self-qa --run — FAIL 고치고 QA 재실행 (2연속 FAIL이면 정지)
   │
   ├────────────── ★ 쌓인 `논의 필요` 확인 (코드를 바꾸는 것만)
   ▼
③ PR              /gs:pr — base 확인 → [DB-<ID>] 접두사
   │
   ├────────────── ★ /gs:problem-log — 일지 기록 건별 승인
   ▼
[사람] 최종 검토 (+ 수동 QA)
```

**회사판의 ②~⑤(검사기·리뷰어·리팩토링·반려자)가 없다.** 그 구간의 연료인 리뷰 원장은 회사 코드리뷰 지적으로 자라는데, 개인 프로젝트에는 리뷰어가 없다. 대신 **동작 검증(QA)은 그대로 남는다** — 코드 퀄리티와 "기능이 제대로 도는가"는 다른 축이고, 개인 프로젝트라고 깨진 채 PR을 올리고 싶지는 않다.

**테섭 배포 단계도 없다.** 개인 프로젝트는 develop·테섭이 없고, 배포는 대개 main 머지에 물린 자동 배포(Vercel 등)다. PR 머지가 곧 배포 트리거이므로 별도 단계를 두지 않는다.

## 노션 접근

개인 업무 로그 페이지를 읽고 쓴다. **식별자·속성·본문 섹션 골격은 [notion-databases.md](../../notion-databases.md#개인-업무-로그)를 따른다.** `notion-home` MCP로만 접근한다.

## §0. 시작 전 확인

1. **인자 파싱.**
   - `notion.com/…` → 개인 업무 로그 페이지 URL.
   - 그 외 → 로컬 설계서 파일 경로(개발·검증용). 도장을 요구하지 않는다.
   - 없으면 멈추고 인자를 요구한다.
2. **범위 확인 — cashwalk 안이면 시작하지 않는다.** 대상 레포 경로가 `레포지토리/cashwalk/` 아래면 한 줄 남기고 멈춘다(정지 조건 F): `회사 작업은 /nudge:implement-loop 로 돌리세요. 이 플러그인은 개인 프로젝트 전용이라 원장 검사·리뷰어가 없습니다.` 회사 코드를 품질 판정 없이 PR까지 보내는 사고를 막는 가드레일이다.
3. **작업 페이지 읽기.** `API-retrieve-page-markdown`으로 `## 기획서`·`## 디자인`·`## 설계서`·`## TDL`·`## 논의 필요`·`## 루프 로그`를 확보한다. 속성 `ID`(`DB-123`)도 `API-retrieve-a-page`로 읽는다 — ③ PR 제목 접두사에 쓴다.
4. **설계서 확정 여부.** 아래 중 **하나라도** 걸리면 시작하지 않는다(정지 조건 B).

   | 확인 | 걸리면 |
   |---|---|
   | `## 설계서` 첫 줄에 확정 도장(`> 설계 확정 · <시각> · 사람 승인`)이 있는가 | **`/gs:design <페이지 URL>`을 먼저 실행하라**고 안내하고 멈춘다 |
   | `## 논의 필요`가 비어 있는가 | 남은 항목을 나열하고 멈춘다 |
   | 설계서에 `TBD`/`미정`/`확인 필요`가 남아 있는가 | 해당 줄을 짚고 멈춘다 |

5. **TDL 채우기.** `## TDL`이 비어 있으면 설계서의 변경 지점에서 뽑아 채운다. **각 항목에 `[FE]`/`[BE]`/`[공통]` 태그를 단다** — 변경 지점의 태그를 그대로 옮긴다. 작업 단위 = 커밋 단위. QA 명세는 **`/gs:self-qa <페이지 URL> --checklist-only`**로 뽑는다. 둘 다 사람 확인 없이 채운다 — 설계서가 확정됐으면 거기서 도출되는 것이라 판단 여지가 없다.
6. **신규 프로젝트면 스캐폴딩 먼저.** 설계서의 스캐폴딩 계획대로 레포·초기 구조를 만들고 첫 커밋을 남긴 뒤 ①로 간다.
7. **상태 파일 초기화.** 대상 레포의 `.omc/state/gs-loop.json`:
   ```json
   { "card": "<URL 또는 경로>", "branch": "<작업 브랜치>", "tdl": [], "qa": null, "pr": null }
   ```
   같은 페이지로 이미 상태 파일이 있으면 **이어서** 돈다(재개). 새로 시작하려면 사용자가 상태 파일을 지운다.

## ① 구현 — FE/BE 에이전트 위임

브랜치는 `feature/<작업명>`. main(또는 기본 브랜치)에서 딴다.

**순서 규칙 — BE가 FE보다 먼저다.** FE는 API 계약 위에 쌓이므로, `[BE]` 항목을 먼저 `gs:backend-dev`에 보내고, 반환된 `API 계약`을 `[FE]` 항목의 프롬프트에 넣어 `gs:frontend-dev`에 보낸다. 서로 의존이 없는 항목 묶음이면 두 에이전트를 **병렬로** 띄운다. `[공통]`(설정·타입 공유 등)은 메인 컨텍스트가 직접 한다.

에이전트 프롬프트에는 **설계서·디자인 명세·맡길 TDL 항목·레포 경로·브랜치만** 넣는다. 대화 이력은 넣지 않는다.

- 에이전트가 `막힌 지점`을 반환하면 **`AskUserQuestion`으로 즉시 묻는다.** 잘못 찍으면 그 위에 쌓은 구현이 통째로 버려지므로, 미루는 비용이 묻는 비용보다 크다. 답을 받으면 해당 에이전트를 다시 띄워 이어가고, `## 논의 필요`에 "무엇을 물었고 무엇으로 정해졌는지"를 적는다.
  - 사용자가 자리를 비운 상태면 가장 보수적인 선택을 하고 `## 논의 필요`에 "무엇을 어떻게 가정했는지"를 적은 뒤 계속한다. 루프가 사람을 기다리다 멈추지는 않는다.
- 에이전트 보고의 `검증`이 FAIL이면(타입체크·빌드) 그 에이전트에게 고치게 한다. **2회 연속 FAIL이면 정지 조건 D.**
- TDL 항목을 끝낼 때마다 페이지 속성 `TODO`를 `남은 n건: …`으로 갱신한다(`API-patch-page`).

### 작업 범위가 늘어났을 때

사용자가 루프 도중이나 끝난 뒤에 기능 추가·수정을 더 요청하면, 코드만 고치고 끝내지 않는다.

1. `## 설계서`(기획 층위면 `## 기획서`)에 추가 요구를 **누적**해 덧붙인다. 지우지 않는다.
2. `## TDL`에 태그 달린 항목을 추가하고, 추가분을 ①과 같은 라우팅으로 구현한다.
3. 구현 뒤 **② QA를 다시 돌린다.**
4. `## 논의 필요`에 "무엇이 언제 추가 요청됐는지"를 한 줄 남긴다.

## ② 셀프 QA

`--skip-qa`가 없으면 **`/gs:self-qa <페이지 URL> --run`**을 실행한다. 자동 항목은 브라우저 판정, 수동 항목은 재현 방법 기록.

- 결과 JSON(`pass`·`fail`·`manual`·`fail_items`)을 상태 파일 `qa`에 기록한다.
- `fail_items`는 해당 태그의 에이전트에게 보내 고치고 **QA만 다시 돌린다.** QA가 **2회 연속 FAIL이면** 멈추고 사람에게 넘긴다(무한 재시도 방지).
- `manual` 항목은 손대지 않는다. 사람 몫이다. "자동화 못 하니 검증 안 함"이 되지 않게 경계가 DB에 남는 것이 요점이다.

## ③ PR

**PR 직전에 쌓인 `논의 필요`를 확인한다.** 문서에만 적고 끝내지 않는다 — `AskUserQuestion`으로 묻는다.

- 루프 중 이미 물어서 정해진 항목은 다시 묻지 않는다.
- **결정이 코드를 바꾸는 것**만 묻는다. 단순 기록용은 문서에만 남긴다.
- 한 번에 하나씩, 많아도 3건까지. 답에 따라 코드를 고쳤으면 ②를 다시 돌린다.

그 뒤 `--skip-pr`이 없으면 **`/gs:pr`**로 PR을 만든다(draft 아님). base는 main(기본 브랜치). 아래 제목 규칙을 `/gs:pr`의 인자로 넘긴다.

### PR 제목

```
[DB-<ID>] <타입>: <요약>        예) [DB-207] feat: 메모 검색 추가
```

- `ID`는 개인 페이지 속성(unique_id)이라 값 자체가 `DB-123` 형태다. **`DB-`를 두 번 붙이지 않는다.**
- 로컬 설계서 파일이면 접두사 없음. 억지로 만들지 않는다.

### PR 본문 `검증` 섹션

- 빌드·타입체크 결과
- QA PASS/FAIL 수, **수동 QA 항목은 개수가 아니라 제목을 전부 나열한다**
- `원장 검사·리뷰어: 해당 없음 (개인 프로젝트 — gs 파이프라인)` 한 줄. **없는 검증을 한 것처럼 적지 않는다.**

## 마무리 — 개인 작업 페이지 갱신

`notion-home` MCP(`API-patch-page`, `API-patch-block-children`)로:

- `## TDL` 전부 체크. 속성 `TODO`는 비움
- `## 해결한 문제`는 **`/gs:problem-log --work-card <페이지 URL>`를 호출해 채운다.** 없으면 "없음" 한 줄
- `## 루프 로그`에 구현 요약(FE/BE 항목 수·커밋 수)과 QA 결과 한 줄
- `## 논의 필요`에 루프 중 쌓인 항목 (물어서 정한 것, 가정한 것)
- 속성 `PR`에 PR URL, `메모 / 일정`에 사람 몫(`수동 QA n건 · 논의 필요 m건`), `상태`를 `정리중`으로

로컬 설계서면 같은 내용을 파일 하단 `## 루프 로그` 섹션으로 붙인다.

### 마지막 출력

한 문단 요약 뒤에 **수동 QA 목록을 붙인다.** 총평은 쓰지 않는다.

```
PR: <URL>                                ← 건너뛰었으면 "없음 · <이유>"
구현: FE n건 · BE n건 · 논의 필요 m건
QA: 자동 PASS n · FAIL n

수동 QA (사람이 직접 봐야 하는 것):
1. <항목 제목> — <재현 방법 한 줄>
2. …
```

**수동 QA를 개수로만 보고하지 않는다.** 항목이 6건을 넘으면 앞의 5건만 펴고 나머지는 "그 외 n건 — QA 항목 DB 참조"로 접는다. 수동 항목이 없으면 `수동 QA: 없음` 한 줄.

## 정지 조건

멈출 때는 **어디서 왜 멈췄는지**와 상태 파일 경로를 남긴다. 재개는 같은 인자로 다시 호출하면 된다.

| | 조건 | 남기는 것 |
|---|---|---|
| B | 설계서 미확정 (§0-4) — 확정 도장 없음 · `논의 필요` 남음 · `TBD` 잔존 | 무엇이 걸렸는지. **`/gs:design <페이지 URL>` 먼저** |
| D | 타입체크·빌드 FAIL 2회 연속, 또는 QA FAIL 2회 연속 | 에러 로그 · FAIL 항목 |
| E | 노션 페이지 접근 실패 (개인 DB는 `notion-home`) | URL, 에러 |
| F | 대상 레포가 cashwalk 안 (§0-2) — 회사 작업 | 레포 경로와 `/nudge:implement-loop` 안내 한 줄 |

## 하지 않는 것

- 설계서를 바꾸지 않는다. 설계가 틀렸다고 판단되면 `논의 필요`에 적고 설계서대로 구현한다.
- 사람에게 물을 곳은 **세 군데뿐이다** — ① 에이전트가 막힌 지점을 반환했을 때, ③ PR 직전 `논의 필요` 확인, 마무리에서 `/gs:problem-log`의 일지 기록 건별 승인.
- FE 에이전트에 BE 항목을, BE 에이전트에 FE 항목을 보내지 않는다. 경계가 애매한 항목은 `[공통]`으로 메인이 한다.
- main에 직접 push하지 않는다. PR까지다. 머지(=배포 트리거)는 사람이 한다.

## 왜 이렇게 나눴나

- **FE/BE를 별도 에이전트로 띄우는 이유** — 혼자 만드는 개인 프로젝트는 한 컨텍스트가 프론트와 백엔드를 오가며 짜기 쉽고, 그러면 API 계약이 "구현하다 보니 이렇게 된" 형태로 굳는다. BE 에이전트가 계약을 먼저 고정하고 FE가 그 위에 쌓는 순서를 강제하면, 계약이 설계서에 남고 재작업이 줄어든다.
- **품질 판정 구간을 아예 안 만든 이유** — 회사판의 원장·리뷰어·반려자는 "사람 리뷰 지적의 재발 방지"가 목적이다. 개인 프로젝트에는 그 지적의 출처가 없고, 코드 퀄리티보다 완성까지의 속도가 축이다. AI 리뷰로 원장을 채우는 변형도 가능했지만, 그건 "사람이 실제로 지적한 것"이라는 원장의 정체성을 깨므로 하지 않았다.
- **배포 단계가 없는 이유** — 개인 프로젝트의 배포는 main 머지에 물린 자동 배포가 대부분이다. PR 머지가 곧 배포 결정이고, 그 결정은 사람의 최종 검토 자리에 이미 있다.
- **묻는 자리를 세 곳으로 못 박은 이유** — 잘못 찍으면 구현이 통째로 헛도는 ①의 막힌 지점, 코드가 PR로 나가기 직전인 ③ 앞, 그리고 기록은 사람이 확인한 것만 쌓여야 하는 problem-log. 미루는 비용이 묻는 비용보다 큰 곳에만 질문을 뒀다.
