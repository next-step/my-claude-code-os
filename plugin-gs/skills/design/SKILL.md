# /gs:design — 디자인·설계 초안 → 사람 확정

설계 권한은 사람에게 있고, AI는 **사람이 검토할 재료**를 만든다. 회사판과 다른 점 하나 — 회사는 피그마 시안이 있지만 개인은 없으므로, UI가 있는 작업이면 **designer 에이전트가 디자인 명세를 먼저** 만든다.

```
/gs:idea ─→ 기획 확정 · 씨앗 (한 줄 목표 · 범위 밖)
        │
        ▼
§0 페이지 읽기
 ①-D 디자인      Agent: gs:designer — UI 있는 작업만
 ①   레포 탐색   Explore → 변경 지점 file:line (신규 프로젝트면 스캐폴딩 계획)
 ②   설계서 6항목 목표 · AS-IS · TO-BE · 변경 지점[FE/BE] · 동작 명세 · 범위 밖
 ③   다이어그램   트리거 해당 시에만. 미해당이면 "해당 없음 + 이유"
 ④   막힐 지점 → ## 논의 필요
 ⑤   논의 필요 해소  ★ 한 건씩 묻는다. 0건이 될 때까지
 ⑥   승인 도장      ★ 사람이 승인해야만 찍는다
        │
        ▼
/gs:implement-loop
```

**⑤가 ⑥ 앞에 있다.** 답이 안 나온 항목을 남긴 채로는 승인 질문이 성립하지 않는다.

## 노션 접근

**시작 전에 [notion-databases.md](../../notion-databases.md#개인-업무-로그)를 읽는다.** 개인 업무 로그는 **`notion-home` MCP**로만 읽고 쓴다.

## §0. 시작 전 확인

1. **인자 파싱.** 첫 토큰이 `notion.com/…` 이어야 한다. 없으면 멈추고 요구한다.
2. **페이지 읽기.** `API-retrieve-page-markdown`으로 `## 기획서`·`## 디자인`·`## 설계서`·`## 논의 필요`를 확보한다. `## 기획서`에 확정 도장이 없으면 `/gs:idea`를 먼저 돌리라고 안내하고 멈춘다 — 기획이 흔들리는 상태에서 설계하면 전부 재작업이다.
3. **이미 확정된 페이지인지 확인.** `## 설계서` 안에 확정 도장(§⑥)이 있으면 `AskUserQuestion`으로 묻는다.
   - `다시 설계` → 도장을 지우고 ①부터. 기존 설계서는 **지우지 않고** 아래에 이어 쓴다.
   - `그대로 진행` → `/gs:implement-loop` 호출을 안내하며 끝낸다.
4. **레포 경로 판정.** `--repo`가 있으면 그것. 없으면 페이지 속성 `프로젝트`로 [레포 경로 ↔ 프로젝트](../../notion-databases.md#레포-경로--프로젝트)를 역인용한다.
   - **`레포지토리/cashwalk/` 아래면 멈춘다** — 회사 작업은 `/nudge:design` 몫이다. 이 플러그인은 개인 프로젝트 전용이다.
   - **신규 프로젝트(레포 없음)면** ①에서 탐색 대신 스캐폴딩 계획을 세운다. 어디에 만들지(`~/Desktop/레포지토리/guesung/<이름>`)와 스택 후보를 ④ 논의 필요로 낸다.
   - 후보가 둘 이상이면 `AskUserQuestion`으로 고르게 한다. 찍지 않는다.

## ①-D 디자인 — designer 에이전트 (조건부)

이번 작업에 **사용자가 보는 화면 변화가 있으면** `Agent` 도구로 `gs:designer`를 띄운다. 프롬프트에는 **확정된 기획서와 레포 경로만** 넣는다.

- 결과의 `디자인 명세 초안`을 페이지 `## 디자인`에 쓰고, `결정 필요`는 ④의 `## 논의 필요`로 합친다.
- 화면 변화가 없는 작업(스크립트·API만·리팩토링)은 건너뛰고 `## 디자인`에 `해당 없음 (화면 변화 없음)` 한 줄을 남긴다 — 안 한 것이 판단인지 누락인지 구별되어야 한다.

## ① 레포 탐색

`Explore` 에이전트를 띄운다. 프롬프트에 **기획서·씨앗·레포 경로만** 넣는다. 찾을 것은 셋이다.

- 기획이 말하는 화면·기능의 **진입점** (라우트 파일 · 페이지 컴포넌트 · API 라우트)
- 거기서 갈라지는 **현재 흐름** — 어떤 상태·API·컴포넌트를 거치는가
- 이번에 **고칠 자리** — `path/File.tsx:120` 수준

**신규 프로젝트면 탐색할 레포가 없다.** 대신 스캐폴딩 계획을 세운다 — 만들 폴더 구조·초기 파일 목록·스택. 이것이 ②의 `변경 지점`을 대신한다(전부 `(신규)`).

**못 찾은 것은 지어내지 않는다.** 추측한 `file:line`은 없는 것보다 나쁘다. 못 찾았으면 ④로 넘긴다.

## ② 설계서 6항목

`## 설계서`에 아래 순서로 쓴다. **초안이다. 확정은 사람이 한다.**

| 항목 | 내용 | 출처 |
|---|---|---|
| 한 줄 목표 | 이 작업이 무엇을 되게 하는가 | 씨앗 |
| AS-IS | 지금 이 화면·흐름이 어떻게 도는가. 신규 프로젝트면 `신규 — 해당 없음` | ① 탐색 |
| TO-BE | 무엇이 어떻게 달라지는가 | 기획서 + ①-D + ① |
| 변경 지점 | `[FE]`/`[BE]`/`[공통]` 태그 + `path/File.tsx:120` 목록. 새 파일은 `(신규)` | ① 탐색 |
| 동작 명세 | 입력·상태·분기 표. BE가 있으면 **API 계약**(METHOD·path·요청/응답)도 여기 | 기획서 + ①-D |
| 범위 밖 | 이번에 안 하는 것 | 기획서 |

- **변경 지점의 FE/BE 태그는 implement-loop의 에이전트 라우팅 키다.** 태그 없는 항목은 implement-loop가 라우팅을 못 하므로 반드시 붙인다.
- 기획서·디자인에 없고 레포에서도 확인되지 않는 동작은 **쓰지 않는다.** ④로 넘긴다.
- `범위 밖`을 비워두지 않는다. 비어 있으면 구현 중 범위가 새는 경로다.

## ③ 다이어그램 — 조건부

아래 표에 **해당할 때만** 그린다. 판단 여지를 남기지 않기 위해 임계값을 숫자로 둔다.

| 트리거 | 그리는 것 | 안 그리는 경우 |
|---|---|---|
| 조건 분기 **2개 이상** (상태 · 권한 · 플랫폼) | `flowchart TD` | 분기 1개 이하 |
| 프론트↔서버 왕복 **2회 이상** | `sequenceDiagram` | 단일 조회 |
| 화면·컴포넌트 상태 **3개 이상** | `stateDiagram-v2` | 상태 2개 이하 |
| 새 파일 **3개 이상** 또는 모듈 경계 변경 | `flowchart LR` | 단일 파일 수정 |

노션에는 **code block(language `mermaid`)** 으로 넣는다. 언어가 거부되면 `plain text` 코드 블록으로 넣고 `## 논의 필요`에 한 줄 남긴다.

전부 미해당이면 다이어그램은 **0개**다. 다만 그때도 `## 설계서` 끝에 한 줄을 남긴다.

```
다이어그램: 해당 없음 (분기 1개 · 단일 파일)
```

다이어그램은 **설계서에 이미 쓴 것만** 그린다. 그림에만 있고 글에는 없는 분기를 만들지 않는다.

## ④ 막힐 지점 → `## 논의 필요`

각 항목은 **`무엇이 불명확한가 → 어느 선택지가 있는가 → 내가 추천하는 쪽과 이유`** 로 쓴다. ①-D designer가 낸 `결정 필요`도 여기 합친다.

여기 들어가는 것:

- 기획서·디자인에도 없고 레포에서도 확인 안 되는 동작
- ①에서 변경 지점을 특정하지 못한 부분
- 레포의 현재 구조와 기획의 요구가 충돌하는 지점
- 신규 프로젝트의 스택·폴더 구조 후보
- 설계서대로 만들면 기존 동작이 깨질 것 같은 자리

## ⑤ 논의 필요 해소

`## 논의 필요`가 0건이 될 때까지 **`AskUserQuestion`으로 한 건씩** 묻는다.

- 한 번에 하나. 답을 받으면 `## 설계서`(또는 `## 디자인`)에 반영하고 그 항목을 지운다.
- 반영으로 다이어그램 트리거가 새로 충족되면 ③을 다시 돌린다.
- 사용자가 "나중에"를 고르면 **페이지를 저장한 채로** 끝낸다. 도장은 찍지 않는다.
- 답하지 않고 자리를 비워도 **가정하고 넘어가지 않는다.** 여기서 찍은 가정은 설계서 본문이 되고, 구현 전체가 그 위에 쌓인다.

**묻기 전에 여기까지의 결과를 노션에 저장한다.**

## ⑥ 승인 도장

`## 논의 필요`가 0건이 되면 `AskUserQuestion`으로 승인을 묻는다. 질문에는 **설계서 요약·디자인 유무·다이어그램 유무**를 함께 낸다.

- `승인` → `## 설계서` **첫 줄**에 quote 블록으로 도장을 찍는다. 그리고 `/gs:implement-loop <페이지 URL>`을 이어서 실행한다.

  ```
  > 설계 확정 · 2026-08-31 14:20 · 사람 승인
  ```

- `보류` → 페이지만 저장하고 끝낸다. 무엇이 남았는지 한 줄로 보고한다.

**AI는 기술적으로 자기 도장을 찍을 수 있다.** 규칙으로 막는다 — `AskUserQuestion` 승인 응답 없이는 찍지 않는다.

## 마지막 출력

세 줄. 그 이상 쓰지 않는다.

```
설계서: <페이지 URL>  ·  디자인 있음/해당 없음  ·  다이어그램 n개
논의 필요: n건        ← 0건이어야 도장이 찍힌다
확정: 2026-08-31 14:20  (또는 "보류 — <남은 것>")
```

## 하지 않는 것

- **`AskUserQuestion` 승인 응답 없이는 도장을 찍지 않는다.** "알아서 해"라고 해도 찍지 않는다.
- 기획서·디자인·레포에 없는 동작을 설계서에 지어내지 않는다. 빈 곳은 `## 논의 필요`로.
- 확인하지 못한 `file:line`을 쓰지 않는다.
- 트리거에 해당하지 않는 다이어그램을 그리지 않는다.
- 코드를 고치지 않는다. 이 스킬은 설계까지다.
- `## TDL`·`## QA 체크리스트`·`## 루프 로그`를 채우지 않는다. implement-loop 몫이다.

## 왜 이렇게 나눴나

- **디자인을 설계 안의 한 단계로 접은 이유** — 회사는 디자인(피그마)이 기획과 함께 도착하지만, 개인은 디자인도 만들어야 한다. 별도 스킬로 빼면 확정 도장이 세 개가 되고 사람이 지친다. 기획(idea)과 구현 사이의 "재료 만들기"는 design 하나로 묶고, 도장은 기획·설계 둘만 받는다.
- **designer를 별도 에이전트로 두는 이유** — 설계 컨텍스트가 디자인까지 하면 "구현하기 쉬운 화면"으로 휜다. planner와 같은 논리다.
- **변경 지점에 FE/BE 태그를 붙이는 이유** — 개인 프로젝트는 한 작업이 프론트와 백엔드에 걸친다. 구현 단계에서 누가(frontend-dev/backend-dev) 맡을지를 설계서가 정해두지 않으면, implement-loop가 임의로 가르게 되고 그 갈림이 곧 설계 판단이다.
- **다이어그램을 조건부로 둔 이유** — 다이어그램이 있다는 사실 자체가 "이건 복잡한 작업"이라는 신호여야 값이 있다.
- **⑤를 ⑥ 앞에 둔 이유** — 미해결 항목을 옆에 두고 승인을 물으면 사람은 그것을 포함해 승인해버린다.
