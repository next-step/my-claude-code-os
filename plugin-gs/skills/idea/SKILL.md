# /gs:idea — 아이디어 → 기획 확정 → 작업 페이지

회사판(`/nudge:work-card`)은 슬랙 스레드에서 기획을 **받아온다.** 개인 프로젝트에는 기획을 주는 사람이 없으므로, 이 스킬이 그 앞단을 **만든다.** 기획 초안은 planner 에이전트가, 확정은 사람이 한다 — "초안은 AI, 확정은 사람" 원칙은 회사판과 같다.

```
/gs:idea       기획서 확정 · 개인 페이지 · 설계서 씨앗
      │
      ▼
/gs:design     (UI 있으면 designer) → AS-IS/TO-BE · 변경 지점 · 확정 도장
      │
      ▼
/gs:implement-loop  frontend-dev/backend-dev 구현 → 셀프 QA → PR
```

## 노션 접근

**시작 전에 [notion-databases.md](../../notion-databases.md#개인-업무-로그)를 읽는다.** 식별자·속성·본문 섹션 골격이 거기 있다. 개인 DB는 **`notion-home` MCP**로만 읽고 쓴다.

## §0. 시작 전 확인

1. **인자 파싱.**
   - `notion.com/…` → 기존 페이지 재개. `## 기획서`에 확정 도장이 있으면 `/gs:design` 호출을 안내하고 끝낸다. 없으면 ②(결정 필요 해소)부터 이어간다.
   - 그 외 텍스트 → 아이디어. ①로 간다.
   - 없으면 멈추고 아이디어를 요구한다.
2. **범위 확인 — cashwalk 안이면 시작하지 않는다.** `--repo`가 `레포지토리/cashwalk/` 아래면 한 줄 남기고 멈춘다: `회사 작업은 /nudge:work-card 로 시작하세요. 이 플러그인은 개인 프로젝트 전용입니다.` 회사 기획을 개인 파이프라인에 태우면 팀 카드·원장과 어긋난다.
3. **레포 판정.** `--repo`가 있으면 기존 프로젝트에 기능을 얹는 작업이다. 없으면 아이디어 내용으로 `~/Desktop/레포지토리/guesung/` 아래 기존 레포 후보를 찾아 `AskUserQuestion`으로 확인한다 — `기존 레포에 얹기` / `신규 프로젝트`. 찍지 않는다.

## ① 기획 초안 — planner 에이전트

`Agent` 도구로 `gs:planner`를 띄운다. 프롬프트에는 **아이디어와 레포 경로(있으면)만** 넣는다.

결과의 `기획서 초안` 6항목과 `결정 필요` 목록을 받는다. **에이전트가 낸 초안을 다듬지 않고 그대로 사람에게 낸다** — 메인 컨텍스트가 손대기 시작하면 어디까지가 에이전트 판단인지 사람이 알 수 없다.

## ② 결정 필요 해소

`결정 필요`가 0건이 될 때까지 **`AskUserQuestion`으로 한 건씩** 묻는다. 에이전트의 추천을 첫 옵션으로 낸다.

- 답을 받으면 기획서 초안에 반영하고 그 항목을 지운다.
- 사용자가 "나중에"를 고르면 여기까지를 로컬에 임시 저장하지 말고 **바로 ③으로 가서 페이지부터 만든 뒤** 미해소 항목을 `## 논의 필요`에 남기고 끝낸다. 재개는 페이지 URL로 한다.
- 답하지 않고 자리를 비워도 **가정하고 확정하지 않는다.** 기획의 가정 위에는 설계·구현·QA 전부가 쌓인다.

## ③ 기획 승인

`AskUserQuestion`으로 기획서 6항목 요약을 내고 승인을 묻는다.

- `승인` → ④로. `## 기획서` 첫 줄에 도장을 찍는다: `> 기획 확정 · <시각> · 사람 승인`
- `보류` → 페이지만 만들어 저장하고 끝낸다(④의 페이지 생성은 수행). 무엇이 남았는지 한 줄 보고.

## ④ 개인 작업 페이지

1. **중복 확인.** `API-query-data-source`로 최근 페이지 `이름`을 훑어 같은 기획명이 있으면 재사용을 물어본다.
2. **생성** (`API-post-page`, parent = 개인 업무 로그 data source). 속성: `이름`=기획명(짧은 명사구), `프로젝트`=[레포 경로 ↔ 프로젝트](../../notion-databases.md#레포-경로--프로젝트) 판정(신규 프로젝트면 비움), `상태`=`진행 중`, `작업 시작 날짜`=오늘.
3. **본문 골격** (`API-patch-block-children`). [본문 섹션 골격](../../notion-databases.md#본문-섹션-골격) 여덟 제목을 그 이름 그대로 만든다 — design·implement-loop가 제목으로 섹션을 찾는다.
4. `## 기획서`에 확정된 6항목(+도장)을, `## 설계서`에 씨앗을 쓴다.

**설계서 씨앗은 두 가지만:**

1. **한 줄 목표** — 기획서의 MVP 범위를 한 문장으로
2. **범위 밖** — 기획서의 범위 밖 그대로

`## 디자인`·`## TDL`·`## QA 체크리스트`·`## 해결한 문제`·`## 루프 로그`는 뒤 단계가 채운다. 지금은 비워 둔다.

## 마지막 출력

세 줄. 그 이상 쓰지 않는다.

```
기획: 확정 <시각> (또는 "보류 — 결정 필요 n건")
개인 페이지: <URL>
레포: <경로> (또는 "신규 — design에서 스캐폴딩 계획")
```

그리고 **`AskUserQuestion`으로 다음 단계를 묻는다.**

- `설계 시작` → **`/gs:design <페이지 URL>`** 을 이어서 실행한다.
- `나중에` → 페이지 URL만 남기고 끝낸다. 재개는 `/gs:design <페이지 URL>`.

## 하지 않는 것

- 기획서를 사람 승인 없이 확정하지 않는다. 이 스킬의 존재 이유가 그 승인이다.
- planner가 낸 결정 필요 항목을 건너뛰고 페이지를 확정 상태로 만들지 않는다.
- 기술 스택·구현 방식을 정하지 않는다. design 몫이다.
- 코드를 쓰지 않는다.

## 왜 이렇게 나눴나

- **planner를 별도 에이전트로 두는 이유** — 기획과 구현을 같은 컨텍스트가 하면, 구현하기 쉬운 쪽으로 기획이 휜다. 컨텍스트를 끊어야 "만들기 어렵지만 문제를 푸는 기능"이 살아남는다.
- **기획 확정을 설계 확정과 분리한 이유** — 기획이 흔들리면 설계가 전부 재작업이다. 층마다 도장을 받아야 되돌아가는 거리가 짧다. 회사판에서 슬랙 기획서가 이미 확정 상태로 도착하는 것과 같은 상태를, 개인판은 이 스킬이 만들어야 한다.
- **회사판 work-card와 갈라진 이유** — work-card는 이미 있는 기획(슬랙)을 노션으로 옮기는 스킬이고, 이 스킬은 없는 기획을 만드는 스킬이다. 입력이 다르면 스킬도 다르다. 팀 카드·스레드 모음 로직은 개인에 존재하지 않으므로 가져오지 않았다.
