# 관측 — 003 delete-note

기능: 등록한 노트를 지울 수 있다. 지운 것은 되돌릴 수 있다(사람이 정한 제약: `deleted_at` soft delete).
배포 형태: 로컬 실행. HTTP가 유일한 통로다(002에서 명령줄이 제거됐다).

## 무엇을 보기로 했나

`feature-loop` ①에서 정했다. **코드를 추가하지 않고 얻어지는 것만** 골랐다.

이번 기능은 002의 관측을 직접 겨냥한다 — 저장된 노트 10건 중 실사용은 1건뿐인데 지울 방법이 없어
"며칠 동안 몇 건 등록했나"를 읽을 수 없게 됐다. 그래서 **삭제가 그 숫자를 되살리는지**가 이번 질문이다.

| # | 관측 | 어떻게 세나 | 0이면 / 무엇이면 무슨 뜻인가 |
|---|---|---|---|
| 1 | 7일 동안 삭제한 노트 수 | `GET /notes/due`의 id 목록에서 **빠진 번호를 센다**(아래) | **0이면 만들었는데 안 쓴다.** 가장 중요한 신호 |
| 2 | **무엇을 지웠나** — 쓰레기(id 1~3, 5~10)인가 실사용 노트(id 4, 11 이후)인가 | 사라진 id를 002의 오염 표와 대조 | 실사용 노트를 지웠으면 **삭제를 「복습 완료 처리」 대신 쓴 것**이다. 그게 004의 입력 |
| 3 | 지울 id를 어떻게 찾았나 | 서술 메모 | `/notes/due`로 찾았나, 앱을 내려 저장소를 열었나. 후자면 관측 마찰이 002보다 나빠진 것 |

**뺀 것** — "실수로 지웠는가". 삭제 시각·복구 여부를 남기는 코드가 필요해 기능이 커진다.
관측 2가 부분적으로 대신한다(실사용 노트가 사라졌는지는 보인다).

### 세는 방법 — id 구멍을 센다

soft delete라 **id가 재사용되지 않는다.** 그리고 복습 완료 처리가 없어서 복습일이 지난 노트는
전부 due 목록에 남는다. 따라서 배포 다음 날부터는:

```
살아 있는 노트 = GET /notes/due 의 id 집합
삭제한 노트    = 1 .. (본 적 있는 최대 id) 중 위 집합에 없는 번호
```

```bash
curl -s localhost:8080/notes/due | python3 -c \
  'import json,sys; ids=[n["id"] for n in json.load(sys.stdin)]; print("살아있음:",ids); print("구멍:",[i for i in range(1,max(ids)+1) if i not in ids] if ids else "전부 삭제됨")'
```

**이 방법은 앱을 내리지 않는다.** 002는 세려면 앱을 내려야 했고(파일 잠금), 001보다 나빠졌다고 기록돼 있었다.
soft delete가 그 마찰을 없앴다 — 지운 행이 남아 있으므로 id가 밀리지 않고, 구멍이 곧 삭제 건수다.

**한계** — 배포 당일(2026-08-30)에는 복습일이 전부 2026-08-31이라 due 목록이 비어 있어 이 명령이 돌지 않는다.
**08-31부터 유효하다.** 기준값은 002가 기록해 둔 id 1~10이다.

### ①에서 실제로 돌려본 것 (001 되먹임 #4)

관측 방법은 정해두는 것으로 부족하고 ①에서 한 번 돌려봐야 한다 — 001에서 얻은 규칙이다. 돌려본 결과:

| 시도 | 결과 |
|---|---|
| H2 Shell로 직접 세기 | **실패** — `MVStoreException: The file is locked`. 8080에 앱이 떠 있었다(19:29 기동) |
| `GET /notes` (전체 목록) | **없다** — 405. 전체 조회 통로는 존재하지 않는다 |
| `GET /notes/due` | 200 `[]` — 복습일이 전부 08-31이라 오늘은 비어 있다 |

002가 "세려면 앱을 내려야 한다"고 적어둔 것이 그대로 재현됐다. 위 「id 구멍」 방법은 이 실패에서 나왔다.

## 무엇이 보였나

### 배포 시점 (0일차) — 2026-08-30

구 프로세스를 내리고 새 jar로 기동했다. `ddl-auto=update`가 **실사용 파일에서 처음으로** `ALTER TABLE`을 돌린 시점이다.

**배포 직전 저장소 상태 (앱이 내려가 있어 직접 읽을 수 있었다)**

```
NOTE 컬럼: ID · CONTENT · NEXT_REVIEW_DATE · REGISTERED_AT   ← DELETED_AT 없음
행: 10건, id 1~10, 복습일 전부 2026-08-31
```

**기동**

```
Started AppApplication in 2.832 seconds     ← DDL 오류 없음
```

**기존 데이터가 새 스키마에서 살아 있는지 확인** (④ 회귀 리뷰어가 요구한 확인). 오늘은 복습일이 전부 내일이라
`/notes/due`가 비어 있어 목록으로는 볼 수 없다. 그래서 기존 행에 직접 닿았다 — 쓰레기 노트 id 1을 지웠다 되돌렸다(순 효과 0).

```
DELETE /notes/1        → 200  content·registeredAt(17:38:05) 그대로, deletedAt 채워짐
GET    /notes/due      → 200  []          # 복습일이 내일이라 비어 있는 것이 정상
POST   /notes/1/restore→ 200  deletedAt=null, nextReviewDate 2026-08-31 (삭제 전과 동일)
DELETE /notes/999      → 404
```

**지적 B는 이번엔 통과했다.** `ALTER TABLE`이 성공했고 기존 행의 값이 보존됐다. 다만 *테스트가 없다*는 사실은 그대로다 —
이번에 안전했던 것이지 다음에도 안전하다는 근거는 아니다.

**지적 G가 실물로 드러났다.** 404 응답이 `노트를 찾을 수 없습니다: id=999` 평문이다. 성공 응답은 전부 JSON이다.
리뷰에서는 "호출자가 오류 경로에서만 파싱 실패한다"는 예측이었는데, 배포에서 눈으로 확인됐다.

**관측 3(지울 id를 어떻게 찾았나)의 첫 데이터가 배포 당일에 나왔다.** 배포 전 상태를 읽으려고 **앱을 내려야 했다.**
앱이 떠 있는 동안은 저장소 파일이 잠기고, 전체 목록 엔드포인트가 없어 HTTP로도 볼 수 없다.
오늘은 복습일이 전부 내일이라 `/notes/due`마저 비어서 **id를 얻을 방법이 하나도 없었다.**
④ 리뷰의 지적 A(삭제한 노트에 다시 도달할 방법이 없다)와 같은 뿌리다 — 이 앱에는 **읽는 통로가 하나뿐이고 그 하나가 좁다.**

## 다음 루프의 입력

**④ 리뷰 지적 9건을 전부 이번 루프에 반영하지 않기로 사람이 결정했다.** 그래서 지적이 곧 다음 루프의 후보다.
반영하지 않은 것이지 틀렸다고 판정한 것이 아니다 — 아래는 리뷰어가 낸 그대로다.

관점 **둘 이상이 독립적으로** 같은 것을 지적한 것부터 적는다. 그게 가장 강한 신호다.

| # | 지적 | 낸 관점 | 사람의 결정 |
|---|---|---|---|
| A | **삭제한 노트에 다시 도달할 방법이 API에 없다.** 읽기 경로가 `GET /notes/due` 하나뿐이고 그 질의는 삭제된 것을 걸러낸다. 삭제 응답을 그 자리에서 붙들고 있지 않으면 되돌릴 수 없다 | 구조 · 회귀 (2/3) | **반영 안 함** — 복구는 개발 쪽에서 저장소를 직접 열어 한다 |
| B | 기존 10건이 든 파일 DB의 **스키마 변경을 어떤 테스트도 거치지 않는다.** 테스트 셋 다 빈 스키마에서 시작한다 | 구조 · 회귀 (2/3) | **백업 없이 배포** |
| C | **삭제가 재시작 후에도 유지되는지** 지키는 테스트가 없다 | 기준 대조 · 회귀 (2/3) | 반영 안 함 |
| D | 재삭제 멱등성이 주석의 주장인데 서비스·HTTP 경로로 검증되지 않는다 | 기준 대조 · 회귀 (2/3) | 반영 안 함 |
| E | 삭제 규칙의 실제 주인이 `NoteDeletion`이 아니라 **파생 쿼리 메서드 이름**이다. 주석은 "한 곳에만 있다"고 단언한다 | 구조 | 반영 안 함 |
| F | `Note`가 `NoteDeletion`을 보관하지 않고 매번 새로 만들어 버린다. 값 객체가 아무것도 강제하지 못한다 | 구조 | 반영 안 함 |
| G | 오류 응답만 `text/plain`. 성공은 전부 JSON이라 호출자가 오류 경로에서만 파싱 실패한다 | 구조 | 반영 안 함 |
| H | 기준 2는 무조건인데 코드는 **복습일이 오늘 이하일 때만** 성립한다. 고칠 곳이 코드가 아니라 기준 문장일 수 있다 | 기준 대조 | 반영 안 함 |
| I | **구 바이너리로 되돌리면 삭제분이 조용히 전부 되살아난다.** 컬럼은 남고 구 코드는 필터를 모른다. 오류도 로그도 없다 | 회귀 | 반영 안 함 |

**A와 C는 이 기능의 목적에 직접 걸린다.** A가 없으면 사람이 되돌릴 수 없고, C가 깨지면 정크 9건이 재시작마다 되살아난다.
둘 다 004에서 먼저 볼 자리다. **C는 ②에서 PM이 승인 단계로 올렸다가 사람이 뺀 항목**이고, 리뷰가 독립적으로 두 번 다시 찾았다.

앞 루프부터 넘어온 후보도 그대로 남아 있다.

- **복습 완료 처리** — 001·002·003 세 번째 미뤄졌다. 없으면 모든 노트가 계속 due에 쌓인다
- **난이도 입력과 간격 알고리즘** — 지금도 고정 1일. 제품 이름에 스케줄링이 없다
- **서버를 계속 띄워두는 방법** — 002의 관측 2가 "띄우기 귀찮다"로 나오면 이게 다음이 된다
