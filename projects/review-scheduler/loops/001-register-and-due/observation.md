# 관측 — 001 register-and-due

기능: 노트를 등록하면 다음 복습일이 계산되고, 지금 복습할 것을 목록으로 볼 수 있다.
배포 형태: 로컬 실행.

## 무엇을 보기로 했나

`feature-loop` ①에서 정했다. **코드를 추가하지 않고 얻어지는 것만** 골랐다 —
관측을 얻으려고 기능을 늘리면 루프에 담기지 않는다.

| # | 관측 | 어떻게 세나 | 0이면 무슨 뜻인가 |
|---|---|---|---|
| 1 | 7일 동안 등록한 노트 수 | `select count(*) from note` | **만들었는데 안 쓴다.** 가장 중요한 신호 |
| 2 | 그중 복습일이 지난 노트 수 | `select count(*) from note where next_review_date <= current_date` | 등록만 하고 한 번도 복습하지 않았다 |
| 3 | 등록·조회할 때 거친 지점 | 서술 메모 | 다음 기능 후보를 가장 많이 내는 관측 |

**뺀 것** — "due 목록을 며칠 열었는지". 조회 로그 코드가 필요해 기능이 커진다. 002로 미룬다.

### 세는 명령 (0일차에 실제로 돌려 확인한 것)

```bash
cd projects/review-scheduler/app
H2JAR=$(find ~/.gradle/caches -name 'h2-2*.jar' | grep -v sources | sort | tail -1)
java -cp "$H2JAR" org.h2.tools.Shell \
  -url "jdbc:h2:file:$PWD/data/review-scheduler" -user "" -password "" \
  -sql "select count(*) from note;"
```

**사용자명은 빈 문자열이다.** `sa`가 아니다 — 이 앱은 `spring.datasource.username`을 지정하지 않았고,
Spring Boot 4는 임베디드 H2에 빈 사용자명을 쓴다(`HikariPool ... user=` 로그로 확인).
`sa`로 붙으면 `Wrong user name or password [28000-240]`가 난다.
H2 버전도 맞춰야 한다 — 1.4.x jar로 붙으면 `File corrupted`가 뜨는데 **파일이 깨진 게 아니라 포맷이 다른 것**이다.

### 이 관측의 한계 (미리 적어둔다)

간격이 고정 1일이고 복습 통과 처리가 없어서, **관측 1과 2가 거의 같은 값이 될 것이다.**
그래도 쓸모는 있다 — 둘이 같다는 것 자체가 "등록만 하고 한 번도 복습하지 않았다"는 신호이고,
그게 002의 입력이 된다.

## 무엇이 보였나

### 배포 시점 (0일차) — 2026-08-30

CLI 진입점을 추가한 뒤 실제로 로컬 실행해 등록·조회했다.

| 관측 | 값 |
|---|---|
| 전체 노트 수 | **3** |
| 복습일이 지난 노트 수 | **0** (전부 다음 날짜인 2026-08-31) |

```
./gradlew bootRun --args="register <내용>"   → 등록됨: [id=1] ... (다음 복습일: 2026-08-31)
./gradlew bootRun --args="list"              → 지금 복습할 노트가 없습니다.
```

등록 직후 `list`가 비어 있는 것은 **정상이다.** 수용 기준 2(최소 1일 뒤)대로 복습일이 내일이다.

재시작 영속(수용 기준 4)도 실사용에서 확인됐다 — `bootRun`은 매번 새 프로세스인데
id가 1 → 2 → 3으로 이어졌다. 앞 프로세스가 저장한 것을 뒤 프로세스가 읽었다는 뜻이다.

### 7일차

> **아직 채우지 않았다.** 배포일 + 7일에 위 세 가지를 여기에 적는다.
> 숫자는 숫자로 적고, 추측은 다음 칸에 적는다.

## 다음 루프의 입력

관측이 나오기 전이라 확정된 것은 없다. 지금까지 나온 후보만 적어둔다.

- **due 목록 조회 횟수 관측** — 001에서 뺀 것. 알림 방식이 맞는지 판정하려면 필요하다
- **복습 통과 처리** — 없으면 모든 노트가 계속 due에 쌓인다. 관측 2가 관측 1과 같아지는 원인
- **난이도 입력과 간격 알고리즘** — 지금은 고정 1일. 제품 이름이 "복습 스케줄러"인데 스케줄링이 없다
- **관측용 조회** — 0일차에 드러났다. 관측을 세려면 H2 jar 경로·버전·빈 사용자명을 맞춰야 했다.
  ①에서 "SQL로 공짜로 얻는다"고 판단했지만 공짜가 아니었다. `count` 명령 하나가 있는 편이 낫다
  (PM 1회차가 낸 "개수를 조회할 수 있다" 기준이 부분적으로 옳았다)

## 루프 기록

관측과 별개로, 이 루프를 도는 동안 나온 사실이다. 다음 루프의 판단 재료다.

| 구간 | 관문 | 결과 | 되돌림 |
|---|---|---|---|
| ② 기획 | `criteria-lint.py` | 5/5 → 3/3 → **4/4 PASS** | **2회** (전부 사람 승인이 반려) |
| ③ 구현 | `./gradlew test` | **exit 0** · 10건 · 실패 0 | 1회 (리뷰 지적 3건 반영) |
| ④ 리뷰 | 회귀 없음 (첫 루프) | 지적 3건 전부 반영 | — |
| ⑤ 배포 | 되돌릴 수 있는가 | **완료** — CLI 추가 후 로컬 실행 | 1회 (진입점 없음) |

**관문은 세 번 다 통과시켰는데 사람 승인이 두 번 걸렀다.** 반려 사유는 영속성 미보장, 복습일 계산 규칙 부재.
형식 채점기가 내용을 판정하지 못한다는 것이 문서의 주장이 아니라 관측이 됐다.

**수용 기준 4개를 전부 충족했는데 제품을 쓸 수 없었다.** 기준이 데이터와 동작만 말하고
"사람이 이걸 쓸 수 있는가"를 담지 않았다. 관문도 리뷰어도 통과시켰고, **배포하려는 순간에야 드러났다.**
이번 루프에서 가장 비싼 발견이다.

**"실패할 수 없는 테스트"를 관문이 잡지 못했다.** 초록불은 그 지적에 대해 아무 정보도 주지 않는다.
확인 방법은 코드를 일부러 망가뜨려 테스트가 빨간불이 되는지 보는 것뿐이었다
(`@Transient` 주입 → exit 1 재현). 이번엔 사람이 손으로 요구해서 일어났다. 1회 관측.
