# 관측 — 002 http-api

기능: HTTP로 노트를 등록하고, 지금 복습할 목록을 조회한다.
배포 형태: 로컬 실행. **이번 루프에서 명령줄 진입점이 제거되어 HTTP가 유일한 통로가 됐다.**

## 무엇을 보기로 했나

001의 관측("명령줄이 쓰기 불편하다")에 대한 답이 맞는지를 본다.

| # | 관측 | 어떻게 세나 | 무엇을 뜻하나 |
|---|---|---|---|
| 1 | 7일 동안 등록한 노트 수 | 저장된 데이터를 센다 | 001과 **같은 자**다. 늘면 통로가 나아진 것 |
| 2 | **서버를 띄워두는가** | 서술 메모 | 띄우는 것 자체가 마찰이면 001의 2초를 다른 마찰로 바꾼 것뿐이다 |
| 3 | 등록·조회할 때 거친 지점 | 서술 메모 | 다음 기능 후보를 가장 많이 내는 관측 |

**001에서 쓰려던 "어느 수단을 썼는가"는 무의미해졌다.** 통로가 하나뿐이다.
대신 2번이 그 자리를 대신한다 — 서버 상주가 명령줄보다 나은지가 이번 루프의 진짜 질문이다.

### 세는 명령

```bash
cd projects/review-scheduler/app
H2JAR=$(find ~/.gradle/caches -name 'h2-2*.jar' | grep -v sources | sort | tail -1)
java -cp "$H2JAR" org.h2.tools.Shell \
  -url "jdbc:h2:file:$PWD/data/review-scheduler" -user "" -password "" \
  -sql "select id, content from note order by id;"
```

**서버가 떠 있으면 이 명령이 실패한다.** 파일 기반 H2는 한 프로세스만 연다. 세기 전에 서버를 내려야 한다.
사용자명은 빈 문자열이다(`sa` 아님). H2 버전도 2.x로 맞춰야 한다.

**저장된 노트 대부분이 사용자가 쓴 것이 아니다.** 숫자만 보면 크게 오해한다.

| id | 출처 | 실사용인가 |
|---|---|---|
| 1~3 | 001 배포 확인 때 오케스트레이터가 등록 | 아니다 (001의 0일차 기준값으로 기록됨) |
| **4** | **사용자가 직접 등록** | **그렇다 — 유일한 실사용 데이터** |
| 5~7 | 002 구현 중 Developer가 수동 검증하며 등록 | 아니다 |
| 8, 10 | 오케스트레이터가 HTTP 동작 검증하며 등록 | 아니다 |
| 9 | CLI 제거 후 Developer가 재검증하며 등록 | 아니다 |

**7일차의 관측 1은 id 11 이후만 세야 의미가 있다.** 지우지 않은 이유는 사용자 데이터를 답 없이
삭제하는 것이 되돌릴 수 없는 조작이기 때문이다(`OS.md` 원칙 2). 기록해두면 지우지 않아도 관측이 산다.

**001과 002의 기여는 숫자로 분리할 수 없다.** 같은 DB, 같은 7일 창이다.

PM과 개발 쪽의 문의는 **관문이 아니라 협의**다. 관문이 네 번 발동하면 고장이지만,
설계 논의가 네 번 오가는 것은 정상이다. **정상을 고장으로 기록했다.**

「자동충족」 정의를 두 번 고친 것도 같은 원인이다 — 통과·실패를 가르려 하니 정확한 정의가 필요했다.
협의였다면 물어보는 말로 충분했다. **이름이 틀리면 그 이름에 딸린 요구까지 따라온다.**

이 정정이 이번 루프에서 가장 값싼 교훈이다 — 새 장치를 만들 때 **어느 부류에 넣을지 먼저 정한다.**
이 OS에는 채점기(기계)와 판정자(서브에이전트)가 이미 있었는데, 새 판정자를 채점기 자리에 세웠다.

**기준 4를 빼고 리뷰로 넘긴 판단은 검증됐다.** "서버 한 번 실행에 등록 두 번 성공"을 기준에서 뺀 이유가
"테스트가 실제 진입점을 타지 않아 겨냥한 위험을 못 잡는다"였는데, ④ 회귀 리뷰어가 정확히 그 버그를
찾았고 **테스트 12건 중 어느 것도 잡지 못한다**는 것까지 확인했다. 기준으로 남겼다면 초록불만 얻었을 것이다.

**CLI 제거가 지적 셋을 코드 네 줄과 함께 없앴다.** A·B·C를 각각 고쳤다면 분기 처리가 더 늘었을 것이다.
