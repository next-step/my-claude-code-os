# 수용 기준 — 002 http-api

HTTP로 노트를 등록할 수 있고, 지금 복습할 노트 목록을 조회할 수 있다.

001에서 만든 동작(복습일 계산, 목록 필터, 재시작 영속)은 이미 참이고 테스트가 있다.
이번 기준은 HTTP라는 새 통로에 대한 것이다.

**범위가 도중에 뒤집혔다.** 처음에는 "명령줄 방식을 이번 루프에서 없애지 않는다"로 정했으나,
④ 리뷰에서 나온 지적 셋(사용법만 찍고 종료 안 됨 / 파일 잠금 충돌 / 판별 규칙 중복)이 전부
**두 진입점을 한 프로세스가 겸한다**는 전제에서 나왔다. 사람이 **명령줄 제거**로 결정을 뒤집었다 —
옛 동작으로 되돌릴 필요가 생기면 버전 관리 이력으로 되돌리면 되고, 그것 때문에 코드를 남겨두지 않는다.
지적 세 개가 코드 네 줄과 함께 사라졌다.

**수용 기준 두 줄은 이 변경에 영향받지 않았다.** 둘 다 CLI를 언급하지 않는다.

PM 3회차. 기술 자문에서 네 개가 걸려 두 번 되돌렸다. 걸린 것과 처리는 아래와 같다.

| 걸린 기준 | 판정 | 처리 |
|---|---|---|
| 상태 코드로 성공 판별 | 자동충족 — 프레임워크가 공짜로 준다 | 응답 본문 요구로 교체 |
| 같은 저장소에 저장 | 자동충족 — 앱 하나면 저절로 참 | 교체 후 삭제 |
| 응답 시간 2초 이하 | 검증 불가 — flaky해진다 | 삭제 |
| 필수 항목 누락 거절 | 자동충족 — 서비스 계층이 이미 검증한다 | 삭제 |
| 서버 한 번 실행에 등록 두 번 성공 | 자동충족 + **테스트로 겨냥한 위험을 못 잡는다** | 삭제 |

마지막 것이 중요하다. 이 스택의 테스트는 자기 컨텍스트를 띄우므로 실제 실행 진입점의 종료 경로를
타지 않는다. 그래서 그 문장을 기준으로 남겨도 초록불만 얻고 위험은 그대로 남는다.

생명주기 위험(실행 진입점이 컨텍스트를 즉시 닫는 것)은 기준이 아니라 **④ 리뷰의 회귀 관점**에서 다룬다.
테스트로 잡히지 않는 것을 기준에 넣으면 통과하는 가짜 테스트가 생긴다.

- 노트 등록에 성공하면 응답 본문에 등록된 노트의 다음 복습일이 포함된다.
- HTTP 요청으로 지금 복습할 노트 목록을 조회하면 응답에 각 노트의 다음 복습일이 포함된다.
