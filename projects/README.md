# projects — OS가 다루는 대상

이 폴더는 **OS의 구성요소가 아니다.** OS가 만드는 **제품들**이 사는 곳이다.
`OS.md` 6절이 갈라놓은 경계가 디렉터리로 드러난 것이다.

| | 무엇인가 | 채점기 |
|---|---|---|
| `.claude/` | **OS 자신** | `lint.py`, `criteria-lint.py` |
| `projects/` | **OS가 만드는 제품** | 각 제품의 테스트 (`./gradlew test` 등) |

섞지 않는 이유는 하나다. OS가 자기를 채점하는 순환이 되면 **"OS가 좋아졌는지"와 "제품이 좋아졌는지"를
구별할 수 없다.** 두 채점기는 서로를 대신하지 못한다.

## 두 개의 루프

이 저장소에는 크기가 다른 루프가 두 개 돈다.

| | 무엇이 한 바퀴인가 | 기록되는 곳 |
|---|---|---|
| **안쪽 루프 — 제품** | 기능 하나 (`OS.md` 3절 네 구간) | `<제품>/loops/NNN-<기능>/` |
| **바깥 루프 — OS** | 제품 하나를 만들며 얻은 개선 | 제품 README의 **「OS로 되먹인 것」** → `OS.md` 결정 로그 |

바깥 루프의 입력은 각 제품 README의 「OS로 되먹인 것」이다.
**그 칸이 비어 있으면 제품만 늘고 OS는 그대로다.** 제품을 여러 개 만드는 목적이 사라진다.

## 구조

```
projects/
  _loop-template/          루프 하나를 시작할 때 복사한다
  <제품명>/
    README.md              이 제품이 무엇인가 + OS로 되먹인 것
    app/                   코드. 여기서 빌드·테스트가 돈다
    loops/
      001-<기능명>/
        criteria.md        수용 기준 — criteria-lint.py 의 입력
        observation.md     배포 후 관측 — 다음 루프 PM 의 입력
```

## 규약

1. **한 루프 = 한 디렉터리.** `loops/NNN-<기능명>/`. `NNN`은 세 자리(001부터), 기능명은 kebab-case.
   번호가 곧 루프 횟수다. 세다가 끊기면 루프가 멈춘 것이다.
2. **`criteria.md`에는 수용 기준만 넣는다.** `criteria-lint.py`가 목록(`- `) **전부**를 기준으로 읽는다.
   설명·메모는 목록이 아닌 문단으로 쓴다. 섞으면 메모가 기준으로 채점돼 관문이 헛돈다.
3. **`observation.md`가 비어 있으면 루프 미완이다.** 배포했는데 관측이 없으면 다음 루프의 입력이 없고,
   그러면 파이프라인이 아니라 일회성 작업이다(`OS.md` 3절).
4. **제품 추가는 디렉터리를 만드는 것으로 끝나지 않는다.** README에 **"내가 이걸 왜 매일 쓰는가"** 를 적는다.
   못 적으면 관측이 돌아오지 않고, 안쪽 루프가 한 번 돌고 멈춘다.
5. **빌드는 `app/` 안에서만 돈다.** 산출물(`build/`, `.gradle/`)은 커밋하지 않는다.
6. **제품 README에 구조·API 형태·기술 선택을 적지 않는다.** 그건 Developer가 정한다.
   적어두면 서브에이전트가 읽고 격리가 깨진다 — 프롬프트로 막은 것이 **파일로 샌다**(`OS.md` 4절 규칙 3).
   실제 구조는 `app/`이 답이다. 규약 2와 같은 병이다: **한 파일에 두 용도를 담으면 자동 장치가 헛돈다.**
